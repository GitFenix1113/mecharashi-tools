管理後台 /admin

開發階段持續擴充中（已涵蓋 12 個資料分頁 + 版本管理子頁）
登入需求需 Firebase Auth 且具 ADMIN / OWNER 角色；版本管理子頁由 AdminRoute gate。寫入受 Firestore Security Rules + App Check 保護

版面規範
編輯彈窗版面（PLAN-033）
後台維護者只用 PC、不考慮手機——這是本節所有決定的前提。 10 個編輯器共用 AdminModal 殼層，版面規則集中在 src/pages/user/admin/shared.tsx， 新增／修改編輯器時沿用即可，不要各自另寫一套。
常數 / 元件值用途與注意
ADMIN_WIDE_MAX_W max-w-[min(90vw,1920px)] 編輯彈窗與 AdminPage 列表容器共用，避免兩者寬度各自漂移。 1920px 上限僅防超寬螢幕（3440px+），2133px 以下視窗不會觸發。 ⚠ 不可改用 w-[90vw]——殼層已有 w-full，兩者都在設 width， 勝負取決於 Tailwind 產生的 CSS 順序而非 class 順序。
GRID_AUTO_FIELDS grid-cols-[repeat(auto-fill,minmax(220px,1fr))] 同質短欄位群（數值、短下拉）專用。⚠ 是 auto-fill 不是 auto-fit： 後者會收合空軌道、讓現有欄位吃掉整列，正是要消滅的「胖輸入框」。 量的是元素自身寬度，窄版彈窗與巢狀卡片自動得到正確欄數。 調密度只改 220px 這一個數字，全站生效。 ⚠ 異質長欄位（名稱、圖片路徑、textarea）不要套用。
GRID_TWO_PANE grid-cols-1 2xl:grid-cols-2 長分頁內部的雙欄：左＝吃寬度的文本區，右＝天生窄的結構化資料。 ⚠ 不可改用 GRID_AUTO_FIELDS——左右欄語意不對等、順序不可互換。 用 viewport 斷點在此是準確的：彈窗寬度 min(90vw,1920px) 本來就直接綁 viewport。
AdminEditTabs pill 樣式 ＋ 數字 badge 編輯彈窗內的分頁列，四個大編輯器共用（原本各寫一份、樣式還不一致）。 badge 傳數字，>0 才顯示。
⚠ 全域紅線：編輯彈窗內不可使用 Tailwind 容器查詢工具類
容器查詢會套用 container-type:inline-size，而該值隱含 contain:layout—— layout containment 會讓該元素成為 position:fixed 子孫的 containing block。 多個編輯器在彈窗內使用 IconField（components/admin/IconPicker）， 它是 fixed inset-0 的全螢幕浮層，一旦祖先套上就會改對齊彈窗的框而非視窗、直接錯位。 RefPicker 同理。內部格線用上表的 GRID_AUTO_FIELDS / GRID_TWO_PANE 達成同樣目的即可。

註：產出的 CSS 裡可能仍看得到該 utility 的定義，那是 Tailwind 掃描器不解析語法、只抓字串所致（連 docs/ 討論它時的字面量都會被掃到，因為 copy-docs 會把 docs 複製進 public/）。判斷有沒有踩雷要看「元素上有沒有這個 class」，不是看 CSS 裡有沒有這條規則。

合併分頁的判準
彈窗內容區在 1080p 下約 760px ≈ 10～11 排欄位。只合併「各只剩 1～3 排」的小分頁， 以 section 標題 ＋ border-t 分隔。 重元件必須維持獨立分頁（PilotSkillRefsTab、 PilotNeuralDriveTab、Module 等級表）——合併會讓它們變成常駐掛載，失去 lazy mount。
