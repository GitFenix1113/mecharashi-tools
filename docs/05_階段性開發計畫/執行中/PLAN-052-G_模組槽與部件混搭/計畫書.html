Problem
問題背景
模組是模擬器僅存的一塊「沒有入口」的功能
元件在 052-D 之後已經可以配了，形態與雲端存檔各有自己的計畫。剩下的兩塊都在這裡：
· 四個模組接口 —— 每台機甲的軀幹／左臂／右臂／腿部各有一個接口， 玩家在遊戲裡各裝一顆模組。站上今天連放的位置都只有唯讀卡片（052-I 的 MechPartStrip），卡片底下那行「部件混搭開放後，每個部位可換成別台機甲的同位部件」 就是在等這個計畫。
· 四部位混搭 —— LoadoutPage 右欄的四部位表整個被註解掉， 註解逐字寫著「等部件混搭（各部位可換不同機甲）開放後，這張表才開始回答 『這一套是怎麼拼出來的』，屆時連同模組接口一起復原」。
地基其實早就鋪好了 —— 而「鋪好」與「接上」是兩件事
052-A／B／C 為本計畫預留的東西全部都在，且全部處於「開了但沒接線」的狀態：
· LoadoutDraft.parts / LoadoutDraft.modules 兩個欄位已存在，值恆為 undefined
· codec v1 的 §PARTS（tag 2）與 §MODULES（tag 3）兩段已實作並有 golden fixture
· resolveChassis() 的 partOverrides 與 moduleMap / moduleLevelOf() 已實作
· ResolvedChassis.moduleSlots[pos].iface 已在四個部位上各帶一個接口型別
本計畫的工程量因此不在「造」而在「接」，而接線正是這個專案最會出事的地方 —— 見下一塊。
⚠ 動工第一件事：module 的分享碼索引仍是空的（052-D D-4 的同一個坑）
LoadoutPage.tsx 的 shareIndexes 裡那一行今天是 module: buildShareIndex('module', [], shareIdAliases('module')) —— docIds 傳的是空陣列，於是 buildShareIndex() 的迴圈一次都不跑， 別名表補的是「推導不出號碼」的缺口、補不了「這個集合根本沒進來」。

component 那一行剛因為同一個原因出過事：052-D 的 A-3 已經把 components 加進 LOADOUT_STAGE_KEYS.equip，但索引那一行漏改了 整整三個 Phase。症狀是 encode 時 toShareId() 回 null ⇒ 元件被靜默濾掉、分享碼裡根本沒有它們；decode 時 toDocId() 回 null ⇒ 元件進 unresolved 被丟掉。兩邊的畫面都不會說任何話。

單元測試抓不到這種事 —— codec 的測試自己建含元件的索引，壞掉的是頁面這一層的接線。 那個坑是瀏覽器實地驗收才發現的。加集合與接索引是兩件事，本計畫的 A-1 把兩件一起做完。

⚠ 盤點時發現、且一度足以推翻決策一的東西：天生模組住在 mech 頂層
Mech 有三個過去沒被總綱點名的欄位：module4Id（76 台有）、 module8Id（80 台有）、moduleFixedIds（副模組 ＋ 專屬模組，共 104 個引用）。 260 個引用零斷鏈。這就是使用者說的「品質預覽每個部位列出的三個模組是機甲天生自己帶的」。

問題來了：這些天生模組裡有 112 顆的 boundMechId 是 null （特性模組 75 筆裡 65 筆是某台機甲的 module4Id、8級模組 50 筆裡 47 筆是某台的 module8Id）， 於是決策六的候選規則會把「別台機甲的天生模組」整批撈進挑選器。

查了 source 才確定這不是漏洞，而是機制本身：特性模組的來源是 拆機甲／商店（81 筆裡 65 筆含「拆機甲」，56 筆帶 dismantleMechIds）。拆掉一台機甲、把它的特性模組裝到自己機上，就是這個玩法。 使用者逐字說的「只要沒有綁定機甲，其他機甲都能使用」講的正是這件事。
⇒ 決策六原封不動成立，候選池維持 186。這一段留在文件裡，是因為下一個讀到 module4Id 的人會產生同樣的疑問，而答案不在程式碼裡、在 source 欄位裡。
Design
設計決策
決策一：候選池 ＝ boundMechId === null 扣掉副模組與 mod_2030 ＝ 186 筆
總綱決策六已裁決規則本體，本計畫只修正數字與排除項：
· 186 而非總綱推算的 188（198 − 副模組 11 − mod_2030 1）
· 排除 slot === '機甲副模組'（11 筆）：它們依規則也「沒綁機甲」， 但那正是機甲天生自帶的那一種，source 為空陣列 ⇒ 玩家無從取得。 available 值域已漂移（10 true ／ 1 false），不可再當唯一 gate， 用 slot 判。
· 明著排除 mod_2030：官方廢案（全 12 個集合零引用、source 是字串 "未知" 而非陣列、無拆解來源）。不排除的話，玩家會在挑選器裡看到一顆 裝不到任何機甲上的幽靈模組。用 id 白名單排除、不改資料 —— 它是 managedBy: auto，改了會被下次爬蟲洗回去。
決策二：接口 gate 走 rarity；接口本身 ＝ f(quality, position)
✅ 2026-08-27 已查證並落地，見 _local-notes/2026-08/2026-08-27_機甲模組接口_資料基礎規則.html。
· Ⅰ型接口 ⇒ 只收 rarity === 'A'（42 筆）；Ⅱ型接口 ⇒ A／S 皆可（186 筆）。
· 接口型別不是機甲的固定屬性，是「品質階級 × 部位」的函式 —— 官方 API 83 台 × 4 部位 ＝ 332 格零例外： S ⇒ ⅡⅡⅡⅡ／A ⇒ ⅠⅡⅡⅠ（軀幹與腿部為 Ⅰ）／B ⇒ 無接口。 armorType 完全不影響。
· 官方每格同時有基礎階與滿階兩個值（rawPart.Interface ／ rawPart.manji.Interface），爬蟲取 manji ⇒ 站上存的是滿品質階，與全站滿級口徑一致。 基礎階：S 級是 ⅠⅠⅠⅠ、A 級完全沒有接口。
· 規則落在 src/utils/mechInterface.ts（expectedInterface() / isInterfaceOffRule()），CI 守門在 mechInterface.test.ts（9 案例全綠）， fixture 由 scripts/gen-mech-interface-fixture.mjs 產出。 資料仍是真相源 —— 規則只用來守門，不取代資料 （規則是今天 83 台的觀察、不是官方保證；改成 derive 的話，破格機甲會讓公式靜默給錯答案且無處可修）。
· ⚠ 「接口資料未建檔」這個狀態已經不存在：美杜莎MK2 那 4 格已依 S 級規則補上 Ⅱ 型， 44 格空字串收斂成 40 格、全部屬於 B 品質。空字串於是只剩單一語意「這台沒有模組接口」， 原本「只有 quality 分得開」的兩義問題自動消失。
· 連帶已完成的文案收斂（原 B-2）：enums.ts 的 UNKNOWN_INTERFACE 更名為 NO_INTERFACE、mech.ts 與 chassisStats.ts 的註解、 MechSlotPanel／MechPartStrip／MechDetailPage 三處 改印「無模組接口」。
決策三：moduleAddLevel 與總模組等級 —— 本輪延後（使用者裁決 2026-08-27，當日修訂）
裁決經過：先裁決「要做，它就是接口槽的意義」；同日查證接口規則後， 使用者複審為「不算很優先，目前我們都預設最高等級，以後再處理」。

為什麼延後是對的：這整個機制的觸發條件是機甲品質階級會變動， 而總綱決策六已定「一律預設滿級、不給玩家選機甲品質階」。 站上永遠只呈現滿階 ⇒ 接口恆為滿階值（S ⇒ ⅡⅡⅡⅡ／A ⇒ ⅠⅡⅡⅠ）⇒ Σ moduleAddLevel 是一個常數，算出來的總模組等級對每台機甲都固定。 做了不會讓任何畫面變得更準，只會多一層要維護的推導。

本輪改為：moduleLevelOf() 維持現行行為（一律回滿級）， moduleAddLevel 欄位讀都不讀。B-1 只保留「讀數值一律走 levels[]」那一項， E-3 的實機驗證整項移出本計畫。

要動工時需要知道的（已查證，不必重查）：
  • 值域：31 顆通用模組Ⅱ型（S 級）為 2，其餘 155 筆為 1。
  • 官方每格接口有基礎階與滿階兩個值，升階讓接口 Ⅰ→Ⅱ —— S 級 Σ 從 4 變 8，而「機甲8級模組」的 levels[] 正好 8 筆； A 級基礎階完全沒有接口、滿階為 ⅠⅡⅡⅠ ⇒ Σ 上限 6。
  • ⚠ 仍未驗證的兩件：影響的是 8 級模組、特性模組還是兩者；四格全空時的基礎值 （若為 0，天生模組會變 0 級，那不合理）。
  • 真正需要它的時機是開放玩家選機甲品質階之時 —— 在那之前它是一個算得出來但沒有人會看到差異的數字。
決策四：LoadoutDraft.modules 只存 {部位: moduleId}，等級一律推導
總綱決策六已定，本計畫重申並補一條理由：模組等級由「部位品質階級 × 部位種類」決定、 不是玩家升的，存下來就是第二真相源。等級一律由 ResolvedChassis.moduleLevelOf() 出。
· 模組不佔重量 ⇒ 出力條與 loadoutBudget() 完全不必動， 這是本計畫與 052-D 最大的差異（元件也不佔重量，但元件有 componentLimit 這個容量帳）。
· 讀數值務必走 levels[]：候選池 186 筆全有 levels[]， 而頂層平坦欄位全 0 者有 163 筆。讀頂層的症狀是「模組裝上去沒有任何效果」，且不報錯。
決策五：SlotRef 擴成帶 kind 的聯集（總綱決策十二，本計畫兌現）
SlotRef 由純武器語意 {bank, slot, side} 擴成 {kind: 'weapon' | 'module' | 'component', …}。052-D 已確認元件用不到這一層 （元件內嵌在 mount.setup 上，沒有旁掛表也就沒有 key 可撞）， 所以這是模組專屬的前置：模組要一個「軀幹的接口」這種座標，而它不是 WeaponEquipSlot。
不另開平行模型的理由不是型別漂亮，是同型級聯：換機甲 → 部位換掉 → 模組掉落； 換武器 → 元件掉落。分兩套就會長出第二、第三支 reconcile()， 而「同一件事在三處各寫一次」正是舊 SimulatorPage 三個 bug 的共同病根。
⚠ slotKey() / parseSlotKey() 是品牌型別的唯一入口，擴充時 round-trip 測試要同步補到 module kind —— parseSlotKey(slotKey(ref)) 恆等於 ref 正規形這條不變式不能因為多一個 kind 就破。
決策六：模組的載入 gate 照抄 052-D 的教訓 —— 空 Map ＝「還沒載入」，不是「沒有模組」
052-D 決策六逐字：reconcile() 對武器是「查不到就刪」， 模組絕對不可照抄。草稿可能在 modules 載入完成前就被 loadDraft 灌進來（分享碼／本機書架／052-E 雲端存檔都走這條）， 症狀是貼一次分享碼、模組就被靜默清空一次。
做法與元件一致：LoadoutWorld.modules 為空 Map 時，規則層跳過模組驗證， reconcile() 不動 draft.modules。
⚠ 時序上安全的原因也一致：stage 在有 pending 時直接跳 equip， 而還原的守衛是 if (pending && !loading) —— loading 為 false 就代表 equip 階段每個集合（A-1 之後含 modules）都到齊了。
決策七：部件混搭 —— 同裝甲類型、Σ 四部位、換機甲即清空
總綱決策七已定規則，本計畫補三條實作面的判斷：
· PART_INCOMPATIBLE 只需一行 sourceMech.armorType === chassis.armorType。不能跨裝甲類型 ⇒ 四部位必定同型 ⇒ 「混搭後裝甲類型由誰決定」自動消失，雙肩槽與執照判定完全不受影響。
· 來源池大小：輕型 27 ／ 中甲 36 ／ 重型 27（扣掉自己是 26／35／26）。 一頁列得完，不必分頁；每個部位都帶 icon（352／360 有圖）。
· 換機甲必須清 draft.parts。今天沒有任何程式寫入這個欄位， 因此 reconcile() 也還沒有這條級聯 —— 換了機甲卻留著舊機甲的部件是靜默的錯， 而且會讓 resolveChassis() 算出一台不存在的機體。這是 D-2 的第一項。
· mech_090_美杜莎MK2 四部位全 0（官方未公布），作為混搭來源時要 標成「數值未公布」而不是列成一組重量 0 的免費部件。
決策八：右欄「已裝效果彙總」只能靠 levels[] 的數值欄位加總
盤點結果直接否掉了一條看起來理所當然的路：候選池 186 筆的 buffIds 與 conditionalEffects 都是 0 筆。模組的效果沒有進 PLAN-019 的 buff 層， 也沒有結構化的條件效果。可用的只有 levels[] 裡 30 個非零數值欄位 （acc_rate／dmg_*／output_bonus…）。
· 加總規則：Σ 四部位所裝模組在各自等級上的同名欄位。
· 186 筆裡只有 7 筆的滿級同時碰到一個以上的欄位 ⇒ 絕大多數模組是「單一數值」， 彙總表會很好讀。
· 每一筆都有滿級 description（186／186）⇒ 挑選器的名稱下掛一行效果摘要 有現成資料可用，不必自己組字串。
· ⚠ 不出衍生的戰力／傷害數字：口徑未定屬傷害計算範疇（總綱決策一④已裁決延後）， 本輪只出「這一套裝了哪些模組、各自加了什麼」。
決策九：決策十三的「同名消歧義」在候選池裡已不存在 —— 工項降級為效果摘要
總綱決策十三（2026-08-26 追加）要處理模組同名。2026-08-27 實測全庫只剩兩組同名：
· mod_2030 ／ mod_2041 皆名為「自擬合模組」 —— 但 mod_2030 已由決策一明著排除，池內只剩一筆，歧義消失。
· 「匯流樞紐」兩筆是 mech_026_破曉者-02 的專屬模組（boundMechId 有值）， 根本不進候選池，且本來就靠 boundPart 區分（legs／torso），非歧義。
⇒ 「名稱下掛一行效果摘要」仍然要做 —— 它對 186 筆全部都有價值（決策八）—— 但它是可讀性工項而不是消歧義的剛需，優先級隨之下降。 「機甲專屬模組補 boundPart 部位徽章」這一項本輪不做：專屬模組不進候選池。
決策十：星夜女神的接口資料 —— ✅ 2026-08-27 已對帳並修正
原記為「動工前需回官方對帳」，已完成。結論與使用者的判斷一致：人員輸入錯誤。
· 它不在官方 83 台名單裡 —— v3.5 新機甲，官方 API 尚未收錄，那四格是人工輸入的。 ⇒ 修改不會被下次爬蟲洗回去。
· ⅠⅠⅠⅠ 正好是 S 級的基礎階 pattern，可能是照著尚未升滿階的遊戲畫面輸入的。
· PLAN-052-A D-1 的程式碼註解逐字寫著「實測星夜女神四格全中（ⅠⅠ型接口）」—— 原值是兩個 U+2160 拼出來的假「Ⅱ」，D-1 正規化時收斂成單一個 Ⅰ，方向收錯了。原意是 Ⅱ。
· 已修正為 ⅡⅡⅡⅡ，同時依使用者裁決把 mech_090_美杜莎MK2 四格 一併補成 ⅡⅡⅡⅡ（S 級規則零例外，套用規則而非編造數值）。共 2 台 8 格，mechs 版本已 bump。
