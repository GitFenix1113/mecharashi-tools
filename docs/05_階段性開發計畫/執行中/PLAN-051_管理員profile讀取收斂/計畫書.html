◆ PLAN-051

管理員 profile 讀取收斂 · Worker 代讀 · 欄位過濾 · 規則收緊

首頁的維護團隊改由 Worker 供應，Firestore 的 profile 讀取收回 isAdmin()——讓管理員 email 不再跟著首頁送進每一位匿名訪客的瀏覽器

Problem
問題背景
管理員的 email 目前任何人都讀得到，不需要登入
firestore.rules 有兩條 profile 讀取規則，第二個條件沒有任何 auth gate：
// firestore.rules（現況） match /users/{userId}/profile/{docId} { allow read: if isOwner(userId) || isAdmin() || resource.data.role in ['ADMIN', 'OWNER']; } match /{path=**}/profile/{docId} { allow read: if isAdmin() || resource.data.role in ['ADMIN', 'OWNER']; }
這是刻意的——首頁的維護團隊區塊（SiteTeamSection）要在未登入狀態顯示， getSiteTeamProfiles() 用 collectionGroup('profile') 撈 role in ['ADMIN','OWNER']，沒有這條就撈不到。
根因：Firestore 沒有「欄位級」讀取授權
Security Rules 的授權單位是文件，沒有 field-level read mask。 一旦允許讀該文件，回去的就是整份文件——而 UserProfile（src/types/user.ts）的 email 是必填欄位。
所以現況等於：每一位匿名訪客進首頁，瀏覽器裡就有全部管理員的 email （開無痕視窗 + DevTools 看 runQuery 的回應即可自行驗證）。 這條路徑改不動規則就解不掉，只能換資料來源。
嚴重度評估：中，不是高
email 不是憑證，拿到也登不進任何東西——本站的後台入口是 Google 帳號 + Firestore 的 isAdmin()，兩者都不因 email 外流而鬆動。
值得修的理由是它降低了針對管理員的釣魚門檻：管理員帳號是後台唯一的鑰匙， 而「誰是管理員 + 他的 email」現在是首頁自動奉送的資訊。屬於該收但不緊急的洩漏。
Design
設計決策
決策一：改資料來源，不試圖用規則遮欄位
如上，Firestore 沒有欄位級授權，任何「讓匿名讀得到但看不到 email」的規則寫法都不存在。 因此規則只能二選一：開放整份文件、或完全關閉。本計畫選完全關閉 （收回 isAdmin()），公開所需的那幾個欄位改由別的管道供應。
決策二：走 Worker 代讀，不另開公開集合
三個方案比較：
方案做法代價結論
A. 公開集合 另建 siteTeam/{uid}，只放可公開欄位，read: if true 同一份資料存兩處。維護者改暱稱／頭像要同步寫兩邊，遲早不一致 不採用
B. Worker 代讀 新增 /api/site-team，Worker 以 service account 讀 profile、只回傳白名單欄位 要先幫 Worker 補 collectionGroup 查詢能力（見決策三） 採用
C. 不顯示團隊 首頁移除維護團隊區塊 犧牲功能。而且那是首頁少數有人味的東西 不採用
選 B 的關鍵是單一資料來源：profile 仍然只有一份，Worker 只是在出口做欄位過濾。 而且它與 PLAN-029 既有的 /api/data/:collection 是同一個模式——同源、免 CORS、 吃得到 zone 限流，還能在邊緣快取（團隊名單幾乎不變，可設長 TTL）。
決策三：Worker 需要先補 collectionGroup 查詢
workers/src/firestoreRest.ts 目前只有 listCollection（單一集合）、 getDocument、commitIncrements、readCounterField， 沒有 runQuery。而 profile 是 users/{uid}/profile/main 這種子集合，要跨使用者撈就得用 collectionGroup + allDescendants。
因此本計畫的第一步是在 firestoreRest.ts 補一個 runQuery() （POST documents:runQuery ＋ structuredQuery）。這是通用能力， 之後其他需要跨集合查詢的端點都用得上。
邊界情況：這三件事不會壞，但要驗
  • 後台使用者管理：getAllUsers() 也走 collectionGroup('profile')， 但呼叫者是管理員，收緊後仍命中 isAdmin() 分支 → 不受影響。
  • Worker 掛掉時的降級：useSiteTeam 現有的 .catch(() => {}) 會讓 SiteTeamSection 回傳 null， 首頁少一塊而不是壞掉。這個行為要保留。
  • 本機與 preview 環境：那兩個環境的 VITE_WORKER_API_BASE 不是 same-origin，新端點要跟既有 /api/* 一樣吃得到 CORS 設定。
Scope
實作範圍與不在範圍內
在範圍內：
  • workers/src/firestoreRest.ts 新增 runQuery()（structuredQuery + allDescendants）
  • workers/src/index.ts 新增 /api/site-team 端點，回傳白名單欄位 （uid / displayName / role / avatarType / avatarUrl / avatarPilotId / gameNickname / gameServer / guild）——不含 email， 並加上邊緣快取標頭
  • src/lib/userApi.ts 的 getSiteTeamProfiles() 改打 Worker
  • firestore.rules 兩條 profile 規則移除 || resource.data.role in ['ADMIN','OWNER']， 並 firebase deploy --only firestore:rules
  • 同步更新 docs/02_技術文件/04_Firebase/資料庫設計文件/security-rules.html 與 users.html（CLAUDE.md 規則 2）
不在範圍內：
  • 把 email 從 UserProfile 移除。它在後台使用者管理有實際用途， 問題不在「存了 email」而在「誰讀得到」。
  • 其他集合的規則調整。遊戲資料早已是 read: if isAdmin()（PLAN-029）， 本計畫只碰 profile 這兩條。
  • Cloudinary unsigned upload preset 的收斂。那是另一個「前端限制擋不住直接呼叫」 的缺口，但修法在 Cloudinary Dashboard 而不在本 repo，另案處理。
  • 啟用 Firebase Storage。storage.rules 至今未部署（Storage 沒開）， 與本計畫無關。
驗收條件
  • 無痕視窗開首頁 → 維護團隊區塊仍正常顯示（頭像、暱稱、伺服器、公會）
  • 同一頁 DevTools 的 Network 全文搜尋 @ → 找不到任何管理員 email
  • 未登入狀態直打 Firestore REST 的 documents:runQuery 查 collectionGroup profile → permission denied
  • 管理員登入後台使用者管理 → 名單與 email 照常顯示（未回歸）
