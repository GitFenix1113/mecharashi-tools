◆ PLAN-052-K

天生模組逐部位化 · Innate Modules by Part

天生模組住在機甲頂層三個欄位、沒有部位也沒有等級 —— 部件混搭上線後那一列一顆都不動。改成用規則推導、保留逐格人工覆寫，並把後台補成主要輸入管道。

一句話：一顆天生模組的等級 ＝ 四個部位各自貢獻的等級加總（＋插槽貢獻 × 部位倍率）， 而站上把它存成機甲頂層的三個 id、沒有部位也沒有等級。 052-G Phase D 讓玩家能換部位之後，這一列就開始說謊了 —— 而且不報錯。
Problem
問題背景
問題一：換了部位，天生模組一顆都不動
模擬器「模組效果」面板分兩塊：接口 0/4（玩家自己裝的）已於 052-G Phase D 跟著部件走； 自帶 4 讀的是 mech.module4Id / module8Id / moduleFixedIds —— 機甲頂層的三個欄位，與部位無關。所以換掉右臂，自帶那一列原封不動。
遊戲裡不是這樣：換掉滿階帕斯卡的右臂，〈彙編矩陣〉整顆消失、〈蓄能模組〉8→6、〈出力模組〉4→3。 症狀是「數字看起來很合理但就是錯的」，沒有任何錯誤訊息。
問題二：三個機制在資料模型裡不存在
① 逐部位等級：MechPart 的 14 個欄位 （antiRiot, armor, dodge, durable, firepower, fixedArmament, hit, icon, interface, mechaIcon, move, output, position, weight）沒有一個講「這個部位帶哪顆模組」。
② 部位倍率：破曉者-02〈匯流樞紐〉的效果是「某部位插槽中的模組等級翻倍」 （20391 軀幹 / 20394 腿部，兩顆同名但效果不同）—— 這件事目前只存在描述文字裡，程式讀不到。
③ 觸發式模組：共 6 顆。復仇女神四顆〈模型-武／月升／憐愛／無恙〉的前提是 〈迸發模組〉達 LV.MAX(8) 進入「限制解除」；彌造者〈帕姆斯陣列〉與星夜女神〈觀星者單元〉 則是機師限定（海莉絲 / 曜）。混搭掉一個部位 → 迸發只剩 6 級 → 四顆一起失效。
問題三：官方 API 已落後兩個版本，不能當主要管道
站上 90 台機甲已更新到 v3.6，官方 aircraft_data 只有 83 台、停在 v3.2。 v3.3 之後的 7 台（莫比烏斯X / 奈芙蒂斯 / 稜鏡 / 尼德霍格 / 雪崩 / 星夜女神 / 美杜莎MK2） 官方完全沒有資料，全靠維護者人工建檔 —— 而他們都已經填好了三個模組欄位。
⇒ 這個計畫的重心不是爬蟲，是後台。爬蟲與對帳腳本只能覆蓋官方有的那 83 台，是輔助不是主力。
Design
設計決策
決策一：矩陣不落盤，用規則推導
90 台 × 4 部位 × 3～7 顆 ≈ 1500 格，而這 1500 格全部是規則的產物。落盤的後果是 官方改版時它會過期、而規則會自動跟上；再加上0/5 定律（選填欄位不會被填滿）， 1500 格人工欄位必然腐爛。通則用算的，例外才落盤。
滿配假設下（見決策六）規則表只有九個數字：
品質 S（滿階）：特性位 每部位 1　8級模組 每部位 2　副模組 每部位 1 品質 A（滿階）：特性位 每部位 1　8級模組 軀幹1 ＋ 腿1（雙臂 0）　副模組 每部位 1 品質 B ：全 0（10 台實測沒有模組資料，也沒有接口欄位）
驗證：57 台 SSR × 兩個端點 × 四部位 —— 8 級模組與副模組 57／57 全中； 「特性位」54／57，三個例外（輝龍／影虎／霸王）是額外疊了一顆專屬模組，不是規律錯。
決策二：專屬模組的逐部位等級，用現有欄位推導
若 position ∈ module.boundPart： level = (module.levels.length > module.boundPart.length) ? 2 : 1
拿站上全部 24 顆專屬模組驗過，零例外：帕斯卡四顆（bp=1, lv=1 → 各 1）、 信仰之眼〈超限框架〉（bp=2, lv=2 → 各 1，合計 2）、輝龍四顆龍威與影虎〈虎魄·無束〉 （bp=1, lv=2 → 各 2）、霸王〈AI火控單元〉（bp=2, lv=2 → 各 1）。 彌造者〈帕姆斯陣列〉（bp=1, lv=2 → 各 2）由站長實機確認：軀幹 LV1～LV3 為 1 級、 LV4（彩）為 2 級。
⚠ boundPart 與 levels[] 早就填好了，這條規則等於免費 —— 但也因此 B-1（回填 levels）是這條規則的前置，那不只是文字、是推導的輸入。
決策三：手動空間掛在部位上，整格取代
interface MechPart { /** 天生模組覆寫。undefined ＝ 照規則推導（絕大多數台）； * 一旦填了就整格取代推導結果，不做部分合併。 */ innateModules?: { moduleId: string; level: number }[] }
三個刻意的選擇：
① 掛在部位不掛在模組 —— 異常的形狀一定是「某台機甲的某個部位很奇怪」， 而專屬模組本來就綁單台，模組層級的覆寫是這個的特例。
② 整格取代，不做部分合併 —— 半推導半覆寫是最難 debug 的狀態， 你永遠不確定畫面上那個數字來自哪一半。
③ UI 必須看得出來 —— 後台與前台都要標「規則算的 / 人工覆寫」。 這與 052-G Phase D 的教訓同源：換過的部件原本在槽位圖上長得跟原廠一模一樣， 最後靠一個橘色 ◆來源機甲 標記才救回來。沉默的覆寫會變成沉默的技術債。
決策四：後台是主要輸入管道，爬蟲是輔助
官方落後兩版（問題三），新機甲一律先在後台建檔。因此本計畫的 Phase C 不是「順便加個欄位」， 是這個計畫能不能長期活下去的關鍵：
· ModuleAdmin 補兩個欄位：slotLevelMultiplier（部位多選）、unlockCondition。
· MechAdmin 的每個部位區塊顯示規則推導出的天生模組（唯讀預覽）， 並提供「改成人工指定」的入口與「清除、回到推導」。
⇒ 維護者看得到規則算成什麼，發現不對就地覆寫，不需要動程式、也不需要等我們。
決策五：unlockCondition 有兩種形狀
type ModuleUnlock = | { kind: 'moduleAtMaxLevel'; moduleId: string } // 復仇女神 ×4（觸發者＝迸發模組 mod_3034） | { kind: 'pilotOnly'; pilotIds: string[] } // 帕姆斯陣列＝海莉絲、觀星者單元＝曜
⚠ 觸發者是「別顆模組」，不是模組自己 —— 復仇女神四顆〈模型-XX〉的描述裡沒有 「限制解除」字樣，那句話寫在〈迸發模組〉的 LV8 文本裡。 任何用「掃自己的描述」來判定的做法都會漏掉這四顆。
⚠ 這與「效果內的條件」不同：影虎〈虎魄·無束〉L2 的「當[虎王]駕駛一整套[影虎]時…」、 輝龍龍威 L2 的「當[戰部渡]駕駛整套[輝龍]時…」不影響模組存不存在，不進 unlockCondition。
決策六：一律滿配假設（站長裁決 2026-08-28）
逐字：「配裝模擬器還沒正式進入傷害模擬，這功能意義不大。」⇒ 不支援「金三＋插槽」這類非滿配， 品質 LV2／LV3 的部件數值也不去補（官方 API 本來也只有兩個端點，而且 manji ＝ 等級70＋品質MAX，兩個維度混在一起分不開）。
⚠ 但要注意：滿配假設擋掉的是「品質階」這個維度，擋不掉「來源機甲」這個維度。 052-G 的 E-3 當初以「Σ 是常數」為由延後，那個前提已被 Phase D 打破 —— 換進來的部件 帶的是它原本那台機甲的模組（不同 id、不同組合），不是同一組常數。
決策七：對帳腳本降級為輔助，但一定要有
新增 scripts/check-part-module-drift.mjs（只讀不寫），跟現有的 check-module-stat-drift.mjs / check-nd-minsum-drift.mjs 同一類： 拉官方 API 解出真實矩陣，與站上規則算出的預測矩陣逐格 diff。三種結果三種處置 —— 全中（什麼都不用做）／某台某格不符（填 innateModules）／ 一整批不符（改規則表，版本性變更）。
它只能覆蓋官方有的 83 台，但價值在於「奇怪的東西」會被自動抓到，而不是等站長發現畫面怪怪的。
Scope
實作範圍與不在範圍內
在範圍內：
  • 型別：MechPart.innateModules?、Module.slotLevelMultiplier?、Module.unlockCondition?
  • 推導層：規則表常數 ＋ resolveInnateModules() 純函式 ＋ 24 顆專屬模組的迴歸 fixture
  • 資料補完：專屬模組 levels[] 回填（腳本已備）、星夜女神〈觀星者單元〉boundPart、 6 顆觸發式模組的 unlockCondition、匯流樞紐 2 顆的 slotLevelMultiplier
  • 後台：ModuleAdmin 兩個新欄位；MechAdmin 部位面板的推導預覽 ＋ 覆寫入口 ＋ 來源標示
  • 模擬器接線：EquippedEffects 的 innate 改讀推導結果；混搭時跟著部件走
  • 對帳腳本 ＋ 掛進 data-patch skill 流程
  • docs 同步：資料模型頁、Firestore 集合文件、回寫 052 總綱
不在範圍內：
  • 非滿配配裝（「金三＋插槽」）—— 決策六已裁決不做
  • A 級的完整品質階梯 —— 只做滿階那一列。A 級品質 LV1 時只有特性模組、連接口欄位都不存在，是另一套規律
  • 品質 LV2／LV3 的部件數值 —— 官方沒有，且與等級維度混在一起
  • 傷害模擬 —— 模組效果怎麼進傷害公式仍延後
  • 爬蟲改寫 —— scrape-mechs.js 的逐部位 parser 不在本輪；官方落後兩版，先把後台與推導做起來。 （檔頭那條「API 回頭刪東西」的警告是誤判，順手改掉即可：那 5 顆一直都在 module_data 字典裡， 只是不在部件的 ModuleCarried。）
