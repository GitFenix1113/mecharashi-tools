Problem
問題背景
問題一：總綱決策九承諾的兩道護欄，沒有跟著 052-E 出貨。
決策九明訂兩件事：①節流 —— savedAt == request.time ＋ 每文件 3 秒， 且 delete 也要節流（否則 delete→create 可繞過）；實測「無節流時單一帳號可寫 43M/日 ≈ US$78/日，3 秒節流後降到 ≈ US$6.1/日」。②同一次 deploy 必須順手收緊 users/{userId} 文件本體，並附了理由：「只鎖 builds 不鎖本體， 上面所有保護都是裝飾」。

兩條都不在線上。實際部署的 match /builds/{buildId} 只有 isOwner ＋ doc id 正規式 ＋ shapeOk；client 側 （src/lib/buildsApi.ts）也沒有任何節流。
⚠ 這不是被裁決延後的，是建檔時整條沒被承接 —— PLAN-052-E 的計畫書與進度表 全文搜「節流」是零結果。歸檔進度表記了三處「與計畫書不同的實作決定」， 但沒有這一條，因為它從來沒有進入 052-E 的視野。

而 2026-08-29 模擬器已對外開放。決策九算的那個 US$78/日 情境， 今天第一次成為真實可達的狀態，而不是紙上推演。
問題二：站上既有的寫入熔斷器，保護不到雲端書架。
workers/src/collectBudget.ts（PLAN-046 決策七）是一套完整的寫入預算熔斷器， 但它守的是統計寫入，而統計走 Cloudflare Worker。 雲端書架是 client 用 Firebase SDK 直連 Firestore 的，一次也不會經過 Worker —— 那套熔斷器對它永遠不會被呼叫到。

⇒ 雲端書架唯一能施加速率限制的地方，就是 Firestore 規則本身。 這正是問題一那條節流不能只當成「漏做的一項」的原因：它不是眾多防線中的一道，它是唯一的一道。
問題三：users/{userId} 文件本體仍然全開。
firestore.rules 的 match /users/{userId} 至今仍是 PLAN-011 為 v1 Build 寫的一行 allow read, write: if isOwner(userId)： 不驗形狀、不驗大小、不驗節流。任何登入者都能往自己的 users/{uid} 塞任意內容、任意大小、任意頻率。

而站上程式從來不寫這個文件。userApi.ts 只寫 users/{uid}/profile/main，buildsApi.ts 只寫 users/{uid}/builds/{pilotId}。052-E 復驗時發現的 「users 集合 0 筆是量測假象、父文件是空殼」正是這件事的另一面 —— 那些父文件之所以是空殼，就是因為沒有任何程式寫過它們。

⇒ 這是一條純粹的攻擊面，零功能依賴。收緊成 allow write: if false 不會弄壞任何現有行為，而它今天擋下的東西是全部。
時間窗和 052-E 當初的論證同構，而且更緊。 052-E 動手的理由是「builds 0 筆 ⇒ 現在改模型零遷移成本，一旦全面公開就再也不免費」。 現在已經公開了，但開放才剛發生、文件數仍極少 —— 問題一那條節流會牽動 updatedAt 的型別變更（見決策二）， 那是一次破壞性 schema 改動，每晚一天成本就高一點。A-1 要先直讀正式庫把實際筆數量出來， 而不是沿用 052-E 那個「0 筆」的數字 —— 052-E 自己就是被一個過期數字絆過的計畫。
Design
設計決策
決策一：先補護欄，觀察是第二順位。
這個計畫的名字有兩半，但兩半不等重。護欄是缺件補完（決策九已經論證過、已經算過錢、 只是沒出貨），觀察是新建能力。缺件補完不需要再討論要不要做，只需要決定怎麼做； 所以 Phase A 全部是護欄，Phase B 才是告警與可觀察性。
如果這個計畫只做得完一半，要做完的是 A 那一半。
決策二：節流要成立，updatedAt 必須從 string 改成 timestamp。這是技術必然，不是偏好。
規則側節流只有一種寫法：request.time > resource.data.updatedAt + duration.value(3, 's')， 而它要求 updatedAt 是 timestamp。現行是 client 寫進來的 ISO 字串 （規則只驗 updatedAt is string），既不能拿來做時間運算， 也可以被偽造 —— client 想寫哪個時間就寫哪個時間。

所以連帶還要加 request.resource.data.updatedAt == request.time： 否則 client 只要每次都寫一個「很久以前」的 updatedAt，節流條件就永遠成立， 那道節流會安靜地失效而不報錯。決策九原文寫的 savedAt == request.time 就是這一條，本計畫沿用，只是欄位名改用既有的 updatedAt（不新增第二個時間欄位）。

⚠ 這是破壞性 schema 變更：既有文件的 updatedAt 是字串。 規則若直接改成只認 timestamp，舊文件會變成更新不了、而且看不出為什麼 （症狀是「我這位機師存不了、別位可以」）。過渡做法見 A-4。
決策三：create 節流不了，所以「doc id 空間有多大」＝「不受節流的寫入有多少次」。
這不是選擇，是技術事實。節流條件必須讀 resource.data.updatedAt， 而 create 時文件不存在、resource 是 null —— 存取它會讓規則求值直接失敗。 所以 A-3 必須拆成 create（無節流）與 update / delete（有節流）兩條，沒有第三種寫法。

⇒ 於是 doc id 能有幾種寫法，就等於攻擊者能做幾次不受節流的寫入。 現行 '^pilot_[0-9]{3}_.*' 的 .* 讓它是無限。
⚠ 這就是「只做 A-3 不做 A-5」會失敗的地方：門裝好了，旁邊的路沒關。 見決策四的兩行算式 —— 那條路不關，決策九算的 US$78/日 一分不降。
決策四：加 exists(/pilots/{buildId})，而且與 A-3 綁成同一次出貨。（使用者裁決 2026-08-29）
決策九原本就寫了「結構上限 ＝ 89 機師 × 5 ＝ 445 套 ≈ 525 KB/帳號（由 exists(/pilots) 鎖住）」， 實際出貨的是 buildId.matches('^pilot_[0-9]{3}_.*') —— 那個 .* 讓 pilot_001_a、pilot_001_b… 無限延伸， 所以「doc id 正規式把面縮小」在份數這個維度上其實幾乎沒有縮小。 exists() 是唯一能把份數真正封頂到「實際機師數」的辦法。

⚠ 建檔時把它寫成「封頂儲存量的可選項」是錯的框架。儲存量那個風險確實小 （每份有界 ≈ 20 KB，塞滿 1 GB 要 5 萬份文件、寫入費卻不到 US$0.1）—— 052-E A-3 據此接受殘餘風險並沒有算錯。真正的作用是讓 A-3 生效，兩行算式：
· 只做 A-3：doc id 空間無限 ⇒ 每個新 id 各 create 一次、完全不受節流 ⇒ 仍是 43M/日 ⇒ ≈ US$78/日，決策九的數字一分不降。
· A-3 ＋ exists()：doc id 空間 ＝ 實際機師數（89）⇒ 89 份 ÷ 3 秒 ≈ 30 writes/秒 ≈ 2.6M/日 ⇒ ≈ US$4.6/日。
後者對得上決策九自己算的「3 秒節流後 ≈ US$6.1/日」—— 也就是說決策九那個數字本來就內含 exists() 封頂。它把兩者寫在一起不是並列兩項防護，是一組。

接得上，零轉換：buildId 就是 pilots 的 doc id （buildsApi.ts 的 buildDoc(uid, pilotId)，形如 pilot_001_艾達）。 規則裡的 get／exists 是特權讀取，不受 pilots 那條 read: if isAdmin() 影響（A-6 要有一條測試釘住這件事，因為它違反直覺）。

代價：每次存檔多一次計費 document read。存檔是人手按的動作 —— 以本站實測日寫入 ≈ 228 次的量級，這連告警門檻的零頭都不到。
⚠ 折衷方案不成立，先排除：收緊正規式（限制後綴長度、字元集）完全不縮小份數， 後綴仍可任意變化；改成純編號 '^pilot_[0-9]{3}$' 也只是把無限換成 1000， 1000 ÷ 3 秒 ≈ US$50/日，一樣不夠。要封到「實際機師數」只有 exists() 一條路。
原本列為 exists() 最大代價的「機師 id 漂移」，實際上不成立。（使用者裁決 2026-08-29）
scrape-pilots-v3.js 產的 id 是 pilot_{陣列位置+1}_{繁中譯名}， 所以理論上官方改一個譯名、或在中間插入一位機師，那位（乃至其後全部）的 id 就會變， 而 exists() 會把這件事從「靜默對不上」變成「存檔被拒」。

但這條路今天不會被走到：全站資料已不再由爬蟲驅動（使用者：官方根本不更新 —— aircraft_data 停在 v3.2，站上已 v3.6，v3.3 之後的機甲全靠人工建檔）。 id 因此是人工維護的穩定鍵，不是每次重抓都可能重算的衍生值。
⇒ 不因這條風險放棄 exists()。日後若真的改號，處置沿用既有流程 （改號本來就要處理熱度統計的幽靈 key），多帶一支 builds 遷移即可。
決策五：告警優先於熔斷，沿用 PLAN-046 決策七的取向。
collectBudget.ts 的註解已經把這個取向寫得很清楚： 「第一道通知請用 Firebase 用量告警（建議設 20,000），熔斷器只當防惡意攻擊的最後防線」， 並且 2026-08-08 特地把預算從「省額度」改為「資料完整優先」，理由是低預算會在流量暴增日誤觸。

對雲端書架而言這個取向更該成立：統計熔斷了只是少一筆數據， 書架熔斷了等於使用者按下「存入」而存不進去 —— 那是使用者可見的功能故障。 在沒有任何證據顯示有人在濫用之前，不值得為它冒這個險。
⇒ Phase B 做的是看得見（告警、後台用量），不是自動擋。 自動熔斷明確排除在範圍外。
決策六：SIMULATOR_INTERNAL_ONLY 留著不刪，而且要把收回條件寫成數字。
旗標已於 2026-08-29 改為 false，但檔案與四處呼叫刻意保留 —— 收回的代價因此是「改一個字」。

但「什麼情況下該收回」如果沒有事先寫下來，真的發生時就會變成臨場判斷， 而臨場判斷發生在最不適合判斷的時刻（帳單來了、或有人正在濫用）。 C-1 要把門檻寫成具體數字（日寫入次數、日費用、異常帳號數）， 連同「收回之後要做什麼」一起寫進 useSimulatorEntry.ts 的檔頭 —— 那裡已經是這件事的單一事實來源。
Scope
實作範圍與不在範圍內
在範圍內：
  • firestore.rules：收緊 users/{userId} 文件本體、 builds 寫入節流（含 delete）、updatedAt 綁 request.time、 補上「節流擋不住份數」的註解
  • src/lib/buildsApi.ts：updatedAt 型別調整、 被節流拒絕時的錯誤呈現（不能只是一個 403）
  • scripts/test-emulator-rules.mjs：新規則逐條補測， 包含「舊字串文件在過渡期仍能更新」這個回歸
  • Firebase 用量告警與 Cloudflare 方案／額度確認（站長任務）
  • 後台可見的雲端書架用量（有多少人在用、寫入量落在哪個級距）
  • 收回條件成文化：門檻數字寫進 useSimulatorEntry.ts 檔頭
不在範圍內：
  • 自動熔斷器 —— 見決策五：書架熔斷等於使用者存不了檔，先告警不自動擋
  • Cloud Function 份數計數器 —— 052-E A-3 否決的理由不變： 把一次 client 寫入換成一條會冷啟動、需要監控、會失敗的後端路徑
  • 052-H 站內熱門配裝 ＋ OG 卡 —— 前置條件（流量）雖已解除，但要等分布看得出形狀， 見總綱進度表
  • 武器改裝 —— 總綱決策十：全庫 180/180 筆 fixedMod.effects／ floatingMod.possibleEffects 皆空，不渲染，不是渲染空的； 要動它得先解決資料，不是 UI
  • 任何模擬器功能面的新增 —— 這個計畫只做護欄與觀察，一項功能都不加
