A-3   builds 寫入節流（含 delete）
firestore.rules · 總綱決策九
待開始
每文件 3 秒節流，update 與 delete 各一條
request.time > resource.data.updatedAt + duration.value(3, 's')。 delete 也要掛，否則 delete→create 的循環可以完全繞過節流（決策九原文就寫了）。

⚠ 依賴 A-4：這個條件要求 updatedAt 是 timestamp， 而現行是 client 寫的 ISO 字串。兩項要一起上，分開上會得到一條靜默失效的節流。

A-4   updatedAt：string → timestamp，且綁 request.time
firestore.rules · src/lib/buildsApi.ts
待開始
型別變更 ＋ 過渡期雙型別容忍 ＋ client 改送 serverTimestamp()
規則加 request.resource.data.updatedAt == request.time： 少了這條，client 每次寫一個「很久以前」的時間就能讓節流條件永遠成立， 那道節流會安靜地失效而不報錯（決策二）。

A-5   exists(/pilots/{buildId})：A-3 的必要組件
firestore.rules · 決策四（已裁決加入）
待開始
doc id 必須是真的機師 —— 與 A-3 同一次出貨，不可分開上
⚠ 這一項單獨看沒有價值，它的作用是讓 A-3 生效。 create 節流不了（決策三），所以 doc id 空間就是不受節流的寫入次數： 只做 A-3 ⇒ id 空間無限 ⇒ 仍是 43M/日 ≈ US$78/日； A-3 ＋ 本項 ⇒ id 空間 89 ⇒ 89 ÷ 3 秒 ≈ 2.6M/日 ≈ US$4.6/日 （對得上決策九算的 US$6.1/日）。 分開上等於裝了一道旁邊有路可繞的門，而帳單數字一分不降。

寫法：exists(/databases/$(database)/documents/pilots/$(buildId))， 掛在 create, update 上、不要掛 delete（沿用既有原則： 清掉一份垃圾文件永遠不會讓情況變糟，擋下刪除只會製造刪不掉的殘留）。 buildId 就是 pilots 的 doc id，零轉換。
⚠ 規則裡的 exists() 是特權讀取，不受 pilots 那條 read: if isAdmin() 影響 —— 這點違反直覺，A-6 要有測試釘住。
⚠ 保留正規式，不要用 exists() 取代它：正規式是先擋掉明顯畸形的 id， 省下那次 exists() 的計費讀取。

「機師 id 漂移」不構成阻礙（使用者裁決 2026-08-29）：全站資料已不再由爬蟲驅動， id 是人工維護的穩定鍵。詳見計畫書決策四後的說明。

A-7   被節流拒絕時，UI 要講得出人話
src/lib/buildsApi.ts · ShelfDialog
待開始
permission-denied 分流：節流 vs 真的沒權限
Firestore 規則拒絕一律回 permission-denied，規則不會告訴 client 是哪一條擋的。 使用者連按兩次「存入」撞到 3 秒節流時，若照現行路徑會看到一句和「你沒有權限」 長得一模一樣的錯誤。

⚠ 沿用 052-E 已建立的誠實文案原則：離線逾時那次的教訓是 「那次寫入我們取消不了，所以不能說『沒有存進去』」 —— 節流這裡相反， 請求根本沒送出，可以明確說沒有存進去。
