天賦裝備修正 · 解除機種限制 · 負重減免 · 潛能等級

機師天賦會改寫「什麼裝得上」與「這把多重」，而模擬器今天一個字都沒讀 —— 維娜點不到任何一把電磁炮、瑪汀妮點不到修理背包，那正是她們天賦的全部賣點。

來源
使用者於 2026-08-30 發現維娜〈罪業信條〉可讓重型機甲裝電磁炮、洛莎〈原型體〉「提升後」才減機槍重量， 並提問「未來這種情況可能還會發生，是否需要設計新的資料結構」。 評估過程與全量掃描結果見 _local-notes/2026-08/2026-08-30_機師天賦影響配裝規則_資料結構提案.md （含可重跑的 dump-all-talents.mjs）。四項設計問題已於同日全數裁決。
Problem
問題背景
問題一：維娜與瑪汀妮被錯誤封鎖 —— 這是站上現存的、看得見的錯
canEquipWeapon() 的 MECH_RESTRICTION 屬 structural 層級， 而 PickerShell 自 052-I 起把 structural 整批不列。於是： 維娜在模擬器裡點不到任何一把電磁炮（12/12 把是 mechRestriction:'medium'，她是重型執照）、 瑪汀妮點不到修理背包（14/14 個是 assemblableArmorType:['Medium']，她是輕型）。 這不是「少算了一點重量」，是站上對玩家說了一句錯的否定句，而且否定掉的正是那兩位機師的核心賣點。
問題二：8 位機師的負重減免完全沒算
火箭 −130（羅斯瑪麗／哈達威／艾琳）、重機槍 −200（格蘭特）、機槍 −80（洛莎）、 霰彈槍 −125（里貝卡）、狙擊步槍 −15%（凱莉，全庫唯一的百分比）、 電磁炮 −360（維娜）、修理背包 −300（瑪汀妮）。 這些天賦的 effects / enhancedEffects / buffIds 全是空陣列， 模擬器讀不到任何東西 ⇒ OVERWEIGHT 判定一律偏重，玩家實際帶得動的配裝會被判成裝不下。
問題三：「提升後」目前只是一個 UI 局部狀態
PilotTalentStrip 的 viewMax（預設滿星）是元件內的 useState。 洛莎／艾琳／里貝卡三人的減重只在提升後才有 ⇒ 一旦天賦會改重量，這個開關就不再是顯示偏好， 而是配裝參數。不升格的症狀是「畫面切回初始版、總重卻沒變」， 或匯出圖顯示初始天賦但總重用滿星算 —— 兩個數字在同一張圖上互相打臉。
方法論教訓：關鍵字掃描在這個資料集上不可靠
第一版盤點用關鍵字（負重／重量／額外裝備）掃，漏掉了整批用「射程+1」「彈倉容量+2」表達的同類規則。 官方文案對同一件事有多種說法（「負重降低」／「重量降低」／「負重-360」）， 下一個新機師會用第四種說法。日後重做這類盤點一律用 _local-notes/2026-08/2026-08-30_dump-all-talents.mjs 全量傾印逐條讀。

A 類影響配裝合法性與重量（本計畫核心）；B 類形狀相同但只改顯示數值；C 類是另一種東西，明著劃在範圍外。

B 類的存在就是「未來還會不會發生」的答案：會，而且已經發生 9 次了。
形狀與 A 類完全相同（作用對象 ＋ 屬性 ＋ 加算／乘算 ＋ 值 ＋ 生效門檻），差別只在「哪一個屬性」與「誰消費」。 因此結構一次做成通用的裝備數值修正，但只有 weight 接進配裝規則層，其餘先存著供顯示／未來傷害模擬用。
C 類 —— 「裝了什麼 → 觸發什麼」（12 筆以上，不在本計畫範圍）
卡夏「若裝備兩把機槍」、亞瑟／奈奧米「雙肩同時裝備導彈」、西爾維婭「裝配手盾時」、凱瑟琳「裝備長柄」、 阿列娜「同時裝備大盾和噴火器」、賽拉「裝備電磁炮時」、瑪阿特「裝備除強襲者背包外的任意背包」、 皮普「雙手均裝配格鬥武器」、莉莉「只裝配一種戰術武器」、弗雷姬塔／鄭樂萱「裝備兩把突擊武器／兩把機槍」……
這些不改任何裝備數值、也不改合法性，只是「配裝滿足條件 ⇒ 某個戰鬥效果成立」，屬傷害模擬層， 既有 SkillCondition 已有雛形（trigger / weaponType / weaponKind）。 硬塞進本計畫的結構會把兩件不同的事綁在一起 —— 刻意排除。
邊界事實：來源只有機師天賦
modules(241) / components(208) / backpacks(181) / pilotSkills(853) / neuralDriveAbilities(440) / buffs(228) 全部 0 筆提到負重、重量或額外裝備 （mechs 的 3 筆命中全是 lore 文案）⇒ 新結構只需掛在 PilotTalent 上，不必做成跨集合機制。
⚠ 但這一條是用關鍵字掃出來的，而上面已證明關鍵字會漏 —— 目前當作「高度可能」而非硬結論。
Design
設計決策
決策一：新開窄型別 loadoutMods，不塞進 SkillEffect
SkillEffect 的語意是「戰鬥期的數值加成」（scope / condition 全是戰鬥詞彙）， 而這批規則是「建構期的裝備屬性改寫」—— 消費端、值域、生命週期三者都不交集。
混在一起的具體代價：EquippedEffects 那類「把所有 effects 攤平加總」的地方會開始顯示 「機槍重量 −80」這種不屬於戰力彙總的列，而要擋掉它就得在每一個消費端各寫一次過濾。
另外兩個致命點：「解除限制」沒有 value 可放（只能塞 value:0）； stat 是開放字串，weight_machinegun 打錯不會有人知道。 封閉聯集則能在新增一種 target 時逼 tsc 補分支，與 REJECTION_CODES 的既有風格一致。
決策二：target 與 stat 分離，泛化到 5 個屬性 —— 但只有 weight 進規則層
若把屬性寫進鍵名（weight_machinegun），就要造 17 種 WeaponKind × 5 種屬性 × {flat,pct} 的組合鍵。拆成 { target, stat, mode, amount } 之後，新增一個武器種類或一個屬性都不必造任何新鍵。
B 類 9 筆先入庫但不接規則層：它們不影響合法性，接了只是把未驗證的數字送進計算。 
// src/types/pilot.ts（或新檔 types/loadoutMod.ts）

/** 這條規則作用在哪些裝備上。封閉聯集 —— 新增一種，tsc 逼你在規則層補分支 */
export type EquipTarget =
  | { on: 'weaponKind';   kind: WeaponKind }      // '電磁炮' / '火箭' / '機槍'…
  | { on: 'backpackType'; type: BackpackType }    // 'Heal'（修理背包）
  | { on: 'weaponId';     id: string }            // 保留：未來若出現「僅某把武器」

/** 可被天賦改寫的裝備屬性。**只有 weight 進配裝規則層**，其餘先存著供顯示／傷害模擬 */
export type EquipStat = 'weight' | 'ammoCount' | 'maxRange' | 'minRange' | 'durability'

/** 生效門檻：'base' ＝ 天賦一到手就有；'max' ＝ 天賦提升後才有 */
export type TalentTier = 'base' | 'max'

export type TalentLoadoutMod =
  /** 裝備數值修正。amount 一律**帶號**（−130 / −0.15 / +2），mode 決定加算或乘算 */
  | { kind: 'stat'; target: EquipTarget; stat: EquipStat; mode: 'flat' | 'pct'; amount: number; since: TalentTier }
  /** 解除機種限制（維娜／瑪汀妮）。刻意不帶值 */
  | { kind: 'allowEquip'; target: EquipTarget; since: TalentTier }

export interface PilotTalent {
  // …既有欄位…
  /** 影響裝備合法性／數值的規則（全庫 18 位機師有）。未填＝這個天賦不改任何裝備 */
  loadoutMods?: TalentLoadoutMod[]
}
決策三：單一 since 欄位，不做 mods / enhancedMods 兩個陣列
比照既有 effects / enhancedEffects 的作法，會逼編輯者把 base 的內容整份複製到 enhanced 陣列 （因為提升後是「初始的一切 ＋ 新增子句」）。漏複製的症狀是「天賦點滿之後反而變重」，而且不會有任何錯誤訊息。
使用者裁決（2026-08-30）：實測 0 筆「兩態數值不同」，且對遊戲設計意義不大 ⇒ 單欄位定案。 真的出現時再補一個選填 maxAmount?: number —— 那是加欄位，不是改結構。
決策四：loadoutWeight.ts 完全不動
它「只吃 { weight }、不認識機師」的設計是對的，改成在 loadoutRules 組 LoadoutWeightSet 時把武器 map 成 { weight: statOf(w,'weight') } 即可。
好處是 loadoutWeight.test.ts 不必為了測減重而生一個假機師， 那支單測守的是「手部取較重組」這條不變式，不該被機師資料污染。
⚠ UI 要講「1100 → 740」，所以呼叫端要另外留一份原重（或給 WeightBreakdown 加 reducedBy）。
決策五：不新增 RejectionCode —— 豁免是「不觸發既有拒絕」，不是「一種新拒絕」
canEquipWeapon() 的 restrictedTo() 那一段加豁免、 canEquipBackpack() 的 BACKPACK_ARMOR_TYPE 同理。
⚠ 但挑選器的 hint 文案要跟著：「因機種限定隱藏 12」在維娜身上必須變成 0，否則玩家看到的是矛盾 —— 清單裡看得到電磁炮，底下卻寫著「隱藏 12 個機種限定」。
決策六：存潛能等級 0–5，不存「天賦有沒有提升」的布林
使用者裁決（2026-08-30）：「提升」的真身是潛能提升 —— 重複抽到同一機師累積的養成軸， 五階內容為：①初始 AP +1 ②駕駛等級→大師Ⅱ ③天賦能力加強 ④駕駛等級→大師Ⅲ ⑤初始 AP +1， 外加「提升後所有屬性提升 2%」。
五階裡有四階不是天賦。布林無法還原等級，等哪天要算 AP 或屬性 %， 就得再加一個欄位並遷移所有已流出的分享碼。今天多存 3 個 bit，換的是那次遷移不必發生。
佐證：站上既有資料早就是「滿潛快照」
佐證數字
ap.init − apBase.init= 2 佔 54/89（＝第 1、5 階那兩個「初始 AP +1」都吃到了）
masterLevel 值域大師Ⅲ 59／精通Ⅳ 15／熟練V 10／超適體Ⅲ 3／大師Ⅳ 2 —— 大師Ⅲ 正是第 4 階的產物
天賦正文descriptionMax 本來就是「提升後」那一段
這與「官方 API 天賦文本是滿晶片污染值」是同一個現象的不同面向：API 吐的是某個養成狀態的快照，站上照單全收。 因此「欄位不存在＝滿潛 5」與既有資料一致，不會引入第二套假設。 
export interface LoadoutDraft {
  // …
  /**
   * 潛能等級 0–5（重複抽同一機師累積）。**欄位不存在＝滿潛 5**，與站上資料的滿潛快照一致。
   *
   * ⚠ 存等級而不是「天賦有沒有提升」的布林：潛能同時決定天賦提升、初始 AP、駕駛等級與屬性 %，
   *   布林**無法還原**等級，等到要算 AP 或屬性時就得再加一個欄位並遷移所有已流出的分享碼。
   */
  potential?: number
}
決策七：天賦加強恆在第 3 階，常數集中一處
使用者裁決（2026-08-30）逐字：「天賦加強絕對在第三階，這是遊戲目前為止沒有破例過的。」
因此規則層寫死 TALENT_BOOST_POTENTIAL = 3，不為此開資料欄位 （依 0/5 定律，一個「每位機師都填 3」的欄位只會變成漂移的來源）。
⚠ 觀察到的雜訊已由使用者判定為資料問題：ap.init − apBase.init 分佈是 {0:10, 1:18, 2:54, 5:7}，使用者判斷「大概是資料填錯或是 A/B 機師，也可能是超適體，以後再處理」。 不阻塞本計畫；日後若真出現破例，改的是一個常數。
決策八：明細印原重，減免說明掛在總重那一列 —— 與官方 UI 一致
使用者提供的維娜整備截圖是一次完整驗算：
巨像部件 945 ＋ 承諾之誓 390 ＋ 炬塔·改Ⅱ(1100−360)=740 ＝ 2075 ＝ 出力 2075
（全庫唯一 output=2075 的重型機甲是巨像，部件總重正是 945，四項全部對上。）
關鍵觀察：官方在武器明細印的是原重 1100，扣減只反映在總重。 站上照做 —— 武器明細維持 1100，總重列印 2075（電磁炮 −360 · 罪業信條）， 玩家兩邊對照時逐格吻合；反過來做會出現「站上寫 740、遊戲寫 1100」的困惑。
決策九：★ 與金框兩種視覺並存（使用者裁決：做，可以試試看）
站上「強化」目前有兩義，必須分開：
· 天賦提升（潛能第 3 階）→ ★ 角標，機師自己的成長
· 專武強化（enhancesTalentName）→ 金框，外部裝備帶來的
兩者可以同時成立（洛莎滿潛 ＋ 裝上專武），所以必須是兩種可疊加的視覺，不能共用一個。
順帶：站上文案叫「滿星」、遊戲 UI 叫「（提升後）」。建議前台改用遊戲原文「提升」， 資料欄位名維持 descriptionMax 不動（改欄位名要動爬蟲、後台、三個頁面，換來的只是名字好聽）。
⚠ 專武沒有「只有該機師能裝」的限制
Weapon.exclusiveFor 的語意是「這是誰的專屬武器」（用於推薦與天賦強化判定）， 不是裝備許可，站上模擬器也沒有擋。評估期間曾因誤讀此欄位而把截圖裡的機師判成零 （她拿的是零的盾牌），此處記一筆以免再犯。
Scope
實作範圍與不在範圍內
在範圍內：
  • TalentLoadoutMod 型別 ＋ PilotTalent.loadoutMods 欄位
  • PilotAdmin 天賦區的編輯 UI（結構化輸入，不是塞 JSON 字串）
  • A 類 9 筆資料填值 ＋ bump pilots 版本
  • 新檔 src/utils/talentLoadoutMods.ts（純函式・可單測）
  • canEquipWeapon / canEquipBackpack 的機種限制豁免 ＋ 挑選器 hint 修正
  • 重量帳接線（在 loadoutRules 組 set 時 map，loadoutWeight 不動）
  • LoadoutDraft.potential ＋ reconcile() ＋ codec §TALENT 追加段
  • 潛能選擇器 UI ＋ ★ 角標 ＋ 總重列減免標示（含匯出圖）
  • 選配：B 類 9 筆入庫 ＋ 武器卡顯示（不接規則層）
不在範圍內：
  • C 類「裝了什麼 → 觸發什麼」（12 筆以上）—— 屬傷害模擬層，用 SkillCondition 而非本結構
  • 潛能的其他產物（初始 AP ±、駕駛等級、所有屬性 +2%/階）—— 使用者裁決「以後再說，這一段有點複雜」。 站上目前存的是滿潛快照，缺的是「每一階各給什麼」這份資料； potential 存等級而非布林，就是為了那天到來時不必遷移分享碼
  • 多天賦機師的支援 —— 全庫 89/89 每人恰好 1 個天賦，先不預留
  • 天賦加強階位逐機師不同 —— 使用者裁決恆為第 3 階，寫死常數
  • 爬蟲自動解析天賦正文產生 loadoutMods —— 18 筆人工填即可，寫解析器的成本高於收益， 且官方文案措辭不穩定（見「方法論教訓」）
