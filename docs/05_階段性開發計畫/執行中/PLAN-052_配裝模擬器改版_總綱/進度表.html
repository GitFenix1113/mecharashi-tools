052-J   雙手武器裝備路徑
2026-08-26 完成 · 8 / 8 工項
已完成
雙手武器裝得上 ＋ 盾擇一（8 工項）
計畫外追加的修復子計畫，起因是 052-I Phase B 的瀏覽器實測： 全庫 40／182 把雙手武器（22%）在模擬器裡沒有任何入口裝得上——不是灰掉、不是附原因，是整批被 omit。 成因是兩個各自正確的決定撞在一起：canEquipWeapon() 的槽位早退直接 reject， 而 enumerateSlots() 刻意不產生 dualHand 座標（這是對的，雙手佔的是兩格 singleHand）。
解法為新增單一入口 mountRefFor(weapon, ref)：手部座標願意接受雙手武器， 由規則層在內部換成它實際佔住的 dualHand 座標，預覽與落地共用同一支， reducer 一行未動（placeWeapon() 走 slotsOverlap()，餵 dualHand ref 本就會擠掉左右手兩把）。 槽位圖比照遊戲整備畫面，左右兩格各印同一把；replaceNote() 那條原本永遠跑不到的死碼自動復活。
Phase D 順帶補上盾擇一：手盾與大盾合計每組一面，主手組與備用組各自計算（SHIELD_LIMIT，situational）。
時機：052-C 剛讓使用者能存書架、發分享碼，而在此之前存下來的每一份配裝都不可能包含雙手武器； 分享碼只進不出，愈晚修愈多既成事實。此 bug 撐到 052-I 才被發現，是因為形態鎖定那條路不經過 canEquipWeapon()。

五條規則 ＋ componentFamilyKey() ＋ 組合特性預覽（15 工項）
元件是模擬器最後一塊明著寫「建置中」的功能——052-I D-3 已把面板畫出來， 但它唯讀。本子計畫把決策五的五條合法性規則落地，並拆掉那條常駐告示。
2026-08-26 直讀正式 Firestore 的盤點，兩處推翻決策五：
① 族數是 56 不是 28——觸 28 ＋ 應 28，總綱那個數字是其中一半 （24 族 6 筆 ＋ 12 族 3 筆 ＋ 8 族 2 筆 ＋ 12 族 1 筆 ＝ 208，族數 56，兩邊都對得起來）。 CI 守門測試的斷言要照 56 寫。
② allowedWeaponTypes 的「觸元件W-警戒 3 筆是漏填」早已補齊： 現為 7 筆部分限定且左右對稱（警戒族 6 筆「射擊」＋ 擴膛 1 筆「突擊」）， 其餘 201 筆長度為 4 ＝ 後台「全選」＝不限。本計畫零資料補丁。
其餘實測全數相符：208 筆、W 80／Normal 128、可裝 W 型的武器 49 把、 always 103／dualWield 3（確認 conditionType 不可當互斥鍵）。 命名 208／208 全合規、觸應不共用任何後綴、觸元件 28 族與 condition 文字完全雙射——決策五要的那條守門斷言成立。
對決策十二的修訂：8 筆固定武裝的 componentLimit 全為 0 （雖然都是 S 品質），代表能裝元件的武器 100% 都在 mounts 裡。 於是「元件的 key 必須掛在三段式 mountKey，否則主手左手與備用左手撞 key」 這條擔憂，在 052-B 選擇把 setup 內嵌在 mount 上時就已經消解—— 沒有旁掛表，也就沒有 key 可撞；「刪格時連元件 key 一起刪」也自動成立。 SlotRef 的 kind 聯集擴充元件用不到，隨 052-G 一起做。
使用者裁決 2026-08-26：同族互斥的判定範圍是單把武器內—— 右手裝憑逸、左手也裝憑逸是可以的。規則層因此只看 mount.setup 一個物件。
⚠ 最危險的一條：reconcile() 對武器是「查不到就刪」， 元件絕對不可照抄——草稿可能在 components 載入前就被 loadDraft 灌進來（分享碼／書架／052-E 雲端存檔都走這條）， 症狀是貼一次分享碼、元件就被靜默清空一次。

② 四部位卡歸位：拆掉「下方那一塊十字」，長進槽位圖裡
在此之前四部位卡是掛在槽位圖下方的一整塊十字（MechPartStrip 自己排版）， 於是同一台機體被講了兩次：上面講武器掛在哪、下面講模組裝在哪，玩家要自己把兩張圖疊起來。 現在 MechPartStrip 只出一張卡（MechPartCard），排版由 LoadoutRig 決定，由上而下：軀幹（整列置中半寬）／ 臂卡插在同側的肩與手之間／腿部／背部。 於是「右肩 → 右臂 → 右手 → 右備用」是一路讀下來的同一欄，順序即機體由上而下的解剖順序。

兩次翻案都記在註解裡：⒜ 腿部與背部的上下（初版把背部排在腿部之上，論證是 「背部與肩、手同屬武器格，不該被部位卡從中切開」——輸給解剖順序）； ⒝ 臂卡的位置（初版接在整欄最下面，那讀起來仍是「武器歸武器、模組收在下面」， 等於換個位置擺兩份清單）。

⚠ dense（容器 < 610px）時雙臂退回整寬兩欄：側欄在那個寬度只剩約 120px， 放不下兩行內容的部位卡。那不是第二套版面，是同一個十字的窄版。 ⚠ 包住卡片的容器也要看 hasParts：卡片自己回 null 之後那些 <div> 仍在，而零高度的子元素照樣吃掉 flex-col gap-2 的兩道 gap。 ⚠ 部位卡不接引線：引線回答「這一格屬於機體哪一側」，而部位卡自己就是部位。

抬頭同時由「槽位」改為「裝備與模組」——這張面板自 052-G 起就同時裝著兩者， 舊抬頭只講到上半部，來找模組的人會略過它。 Parts · Modules 抬頭隨歸位拆掉（卡片已不相鄰，抬頭會指向四張散開的卡）， 原本那句「部件混搭開放後…」改由 PART_MIX_NOTE 掛在整張圖的最下緣。

③ 中欄放大：欄寬封頂，餘裕全給立繪
使用者逐字：「裝備名稱似乎普遍沒有那麼長，可以把中間的圖再放大、縮窄裝備欄位的寬度」。 在此之前兩側是 minmax(0,1fr)，於是視窗每寬 100px 就有 100px 被平均倒進 兩欄的右側留白（實測：中欄 1050px 時單欄 365px，而一格真正用得到的是 圖示 42 ＋ 六個字 90 ＋ 重量 30 ＋ 內距間隙 ≈ 200）。版面越寬，主視覺佔比反而越小。

改成側欄 minmax(0,250px)、中欄 minmax(164px,1fr)： grid 先把非彈性軌撐到上限，剩下的全部歸中欄，立繪再以 w-full max-w-[340px] aspect-square 封頂。 中欄那個 min 取 164（＝改版前的固定立繪尺寸）， 於是容器 610–738 這一段與改版前逐 px 相同，窄端零回歸。 三欄比例另由 360/1fr/420 改為 320/1fr/420，中欄各斷點 +40px； 右欄 420 不動——那是 2026-08-27 為模組清單列從 380 調上來的，收窄等於推回一半。

⚠ 立繪改用 aspect-square 而非寫死 px：高度由寬度算出來， 立繪非同步載入一樣不會推位（那正是當初寫死尺寸的原因，換法不同、保證相同）。 方框必須維持正方形且等於圖的實際尺寸，否則引線落點（ANCHOR 是方框的比例座標） 會飄到機體外面的空白上。

⚠ 踩過一次：第一版把 class 寫成 `grid-cols-[minmax(0,${SLOT_MAX_WIDTH}px)_…]`。 Tailwind v4 掃的是原始碼裡的字面值，樣板插值產不出任何 class， 而且不會報錯——症狀是版面靜靜退回單軌 grid。已改為完整字面值常數並附警告註解。
