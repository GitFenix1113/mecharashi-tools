Problem
問題背景
現行配裝模擬器的根本問題不是「功能不足」，是資料模型只有兩個單值欄位
SimState（SimulatorPage.tsx:48-59）與 Build（src/types/user.ts:40-58） 都只有 weaponId ／ backpackId 兩個單值 —— 連「左手一把、右手一把」都表達不了。 它同時擋住五件事：① 中甲雙肩＋雙手＋背部的多槽配裝 ② 左右手區分 （曜的 skill_映纏「同時裝備刀劍及機槍」、mod_異械模組「雙手兩把種類不一致 +24%」都需要） ③ 強襲者背包的備用套 ④ 海莉絲的 per-form 多套 ⑤ 元件掛到每一把武器上。 而且沒有 version 欄位，日後無法 lazy migration。
逐段稽核找到 31 條缺陷，其中三塊「渲染了但資料全庫皆空」
· 過濾層：中型執照篩選靜默全放行（:179 用 '中甲' 比 MechLicense.MEDIUM='中型'，影響 37/89 位機師）、 mechRestriction 完全沒擋、背槽不互斥（181/181 個背包 slot='back'）、 出力帳漏算三種加成、順序相依的重量帳。
· 元件層：componentLimit 從未被讀取 ⇒ 135/180 把武器可以裝到 6 個元件（官方是 4 個槽）； W 型元件與 allowedWeaponTypes 從未過濾；元件是「整台機甲一組」而非掛在武器上。
· 三個恆空面板：改裝（180/180 把武器 fixedMod.effects 全空，且該步驟沒有下一步按鈕）、 科研（pilotResearch 只有 1 筆且 pilotId 對不上，89/89 位機師全失效）、 可達增益（全庫 buff／技能 effects 合計 0 筆、323 筆 buffIds 100% 解析失敗）。
時間窗：users 集合實測 0 筆文件、builds 0 筆
2026-08-23 以 serviceAccountKey.json 唯讀實測確認。現在改配裝資料模型不需要遷移腳本； 一旦對外開放存檔（本計畫已定案為全面公開），任何形狀錯誤都要洗使用者資料。
⚠ 動工前要再跑一次這個實測，並列入 052-A 的驗收條件。
⚠ 另注意：導覽列雖以 isAdmin gate，但 App.tsx:74 的路由沒有 AdminRoute、 ProfilePage 三處入口對所有登入者開放 —— 這個前提隨時可能被打破。
Design
設計決策
本計畫的由來與方法
2026-08-23 以 11 個 agent 做多階段調查（4 路現況盤點 → 5 路設計 → 2 路批判／紅隊）， 再由使用者分三輪答覆 35 題遊戲事實與產品取捨。 完整調查、線框圖與逐條證據存於 _local-notes/2026-08/2026-08-23_配裝模擬器_完整設計評估.html（本機、不進版控）； 本文件為權威記載，兩者衝突時以本文件為準。
決策一：四條「數值必須先釘死」的遊戲事實
紅隊拿官方整備截圖逐格對帳，發現五份獨立設計一致採用的公式都是錯的。四條皆已由使用者裁決：
① 總重量 ＝ 機體 ＋ max(主手組, 備用組) ＋ 肩 ＋ 背 —— 不是加總。 實測：先鋒 825＋max(800 戕神者, 850 Z15)＋150 ＝ 1825 ✓（加總會得 2625，誤差 44%）； 四個形態四組官方數字全數對帳通過。
② 機甲火力 ＝ Σ 四部位（＋科技）；mech.firepower 頂層欄位是爬蟲抓官方欄位的產物、毫無意義。 佐證：品質預覽四張截圖中，軀幹／雙臂／腿部在同一品質階的火力數字完全相同（1040／1108／1186） ⇒ 部位存的是「每部位值、四份鏡射」。實測 83 台 scraped 機甲的頂層值 ＝ 單一部位值， 7 台手建的頂層 ≈ Σ ⇒ 站上目前顯示的是實際的 1/4。
③ 出力是 per-form 的：3675 vs 3375 差的 300 來自強襲者背包；戰術／虛粒子形態的背槽被背部武器佔住 ⇒ 沒有背包。 ⇒ effectiveOutput() 與 totalWeight() 必須吃 formKey，不能吃整份 Build。
④ weapon.attack 是「全部連擊的總和」，官方顯示的是「每擊值」，且官方值比 DB 高 17.3–18.6% 且逐把不同 （已排除機師五維、kindCoefficient、單一全域倍率；而命中值 1:1 完全相符）。 使用者裁決：屬傷害計算範疇，延後至傷害模擬計畫。
決策二：Loadout v2 —— 落盤是「一串分享代碼」，記憶體是結構化型別
· 落盤：users/{uid}/builds/{pilotId}，一位機師一份文件，slots: {'0'..'4'} map， 每格內容就是一串 base64url 分享代碼。
· 三個決定性理由：(1) Firestore 規則沒有位元組長度運算子、不能對動態 key 迴圈、也沒有 count() —— 巢狀結構在規則層設不了上限，一個帳號可以塞近 1 MiB 的合法形狀 JSON；收斂成單一字串後 code.size() <= 1024 是精確且繞不過的上限。 (2) map key 白名單讓「每機師 5 套」變成結構性事實（規則沒有 count()，計數欄位一定會漂移）。 (3) 儲存＝分享是同一串字，沒有第二套序列化會漂移。
· 記憶體：結構化 Loadout（codec 的解碼目標），元件內嵌在 mount 上 —— 旁掛 Record<MountKey, …> 與 mounts 陣列是兩份要手動同步的資料， 刪掉左手武器忘了刪 key，下一把同槽武器會靜默繼承上一把的元件。 這與 form.ts 拒絕 lockedSkillIds、weapon.ts 拒絕反向索引是同一條理由。
· 刻意不落盤：機體數值、可達 buff、總重量、Build.result（現行有，刪除）、 機甲／武器名稱、模組等級、情境（目標裝甲／距離／HP%／AP）。
決策三：槽位詞彙 —— bank 是正交的第四個軸，不是第四套部位詞彙
PLAN-047 決策一禁止再開第四套部位詞彙（全站已有 WeaponEquipSlot／MechPartPosition／Backpack.slot）。 SlotBank = 'main' | 'backup' 不違反這條：它與 slot 正交 —— 備用手上的武器 equipSlot 仍然是 singleHand， 所以 mount.slot === weapon.equipSlot 這條 0 例外的硬規則不受影響。
mountKey 一律三段式 bank:slot:side，由 slotKey() 單一入口產生、 parseSlotKey() 解析，round-trip 進 npm test。
⚠ 紅隊發現：五份設計對這個軸有四種寫法，其中兩份的 mountKey 是 slot:side 兩段 —— 主手左手與備用左手會產生同一個 key，兩把武器的元件互相覆蓋。這不是風格差異，是會靜默毀資料的 bug。
決策四：形態 —— 四個形態一視同仁，全鎖那一套不落盤
使用者逐字：「其實四個形態都是各自一套獨立裝備，只是虛粒子形態已經有固定武裝綁死了，你也改不了。」
· loadouts: Record<formId, EquipSet>，沒有形態的機師固定用 'default' 一把鑰匙。
· 全鎖形態（海莉絲虛粒子／曜巡航）不出現在 loadouts 裡 —— 那一套 100% 由 form.restrict.mounts derive；落盤第二份就會有兩份對不上的可能，而玩家本來就改不了。
· 武器與背包都獨立，所以各套的重量／出力預算完全分離。
· MechForm 新增 independentLoadout?: boolean（海莉絲 3 筆（先鋒／突擊／戰術）；曜 0 筆）， 並提供全站唯一入口 equipSetKeys(pilotId, forms)：有 independent 就回那些 formId，否則回 ['default']。 UI 一律 map over 它，不要 map over Object.keys(loadouts) （後者在「存檔之後才新增形態」時會少畫一個分頁，而且不會報錯）。
· FormRestrict 不需要 lockCurrent 分支：曜的巡航形態也是「換掉並鎖住」 （專屬固定武裝 幽弧／夜燼，2026-08-28 查證：weapon_181_幽弧／weapon_182_夜燼 已建檔，皆 isFixedArmament: true；form_曜_巡航 的 restrict.mounts 已掛上這兩把），兩位調構師走同一條規則。 weaponIds: string[] 升級為 mounts: ArmamentMount[]（才畫得出哪一把在哪個槽）。

⚠ 補充裁決（2026-08-28，使用者）：曜沒有形態分頁，而且 forms 裡那兩筆空著的 independentLoadout 是正確資料。
使用者逐字：「曜的兩筆形態：遊戲中實際上連形態頁面都沒有，就跟一般機師一樣只能配一套裝備。 但真實狀況就是，因為曜只有原始的機兵形態和巡航形態，而巡航形態裝備是固定武裝，所以確實也只能弄一套裝備。」
⇒ 曜走一般機師的單套 default 配裝，equipSetKeys('pilot_088_曜') 回 ['default']、hasIndependentLoadouts() 回 false，皆是正確行為，不是 bug。
⇒ 不要「順手」把 form_曜_機兵 的 independentLoadout 補成 true—— 補了就會在站上長出一個遊戲裡不存在的分頁列。規格與資料在同一頁互相打臉時， 後來的人一定會去改比較好改的那一邊，而那一邊是資料，所以這句話寫在這裡。
⇒ 唯讀卡的判準是「這位機師有沒有分頁列」，不是「有沒有 fixedArmament 形態」： 有分頁列，鎖死的那一格才需要被解釋。因此 052-F 只畫海莉絲虛粒子一張唯讀卡， 曜的巡航形態不畫——幽弧／夜燼在武器圖鑑查得到（PLAN-040 已建檔）， 那裡才是「這兩把是什麼」的去處；配裝頁回答的是「這一套裝了什麼」。
（本段回寫自 PLAN-052-F 的 A-1／A-3；原表列「曜 1 套 ＋ 1 唯讀」的「1 套」 指的是一般機師的預設那一套，不是一個形態分頁，已一併改寫掉以免誤讀。）
決策五：元件 —— componentLimit 是總槽數，互斥判準是名稱後綴
使用者逐字：「那是槽位，一個槽一個元件，SS 和 S+ 武器總槽＝4，意思就是觸＋應總和四個，暫時沒有元件會佔領 2 個。」
五條合法性規則（現行一條都沒做）：
① 總槽 trigger + effect <= componentLimit（SS/S+ = 4、S = 3、A/B = 0）
② 分項 trigger <= 3 且 effect <= 3（不能 4 個全裝觸元件）
③ componentsWType === 'W' 只給 dualHand／back 武器（W 型 80 筆，符合條件的武器只有 49 把）
④ allowedWeaponTypes 過濾（觸元件W-警戒 3 筆是漏填，要補「射擊」限定）
⑤ 同族互斥：名稱後綴，觸／應都適用，且跨 W/Normal 變體（「憑逸W 和 憑逸 不能兩顆都裝」）
互斥不落 Firestore 欄位：判準既然就是名稱，落一個 familyKey 只是把同一件事寫第二遍，改名時兩份會靜默不同步。 改做 componentFamilyKey() 單一入口 ＋ CI 守門測試（斷言 208 筆推出 28 族且與 condition 文字雙射）。 ⚠ conditionType 絕對不可當互斥鍵（實測 106 個觸元件裡 always 103 筆，用它會讓玩家永遠只能裝 1 個）。
求值模型：觸元件成立時逐一個別判定每個應元件（2 觸 2 應 ⇒ 每個應元件各判兩次）， 但同一個應元件被多個觸元件觸發不疊加 ⇒ 期望值 P = 1 − Π(1 − p_ij)。 官方「組合特性」面板會直接印出每一條配對的最終機率（實測樣本：觸W-憑逸 Lv7 × 應 Lv4/5/6 → 33%／41%／47%）， 機率是「(觸,應) 配對」的屬性；反推公式屬傷害計算範疇，本輪只顯示 Lv。
決策六：模組 —— 四個接口槽是「額外裝備」，與機甲天生模組並存
使用者逐字：「品質預覽每個部位列出的三個模組是機甲天生自己帶的。每一個接口可以再『裝備』一個模組。」
· 四個接口槽（每部位 1 個），玩家各裝一個模組；與天生模組並存、不互相取代。
· 接口 gate：MechPart.interface 為 Ⅰ型 ⇒ 只能裝 rarity === 'A'；Ⅱ型 ⇒ A/S 皆可。 實測 360 格已填 316（S 機甲 248 格 Ⅱ型、A 機甲 Ⅰ/Ⅱ 各 32 格混合、B 機甲 40 格空白、4 格錯字「ⅠⅠ型接口」）。
· 候選清單 ＝ boundMechId === null（Q-2 已解，2026-08-25）—— 使用者逐字：「這就是為什麼當初模組要設計『綁定機甲』這件事，基本上只要沒有綁定機甲，其他機甲都能使用。」
⇒ 候選不是按 slot 類別挑（原本猜的「通用 62」或「含特性／8 級共 207」兩案皆作廢）， 而是一條欄位判斷。實測（2026-08-25，242 筆模組）：不綁機甲 199 筆（S 158／A 41），綁機甲 43 筆； 且 199 筆的 boundPart 全為 null —— 今天沒有任何「限定部位」的通用模組，部位 gate 先不做。
⇒ 與接口 gate 相乘：Ⅱ型接口候選 199 筆、Ⅰ型接口候選 41 筆（A 級：通用 30 ＋ 特性 11）。 挑選器規模落在「一頁列得完」與「需要分類」之間，建議 Ⅱ型走分類分頁、Ⅰ型單頁。
· ⚠ 待複查（不阻塞 052-D，052-G 動工前處理）：199 筆內含 機甲副模組 11 筆 （出力／回避／增傷／承傷…＝與天生模組同名），依規則它們也「沒綁機甲」，但那正是機甲天生自帶的那一種。 建議挑選器排除 slot === '機甲副模組'（⇒ Ⅱ型 188 筆）。 另 available 值域已漂移：原記「副模組 11 筆 false」，2026-08-25 實測為 10 筆 true／1 筆 false ⇒ available 不可再當唯一 gate。
· B 品質機甲「沒有接口」，不是「未建檔」（使用者確認）—— B 級 10 台 40 格空白是真的沒有這個槽，應由 quality derive，UI 寫「此機甲無模組接口」； 真正的未建檔只有 S 級美杜莎MK2 那 4 格（v3.6 佔位機甲）。 ⇒ src/types/mech.ts 對 '' 的註解（現寫「B 品質刻意不補」＝未建檔）與 MechPartsTable 的「接口資料未建檔」文案需要跟著改，列入 052-G 工項。
· ⚠ 星夜女神（S・v3.5）四部位全 Ⅰ 型 —— 位置與筆數都與原記「4 格錯字ⅠⅠ型接口」吻合， 疑為 052-A 資料修正時被正規化成 Ⅰ 型。需回官方對帳：若實為 Ⅱ 型，則Ⅰ型接口只存在於 A 級機甲 （與使用者說法一致），Ⅰ型候選池的用途也只剩那 16 台。
· 模組等級由「部位品質階級 × 部位種類」決定，不是玩家升的 （升級某部位品質會讓某個模組 LV.1/8 → LV.2/8，且雙手提供的與軀幹腿部不同）。 牽涉特殊模組，本輪延後：一律預設滿級、不給玩家選機甲品質階。
· ⇒ Loadout.modules 只存 {部位: moduleId}，不存 level —— level 是 ResolvedChassis 的推導值，存下來就是第二真相源。
· ⚠ 讀數值時務必走 levels[]：實測 236/240 模組的數值住在 levels[]， 頂層平坦欄位 177/240 是 0（mod_4001 頂層 acc_rate=0，各級卻是 3/5/7/10）。
決策七：部件混搭 —— 做，但限同裝甲類型；數值合成規則未定前不出衍生數字
PLAN-047 決策十二④「不做部件混裝」作廢（使用者決定要做）。
· 不能跨裝甲類型混搭 ⇒ 四個部位必定同類型 ⇒ 「混搭後裝甲類型由誰決定」這個問題自動消失，雙肩槽與執照判定完全不受影響， PART_INCOMPATIBLE 只需一行 sourceMech.armorType === chassis.armorType。
· 只有軀幹有出力；總重量 ＝ 四部位 ＋ 武器（實測彌造者 Σparts.weight = 825 = 頂層、 torso.output = 3375 = 頂層，兩者皆佐證）。
· 機體所有數值一律由 ResolvedChassis 出，全站停止讀 mech.firepower。
· 合成規則（Q-1 已解，2026-08-25）：除火力外的數值一律「Σ 四部位總和」。 包含最難的那一題 命中 —— 兩隻手臂各有一個值，混搭成一左一右不同來源時直接相加， 不取平均、也不分手獨立。耐久／護甲／閃避／移動／抗暴同理。
⇒ 原本「規則確認前不出混搭後的衍生數字」的限制解除：混搭後的機體數值可以直接出。
⇒ 部件混搭的 UI 仍排在模組槽之後 —— 那是工程順序（052-G 兩段式），不再是資料缺口。
決策八：分享代碼 —— 純前端自包含編碼，不開後端短碼
· 二進位 TLV/section 制（每段一個 tag + length，未知 tag 一律跳過並記入 unmodeled）＋ base64url ＋ 1 byte checksum。
· FMT 版本位元組與文件 schema 版本分開，不共用常數：兩者演進節奏不同，強制共用會造成無謂的相互 bump， 而每一次無謂的 bump 都是一批舊碼失效。
· id → 數字用既有 doc id 的流水號，不新增欄位（再開一個 shareId 欄位就是同一件事的第二個真相源）。 核心不變式：流水號是身分不是位置 —— 新增 weapon_179 不會讓 weapon_178 位移。
· ⚠ 唯一破口是流水號被回收：src/utils/idSlug.ts:82 的 maxEntitySeq 是「掃現有 ID 取 max」， 刪掉 178 再新增會再次產生 178，舊代碼就靜默指向另一把武器。而本專案確實會改 doc id （08-17 備份裡 mechs／pilots 各有 6 筆無流水號，08-23 才補號）。 ⇒ share-id.lock.json（進版控）＋ scripts/check-share-ids.mjs（改指即 exit 1）＋ 後台續號改 max(lock, live)+1，並寫進 data-patch skill 的流程。
· 三個必須在 v1 就正確的細節（事後補要洗掉所有已存資料）：SLOTB 要有 bank 位元、 §MODULES 段要在 v1 就開、形態身分不可用 form.order （FormAdmin.tsx:269-270 是自由輸入欄位，後台一次重排就讓所有既存代碼靜默指向另一個形態）。

決策九：配額與開放範圍
· 完全公開：未登入也能用。⇒ 要移除導覽的 ADMIN gate；訪客本機書架成為 MVP 必要項。
· 已登入：每機師 5 套（Firestore 規則的 map key 白名單，結構性、繞不過）。 結構上限 ＝ 89 機師 × 5 ＝ 445 套 ≈ 525 KB/帳號（由 exists(/pilots) 鎖住）。

決策十二：槽位定址擴成帶 kind 的聯集；模組與元件的版面落點一次定死 （2026-08-25 追加，推導過程見 _local-notes/2026-08/2026-08-25_配裝模擬器_模組與元件版面提案.html）
起因：使用者指出「目前的版面無法配置模組和元件」—— 不是還沒做，是連放的位置都沒有。
· 型別：SlotRef 由純武器語意 {bank, slot, side} 擴成 {kind: 'weapon' | 'module' | 'component', …} 的聯集，不另開平行模型。 理由不是型別漂亮，是兩者都有同型級聯：換機甲 → 部位換掉 → 模組掉落；換武器 → 元件掉落。 分兩套就會長出第二、第三支 reconcile()，而「同一件事在三處各寫一次」正是舊 SimulatorPage 三個 bug 的共同病根。
