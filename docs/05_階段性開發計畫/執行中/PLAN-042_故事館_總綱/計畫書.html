Master Plan（大綱）
一句話：把機甲與機師的逸聞從詳情頁末端的一段純文字，升級為獨立於圖鑑的沉浸式故事館—— 自己的路由、自己的視覺調性、自己的資料集合與編輯台。本總綱只放兩館共用的決策， 館別專屬的實作拆到 042-A（機師）與 042-B（機甲）。
2026-08-23 升格說明：本計畫原名「PLAN-042 機甲故事館」，範圍只含機甲，並在「不在範圍內」清單中 明列「機師故事館 —— 版面需求與機甲不同（人物半身像 vs 機體全身），另立 PLAN 處理」。
該排除理由已於 2026-08-23 失效：官方友情贊助的素材包提供了 54 張機師全身直幅立繪， 比例中位 0.58，與機甲的直式全身同族（官網 hero/ 是 768×1400 = 0.55）。 兩館的立繪欄版面因此可以共用同一套，不需要為比例做參數化。
同時確認兩館共用的東西遠多於預期（路由、chrome、章節元件、顯影動畫、換膚層）， 故將本計畫升格為總綱，拆出 042-A / 042-B。先做 042-A 機師館，理由見下方子計畫表。
Research
官網動畫拆解（兩館共用的研究成果）
以瀏覽器直接解析 ma.tentree-games.com 的 DOM、CSS 與執行期 opacity 取樣，還原其實際行為。 技術棧 jQuery + fullpage.js + owl.carousel。機甲區（#mecha）與機師區（#hero）是同一套四層圖層架構， 連 keyframe 都共用（.hero-name 用的 keyframe 就叫 mechaData）—— 官網自己就在兩區之間共用動畫，這是「兩館共用元件」最直接的背書。

機師區線稿領先彩圖約 450–500ms；機甲區實測是 250ms。 LoreArt 元件的延遲必須是 prop 而非寫死，否則兩館接上時要二次重構。
不照抄的部分：官網的姓名與資料塊是切好的 PNG（每個實體 4 張圖），而且官網只有 8 位機師（行銷精選頁）。 我們有 89 位機師 + 90 台機甲，且立繪構圖離散度極大（alpha bbox 寬度佔比 0.39–1.00、中心 x 0.38–0.64）。 「把文字壓在立繪的負空間上」我們做不到，硬做會有一大批壓到臉或壓到空白。
→ 版面必須是「固定骨架 ＋ 浮動立繪」：立繪待在自己的欄位、文字待在自己的欄位、兩者不互相依賴。 天花板是「每張都不出錯」，不是「每張都恰到好處」。
Architecture
共用架構（兩館必須一致的六個決策）
決策一：內容分成兩層，資料現況完全相反
層內容現況歸屬
A 檔案層 機師：fullName / profile{性別,血型,身高,additionalInfo} / lore
機甲：lore / 類型 / manufacturer（待新增）		 機師 89/89 · 機甲 89/89 留在 pilots / mechs
B 章節層 逸聞 PART 1..N，每 PART 有標題與數百字正文 0 筆，完全不存在 另開 pilotLore / mechLore
B 層才是故事館的主體，A 層只是它的扉頁。
決策二：接縫判準是「誰是權威來源」，不是「故事 vs 數值」
爬蟲寫的留 pilots / mechs；人寫的進 pilotLore / mechLore。
這條比「故事 vs 數值」好用，因為它能回答 lore 這種看起來像故事、其實是官方原文鏡像的邊界案例。
  • lore（detail.Introduction 的鏡像）不搬 —— 圖鑑的 hover 浮窗（EntityRefView.tsx:68） 與引用稽核（entityRefs.ts:296，origin 就叫「機師簡介」）都在用它。搬走 = 浮窗變空白，或兩個真相源。
  • profile / additionalInfo 不搬 —— 爬蟲每次補丁都會重寫 （scrape-pilots-v3.js:464-467, 483-489）。搬走後兩份會慢慢漂移，而且沒有任何機制會發現。
  • lore 集合承載所有編輯得動的展示文本：章節、旁白、署名結構化、additionalInfo 的顯示順序與白名單。
決策三：型別共用（src/types/lore.ts），集合分家（pilotLore / mechLore）
型別在兩館之間完全同構，speakerId → pilots 對機甲與機師都成立。 但集合不可合一，因為版本 gate 是集合級（versions.ts:37-45）、Worker 只有整包端點（無單文件路由）。 合一的後果是「改一台機甲的 PART 2 → 機師故事館的快取一起失效」「看一位機師的故事 → 連 90 台機甲的逸聞一起下載」。 
// src/types/lore.ts —— 兩館共用
export interface LoreCommentary { speakerId: string; text: string }
export interface LoreChapter {
  key:    string      // 穩定鍵，後台新增章節時自動產生。必填——見決策五
  label?: string      // 'PART 1'；未設定則依索引生成
  title:  string      // '光環遍身'
  body:   string      // 正文，支援 PLAN-019 的 [引用] 標記
  source?: string     // 出處署名（'——《週刊米赫瑪·文娛版》'）
  commentary?: LoreCommentary[]
}
⚠ 新 CollectionKey 有七處同步成本，本專案已為此炸過一次。 collectionKeys.ts 檔頭自己列出這份清單被四處複製、每處都漏過； PLAN-048 把「activityTypes 開成新 CollectionKey」列為否決項，註明「PLAN-043 就是漏掉 backpackSkills 炸在正式站」。
要同步：collectionKeys.ts、workers/src/index.ts 的 ARRAY_COLLECTIONS（漏＝正式站 404、本機全綠）、 bump-data-version.mjs 的 KNOWN_KEYS（漏＝整條指令 exit(1)）、entityRefs SPECS、 測試 helper、firestore.rules、GameDataContext 的 state ＋ switch ＋ 型別。
⚠ localStorage 已經在門檻上。實測全集合快取展開後佔用達 4.2–4.5 MB （UTF-16 計，pilots 一個就 2.09 MB），逼近 Chrome 約 5 MB 上限。而 GameDataContext.tsx:41-47 的 writeCache catch 是空的——配額超限的症狀是「每次都靜默重讀」，零錯誤訊息。
逸聞集合要嘛跳過 localStorage 層、要嘛設體積上限。
⚠ 故事館全程不新增 RefType。common.ts:44-51 逐字列出新增 RefType 要補五處窮舉消費端， 其中 RefPicker.tsx:23 的 REF_TYPE_OPTIONS 是手寫陣列、漏了不報錯。 speakerId 只允許指向 pilots。
決策四：導覽形態是「章間離散、章內連續」
單章 pager ＋ 常駐具名章節軸（PART 3 · 落葉需歸根，不要圓點——圓點只說「還有別的」，具名軸說「別的是什麼」）。
  • 換章只接離散輸入：點章節軸、◀▶、容器聚焦時的 ←→、手機水平滑動。絕不接滾輪。
  • 章內正文超高就正常垂直捲動。「一屏放得下」在本站做不到—— root font-size 是 19px 不是 16px（Layout.tsx:17 的 FONT_SIZE_MAP，且使用者可調三段）， 1366×768 筆電扣掉 header/subnav 後只剩約 667px，一段 500 字約需 585px。任何按 16px 心算的版面預算都低估兩成。
  • N === 1 時整套導覽底盤不渲染（章節軸、頁碼、◀▶、下一章列全部不掛），單章佔滿閱讀區。 上線初期 N=1 是主路徑，不是邊界情況。
⚠ 明確否決 scroll-snap 分屏。站內已實作過、失敗過、並以明文原因刪除（src/index.css:145-151）： 「把離散選擇綁在滾輪／觸控板這種連續輸入上，於是『輕輕滾一下就整頁彈回 Hero』是結構必然，而不是可以調參數修掉的 bug」。 而且它本質仍是捲動，沒有解決「不要一直往下捲」的訴求。官網那套 fullpage.js 全屏換頁同樣不引入。
決策五：PART 進網址，鍵必須是後台自動產生的必填穩定鍵
路由 /lore/pilots/:id/:part。網址是唯一真相（PLAN-050 判準，與便利性無關）—— 為的是可分享的深連結、社群預覽卡、PLAN-046 的「哪個 PART 有人讀到」統計、瀏覽器上一頁。
不能用陣列索引：日後在 PART 2 後插一章，所有已分享的連結會集體指向錯誤章節，而且不報錯。
也不要開 key?: string 這種選填欄位——PLAN-041 已把 0/5 定律精確化為 「每一個投機性的選填欄位都是空的（SkillVariant 0/710、SkillArea 0/710、effects 全庫非空 0 個）」， 加 fallback 的選填鍵實務上沒人填，上線跑的就是那個以索引為底的 fallback。 正解：由後台編輯器在新增章節當下自動產生並寫入的必填鍵，讓「不填」在資料上不可能發生。
決策六：留在 Layout 之下，用第三種 chrome ＋ 紙色換膚做「介面上分開」
  • 不要另開平行的頂層 Route。Layout.tsx:116 是 usePageTracking() 的全站唯一呼叫點， 而 routeKeys.test.ts 只斷言路由有沒有登記進 ROUTE_PATTERNS、不斷言它有沒有真的被追蹤。 脫離 Layout 的後果是 PLAN-046 對整個故事館永遠 0 筆，而 npm test 全綠。
  • 把 Layout.tsx:121 的 isFullHeightPage 布林升成 chromeMode: 'default' | 'viewport' | 'immersive'。目前那個布林同時決定 footer 與手機 Tab Bar 佔位， 再加一個特殊頁面就會變成多個布林交叉判斷。
    immersive ＝ 無 subnav、無 footer、無底部佔位、header 縮成一條半透明帶只留館名與「離館」。
  • 紙色展場：在祖先 .lore-shell 重寫 --color-bg-dark 等 token （Tailwind v4 的 utility 在使用點讀 var(--color-*)，實測 dist CSS 內出現 343 次）， 約 20 行 scoped CSS，退場只要拿掉那層 class。
    三個例外必處理：:root { color-scheme: dark } 不是 token（原生捲軸/下拉要另行宣告）、 body 的 homepage_background.webp 覆寫不掉（館內要自己鋪不透明底）、 全站約 35 處硬寫色值（集中在 timeline/、auth/、profile/，故事館幾乎不重用）。
  • 導覽列入口走 NavGroupTrigger，但 items 要排除在 SUB_NAV_GROUPS 之外—— 它直接沿用 NAV_GROUPS 的同一份 items 陣列，只要把 /lore/pilots 寫進任何一個 group， 館內就會自己長出圖鑑式的分頁列，沉浸直接破功。
⚠ immersive 只能是「收掉 chrome」，不可再引入 scroll-snap 全屏。 PLAN-050 Phase B 正是為了捲動誤觸把 PLAN-015 的 scroll-snap 全屏架構整段移除。

兩館都不做的事
  • 玩家標籤與評分（遊戲圖鑑裡的「老婆／暴力／抽爆」與 5.0★）——主觀且本站無資料，不列入。
  • 陣營／世界觀條目——陣營歸屬會隨劇情變動、資料易失效。 且 glossaryTerms 那 2 筆陣營詞條是為了複合 faction 值消歧而存在，不是陣營敘事的承載層； GlossaryTerm.aliases 的契約是「[xxx] 引用的同義詞」，全站沒有 faction→term 的解析路徑。真要做需要新的解析層。
  • 官方 lore 原文插 [xxx] 標記——理由是編輯分層（lore 要當官方原文鏡像， 可編輯的展示文本住在 lore 集合），不是「爬蟲會洗掉」（實測補丁路徑 scrape-pilots-v3.js:751-771 從不寫 lore）。
  • 交叉連結自動生成——實測誤判明確：奧菲利亞被判成提及「瑪麗」（實為「羅斯瑪麗」的子字串）、 真嗣同時命中「迪恩」與「迪恩·奈特」（name/fullName 重複）。要連就人工連。
  • 官網 fullpage.js 全屏捲動換頁——與既有 Layout 衝突，且 PLAN-050 已為此移除過一次。
