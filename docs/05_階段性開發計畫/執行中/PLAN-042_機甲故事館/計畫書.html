Problem
問題背景
問題一：逸聞被當成「附註」而非「內容」
目前 Mech.lore 只是 MechDetailPage.tsx:548 底部一個 <p>，整段長文擠在數值表格之後，沒有章節、沒有節奏。官方遊戲內的逸聞是分 PART 1 / PART 2 章節、並穿插 NPC（如娜塔莉亞）頭像旁白的敘事體驗 —— 目前的呈現完全丟失了這層結構。
問題二：沒有能撐起版面的大立繪
現有 public/images/mechs/<名稱>/portrait.png 是半身裁切圖（約 560×340），只夠當列表縮圖，放大到全高面板會嚴重糊化。Mech.halfPortrait 也是同樣性質。故事館需要全身立繪這個新素材層級。
問題三：製造商欄位全站不存在
官網右上角的「類型 / 製造廠商」是立繪面板的重要資訊錨點，但經確認 src/types/mech.ts、scripts/scrape-mechs.js 皆無任何廠商欄位（grep 全站 manufacturer / 廠商 / 製造 均無結果）。機甲目前可展示的敘事型 metadata 幾乎只有廠商，這個欄位必須補上。

官網動畫拆解（實測結果）

技術棧：jQuery 1.10 + fullpage.js + owl.carousel。機甲區為 .mecha.pages，切換靠 .ma-menu ul li.go-mXX 的 click handler。

不照抄的部分
官網的名稱與資料塊是切好的 PNG 圖片（每台機甲 4 張圖）。本站改用真文字 + CSS writing-mode: vertical-rl 直書排版，理由：可被搜尋、可被螢幕閱讀器讀取、支援 i18n、每台機甲省下 2 張圖的維護成本。
Design
設計決策
決策一：線稿層以 CSS 濾鏡即時生成，不另備素材
本站只有彩色立繪、沒有官方那種手繪線稿層。已實測比較兩種即時生成法：
方案做法實測結果
SVG 邊緣偵測 feConvolveMatrix 拉普拉斯核 不堪用 線條破碎、失去輪廓，只抓得到高對比邊界
色彩加亮素描
（採用）		 灰階底圖 + 反相模糊層以 mix-blend-mode:color-dodge 疊加 幾乎重現官方線稿 結構完整、線寬相近，僅暗部略有顆粒
/* 已在官網彩圖上實測通過的參數，暗部顆粒可調 blur 半徑 */ .lore-art { isolation: isolate; } /* 關鍵：限制 blend 範圍 */ .lore-art__base { /* 灰階底 */ filter: grayscale(1) brightness(1.1); } .lore-art__dodge { /* 反相模糊 → 色彩加亮 */ filter: grayscale(1) invert(1) blur(3px); mix-blend-mode: color-dodge; }
好處：零額外素材成本、機甲新增時自動就有線稿層。透明去背 PNG 已驗證可正常運作（isolation:isolate 之下透明區會正確落回紙色底）。
決策二：章節 + NPC 旁白的資料結構
保留既有 lore 欄位向後相容，新增 loreChapters。前台優先讀 loreChapters，沒有才回退 lore。
// src/types/mech.ts export interface LoreCommentary { /** → pilots 集合的機師 ID，用於取頭像與姓名（如娜塔莉亞） */ speakerId: string text: string } export interface LoreChapter { /** 章節序號標籤，如 'PART 1'；未設定則依索引自動生成 */ label?: string /** 章節標題，如 '新型試驗機' */ title: string /** 正文，支援 PLAN-019 的 [引用] 標記 */ body: string /** 章節末的 NPC 旁白，可多則 */ commentary?: LoreCommentary[] } export interface Mech { // …既有欄位… lore?: string // 保留，作為無章節時的回退 loreChapters?: LoreChapter[] // 新增：章節化逸聞 manufacturer?: string // 新增：製造廠商（如「卡瑪達」） loreArt?: string // 新增：全身立繪路徑 }
決策三：獨立路由 /lore，與圖鑑職責分離
圖鑑頁（/mechs/:id）的職責是查數值，故事館的職責是讀故事，兩者的版面需求相衝（前者要密集表格、後者要留白與大圖）。故獨立開頁，並在 MechDetailPage 的 lore 區塊放一個「閱讀完整故事 ▸」導向故事館。
路由頁面說明
/loreLoreHomePage機甲牆：縮圖網格 + 廠商/類型篩選，標示哪些已有故事
/lore/mechs/:idMechLorePage單台機甲故事頁：左章節、右立繪
決策四：新增 EDITOR 角色，以欄位級規則限縮協作者權限
故事資料需要他人協助輸入，但現行 firestore.rules 下所有遊戲資料集合都是 read/write: if isAdmin()，給人 ADMIN 等於交出全站所有集合的讀寫權（機師、武器、BUFF、變更歷史全都能動），不可行。 故在既有 USER / ADMIN / OWNER 之外新增第四級 EDITOR，用 affectedKeys().hasOnly() 把可寫範圍鎖死在故事三欄位 —— 這個手法已在本檔 L138 用於防止使用者自行提權，有現成先例。
// firestore.rules function isEditor() { return isAuthenticated() && get(/databases/$(database)/documents/users/$(request.auth.uid)/profile/main) .data.role in ['EDITOR', 'ADMIN', 'OWNER']; } match /mechs/{docId} { // 注意：原本是 allow write（= create+update+delete）。拆開時不可放寬其餘動作。 allow read: if isAdmin(); allow create, delete: if isAdmin(); allow update: if isAdmin() || (isEditor() && request.resource.data.diff(resource.data).affectedKeys() .hasOnly(['loreChapters', 'manufacturer', 'loreArt'])); }
決策五：編輯台「只寫不讀」Firestore，讀取走 Worker /api
上面規則刻意沒有給 EDITOR read 權限。理由：PLAN-029 把直連讀取收緊成 isAdmin() 的整個目的就是防白嫖與爬取， 若為了讓協作者編輯而開放 mechs／pilots 的直讀，等於為每個 EDITOR 帳號重新打開那個洞。
而這其實不必要：Firestore 的 update 不需要 read 權限，規則內的 resource.data 由規則引擎在伺服器端取得，與 client 是否可讀無關。 因此編輯台可以讀走前台同一條 Worker /api 管道（fetchWorkerCollection）、寫走 client SDK updateDoc，EDITOR 全程不需要任何直讀權限。
// 編輯台資料流：讀寫走不同管道 讀　LoreEditor ──▶ fetchWorkerCollection('mechs') // src/lib/api/workerData.ts 　　　　　　　　　└─ Worker service account ──▶ Firestore // 繞過規則，EDITOR 免 read 權 寫　LoreEditor ──▶ updateDoc(mechs/{id}, { loreChapters }) // client SDK，受上方規則把關 　　　　　　　　　└─ 存檔後 patchCollectionItem() 就地同步，免重讀
附帶好處：協作者用的是獨立的精簡編輯台（/lore-editor），而不是塞滿數值欄位的 MechAdmin，誤觸風險與學習成本都更低。
決策六：靜態化出口 —— 逐台切換，非全站一次切
依「確信資料不再變動後改成純靜態」的方向，做一支匯出腳本把 Firestore 的故事資料倒進 src/data/lore/ （本站已有 bossDrops.ts、siteChangelog/、patchVersions/ 三個靜態資料先例）。
解析順序為 static-first + 動態回退，粒度是單台機甲而非全站：已定稿的機甲進靜態檔、走零查詢；還在編的照常走 Worker。 這樣不必等全部機甲定稿才能享受靜態化的好處，也不需要一個全域開關來回切。
// 解析順序（單台粒度） const chapters = STATIC_MECH_LORE[mechId] // ① 靜態檔有 → 零查詢 ?? mechFromWorker?.loreChapters // ② 回退 Worker /api ?? (mech.lore ? [{ title: '', body: mech.lore }] : []) // ③ 回退舊欄位
回頭要改：維護者可直接編 TS 檔，或跑反向匯入回 Firestore、改完再匯出一次。腳本需雙向皆可。
風險：靜態化會把長文打進 bundle
逸聞是長文，100+ 台機甲全靜態化後估計 100–300KB。絕不可進主 bundle —— 故事館路由本來就是 lazy 掛載，靜態資料必須以 import() 落在該 chunk 內， 確保沒進故事館的使用者一個位元組都不會下載到。此項須在 F-3 以實際 build 產物驗證，不能只靠推論。
邊界情況：只有 lore 沒有 loreChapters 的機甲
前台以單一無標題章節渲染既有 lore 全文，版面不變、不出現空的 PART 標籤。不寫自動切章 migration —— 機械式切段落只會產生語意錯誤的假章節，章節劃分是編輯決策，交由後台人工處理。
邊界情況：沒有全身立繪的機甲
loreArt 未設定時退回 portrait.png，並套用 object-fit: contain + 上限寬度避免糊化，同時關閉線稿顯影動畫（半身圖做顯影效果反而突兀）。故事館首頁對這類機甲標示「立繪待補」。

Scope
實作範圍與不在範圍內
在範圍內：
  • 型別擴充：LoreChapter / LoreCommentary / Mech.loreChapters / Mech.manufacturer / Mech.loreArt
  • 全身立繪素材規格與匯入流程（public/images/mechs/<名稱>/lore-art.png）
  • MechLoreArt 顯影動畫元件（CSS 偽線稿層 + 錯位淡入 + 縮圖切換）
  • 新路由 /lore（機甲牆）與 /lore/mechs/:id（機甲故事頁），含手機版
  • 章節與 NPC 旁白的前台渲染元件
  • 後台：章節編輯器、旁白編輯器（speakerId 挑機師）、廠商欄位、立繪上傳
  • EDITOR 角色：型別、firestore.rules 欄位級授權、EditorRoute、OWNER 的角色指派 UI
  • 協作者編輯台 /lore-editor：讀走 Worker /api、寫走 client SDK，只碰故事三欄位
  • 靜態化出口：雙向匯出／匯入腳本、static-first 逐台解析層、bundle 產物驗證
  • 導覽列新增「故事館」入口；MechDetailPage lore 區塊加導向連結
  • docs 同步：docs/02_技術文件/02_資料模型/ 機甲資料模型頁、users.html（新角色）
不在範圍內：
  • 機師故事館 —— 版面需求與機甲不同（人物半身像 vs 機體全身），另立 PLAN 處理
  • 世界觀／陣營勢力條目 —— 陣營歸屬會隨遊戲劇情變動，資料易失效，本期排除
  • 逸聞正文的實際撰寫／輸入（屬 Phase E 長期資料作業，非開發任務）
  • 爬蟲自動抓取廠商資料（官方 API 未提供，本期以後台人工填入）
  • 官網那套 fullpage.js 全屏捲動換頁 —— 與本站既有 Layout 衝突，不引入
風險：選填欄位的「0/5 定律」
本站既有經驗：新開的集合會被填滿，新加的選填欄位不會。loreChapters / manufacturer / loreArt 三者都是選填欄位，有很高機率長期停在低填充率。
緩解措施：① 故事館首頁直接把「待補」卡片可視化，讓缺口一眼可見；② 後台機甲列表加「故事完整度」欄；③ Phase G 明確列為長期維護任務並轉入「觀察維護中」追蹤，而非假裝開發完成就結案。
實作地雷：角色聯集型別重複定義在三處
新增 EDITOR 時必須同步三個地方，漏改任一處都會產生型別與執行期不一致：
  • src/types/enums.ts:309 — UserRole const 物件
  • src/types/user.ts:17 — 手寫聯集 'USER' | 'ADMIN' | 'OWNER'
  • src/lib/userApi.ts:71 — updateUserRole() 參數又寫了一次同樣的聯集
順手把後兩處改成引用 enums.ts 的 UserRole，消掉這個重複來源。
連帶影響：稽核與快取失效也要放行 EDITOR
只放行 mechs.update 是不夠的，還有兩條路徑會擋住協作者：
  • 稽核：changeHistory 的 create 目前限 isAdmin()。協作者的修改更該留痕，須放行 EDITOR 並維持 actorUid == request.auth.uid 的防冒名綁定。
  • 快取失效：存檔後需 bumpDataVersion('mechs')，但 meta 是 write: if isAdmin()。須讓 EDITOR 可更新 meta/gameData。
    殘留風險：EDITOR 可反覆 bump 版本強制全站快取失效、推高 Firestore 讀取量。屬小型濫用面，考量 EDITOR 由 OWNER 逐一指派、人數可控，本期接受不另做限流。
Quality
效能與可及性考量
項目風險對策
大立繪體積 中 全身立繪輸出 WebP、長邊上限 1400px；縮圖切換時只預載相鄰 ±1 張，其餘 loading="lazy"

Firestore 讀取量 無 故事館走既有 useMechs() 快取層（GameDataContext 三層快取），不新增集合、不新增讀取路徑
