資料可信度的前提（貫穿整份計畫）
  • 資料包是陸版 2026-09-20 建置的快照（BuildNum 376_ZiLongA）。台版數值口徑與陸版相同，只是改版時間不同步；台版若有平衡差異，資料包反映不了。
  • 驗證只證明「擷取正確、關聯正確」，不等於戰鬥結果正確；首領面板是依公式推算、未經遊戲內實測，Fix64 取整可能讓末位差 1。
  • 文字全是簡中，敵方 NPC 名、技能名、關卡名都要有台版譯名（見開放問題 ②）。

  • 擷取段沿用 Python：直接移植已驗證的 raid_crawl.py／calc_boss.py／db.py；E:\Mecharashi_Data\unitypy-venv 已存在，scripts/export-gacha-prefab.py 是先例。以 python -I 執行，只讀資料包，拒絕把任何檔寫進資料包目錄。
  • 組裝段用 Node：要讀 Firestore 的對照表與時間線，firebase-admin 已在 Node 端。Node 入口必要時自己呼叫 ① 並檢查擷取結果是否過期，站長只需要記一條指令。
  • 報告沿用 diff-game-dump.mjs 的慣例：輸出 _local-notes/<YYYY-MM>/<YYYY-MM-DD>_武裝討伐匯入.html＋同名 .json；「下一步」是標 ✅／⬜ 的照抄清單，做完一步重跑會變 ✅ 而不是消失。
  • PARSER_VERSION比照公告管線（PLAN-048）：解析規則一改就 +1，草稿記下版本，報告能分辨「資料變了」與「解析器變了」。
決策二：資料放 Firestore 經 Worker 供應，不放 repo 靜態 JSON
曾考慮比照卡池動態（src/data/gachaFx/）把資料做成靜態 JSON 打進前端。不採用，理由：
  • repo 與前端打包都是公開的，整包 JSON 等於繞過 PLAN-029 的反爬兩層（Worker 守門／zone 限流）與 read: if isAdmin()，也與開放問題 ① 的保守選項衝突。
  • 譯名校對要能在後台改、改完立刻生效；靜態檔每改一字都要 commit＋部署。
  • 與其餘遊戲資料走同一條版本 gate 三層快取（記憶體 → localStorage → Worker），不需要新機制。
決策三：五個集合——三個公開、兩個後台限定
集合一份文件＝文件 ID筆數／估計大小誰讀
raidSeasons一期（期名、副標、難度清單、四個關卡組摘要、每週加成與規則、台版版本連結、公開旗標）raid-21（期 ID 兩位數）21 筆／小前台列表頁（Worker）
stages一期的一個關卡組（含四難度變體、開場陣容、增援時程、懸賞線索、敵方 Buff 字典）raid-21-g183 筆／預估 400 KB 上下期詳情頁（Worker）
bosses一個關卡組的一位首領（含四難度變體的面板與技能）raid-21-g1-luke 類（實作時定 slug 規則）約 85 筆／預估 250 KB 上下期詳情頁；日後傷害模擬的「打誰」目標
raidDrafts一期的匯入草稿（三集合的待發布內容＋該期首領的逸聞全文與原文雜湊＋差異＋異常＋待校清單＋解析器版本）同 raidSeasons21 筆僅後台；腳本以 admin SDK 寫入
raidTerms譯名對照表的一個分片（依種類：期／勢力／關卡／單位／技能／Buff／懸賞／線索／台詞／長文；逸聞正文量大，另成一片）種類名約 8 筆；每片 < 1 MB僅後台與匯入腳本
  • stages／bosses 沿用 PLAN-019 當初設計的名稱與型別，以 category: '討伐'（既有 StageCategory.RAID）區分；日後首領剿滅、定點突襲等首領類玩法可以共用。
  • Worker 只供整個集合（/api/data/:collection）；列表頁只載 raidSeasons，進期詳情頁才載 stages＋bosses。兩者合計預估與機師集合（1.3 MB）同量級以下；A-7 的報告會印出實際大小，超過 1 MB 就回頭評估 Worker 單文件端點，不在此預先實作。
  • 只服務單一期的資料（敵方 Buff 字典）放在 stages 文件內，讓每份關卡文件能獨立渲染，代價是同期內少量重複。
決策四：難度是型別上的第一級維度，技能文字與面板依難度分開存
  • enums.ts 新增 RaidDifficulty，值用穩定代碼（normal／hard／hell／d4，對應遊戲列舉 1–4），顯示名走對照表——陸版是「初试／磨炼／死境／炼狱」，陸版自己還混用「磨练」，台版用語屬於開放問題 ② 的一部分。
  • Stage.raid.variants 與 Boss.variants 皆為 Partial<Record<RaidDifficulty, …>>：第 1 期只有 normal、第 2–5 期沒有 d4，前台依實際有的鍵畫分頁。
  • 每個變體存完整技能清單，不做跨難度去重；「此難度與初試不同」的提示由前端比對文字產生。
  • 不只技能：懸賞條件也會隨難度變（第 21 期「小心翼翼」初試／磨鍊是護盾不超過 4 層、死境起 3 層），線索詳情更是逐難度加長（每升一級多一段），所以懸賞與線索也存在變體裡，前台可以標出「此難度新增的那一段」。
  • 難度強化 Buff 的名稱是開發備註（*#…），不顯示名稱，只把屬性值翻成「HP +29.7%、裝甲 +14.2%…」這類人讀文字（大型首領另一組、第 6–7 期舊 ID 也要對到）。
決策五：「增援時程」由戰場觸發器的結構化條件推出，不用企劃備註
  • 2,124 次召喚全可解析，但 raid_crawl_out.json 的 trigger 欄位其實是企劃備註（m_desc）：574 筆是空的，其餘像「3回合增援」「增援预警召唤」「招副T2阶段」，不能當資料、也不能顯示。
  • 回合數要從觸發器的條件（BattleTriggerConditionType）與動作（SummonAtSceneObject／Summon）推：回合條件 → 「第 N 回合」；其他條件（首領軀幹耐久 ≤ 75%、某單位被擊破…）→ 依對照表轉成中文條件句。
  • 條件／動作型別 → 中文模板的對照放 scripts/lib/raidTriggerTypes.json（人可維護）；對不到的型別在報告列成 ⬜，前台顯示「特定條件觸發」而不是空白或猜測。
  • 同一時點、同一模板的單位合併成「×N」；屬於成就判定的觸發器不進增援時程。
  • 預覽時從第 21 期第 1 關（戰場 8538）實查到的三種形態，型別要都能表達：
    1. 回合條件：Round 1／2／3 是「增援預警」、2／3／4 才是召喚——預警要另外標，玩家在遊戲裡看得到預警標記。
    2. 戰場狀態條件：「招副T」是回合結束時檢查黑板變數（護衛被擊破後設旗標）才重新召喚，要翻成「自律戴亞斯被擊破 → 該回合結束時於機兵站重新部署」；黑板變數的語意只能靠同一戰場其他觸發器反推，對不到就退回「特定條件觸發」。
    3. 每回合固定事件：「每回合上護盾」無條件、每回合開始對首領加層（初試／磨鍊 1 層、死境／煉獄 2 層），以一條「每回合開始：…」呈現，不塞進每一格回合。
決策六：首領面板一律標「推算值」；數值取戰場 ref=BOSS 的實際模板，BossID 只供顯示
  • 取哪個模板：307 關中有 14 關的 BossID 指向別的難度的同名首領，所以 BossID 只拿來顯示名字與頭像；數值一律用戰場 JSON 裡 m_refName=BOSS 那個單位的 m_configId。第 11、12 期最終關的首領 m_actorType=1，也要當敵人模板解析。第 20–21 期戰場以 m_absoluteLevel 覆寫等級，推算要用覆寫後的等級。
  • 推算內容：部位耐久與裝甲、武器攻擊、機師屬性（移植 calc_boss.py），同一乘區先相加再乘；結果存整數，BossVariant.estimated: true，並附「未計入」清單（天賦條件減傷、疊層護盾、機師適性等戰鬥中才成立的效果）。
  • 回歸基準：筆記裡卢克（第 21 期）與皮普（第 9 期）的 4 難度數字寫進 scripts/lib/raidRegression.json，每次匯入都比對，不符就在報告標 ⚠——之後遊戲內實測對上，再把基準換成實測值。
  • 兩筆疑似陸版設定錯誤（第 10 期磨鍊 110202、第 13 期磨鍊 113203：戰場實際放的是初試模板，等於磨鍊沒強化）：
    1. 前台照戰場實際資料呈現（數字會與初試相同），首領卡加註「陸版資料中此關磨鍊未套用難度強化，台版是否相同未經實測」。不自行「修正」成推測的強化值——補值等於編造。
    2. 記在 scripts/lib/raidAnomalies.json（關卡 ID、現象、處置、驗證狀態），站長遊戲內確認後更新狀態，前台註記跟著變。
    3. 匯入腳本另有通用偵測：「BossID 與實際模板不同」分成「只是指向他難度同名首領（顯示用，無害）」與「高難度實際用了初試模板且無其他強化來源（疑似未強化）」兩類，後者一律進報告 ⚠，讓之後的新期也抓得到，不靠這兩筆寫死。
決策七：文字標籤轉成站上可渲染的格式，開發備註一律不上站
  • <buf ID=n>[名稱]</buf>（500 個，其中 42 個沒附名稱要用 Buff 表補）→ 轉成可點的 Buff 標記，說明來自關卡文件內的敵方 Buff 字典；<terrian>、<range> 轉成文字，<color> 只保留語意上的強調。
  • 敵方 Buff 不在站上 buffs 集合（那是玩家側官方 ID），v1 不寫 descriptionRefs、不加進 entityRefs 的 SPECS——避免牽動 cascadeDelete 與 useRefScanData（新集合寫進 SPECS 會在規則未部署時弄壞既有的後台刪除）。在 boss.ts 註解寫明「日後若要引用站上實體，必須先補 SPECS」，延續 PLAN-019 留下的警告。
  • 不顯示：*# 開頭的開發備註、HiddenAchievementIds、戰場內部代號（DescStrKey 的「Raid副本11-1简单」之類）、觸發器 m_desc。
決策八：譯名對照表存 Firestore（raidTerms），以簡中原文為鍵；校對結果不會被重新匯入洗掉
  • 查表順序：① 對照表裡「已校」的條目 → ② 開放問題 ② 選定的來源（infodata 或截圖對照，結果同樣寫進對照表）→ ③ 簡→繁 機械轉換，標「待校」。長文（技能說明、線索詳情）走 ③，但會先把文中出現的已知專有名詞換成台版譯名再轉。
  • 鍵是簡中原文，不是單一欄位：同一個「卢克」出現在 4 個難度、多個關卡，校一次全站生效。條目欄位：種類、簡中原文、台版譯名、狀態（已校／待校）、來源（infodata／截圖／機轉／手動）、首次出現的期。
  • 為什麼不用 repo JSON：校對發生在後台審核頁，存 Firestore 才能在頁上改完立刻重算預覽；腳本以 admin SDK 讀同一份。這也避開了舊爬蟲「整筆覆寫洗掉人工欄位」的老坑（PilotTalent.manual 那次）——人工校對只存在對照表，草稿與發布文件都是對照表套出來的結果。
  • 機械轉換工具候選 OpenCC（台灣用語 s2twp，Node 端 opencc-js），實作時確認授權與包體後定案；只在匯入端使用，不進前端打包。
  • 前台標示：文件帶 i18nPending（待校欄位清單），前台在對應名稱旁加小標「待校」，頁尾說明譯名尚在校對。
  • 可自動帶入的既有台版譯名（不必等 ②）：期名（時間線 armamentRaids[].name）、獎勵武器／背包名、與玩家機體同名的敵方機體（站上 mechs）、與可抽機師同名的首領（站上 pilots，例：第 15 期的摩根娜）。
決策九：哪幾期上站、標什麼狀態——依台版時間線的 twDate 判定
  • 先以期名把資料包的期對上時間線的 armamentRaids，該版本半期的 twDate 決定狀態：已過 → 台版已開放；未到 → 台版預計開放（例：2026-10-24 時第 15–18 期已開放，第 19–21 期是推估日期）。
  • 「預計開放」的期也產草稿、可上站，前台標「台版預計 YYYY/MM/DD」（虛線框），與版本時間線本來就公開推估版本的做法一致；站長不想提前公開時用後台公開開關擋（D-3）。
  • 台版時間線只從 v2.8 起有資料（第 15 期「無名之輩」起），v1.0–v2.7 是空白佔位。對不上時間線、但期號小於已對上的最小期號者，視為台版早已開放（兩邊開放順序相同）。
  • 連時間線都還沒有的期（陸版先開、台版尚未公告）只進報告「台版時間線未收錄」一欄，不產草稿；時間線補上後重跑就會出現。
  • 期名對不上（譯名不同）時不猜：報告列 ⬜「請在對照表補這一期的台版期名」。
  • raidSeasons 存台版版本號與時間線連結，版本情報的武裝討伐欄位可直接連到 /raids/raid-21。
決策十：重裝征伐（RaidActivity，台版 v3.5）明確排除在本計畫外
  • 結構不同：活動 → 4 個難度群組、各 3／4／5／6 關＋1 最終關；有信標解鎖數、「終局協議」部署數、只有初試有 12 台支援機，與武裝討伐「期 → 4 難度 → 固定 4 關」不能共用一套型別而不扭曲。
  • 易混淆處要在型別註解寫清楚，避免日後誤建：「重装征伐·极境」是榮譽章名，第 4 難度仍叫「炼狱」；EnhancementLevelReplaceId 18 是玩家方等級補正（拉到 Lv70、科研全解），不是敵人難度來源。
  • 匯入腳本遇到時間線上的「重裝征伐」條目，報告標「略過：RaidActivity，不在 PLAN-064」，不算未對上。
  • 型別預留 Stage.raid.kind: 'dungeon'，日後另開計畫時加 'activity' 分支；22 關已證實可串，屆時可複用本計畫的擷取、譯名與後台。
決策十一：前台路由用 /raids、/raids/:seasonId；後台放 /admin/raids
  • 敵人資訊是圖鑑型內容，與 /pilots、/mechs 同層最好分享、最利於收錄。代價是新頂層路徑：必須到 Cloudflare 把 /raids 加進 SPA fallback 白名單（CLAUDE.md §3），build 與 test 都抓不到，列為站長任務 F-3 並附 curl 複驗。
  • 若站長不想動 CF 規則，替代方案是 /guides/raids（沿用既有前綴），審閱時一句話即可改。
  • 後台留在 /admin 底下，不另開頂層路徑。
  • src/lib/seo.ts：PAGE_TITLES 補兩條、sitemap 歸屬比照圖鑑詳情頁；詳情頁以 usePageTitle() 換成期名。
決策十二：例行流程要能不靠 AI——「新一期討伐」一條指令＋照抄清單
  • 陸版改版、重新擷取資料包後（工具會拒絕覆蓋舊 SQLite，輸出到新目錄），站長跑 node scripts/import-raid-dungeons.mjs（預設取最新資料包），看報告「下一步」：補譯名 → --write → 後台審核發布 → 重跑確認全 ✅。
  • 流程寫進 public/images/game/README.md 的改版例行清單，並在 CLAUDE.md 6.5 補一句（現在寫「唯一仍在運作的擷取是活動」）。
  • 只有遊戲改了規則（新觸發器型別、新屬性、新結構）才需要開發者：這些都會在報告以 ⬜／⚠ 浮出來，而不是默默產出錯資料。
  • 審核佇列是站長的：腳本與開發者不代為發布、不代為把「待校」改成「已校」。
決策十三：強敵圖鑑當首領的「人物層」，戰鬥資料當「關卡層」，兩層用戰場＋模板接起來
  • 人物層（強敵圖鑑，type 2 的 83 筆）：勢力名、勢力徽章、首領名、台詞、逸聞。這是玩家在遊戲裡認得的樣子，也是台版譯名最集中的地方。
  • 關卡層（RaidDungeon）：各難度的面板、技能、陣容、增援、懸賞。
  • 對接：圖鑑條目的 StrongEnemyList 指向初試戰場＋敵人模板，對上本計畫的關卡組；bosses 文件記 atlasId。已發現 1 筆對不齊（第 14 期梅利圖斯指到第 3 組的磨鍊戰場，而它其實是第 4 組首領），所以匯入時以「戰場、模板、名字」三者交叉比對，不一致就列 ⚠，不靠單一欄位。
  • 勢力存在 raidSeasons（每期一個勢力：北陸殘黨、雷擊小隊、盧諾家族…），徽章鍵沿用 PLAN-059 的 Icon_logo_* 徽章庫，缺的圖列 ⬜ 交圖片匯入流程補。
  • 同一角色多次出場不合併：圖鑑本身就是每次出場一筆、逸聞各自不同；前台只在首領卡加「也出現在：第 10、13 期」的互連。
  • 首領剿滅（type 1 的 59 筆）同一套表，本計畫擷取時略過，但解析器寫成通用的，留給日後與元件掉落合併時使用。
  • 標籤（SkynetStrongEnemyLabelInfo）不擷取；解析等級、擊殺次數這類遊戲進度數值也不上站。
決策十四：逸聞歸故事館——本計畫負責「擷取＋翻譯＋審核」，故事館子計畫負責「呈現＋協作校對」
  • 本計畫做的：逸聞（武裝討伐 83 位、約 330 篇，每篇標題＋正文）隨同期的草稿進 raidDrafts，與其他文字走同一張譯名對照表與機械轉換，在 /admin/raids 可預覽、可看待校。討伐頁的首領卡只放台詞與一個「逸聞 N 篇 → 故事館」入口。
  • 交給 PLAN-042 新子計畫做的：故事館的集合（暫名 enemyLore，比照 pilotLore／mechLore，含 rev 衝突檢查）、強敵在故事館的呈現方式（第三館或卷宗頁，由子計畫決定）、LORE_EDITOR 協作校對、從草稿發布逸聞。
  • 為什麼這樣切：逸聞是長文敘事，最需要人校對，而故事館已經有協作編輯角色與編輯台（PLAN-042-H）；擷取管線則與討伐資料同源、同一張對照表，拆開做會重寫兩次。
  • 已校的篇章不被重新匯入覆蓋：協作者校對過的逸聞加「已校」鎖；之後陸版原文若變動，報告列 ⚠「原文已變，此篇已人工校對，請人工比對」，不自動蓋掉（記取舊爬蟲洗掉 PilotTalent.manual 的教訓）。這條規則在子計畫實作，本計畫的草稿格式先預留「原文雜湊」欄位讓它比得出來。
  • 首領與可抽機師同名者（以暫譯名比對站上機師，至少 11 位：吉賽爾、索妮婭、喬恩、皮普、摩根娜、阿列娜、貝爾莎、凱倫、加雷斯、泰歐、葛里高利）：機師故事館頁可加「強敵檔案」連結，細節由子計畫決定。
