◆ PLAN-062

故事館使用統計Lore Analytics · 進館漏斗 · 章節留存

後台使用統計（PLAN-046）設計時故事館還不存在。故事館的路由雖然有被計數，但只混在「頁面熱度」裡；看不出是哪位機師的故事被讀，也看不出讀到第幾章。本計畫把故事館拉成獨立的區塊與統計類別。

Problem
問題背景
現況：故事館其實有被計數，只是看不出來
故事館的三條路由早已登記在 src/lib/analytics/routeKeys.ts 的 ROUTE_PATTERNS／ROUTE_LABELS， 並且依 PLAN-042 總綱決策六掛在 Layout 之下，因此自 2026-09-10 程式上線起（入口收到 2026-10-13 才正式開放），analyticsDaily.byRoute 就一直有 lore、lore_pilots_detail、lore_pilots_detail_detail 三個 key。 它們目前和其他頁面混在儀表板的「頁面熱度」清單裡。
缺口一：看不出是哪位機師的故事被讀
ENTITY_ROUTES 刻意把 /lore/pilots/:id 與 /lore/pilots/:id/:part 併進 pilots 類別， 和圖鑑詳情頁混在一起。副作用是「熱門機師 TOP 20」也被灌進了故事館的讀者，而這份排行的用途是「決定資料要優先補誰」： 讀逸聞的人並不需要圖鑑的資料。
缺口二：看不出哪個 PART 有人讀到
PLAN-042 總綱決策五把 PART 放進網址，列出的理由之一就是「PLAN-046 的『哪個 PART 有人讀到』統計」。 但 toPageKey 會把 :part 折成 detail，所以 part 的值從來沒被記錄過，這個承諾一直沒有兌現。
缺口三：折返率的解讀套在故事館會誤導
章節翻頁、切換機師都會換網址，每次都讓 pv +1，所以故事館兩個詳情頁的 pv／upv 一定偏高。 儀表板「頁面熱度」的說明寫「差距越大＝資訊沒一次給足」，套在故事館正好相反：翻得多代表有人在讀。 （與 PLAN-046 觀察期記下、尚未查明的 versions_timeline_detail 折返率 9.24 同類，但那一頁不在本計畫範圍。）
Design
設計決策
決策一：故事館與圖鑑分開統計，不再併入 pilots（站長 2026-10-15 裁決）
新增 lorePilots 類別後，/lore/* 只記進故事館自己的類別。這推翻了 routeKeys.ts 原本 「從圖鑑進來還是從故事館進來都算一次」的合併理由：當初合併是因為已部署的 Worker 會靜默丟掉新類別（PLAN-043 雙名單陷阱）， 不是因為兩者語意相同。只要照決策四的順序先部署 Worker，這個限制就不存在了。 「熱門機師」因此回到純圖鑑的語意，符合它「決定資料補誰」的用途。
決策二：沿用既有的 entity 管線，不開新集合
新類別寫進同一份 analyticsEntity/{YYYY-MM} 月文件。同一次 flush 本來就會寫這份文件，只是多幾個欄位，所以：
  • 寫入次數不變，熔斷預算（日 50,000）不受影響。
  • firestore.rules 不用改（同一個集合）。
  • Worker 只改一行：workers/src/collect.ts 的 ENTITY_TYPES 加入 'lorePilots'、'loreParts'。 這是閉集合（統計類別不隨頁面增減），與 PLAN-046 決策八「Worker 不放頁面白名單」不衝突。
  • 去重沿用 markReported：同一次造訪內，同一位機師、同一章各只算一次。
決策三：章節 id 用 ${pilotId}--${partKey} 扁平化，不用巢狀 map
例：pilot_049_海莉絲--part-2。Worker 的欄位路徑只組一層 type.`id`；改成巢狀 （loreParts.`pilot`.`part`）要改 payload 格式與組欄位路徑的程式，等於擴大 PLAN-046 鐵律②的審查範圍。 扁平化則完全不動那段程式，只動閉集合。
  • - 本來就在 isSafeEntityId 的字元白名單內（前端與 Worker 各一份，都是格式規則不是名單），欄位路徑的安全性不變。
  • 章節 key 由 makeChapterKey 產生，格式固定為 part-N，不含 --；拆解時取最後一個 --。
  • 長度上限 60 字元：機師 id 約 15 字元，加上 --part-NN 綽綽有餘。
決策四：部署順序 — Worker（Phase B）一定要早於前端（Phase C）合併進 main
Worker 不在 CI 裡，要站長手動 cd workers && npm run deploy。順序反過來的話，新類別會被舊 Worker 靜默丟掉， 統計又不會回溯，那段資料就補不回來。Phase B 單獨上線是安全的：舊前端不會送新類別，行為完全不變。
決策五：Phase A 先做，只用既有的 byRoute
進館漏斗（館首頁 → 扉頁 → 章節）不需要任何新埋點，資料自 2026-10-13 正式開放起就有，做完馬上能看。漏斗只計開放後的日子：之前入口收著，只有零星的直接連結瀏覽，混進來會稀釋「佔全站有效瀏覽」。 UPV 是「同一次造訪內同一個 key 只算一次」，三個 UPV 本身就是「有幾次造訪走到這一步」；pv 則依頁面換個說法： 扉頁的 pv 含切換機師，章節的 pv 含翻頁。「頁面熱度」裡的故事館三列保留（才看得出它在全站的份量），但不再顯示會被誤讀成折返的灰字。
漏斗的已知限制：深連結
分享出去的章節連結會直接跳進閱讀模式、略過館首頁與扉頁，所以「扉頁 → 章節」的比例不是嚴格的子集合，理論上可能超過 100%。 儀表板照實顯示，並在說明裡註明。
決策六：章節留存用真實章節清單過濾，按需載入
要知道一位機師總共幾章、章名是什麼，得讀 pilotLore。它是 NO_LOCAL_CACHE_KEYS（不進 localStorage）， 每次載入約 89 次讀取，所以做成按一下才載入，不拖累儀表板的開頁成本。 不在真實章節清單裡的 key（已刪除的章節、手打錯的網址在轉址前被記到的一次）不顯示：這類雜訊不在記錄端擋， 因為 track.ts 刻意不依賴 React、拿不到故事資料。
決策七：實體排行加「本月／上月」切換（站長 2026-10-15 要求）
entity 文件是月粒度，月初資料很少，排行幾乎沒有參考價值。切換同時套用到既有的熱門機師／機甲／武器與新的熱門故事、章節留存。 多讀一份月文件＝多 1 次讀取，並沿用 API 層 5 分鐘的記憶體快取。
決策八：REPORTED_MAX 從 50 調到 150
頁面 key、實體 key、章節 key 共用這個上限。一口氣讀 10 位機師、每位 3 章就會逼近 50，超過之後的新章節會少算 （markReported 回傳 false 就不計）。session.ts 原註解寫「會被重複計 UPV」，與實際行為相反，一併修正。 150 個短字串的 localStorage 成本可以忽略。
切換當月的「熱門機師」會一半含故事館、一半不含
Phase C 上線那個月的 pilots 類別，上線前含故事館讀者、上線後不含。儀表板只在那個月的熱門機師上加一行註記， 不做資料修補（統計不回溯，也無從拆分）。
Scope
實作範圍與不在範圍內
Phase內容依賴
A儀表板新增「機師故事館」區塊（進館漏斗，用既有 byRoute）；頁面熱度的故事館列不顯示灰字 pv無
BWorker ENTITY_TYPES 加 lorePilots／loreParts；站長手動部署無
C前端改成分開記錄：故事館不再進 pilots、新增章節 id；REPORTED_MAX 150；型別與資料庫文件B 已部署才能合併進 main
D儀表板：熱門故事 TOP 20、章節留存（按需載入）、本月／上月切換可先寫，C 上線後才有數字
不在範圍內：
  • 閱讀時長／停留時間：需要另一種彙總方式（總秒數加分桶），SPA 的背景分頁也很容易把數字灌高。先用章節留存回答「有沒有讀下去」。
  • 機甲故事館：PLAN-042-B 上線時比照新增 loreMechs 類別，章節 id 格式沿用決策三。
  • /lore/* 兜底轉址被記成 notfound：館內打錯的網址在轉回 /lore 前會命中全站的 *，記一次 404。只污染 404 那一列，不影響故事館的數字。
  • versions_timeline_detail 折返率偏高：屬 PLAN-046 觀察期的待查項。
