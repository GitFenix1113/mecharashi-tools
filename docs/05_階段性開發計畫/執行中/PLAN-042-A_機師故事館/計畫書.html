一句話：把 89 位機師的檔案與逸聞做成一座紙色的沉浸式展館—— 左卷宗右立繪、章節以具名軸切換、線稿顯影成彩圖。
本子計畫同時建立兩館共用的全部元件（LoreArt / LoreChapterPager / 紙色換膚 / chromeMode）， 042-B 機甲館直接引用。
為什麼機師先做
立繪 53/89（S 級 85%）已由官方素材包到位、檔案簡介 89/89 完整且 38% 是帶署名的引文體； 機甲那邊 lore-art 實查 0 檔、需要 90 張人工出圖。 先做機師 ＝ 用近乎零的素材成本把共用元件驗證完。
Problem
問題背景
問題一：機師的敘事資料被壓在圖鑑頁的最底下
PilotDetailPage.tsx 共 1550 行，其中 lore 只是 :1484 一張灰卡片加一段 <p class="whitespace-pre-line">。而 profile.additionalInfo（81/89 有值、 全站 94 種自由鍵名，如「入獄次數」「嵐物質汙染程度」「註冊寵物」， 奈奧米的鍵名字面就是 ▇▇、值是「你別想從這裡知道更多了」） 被當成一列列的小字資料，完全沒有被當成角色塑造來呈現。
問題二：官方逸聞（PART 1..N）我們一筆都沒有
官方遊戲內機師有兩個不同的頁面：「機師檔案」（＝我們的 lore ＋ profile，已 100% 有值） 與「逸聞」（PART 1「光環遍身」／PART 2「定命恩垂」／PART 4「落葉需歸根」…，每段數百字）。 後者完全不在我們的資料裡，也不在官方 API 的 detail.Introduction（那是前者）。 須以 OCR 輔助人工輸入——實測機師約三週才出一位，輸入量可負擔。
問題三：38% 的引文體與署名結構完全沒被利用
實測 89 篇 lore 中 34 篇以「開頭（世界內引文體）、35 篇結尾帶出處署名： ——《週刊米赫瑪·文娛版》、——露西亞的定期報告、——奈奧米給阿諾德的簡報、 ——一份無署名的文件報告、——同盟軍防衛營脫口秀錄音節選。
這批文字的體裁就是剪報與卷宗，目前卻被排成一坨無差別的小字。 把署名抽成右對齊小字＋細線、正文套 blockquote 語彙，是純排版、零資產成本的美感槓桿。 對照：機甲的 lore 引文體 0 篇、署名 0 篇——這是機師館獨有的資產。

線稿濾鏡（color-dodge 偽線稿）在人像上的風險：只有 1 位需要退路
失效模式是不出線，而非爆白：color-dodge 是比值運算，brightness(1.1) 等於把門檻設在 「鄰域須比自身亮 10% 以上」，平滑高光達不到門檻。L>0.70 亮度帶的 ink 覆蓋率實測 0.0%。
素材批次觸發 >35%臨界 25–35%
舊 1240×1080 三分身（87 張）零 53.2% ／ 卡米拉 35.2%曜 32.9%（半透明像素高達 28.4%）
新官方全身立繪（54 張）零 54.2%（唯一）戰部渡 26.7 ／ 卡米拉 26.2 ／ 虎王 25.2
新素材亮度分布均勻得多（全體平均亮度中位 0.375、半透明像素 4.8–12.1%）。 驗收樣本：零（唯一觸發）／戰部渡・虎王（臨界）／凱登 1.8%（最暗對照）。 注意：洛莎、艾達雖是白髮，實測平均亮度只有 0.296 / 0.385、L>0.70 佔 8.5% / 14.0%， 都很安全，不要拿它們當驗收樣本。
⚠ blur 半徑是 CSS px，不是原圖 px。1240px 原圖顯示在約 620 CSS px 時，blur(3px) 等效原圖 6px。 這個陷阱會讓人「因為圖變大就調大參數」而調錯。
Design
設計決策
決策 A-1：立繪走三層 derive，不開任何欄位
層路徑慣例覆蓋用途
①/images/pilots/<名>/lore.webp53故事館主視覺（官方全身立繪轉檔產物）
②/images/pilots/<名>/full.webp87缺 ① 時的 fallback（1240×1080 三分身，需底部 mask）
③/images/pilots/<名>/half.webp89機師牆／縮圖／og:image（340×340，共 2.2 MB，與 /pilots 同 URL、瀏覽器快取直接命中）
解析順序 ①→②→③，丟進既有 imageCandidates（assets.ts:87-97）＋ FallbackImage，缺圖自動往下退。
不要開 loreArt 欄位——那是 89 筆各排一次人工填值，且十之八九停在低填充率 （原 PLAN-042 自己就把它列為 0/5 定律風險）。檔案在不在，generate-image-manifest.mjs 掃一次就知道。
也不要建「立繪待補」清單——缺的多是 A/B 級配角與尚未進素材包的新機師，素材包一更新就自然補上， 那份清單會長期為空轉。
⚠ derive 是對檔名慣例的耦合。patch-image-paths.mjs 日後若改命名，全站會靜默退回 half 而不報錯。 把 derive 規則收在 src/utils/assets.ts 單一出口並補單測（assets.test.ts 已有 full.webp 樣本可掛）。
實測佐證：89 筆中 88 筆 portrait 含 half.（唯一例外賽拉是空字串）， 套 replace('half.','full.') 後對應實體檔案 88/88 全部存在。
決策 A-2：lore 與 profile 一個都不搬
依總綱決策二的「誰是權威來源」判準。三條套用結果：
判準依據結果
消費端定位PLAN-041:419「唯一的共同點是有沒有頁面在渲染它」 profile.* 與 additionalInfo 正被 PilotDetailPage.tsx:1219-1232 渲染 → 留
權威來源scrape-pilots-v3.js:464-467, 483-489 從官方 detail 產出 爬蟲每次補丁都重寫 → 留（PilotAdmin 的 profile 分頁本質是「修正爬蟲」）
載入成本逐欄位實測 lore 4.0%（51 KiB）＋ profile 0.9%（11 KiB）＝ 4.9%。 搬走 pilots 只從 1264 → 1202 KiB → 留在 pilots 無害
pilots 集合真正的肥肉在別處（供日後參考，不屬本計畫）： biometicComputer 51.2%（647 KiB） ＋ neuralDrive 34.3%（434 KiB） ＝ 85.5%。 而 biometicComputer 沒進 Pilot 型別、全站只有 PilotDetailPage.tsx:1148 一個消費端、還是用 as unknown as Record<string, unknown> 硬轉進去的。
唯一該動的 UI 位置：把 lore 的 <Field> 從 PilotAdmin 的 basic 分頁 移到 profile 分頁（語意上該與 gender/height/bloodType/AdditionalInfoEditor 同組）。 零風險——form 是單一 useState<Pilot>，分頁只是顯示分區。
決策 A-3：檔案層當「扉頁」，逸聞從 PART 1 起算
/lore/pilots/:id ＝ 扉頁（立繪 ＋ 直書姓名 ＋ 三枚徽記 ＋ 檔案卡 ＋ 引文體檔案簡介）， /lore/pilots/:id/:part ＝ 逸聞章節。
理由：扉頁永遠有內容（89/89）——逸聞 0 筆的今天，故事館上線不會是 89 個空展間。
⚠ 附帶技術後果：檔案層進館 ⇒ /lore 路由要 ensureLoaded(['pilots'])， 那個 lazy chunk 一進來要先拉 1287 KiB / gzip 約 206 KiB 的機師整包。 故事館的「純欣賞、低流量」特性會被這筆載入抵銷。
緩解：機師牆頁本來就要載 pilots（要名字與縮圖），使用者多半是從牆進到單頁，屆時已在記憶體快取內、0 額外讀取。 直接深連結進單頁的情況才會付這筆——可接受。
決策 A-4：紙色展場
四個理由：① 紙色最貴的那筆成本（87/87 都要做底部 mask）已因全身立繪而消失，只剩 fallback 的 36 位； ② 線稿顯影的原型是「藍圖顯影成實機」＝白紙黑線，放深底會變成比較像 HUD 的東西， 官網 hero/bg.jpg 本來就是米白紙底 ＋ 紅色斜切 ＋ 淡線稿底紋； ③ 與 38% 引文體 ＋ 檔案鍵值的剪報／卷宗體裁一致； ④ 色彩是「介面上分開」最強的訊號——換路由使用者未必察覺，換底色一眼就知道進了另一個地方。
⚠ 進場亮度跳變：從全站深色點進來會刺眼。需要一段 200–300ms 的底色過渡當「推門進館」的儀式， 順便蓋掉字體與版面 reflow。
決策 A-5：排版由資料的實際形狀決定，不套通用文章樣式
實測特徵（88 筆 lore）數量處理
以「或引號開頭（引文體）34（38.6%）整章套 blockquote 語彙：左細線、字距微調。不要 drop cap——首字放大會放大到那個引號本身，中文排版上是壞的
結尾帶 ——／一一／-- 署名35（39.8%）署名抽成獨立欄位，右對齊小字 ＋ 分隔細線
段落數 = 1 段48（54.5%）不可程式自動切段——機械式切段落只會產生語意錯誤的假章節
段落數 ≥ 2 段402段28／3段5／4段2／5段2／6段1／7段2
署名抽取可半自動：以「位置 > 60%、尾段 ≤ 30 字、不含句號」的啟發式在 89 篇重跑， 實測命中 30 篇、誤判 0 篇、漏抓 3 篇（尾帶句號者被踢掉）。 跑一次性草稿腳本 ＋ 人工複核，不要在執行期即時 parse。
其餘零成本美感槓桿（先做完這些再決定要不要付中文襯線 webfont 的預算）： 直書姓名（全站 writing-mode 零使用，新東西但零風險）、 天賦徽記（public/images/skills/天賦技能/ 170 張 128×128 現成，89 位共 86 個相異圖示； ⚠ 有 3 位機師的天賦既無 icon 也無 iconLocal，徽記元件必須有無圖 fallback）、 陣營徽記改成「文字刻在圓環內」不要畫圖（30 個值、18 個只有 1 人，畫圖是會隨改版增生的美術債）、 展示型元素用 px/cqw 正文才用 rem（否則使用者選「大」字級會把構圖撐爆）、 inline SVG feTurbulence 噪點一份三用（底部 mask／紙張材質／暗角）。
放棄手寫簽名：89 位無簽名素材，且 fullName 實測全部含 0 個拉丁字元 （葉夫根尼·伊萬諾維奇·高曼／洛莎·迪亞茲），script 字體渲染中文必走味。

風險：中文襯線字體的成本被普遍低估
紙色展場下宋體對「檔案／報告」調性的加成最大，但：今日語料（89 篇 lore ＋ 機師名 ＋ additionalInfo） 已有 1811 個相異 CJK 字，而故事館的整個目的是再灌入逸聞 PART，字集會朝 3000+ 逼近， 思源宋體 TC 子集的實際落點是 0.8–1.2 MB（不是常說的 300–600 KB）。
更麻煩的是字集漂移：內容住在 Firestore（動態），子集卻在 build 時產生 —— 每新增一章就可能出現不在子集內的字，同頁混排兩套字體比不換字體更醜。 且牴觸 index.css:L13-14 明寫的「中文本體字刻意不自託管」，還要考慮中國線路（PLAN-029）的下載體積。
→ 先把上述零成本槓桿做完再回頭決定，破例時要連帶處理字集漂移方案。
風險：兩個既有隱患必須在動工前處理
  • pilots 的寫入是 setDoc 全量覆寫、且完全沒有稽核。 src/lib/api/pilots.ts:17-21 → guardedSet 的 setDoc(...) 無 merge； 且 updatePilot 不走 saveWithHistory（ChangeTargetKind 聯集裡沒有 pilot）。 故事另開集合後這條競態自動消失，但新集合一定要掛上 saveWithHistory （changeHistory.ts 註解自己寫明「底層 helper 是集合無關設計」，接上去成本極低）。
  • 爬蟲 batchWrite 的 batch.set 沒有 merge: true （scrape-pilots-v3.js:117）。--force 會整份覆寫機師文件，洗掉 talent.buffIds / manual / debutVersion。既有隱患，既然要動這個檔案就順手補上。
