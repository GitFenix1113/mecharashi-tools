◆ PLAN-065-B

引擎 A：面板與單擊 資料編譯 · 面板 · 單擊 · /sim/v1/run

傷害模擬的第一個可計算版本：從遊戲資料編譯引擎資料、算出攻方面板與單次攻擊的期望傷害，經 /sim/v1/run 回傳；先不含任何 Buff 效果。

Problem
問題背景
065-A 把地基鋪好了，接著要有第一個「算得出數字」的引擎
站上實體已能對到遊戲記錄、私有 repo 與 Worker 骨架就位；評估階段的 Python 試算原型證明面板與單擊可以精確重現。 065-B 把它做成正式引擎：資料由管線編譯、計算在 Worker 執行、結果以契約 v1 回傳，並有自動化測試守住。
第一版刻意不含 Buff
天賦、模組、元件、背包、武器被動等效果要等 065-E（常駐效果）與 065-F（條件與攻擊方式）。065-B 的結果會把這些來源全部列進「未計入」，並一律標「推算」。
Design
設計決策
文件政策
本計畫書與進度表公開在 /documents，只寫工作項目、介面與驗收；計算方式、規則與預測值都在私有 repo mecharashi-sim。
決策一：資料在建置期編譯、打包進 Worker
私有 pipeline 讀本機遊戲資料包，輸出引擎需要的子集（含版本戳 manifest）；Worker 部署時一起打包，執行期不讀 Firestore。 武裝討伐首領與訓練木樁的守方資料也在建置期算好（推算值）。
決策二：引擎是純函式
引擎只吃「契約 v1 的請求＋引擎資料」，回傳結果，沒有 I/O；Worker 只負責驗證、預算、呼叫與回應。這讓同一份引擎可以被測試、驗證台與日後的離線工具共用。
決策三：第一版用浮點數，結果標「約」
與遊戲結果的差異只在取整邊界（±1）；需要逐位一致時再加精確模式。
決策四：以 Python 原型為對帳基準
評估階段的原型已與站上面板逐位一致；正式引擎必須在同樣輸入下與原型逐格相同（每擊整數一致、機率在浮點誤差內）。
2026-10-29 補充：與原型一致只證明「一致」，不證明「正確」——原型沒涵蓋或算錯的規則，另以私有 repo 的規則回歸測試守住（審查發現 3 處，已更正並補測試）。
決策五：未計入要說清楚
每個沒有算進去的來源（Buff、條件、尚未支援的攻擊方式、未連結的實體）都列在回應的「未計入」清單並附原因，不默默忽略。
Scope
實作範圍與不在範圍內
在範圍內：
  • 引擎資料編譯 v0（玩家側：機師、仿生電腦、潛能、適性、機甲套裝與部件、武器、改裝、科研、預設攻擊技能；驗證目標：武裝討伐首領、訓練木樁）。
  • 攻方面板、守方向量、單次攻擊（命中、暴擊、部位、擊數、取整）與每輪期望值。
  • /sim/v1/run：請求驗證、工作量預算、回傳結果與分組小計；ping 回報實際版本。
  • 測試：站上面板基準、首領面板基準、與原型逐格對帳、Worker 端到端。
不在範圍內：
  • 攻方的 Buff 與所有條件式效果（065-E、065-F）。首領面板的計入範圍依私有 repo 規則（2026-10-29 審查後定案）。
  • 追擊、連續攻擊、額外打擊等攻擊段（065-F）；固定傷害、濺射等支線（065-H）。
  • 逐位一致的精確模式、二進位資料格式（之後視需要）。
  • 前台 UI（065-D）；管理者驗證台（065-C）。部署後 run 端點沒有前台入口，不算總綱定義的「對外開放」（見總綱「對外開放時機」）。
驗收
  • 站上機師、機甲、武器面板基準全綠（已知例外列白名單並註明原因）。
  • 首領面板與評估階段的獨立重算一致（已知例外列白名單）。
  • 評估階段原型的預測表（6 組配裝 × 4 個目標）逐格一致。
  • Worker 端到端：合法請求回結果、非法請求被擋、超過預算回 422、kill switch 照常。
  • 本機量測單筆與批次的 CPU 時間，記錄在私有 repo。
  • 審查發現的規則問題各有回歸測試；一般請求的回應依決策 C1 的公開範圍處理（不回內部欄位、不提供逐點掃描所需的精度）。
