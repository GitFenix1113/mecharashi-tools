一句話：把 90 台機甲的逸聞接進 042-A 建立的故事館底盤。 元件、路由、chrome、換膚、章節導覽全部沿用，本計畫只做機甲專屬的三件事： 立繪素材工程、manufacturer 欄位、mechLore 集合與機甲側頁面。
為什麼排在機師之後
機師的立繪 53/89 已由官方素材包到位、轉檔即用；機甲的 lore-art 實查 0 檔， portrait.webp 只有 560×340（半身裁切），放大到全高面板會嚴重糊化 —— 需要 90 張人工出圖，這是本計畫最大的一筆成本，也是它被排在後面的唯一原因。
共用元件由 042-A 先驗證完，本計畫接上時風險大幅降低。
Problem
問題背景
問題一：逸聞被當成「附註」而非「內容」
Mech.lore 目前只是 MechDetailPage.tsx:317 的一段 <p>， 整段長文擠在數值表格之後，沒有章節、沒有節奏。官方遊戲內的逸聞是分 PART 1 / PART 2 章節、 並穿插 NPC（如娜塔莉亞）頭像旁白的敘事體驗。
問題二：沒有能撐起版面的大立繪
public/images/mechs/<名>/portrait.webp 是半身裁切圖（約 560×340），只夠當列表縮圖。 Mech.halfPortrait 也是同樣性質。故事館需要全身立繪這個新素材層級， 而它目前一張都沒有。
問題三：製造商欄位全站不存在
官網右上角的「類型 / 製造廠商」是立繪面板的重要資訊錨點，但 src/types/mech.ts 與 scripts/scrape-mechs.js 皆無任何廠商欄位（grep 全站 manufacturer / 廠商 / 製造 均無結果）。 機甲可展示的敘事型 metadata 幾乎只有廠商，這個欄位必須補上。
對照：機師有 additionalInfo 81/89、94 種自由鍵名， 以及 34 篇引文體 / 35 篇署名——機甲這邊一項都沒有（實測機甲 lore 引文體 0 篇、署名 0 篇）。 機甲館的敘事密度天生低於機師館，版面要有心理準備。
Design
設計決策
決策 B-1：立繪素材規格
public/images/mechs/<名>/lore-art.webp，長邊上限 1400px、四周留約 5% 安全邊距、WebP。
比例對齊 042-A 的實測值：機師官方全身立繪比例中位 0.58，官網 hero 是 0.55。 機甲出圖時採同一個級距（約 0.5–0.65 直幅），兩館的立繪柱才能共用同一套版面而不必參數化。
⚠ 這是本計畫的關鍵前提。若機甲立繪最後做成別的比例，042-A 建立的立繪柱就得改成參數化， 那是一次橫跨兩館的重構。出圖前先確認比例。
決策 B-2：偽線稿濾鏡必須用機甲素材重新調參，不可假設沿用
042-A 已驗證 color-dodge 偽線稿在人像上的表現（54 張實測，只有零觸發 >35% 高光門檻）。 但機體的材質、金屬高光、硬邊輪廓與人像完全不同 —— 參數與失效門檻都要重測。
原 PLAN-042 說「已在官網彩圖上實測通過」，那是對官網的機甲圖測的， 不等於對我們的機甲立繪成立（我們的還沒畫）。素材出來後補一次量測。
決策 B-3：mechLore 集合，與 pilotLore 分家
型別完全共用 042-A 的 src/types/lore.ts，但集合分開—— 版本 gate 是集合級、Worker 只有整包端點，合一會導致「改一台機甲的 PART 2 → 機師故事館快取一起失效」。
LoreCommentary.speakerId 指向 pilots，對機甲同樣成立（官方旁白就是娜塔莉亞這類機師）。
決策 B-4：Mech.manufacturer 留在 mechs，不進 mechLore
依總綱決策二的「誰是權威來源」判準：廠商是機甲的客觀屬性、圖鑑側也會用， 與 lore 同層、留在 mechs。只有章節與旁白進 mechLore。
官方 API 未提供廠商資料，本期以後台人工填入（爬蟲自動抓取不在範圍內）。
⚠ 0/5 定律：manufacturer 是新加的選填欄位，本專案的既有經驗是 「新開的集合會被填滿，新加的選填欄位不會」。緩解：後台機甲列表加「廠商」欄讓缺口可見， 並在故事館扉頁把未填者顯示為「廠商未載」而非留白。
