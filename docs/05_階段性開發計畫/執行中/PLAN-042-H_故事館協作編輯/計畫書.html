◆ PLAN-042-H

故事館協作編輯 LORE_EDITOR · 欄位級授權 · 首頁協作者頭像

啟用總綱裡降級為備案的 EDITOR 角色：新增 LORE_EDITOR，只能進故事館編輯台、只能寫故事館四個集合，碰不到遊戲數值；首頁維護團隊多一列「故事館協作編輯」放上這些人的頭像。

Problem
問題背景
站長決定開放協作（2026-10-17）
PLAN-042 總綱在 2026-08-23 把「EDITOR 角色與協作編輯台」降級為備案——當時判斷內容輸入不是瓶頸、單人維護不需要協作台，並註明「日後若真要找人協作，另開子計畫」。 兩館都已對外開放之後，站長決定找人一起編故事內容，備案轉正。
現行權限只有「全有或全無」
故事館編輯台掛在 AdminRoute 底下，規則層四個故事館集合都是 isAdmin()。要讓人編故事，唯一的辦法是給 ADMIN——那等於把機師數值、武器、模組、公告審核、使用統計全部交出去。
存檔不只寫一份文件
saveWithHistory 一次存檔會碰四個地方：直讀 pre-image、寫本體、meta/gameData bump 版本號、changeHistory 記一筆。只放行本體的話，協作者的存檔會「本體寫進去、版本號沒 bump」——其他人讀到的永遠是舊快取，而且沒有人會發現（bump 失敗是 .catch(() => '') 吞掉的）。
Design
設計決策
決策一：角色名 LORE_EDITOR，不是總綱原稿的 EDITOR
名字寫明範圍。日後若有攻略、公告之類的協作者，各自一個角色，不會出現「EDITOR 到底能編什麼」的歧義。 UserRole 排序 GUEST → USER → LORE_EDITOR → ADMIN → OWNER；新增 ProfileRole = Exclude<UserRole, 'GUEST'> 取代散在各處的 'USER' | 'ADMIN' | 'OWNER' 字面聯集。
決策二：授權範圍＝編輯台的四個分頁，且不能刪
pilotLore／mechLore／factionEmblems／mechMakers 開 read, create, update: if canEditLore()，delete 留 isAdmin()。 編輯台本來就沒有刪除路徑（lib/api/pilotLore.ts 檔尾），這條把「協作者用 client SDK 直接刪一整份人工長文」也一併關掉。 read 要開是因為 saveWithHistory 存檔前直讀 pre-image；編輯台的列表本身走 Worker，不靠這條。遊戲資料一律維持 isAdmin()。
決策三：附帶寫入用欄位級授權鎖死
meta/gameData：只開 update、只開這一份文件，isLoreVersionBump() 用兩層 affectedKeys().hasOnly()——頂層只准 versions／updatedAt，versions 裡只准故事館四個鍵。 否則協作者能 bump 任意集合，等於能讓全站所有訪客重抓整包資料。
changeHistory：create 加一條分支，target in ['pilotLore','mechLore']（徽章與廠商是 writeDoc＋bump、不留稽核），actorUid == auth.uid 的防冒名照舊；讀取仍只給管理者。
systemLog：create 由 isAdmin() 放寬到 canEditLore()——協作者正是最可能撞上「存檔被拒」的人，沒有這條，那份診斷證據只會永遠卡在他們的 localStorage。
決策四：路由留在 /admin/lore，不開 /lore-editor
總綱原稿要另開一條協作者路由；但新的頂層路徑要補 Cloudflare Transform Rule 白名單（CLAUDE.md §3），漏掉就是 HTTP 404。 改成 AdminRoute 多一個 lore prop 放行 LORE_EDITOR；協作者進 /admin 直接導向 /admin/lore，導覽列的紫色入口對他顯示「故事館編輯台」。編輯台麵包屑對非管理者不給「後台管理」連結。
決策五：角色判斷收進 src/utils/userRole.ts
isAdminRole()（後台全區）與 canEditLore()（編輯台）。本計畫碰到的地方（AdminRoute、Layout、AdminPage、AdminLorePage）改用 helper； 沒碰到的既有手寫判斷（useSimulatorEntry、MechAdmin 的 OWNER 判斷）語意本來就是「管理者」，不順手改。helper 與 rules 的角色清單要一起改，兩邊互相註記。
決策六：用戶管理改下拉選單，不提供指派 OWNER
原本是「升為 ADMIN／降為 USER」切換鈕，多一個角色就裝不下。選項＝一般用戶／故事館協作編輯／管理者（ASSIGNABLE_ROLES）；OWNER 的移轉不該是選單裡的一個選項（rules 允許，UI 不提供）。LORE_EDITOR 徽章用 cyan，與編輯台同色。
決策七：首頁團隊區塊多一列，Worker 快取鍵換 v2
「攻略作者/資料彙整者」下面加「故事館協作編輯：」，頭像列允許換行（人數可能比上面兩列多）。 名單來源 /api/site-team 的角色清單加 LORE_EDITOR（前端直連回退的 SITE_TEAM_ROLES 同步）； 快取鍵由 site-team 換成 site-team-v2，否則部署後最多一小時內讀到的仍是舊名單，驗收時會誤以為部署失敗。
順帶的既有行為（不需要改）
使用統計（lib/analytics/track.ts）只記 USER 與未登入，協作者和管理者一樣被當成維護者排除在外——這是想要的結果。
Risk
已知風險（不在本計畫處理）
⚠ 多人同時編同一份文件會整份覆寫
saveWithHistory 是整份覆寫、沒有衝突檢查；changeHistory 的 update 也不存前一版快照（PLAN-030 決策五）。 2026-10-14 已發生過一次：舊分頁存檔洗掉了克洛伊 pilotLore 的三個欄位。單人維護時這是「自己跟自己的舊分頁」，開放協作後變成「兩個人同時開同一位」——後存的人會靜默蓋掉先存的人，且無法從稽核記錄還原。 建議另立案：存檔前比對文件 updateTime（不一致就擋下並提示重新整理），並讓 lore 兩類的 update 留前一版快照。在那之前，靠分工（每人負責不同機師／機甲）與定期備份（backup-firestore.mjs）。
⚠ 模擬器模式下協作者的編輯台會載入失敗（預期行為）
編輯台的列表要讀 pilots／mechs，正式站走 Worker；.env.emulator 關了 Worker（VITE_USE_WORKER=false），直連 Firestore 時協作者讀不到遊戲資料。 要在本機驗協作者的完整存檔流程，用「讀取走正式 Worker、寫入落模擬器」的混合模式（做法見進度表 D-2）。
Scope
實作範圍與不在範圍內
在範圍內：
  • 角色：src/types/enums.ts、src/types/user.ts、src/utils/userRole.ts（＋測試）
  • 規則：firestore.rules（canEditLore／isLoreVersionBump、四集合、meta、changeHistory、systemLog）與 scripts/test-emulator-rules.mjs
  • 前端入口：AdminRoute、App.tsx、AdminPage、AdminLorePage、Layout、UserAdmin
  • 首頁：SiteTeamSection、useSiteTeam、userApi 的 SITE_TEAM_ROLES；Worker /api/site-team
  • 文件：Firestore 設計文件（enums／users／security-rules／四集合／changeHistory／systemLog）、頁面規劃（首頁／管理後台／故事館）、總綱、更新履歷
不在範圍內：
  • 存檔衝突檢查與 update 快照（見上方風險，建議另立案）
  • 協作者看自己的編輯歷史（/admin/history 仍只給管理者）
  • 故事館內的協作者署名（館內「本篇由誰整理」之類的 credit）——首頁那一列先上，館內要不要掛等有協作者再議
  • 邀請流程：被授權的人要先自己登入一次（profile 才會存在），再由 OWNER 在用戶管理改角色
