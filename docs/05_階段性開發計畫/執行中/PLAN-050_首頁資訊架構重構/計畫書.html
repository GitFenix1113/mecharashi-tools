Problem
問題背景
問題一：離散的檢視選擇被綁在連續的環境輸入上
首頁是一個兩頁的 scroll-snap 容器（src/index.css 的 .homepage-snap）。 「看 Hero 還是看資料」這個離散意圖，被綁在滾輪／中鍵／觸控板這種 連續、含噪、裝置相依的環境輸入上。必然的後果是兩種錯誤： 「我沒想切、它切了」與「我想切、它不切」，而錯誤率取決於使用者的滑鼠與瀏覽器， 開發者在自己機器上測不到。

更根本的是：Hero 是一道每次進站都要付費的門。 它裝的是站務履歷與團隊介紹 —— 一次性內容；而門後是每週回訪的版本資料。 頻率決定版面，現況剛好相反。
問題二：兩種長寬比需求正交的內容，共用同一條捲動軸
甘特是寬而扁（寬度＝週數，離散且上限 6–8；高度＝活動數 × 38px）， 卡片流是窄而長（@2xl 以上才雙欄，內容無高度上限）。 兩者都吃垂直捲動，卻被放進 VersionGanttPanel 的同一個捲動容器。 這在版面上無解：甘特的列數把卡片流推到摺線以下，而壓短甘特只能靠砍活動。

關鍵推論：「展開版面」這顆按鈕把預算花在只有 6 個刻度的軸上 —— 每週欄從 123px 變成 277px（最低需求 80px），而甘特長條的資訊上限是一行截斷文字。 寬度不是瓶頸，列數才是。
關於 PLAN-048 的 488px 與本計畫的 247px 為何不同 —— 兩者都對
PLAN-048 進度表記載「甘特＋卡片區 186 → 488px（2.6 倍）」，那是資訊表收合後的數字， 該階段的成果完全成立。但 loadCollapsed() 預設回傳 false， 沒有點過收合鈕的使用者拿到的是展開態，也就是 247px。 PLAN-048 把最佳情況從 121px 拉到 488px；本計畫要處理的是預設情況仍然是 247px， 以及「索引與內容在同一條軸上、看了這個就看不到那個」的結構問題。
Design
設計決策
決策一（Q1）：Hero 降級為可收合頂欄，內容優先 —— 且方案 C 是可接受的升級路徑
刪除 scroll-snap 容器，資料面板成為 / 的預設與唯一版面； Hero 三塊（站名／SiteChangelog／SiteTeamSection）收成一條可展開的頂帶。 首訪自動展開、回訪收起（localStorage 旗標，比照 VersionGanttPanel 的 loadCollapsed() 寫法）。

不做「隱晦的左右切換按鈕」。隱晦＋必經＝發現性失敗； 而改變軸線（上下→左右）只是換一組會誤觸的手勢（Shift+滾輪、觸控板橫掃、 iOS 邊緣返回），沒有解決根因。要換的是輸入型態，不是軸線。

站長補充（2026-08-19）：「動畫不是必要的，當初覺得很炫，但實際上我並沒有這種設計能力」、 「首頁的公告和 Hero 藏進 about 不見得是不能接受的，功能優先」。 因此原分析報告判為「不建議」的方案 C（Hero 移到 /about）改列為 Phase B 的可選升級路徑，而非否決項 —— 若 Phase B 完成後頂帶仍在跟內容搶空間，直接走 C。
決策一の修訂（站長定案，2026-08-19 Phase C 完成後）：改為「資料離開首頁」而不是「Hero 離開首頁」
原決策的方向是「內容優先 → 資料面板成為 / 的預設與唯一版面，站務收成頂帶」， 而 B-4 預備的升級路徑是把站務推到 /about。實際定案是反過來的那一邊：

「首頁就不要使用 Quick Table、灰燼行動、Timeline 三個快速分頁了，反正我們已經做了版本情報， Quick Table 應該要盡量完整呈現。首頁就維持原本的公告 ＋ 開發者清單，剩下三者讓使用者去點吧。」

理由成立且比原決策更乾淨：Phase A 之後版本情報已經是完整的一區，速覽表留在首頁永遠只能拿到 min(96vw, max(48vw, 780px)) —— 十一個欄位（類別 ＋ 5 版本 × 機師/機甲）在 780px 下 每格只剩 60px，等於兩邊都做不好。移出之後速覽表拿到 1500px，首頁則回歸單一職責。

連帶結果：B-1 的可收合頂帶（HomeHeroBar）與 HomeTabPanel 一併刪除 —— 收合是為了跟資料面板搶空間，面板走了就沒有東西要搶；首頁改回一般文件流， footer 由 Layout 統一渲染，.viewport-shell 只剩 /versions 在用。 B-4（Hero 移到 /about）因此永久不執行：站務履歷留在首頁，曝光度沒有損失。
決策二（Q2）：導覽列新增「版本情報 ▾」下拉，三個檢視做成 routed tabs
【2026-08-19 修訂】頁內的那條 tab bar 已隱藏 —— 導覽列的下拉就是入口，頁內再放一條是同一組導覽出現兩次，而它吃掉的是 Timeline 最缺的垂直空間。 「routed tabs」保留的是路由那一半（三個網址、深連結、分流統計）， 不是外觀那一半。
/versions/quick｜/versions/grayops｜/versions/timeline， 共用一個 layout route 與同一條 tab bar（外觀不必改）。 沿用既有的 ContentNavDropdown 元件，導覽列只增加一項。

為什麼是獨立下拉而不是塞進「攻略/工具/文件 ▾」：版本情報是本站主打內容之一， 藏在攻略底下與其實際份量不對稱。

為什麼是 routed tabs 而不是三個頂層頁：routed tabs 同時拿到深連結、上一頁、 統計分流，又保留「這三者是一組」的心智模型，導覽列只 +1 項而不是 +3 項。
決策三（Q4）：banner 桌機用信箱式頂帶、行動版用角落暈影，兩者並存
現況為了搶回對比度，已長出三個互相耦合的調整鈕，而且三次都往同一個方向調（把圖蓋掉）：
常數位置現值原始碼註解自陳的理由
BANNER_OPACITYVersionExpandedPanel.tsx:22opacity-40「原 opacity-80，過亮」
BANNER_SCRIMVersionExpandedPanel.tsx:25/60 /70 /85「原 /20 /35 /65，頂部幾乎沒遮」
SURFACEVersionGanttPanel.tsx:76bg-bg-dark/75「原 /40，太透，11–13px 文字下方直接是機甲立繪，讀不到」
這是裝飾與可讀性的零和：細字疊在亮度變動的照片上，無法保證任何一版 banner 都達到 WCAG AA（4.5:1）；唯一能保證的做法是把 scrim 加到圖看不見，那就等於沒放圖。
改法是換位置而不是丟掉：桌機把 banner 移到頂部 96–120px 的信箱式色帶 （object-cover object-top、右端漸暗），版本名與服別切換壓在暗端； 行動版垂直預算最緊，改用不吃高度的角落暈影。 資料區因此可以變成不透明實色，三個常數全數退場、backdrop-blur 一併移除。
決策四（Q3）：Phase A 先單獨上主站跑 1–2 週收數據，再決定 Phase C/D 的順序
Phase A 完成前，三個檢視全部記成 /， 「Gray Ops 到底有沒有人看」「行動端佔比多少」目前無從得知。 這兩個數字直接決定後續投入：若行動端過半，Phase C（桌機左右分割）的收益只作用在少數人身上， Phase D（行動版）必須提到 Phase C 之前。

先量再改，是這個計畫唯一能把優先順序從猜測變成事實的方法。

2026-08-19 現況：Phase C 在數據回來之前就完成了（風險自負但成本已付）， 因此「C 與 D 誰先」這個問題自然消解。決策四剩下的效力在於 D-1／D-2 值不值得做， 以及 /versions 的預設分頁該是哪一個 —— 兩者都還是等 A-6。
決策五：Timeline 改主從分割（master–detail），比例 55/45
甘特與卡片流各自擁有獨立的 overflow-y-auto overscroll-contain 捲動軸。 1920 下左側 55%＝1000px → 每週欄 148px（遠高於 80px 下限）； 右側 820px 跨過雙欄門檻。 ⚠ 這裡的「@2xl＝672px」在實作時被實測推翻：容器查詢的 rem 是對 根字級解析，本站根字級 19px，@2xl＝42rem 因此是 798px； 右欄扣掉內距只剩 780px，差 18px 卡在門檻下，雙欄從來沒生效過。 已改用 px 門檻 @[760px]（要限制的本來就是卡片寬度，是個 px 量）。 這與本計畫「已知技術陷阱」第 2 條是同一個坑 —— 連寫計畫的人自己也踩了一次。 比例可拖曳並存 localStorage。

同時取消 clip-path 圓形展開的 modal：它讓「比較兩個版本」不可能， 而那正是版本頁最常見的問題。改成信箱帶上的 ◀▶ ＋ route 參數， 抵達甘特的互動步數從 4 步降到 1 步，且每個版本可深連結。

順帶移除 VersionTimeline 的滾輪劫持 （VersionTimeline.tsx:60-74 的 wheel + preventDefault）—— 它存在的唯一理由是原始碼註解寫的「避免觸發頁面 snap 捲動」。 一個反模式為了掩蓋另一個反模式而存在；snap 一走它就沒有存在理由， 而它本身也違反決策一的原則。
已知技術陷阱（實作時必須處理）
  • overflow: hidden 的容器仍可被程式化捲動。 若 Phase B 採用「兩頁並存 + transform 位移」的做法，Ctrl+F 命中畫面外那一頁時瀏覽器會強捲容器、把位移弄亂。 必須配 inert + content-visibility: hidden，或乾脆只掛載當前那一頁。
  • 本站 root font-size 是 19px 不是 16px （Layout.tsx 的 FONT_SIZE_MAP，預設 md）。 所有 rem 與 Tailwind spacing 都是瀏覽器預設的 1.19 倍： h-8＝38px、p-4＝19px/邊、h-12＝57px。 任何按 16px 心算的版面預算都會低估約兩成。
  • main 是 flex-1 但沒有 min-h-0 （Layout.tsx:246）。它的 min-content 高度由子容器決定， 子容器只要比可用高度高 1px，root 就會超出 min-h-screen 而多出一條文件捲軸。
  • Tailwind 的 lg: 在本站是 1024px，而 md:70vw → lg:48vw 這類「兩個不同 vw 比例」的斷點在數學上不可能連續 （0.70·B 恆大於 0.48·B）。要消斷崖只能引入 px 下限。

報告初稿主張實測結果正確結論
把 lg:max-w-[48vw] 改成 xl: 就能消掉 1024px 的寬度斷崖 錯誤 移到 xl 只是把斷崖搬家而且挖更深： 70vw@1279＝895px → 48vw@1280＝614px，落差從 224px 變成 281px 改用 px 下限壓平曲線。已於 2026-08-19 實作為 max-w-[min(96vw,max(48vw,780px))]
scroll-snap-type 改 proximity 可讓誤觸的滾輪「等於無效操作」 過度樂觀 只對小位移成立（中鍵拖曳已驗證）； 一般滾輪多格累加會越過吸附閾值而停在半截，上下兩頁各露一半 真正的元兇是 scroll-snap-stop: always（分頁器語意）。 定案為 mandatory + 移除 scroll-snap-stop
垂直預算：甘特列高 32px、可用高 296px 低估 實測 38px／247px（19px root 造成 1.19 倍） 結論方向不變，但擁擠程度比報告寫的更嚴重。 報告 §3.1 已補上實測校正表
