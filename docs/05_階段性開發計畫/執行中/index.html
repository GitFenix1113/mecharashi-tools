PLAN-050 · 首頁資訊架構重構

源自使用者反饋的兩個問題，追下去發現是同一個根因的兩種症狀：首頁把「離散的檢視選擇」綁在「連續的環境輸入」上，又把三種長寬比需求完全不同的內容塞進同一個 48vw 的框裡。
問題一不是「動畫該用什麼手勢」，是不該有這道門。Hero 裝的是站務履歷與團隊介紹（一次性內容），門後是每週回訪的版本資料——頻率決定版面，現況剛好相反。因此不做「隱晦的左右切換鈕」（隱晦＋必經＝發現性失敗），而是刪掉 scroll-snap 兩頁架構（PLAN-015 的產物，也正是誤觸的結構成因），Hero 降級為首訪展開／回訪收起的頂帶。站長明確表示「動畫不是必要的」「藏進 about 也可接受，功能優先」，故原判為不建議的「Hero 移至 /about」改列可選升級路徑而非否決。
問題二不是空間不夠，是空間花錯地方。實測：甘特＋卡片容器可用高僅 247px 而甘特區塊 532px，scrollHeight 1217px——只有兩成內容在畫面內，卡片流可見高度實測為 0px。更關鍵的是按下「展開版面」把寬度加倍（922→1843px、每週欄 123→277px），垂直預算一格沒變、多露出 0 張卡片：預算被砸在只有 6 個刻度的軸上，而長條的資訊上限是一行截斷文字。寬度不是瓶頸，列數才是。根因是甘特（寬而扁）與卡片流（窄而長）長寬比正交卻共用同一條捲動軸，解法是主從分割成兩條獨立軸。
三個檢視改 routed tabs（/versions/:view）＋導覽列新增「版本情報 ▾」：一次拿到深連結、上一頁與分流統計——現況三個 tab 全記成 /，「Gray Ops 有沒有人看」「行動端佔比多少」目前無從得知，而後者直接決定 Phase C/D 誰先做。故 Phase A 刻意單獨上主站跑 1–2 週收數據再定序。
P0 止血（移除 scroll-snap-stop、補 overscroll-contain、寬度下限 780px）已於 2026-08-19 完成推送，不在本計畫範圍。整個計畫零資料模型變更、不需 bump 版本。

PLAN-049 · 問題回報與功能建議

站上資料由爬蟲蒐集後人工修正，錯誤無法避免，但目前沒有任何回饋迴路——玩家看到錯的數值，除了私訊維護者以外無處可去。2026-08-18 補上的 GitHub issue 模板服務的是「會用 GitHub 的人」，一般玩家不會為了回報一個數值去註冊帳號，預期回報率趨近於零。本計畫做站內表單，涵蓋資料錯誤 / 功能異常 / 功能建議三類，共用一個 feedback 集合與一套狀態機。
拍板一律需登入（訪客看得到入口但不能提交），這個決定的連鎖效應比表面上大——它讓本計畫不需要動用 Cloudflare Worker。與 PLAN-046 使用統計正好是對照組：統計要涵蓋訪客 ⇒ 不能要求登入 ⇒ client 直寫等於 create: if true（任何人可迴圈寫爆額度）⇒ 必須 Worker 代寫；回報要求登入 ⇒ create: if isAuthenticated() && uid 綁定 有身分可追溯 ⇒ client 直寫 + 規則守門即可，省下整個端點。寫入範式直接沿用 systemLog（PLAN-045）已驗證的 append-only + uid 綁定。
回報對象不另發明欄位，直接用既有的 EntityRef——其 RefType 已涵蓋 pilot / mech / weapon / module / backpack / component 等所有可能被回報的實體，於是詳情頁按下回報可自動預填對象（使用者只需填「哪裡錯、正確值是什麼」），後台則用現成 RefChip 渲染成可點連結。feedback 刻意不進 GameDataContext：三層快取是為版本化的靜態遊戲資料設計的，套在隨時被管理員更新的動態資料上只會讓使用者看到過期狀態。
限流正面回應 PLAN-045 決策四的顧慮：第一版只做登入門檻 + 規則層欄位長度驗證 + UI 節流 + 事後封鎖，不做規則層時間窗 rate limit（第二階段設計已備妥，屆時走獨立 feedbackThrottle 集合並強制 lastAt == request.time 使其無法偽造）。⚠ 封鎖標記不能放 users/{uid}/profile——現行規則只擋 role，其餘欄位本人可自由修改，被封鎖者能自己解封，須一併加入禁改清單，這是本計畫唯一動到既有規則之處。最大風險不是技術而是維運：回報堆積無人處理，故「讓回報有下文」的 adminReply 是必做而非加分項。

PLAN-048 · 時間線甘特圖改版

甘特圖有三個結構性問題，而且都不是調 CSS 能解的。tooltip 被裁切是因為容器 overflow-y-auto 而浮窗 absolute bottom-full 永遠往上長——z-index 對 overflow 裁切無效，實測共 11 層 clipping ancestor，只有 portal 有效。一週活動只剩一個 12px 圓點，因為 activityToColumns() 把起點量化到下一個週界，實測 27/75 筆（36%）是這種。而「維護者打了很多資料卻看不到」根本不是顯示問題——TimedActivity 沒有描述欄位，獎勵只能硬塞進 name（瑞歲百角戲(輕型通用改裝模組*1 仿生超導體*2)）。
方案定調 「甘特＝索引，卡片＝內容」：甘特留在原地繼續與週次表共用同一條軸、降級成日精度概觀，內容改由正下方同一個捲動容器內的卡片流承載，並做甘特↔卡片↔週欄三向連動——這是四份提案中唯一正面加強「對照版本週次」原始動機的機制。評審抓到四案共同盲點：把「資訊看不到」誤診成「資料不夠」，玩家三個問題裡有兩個半能從既有 startDate + weeks 直接算出（第 N/M 週、剩幾天、末週），零欄位、零維護成本、100% 覆蓋。Phase 0 僅 5h、零資料模型變更即可全解前兩個痛點。
另含台版公告管線：實測台版是靜態 JSON（副檔名 .html 但內容是 JSON），不需 Playwright、無反爬，PoC 從 117 篇週報抽出 522 筆活動、名稱失敗率 0%；陸版公告頻道則已廢棄（2 篇、停在 2023-10），明確接受「台版自動化／陸版人工」的不對稱。⚠ 258 篇公告只存在於前代理商網域 ma.tentree-games.com（代理權 2026-01-05 已移轉），全量歸檔優先度高於任何功能，故排在 Phase 0。

PLAN-047 · 槽位與裝備限制模型

機甲側沒有任何欄位說得出「我有幾個肩槽、幾個背槽」。武器側說得出自己的限制（mechRestriction / equipSlot），但反方向完全空白——REV-01 的［嵐質儲能艙］×2 要吃掉兩個肩槽這件事，無法從武器側推導。而模擬器的 getFilteredWeapons 全文只有一條規則（重量夠不夠），既不看機甲類型也不看槽位，於是輕型機甲照樣選得到 43 把中甲限定武器。本計畫補上共用槽位詞彙 ArmamentMount（slot 直接沿用 WeaponEquipSlot——全站已有三套部位詞彙，第四套會與 weapon.equipSlot 不可互推，校驗腳本就寫不出來），並刻意不開 shoulderSlots 欄位：derive 規則已覆蓋 63/63，而同型別裡的 leftShoulderSlot 三欄設計良好卻實測 0/62 填寫，「保留未來可能性」改兌現成單一 derive 入口 mechSlotCapacity()。另有一條獨立的退場理由：stripUndefined 會濾掉 undefined，導致槽位欄位一旦寫進去就再也取消不掉。
「戰術武器限中甲」實測不需要新規則——type==='戰術'(43) 與 mechRestriction==='medium'(43) 雙向零反例，且 22 把肩武器 100% medium，武器側已 100% 表達。Phase D 順手修兩個既有 bug：背部武器與背包可同時裝上、以及 :181 把 '中甲'(ArmorType) 拿去比 '中型'(MechLicense) 造成的靜默全放行。掛 chassis 還是 MechPart 列為 Open Question（「同時攜帶兩門」的條件句與全機種通用的 Ⅱ型接口 都指向部件，但破曉者-01／霸王根本沒有武裝來源模組），連同舊存檔相容性一起阻塞資料落盤與 gate。

PLAN-046 · 網站使用統計

目前唯一的觀測手段是 Firebase 主控台的讀寫次數，它能回答「花了多少額度」，卻答不出「哪些頁面真的有人用」——而後者才是決定改版順序與資料補齊順序的依據。更關鍵的是 PLAN-029 的中國訪客策略至今無從驗證：Worker 同源代理、字體自託管、邊緣改寫都做了，卻只能說「應該有用吧」。本計畫用長期閒置的 Firestore 寫入額度，建一套同源第一方埋點（走既有 /api，攔截器擋不掉、中國訪客也統計得到，這正是不用 GA4 的理由）。去重採三層識別碼：visitorId／sessionId（10 分鐘閒置，且閒置由活動訊號判定，否則慢讀者的 session 會被誤切）／已報頁面 Set，同頁同次造訪只計一次 UPV，但 PV 雙軌保留——兩者比值即「折返率」，是資訊沒給足的訊號。資料走預聚合日文件（看 30 天＝30 reads），一個 session 離站時 sendBeacon 批次寫一次，寫入量與逛幾頁完全脫鉤。
安全面：不開匿名 Firestore 寫入，改由 Worker 代寫，但這讓 Worker 從純唯讀變成有匿名可觸發的寫入路徑，因此立兩條鐵律（文件路徑由伺服器時間算出、欄位路徑一律由程式碼組出，payload 只准給數字）。另含寫入預算熔斷器（超出免費額度自動停止計數並標記 truncatedAt，避免報表默默說謊）與 COLLECT_ENABLED kill switch。Worker 端刻意不放頁面白名單，改用格式正則防護——放名單就是重演 PLAN-043 的雙名單不同步事故。不記錄個別使用者行為。

PLAN-042 · 機甲故事館

機甲的逸聞目前只是詳情頁最底下一個 <p>，整段長文擠在數值表格之後；而官方遊戲內的逸聞是分 PART 1 / PART 2 章節、穿插娜塔莉亞等 NPC 頭像旁白的敘事體驗。本計畫另開 /lore 獨立路由做成左文右繪的沉浸式故事館，並復刻官網那招「線稿顯影 → 彩圖疊上」的立繪切換動畫——已實測拆解官網為四層背景圖 + 錯位淡入（線稿領先彩圖 250ms）；本站沒有線稿素材，改以 color-dodge 素描濾鏡即時生成，實測幾乎重現官方質感（邊緣偵測法已驗證不堪用）。順帶補上全站不存在的 manufacturer 欄位，以及撐得起全高面板的全身立繪素材層（現有 portrait 僅 560×340 半身裁切）。
因故事資料需他人協助輸入，另含兩塊：新增 EDITOR 角色（現行規則下所有集合皆 read/write: if isAdmin()，給人 ADMIN 等於交出全站讀寫權；改以 affectedKeys().hasOnly() 把可寫範圍鎖死在故事三欄位，且刻意不給 read、編輯台讀取改走 Worker /api），以及靜態化出口（資料定稿後逐台切成 src/data/lore/ 零查詢，非全站一次切）。機師故事館與陣營勢力不在本期範圍。

PLAN-041 · 機師形態變化

調構師的四個形態（先鋒／突擊／戰術／虛粒子）其實已經有資料——四筆文件躺在 pilotSkills 的 710 筆裡、正文逐字完整，但實測 0 位機師的 skills 陣列引用它們，前台從建立到今天一次都沒顯示過。而 PilotSkill 型別裝不下形態真正需要的東西（武器限制、固定武裝鎖定、顯示順序、增益連結），現況已經在拿 skill.weapon.categories 硬撐。本計畫把四筆遷成獨立的 forms 集合、改掉 12 條 inbound 引用、蓋出條件式第 4 分頁與跨分頁常駐的「特殊能力」列，並順手拆掉 PLAN-019-B 那套 0 筆資料、從未渲染過、卻仍在後台誘導維護者建錯地方的 mutexGroup 引擎。42 筆「形態 × 武器 → 子技能」矩陣列為 N2，可延後。2026-08-09 訂正：海莉絲突擊／先鋒形態多出的「備用武器槽」與 +300 出力上限，實測是強襲者背包（backpacks/60101706，全庫唯一的 BackupEquipment）給的，不是形態能力——形態既不改機甲數值也不改槽位配置，因此 FormRestrict 維持 discriminated union、MechForm 維持不開 effects，兩個核心決策都不必動。固定武裝清單同步從 4 種訂正為 6 種；槽位模型歸 PLAN-047，本計畫只與它共用 ArmamentMount 型別，阻塞不變也不加深。

PLAN-038 · 社群連結預覽（Open Graph）系統

站長回報網站在 LINE 有連結預覽、Discord 完全沒有。診斷確認根因單一：index.html 沒有放任何 og:* 標籤——Discord 的爬蟲不執行 JS 也沒有 <title> fallback，找不到 og:title／og:image 就完全不顯示卡片；LINE 則退而求其次抓標題撐出陽春卡。分兩層修：Tier 1 補齊全站靜態標籤（可獨立上線）；Tier 2 延伸既有 Cloudflare Worker，用 HTMLRewriter 讓機師／機甲／武器詳情頁分享時顯示對應肖像與名稱。og:image 素材策略刻意重用既有實體圖片欄位，不另開一套美術維護線。

PLAN-026 · 召喚單位展示
