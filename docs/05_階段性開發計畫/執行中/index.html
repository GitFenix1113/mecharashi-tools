PLAN-052-F · 形態獨立配裝

模擬器今天對海莉絲給出一套配裝，而遊戲裡是三套可配 ＋ 一套鎖死。這與「還沒做元件」不同——元件缺席時玩家知道自己沒看到，形態缺席時玩家看到的是一個看起來完整、實際上只對四分之一情況成立的配裝。重量與出力尤其如此：總綱紅隊已驗過出力是 per-form 的（先鋒 3675 vs 另一形態 3375，差的 300 來自強襲者背包）。
地基全都鋪好了，工程量不在「造」而在「接」＋「補三個沒人回答的問題」：draft.sets / activeSetKey 是 052-A C-3 就落地的模型、reconcile() 已逐套掃裝備、canEquipWeapon() 已有 FORM_WEAPON_TYPE、utils/forms.ts 三支純函式已完成並有單元測試，LoadoutPage 甚至已在算 activeKey——缺的只是那排分頁沒有被畫出來。
2026-08-28 直讀正式庫切片查證：forms 6 筆齊全（海莉絲 4／曜 2）、20 條 refType:'form' 引用已遷移、0 條 dangling、舊形態文件已清除——PLAN-041 Phase C 的資料工作實際已完成。
✅ Phase A 完成（2026-08-28，4/14）——三個「答案在使用者腦中、不在程式裡」的問題都已落地：
· 曜沒有形態分頁，資料本來就是對的（A-1 使用者裁決）：遊戲裡曜連形態頁面都沒有，independentLoadout: undefined ⇒ equipSetKeys() 回 ['default'] 是正確行為不是 bug。總綱那句「曜 1 套 ＋ 1 唯讀」已改寫（A-3），並明文寫上「不要順手把欄位補上」——規格與資料互相打臉時，後來的人一定會去改比較好改的那一邊，而那一邊是資料。
· 唯讀卡的判準改成「有沒有分頁列」：equipSetKeys() 讓鎖死的形態不佔分頁（那是對的），C-1 補的是它的另一半——但今天只畫海莉絲虛粒子一張；曜沒有分頁列，畫了就是站上多出一個遊戲沒有的東西（幽弧／夜燼在武器圖鑑查得到）。
· 出力基準釘死，並訂正了 E-1 的配對（A-2）：3375 ＝ 彌造者軀幹出力、＋300 ＝ 強襲者背包（唯一數值來源是背包技能正文，已硬編進 BACKPACK_OUTPUT_BONUS 並由單測鎖住）。⚠ 原訂「先鋒 vs 突擊」對帳是錯的——兩者能裝的武器全在手部槽、背槽都空著 ⇒ 都是 3675，那個測試會綠卻什麼都沒防到；能拉開差距的是戰術（44 把只有 back／shoulder，背槽被佔 ⇒ 3375）。
· 順手發現一條既有斷線（歸 052-G）：loadoutBudget() 沒把 modules 傳給 effectiveOutput()，OutputBreakdown.modules 恆為 0。
✅ Phase B 完成（2026-08-28，8/14）——分頁列上線： 新元件 FormTabs.tsx 掛在「裝備與模組」面板的抬頭列（機甲名與裝甲徽章的右邊、槽位圖正上方）。 ⚠ 位置改過一次：初版擺在 sticky 抬頭、緊貼 OutputBar 上方（理由是「分頁與它統轄的數字一起 sticky」）， 但站長實測逐字回饋「這邊有點不顯眼，我找了一陣子才找到形態切換的操作」—— 那一排混在機師／機甲／方案名稱那幾顆同色同形的卡片之間，看起來像又一個欄位而不是可以切換的東西。 理論上的歸屬性輸給實際上的找不到。原本的代價（sticky 數字失去歸屬）改由 OutputBar 的 形態標籤補上（「TOTAL / OUTPUT 戰術形態」，是標籤不是第二排可點的分頁），挑選器底部的預算行同樣帶著它。 本機 emulator 實測海莉絲三分頁逐套獨立：先鋒 975 / 3,675（強襲者背包 +300）、 戰術 1,925 / 3,375（背槽被戰術武器佔住）、突擊 825 / 3,375，切換來回不串味 —— A-2 釘下的基準在瀏覽器裡重現。360px 單列不折行、無水平溢出。
⚠ B-3 的前提在動工時就已經不成立：FORM_WEAPON_TYPE 是 structural tier， 而 PickerShell 在 052-I 驗收後把 structural 的項目整批不列 —— 於是「戰術形態只能裝備戰術類武器」那句 reason 只掛在被濾掉的列上，一個字都到不了畫面， 玩家看到的是「符合 0 / 131」＋「這一格沒有任何可裝的裝備。」。 改法是把同一件事講在清單之上（新 formWeaponHint() 走既有的 hint prop）。
⚠ 另補一個真的洞：setActiveSet 不驗 key。頁面那側會把不合法的 activeSetKey 退回第一個分頁，但那只修了畫面 —— 動作讀的是 draft.activeSetKey 本人，症狀會是「畫面停在先鋒分頁， 裝上的武器卻寫進一個不存在的鍵」，沒有錯誤訊息。已收在 reducer 並附測試。
✅ Phase C 完成（2026-08-28，10/14）——第四個形態不再是零存在感： 判準落地成 lockedFormCards(pilotId, forms)（utils/forms.ts，第一行就是 if (!hasIndependentLoadouts(...)) return []），所以「有沒有分頁列」這件事 寫在程式裡、可單測，而不是寫在某個元件的註解裡。呈現拆兩處：分頁列尾端一個 唯讀標記（<span>、不掛 role="tab"，靠「切角＝可互動／圓角＝唯讀」與分頁區分） 回答「還有第四個形態」；槽位圖下方一張 <LockedFormCard> 回答「它裝了什麼」。 實測：海莉絲 1 張、曜 0 張、其餘 87 位 0 張。
⚠ C-2 的三句前提全部不成立，已訂正。工項寫著「固定武裝的重量實測為 0 ⇒ 算與不算等價 ⇒ 建議改印『不佔配裝額度』」——但耀星／隕星／千星各 100、合計 300， loadoutWeightSet() 的註解逐字寫著「固定武裝要計入：golden fixture ④ 1125 ＝ 825 ＋（100＋100）＋ 100」，而 1125 正是官方整備畫面上的數字。 印「不佔配裝額度」會同時與引擎、官方畫面、既有 golden fixture 三邊打臉。 （重量為 0 的是曜的幽弧／夜燼——已知 bug #10 講的是那兩把。） 改成照印真數字：1,125 / 3,375 ＋「照樣計入重量，只是玩家改不了」。 「改不了」與「不佔額度」是兩件事。
⚠ 實測時另抓到一個 bug：沒選機甲時卡上印成「300 / 0」（出力來自軀幹）—— 看起來像超重 300，其實只是還沒選機甲。已補分支改印「固定武裝合計 300」。
✅ Phase D 完成（2026-08-28，12/14）—— 分享碼帶全部分頁，匯出圖印當前那一套。兩件其實都已經寫好了： codec 的 encodeSets() 一直是寫全部的鍵 ＋ 一個 ACTIVE 索引（10,000 份 round-trip 早已涵蓋多套）， 匯出圖抬頭也一直印著 ctx.form?.name。
⚠ 但吃進來那一端有一個真的洞：reconcile() 的分頁鍵過濾在 forms 尚未載入時會把三個形態分頁整批刪掉——而且不進 removed， 所以不跳 toast、沒有 [復原]、畫面一個字都不說，玩家看到的是「貼了碼，三套只剩一套」。 頁面的還原守衛今天擋得住，但那是另一個檔案裡的時序，而 reconcile() 每個動作都會跑， 052-E 的雲端存檔又會再開一條灌入路徑。已補上形態的載入 gate—— 元件（052-D）與模組（052-G）各自都在同一支函式裡留了一行，這是形態的那一份。
另補兩件小的：分享碼旁註明「（含 3 個形態分頁）」（圖上一套、碼裡整份，而收圖的人手上只有這張圖）、 檔名帶形態名（三張同名只會被瀏覽器加 (1)(2)，而那個編號與形態無關）。
實地驗收（本工項明文要求，不可只靠單測）：三分頁各配一套 1,045/3,675 · 1,195/3,375 · 1,925/3,375 → 複製連結 → 全新瀏覽器 context 開啟 → 三頁逐一比對全部相符，activeSetKey 與方案名稱一併還原。
D-3（橫幅）提前到 B 一起出貨：兩處文字與分頁列在同一段 JSX 裡， 分頁列上線那一刻「形態分頁尚在後續階段」就是一句假話。 新的黃字改講「武器／背包／元件／重量出力逐頁分開；機甲／模組／算力四套共用」—— 分頁列講得出「有幾套」，講不出「切過去之後哪些會跟著換」。

✅ Phase E 開發者項目完成（2026-08-28，13/14）—— E-1 不必再寫：它在 B-2 就做掉了。 simReducer.test.ts 的「每一套各自算重量／出力」逐條對上 E-1 開的四個條件 （配對是 A-2 訂正後的先鋒 vs 戰術、四條斷言含 notEqual 與差值 300、 fixture 把背槽各掛什麼寫死在 action 序列裡、兩套都沒裝出力模組）。 本次刻意不為了讓工項有東西可做而補一份重複的測試——兩份斷言會各自漂移， 日後基準改動只有一邊被改到，正是 052-J 的同一類坑。 （E-1 的檔案欄一併訂正：測試在 simReducer.test.ts 不在 loadoutRules.test.ts， 因為要造出「同一份 draft、兩個 key」得先有一份被 reducer 正常建出來的多分頁 draft。） npm test ⇒ 939 則全綠。
⚠ E-2 補上上一輪唯一沒有真正做到的那一項：先前的匯出圖驗收是「攔 a.download 讀檔名」， 沒有人打開過那張 PNG——而 toPng() 會失敗的方式（圖片污染畫布、字型沒嵌進去、 提早放行拍到舊版面）正好都不影響檔名。本次實際下載兩張並開起來看： 2000×2696、2.59MB／2.61MB，真的落到下載資料夾，位元組數與 dataURL 解出來一致； 沒有破圖——立繪、機甲圖、特效與中文字型全部有進圖， 數值 1,925/3,375（戰術）與 1,045/3,675（先鋒）與頁面、與 A-2 基準三邊相符， 兩張檔名確實不同（沒有變成 (1)），console 零錯誤。
⏳ 剩下的 1 項是「站長本人過目」，開發者代不了—— B-1 分頁列的位置就是被站長一句「我找了一陣子才找到」推翻的， 那個問題沒有任何一條測試、也沒有任何一次開發者目視抓得出來。

PLAN-052-G · 模組槽與部件混搭

模擬器僅存的兩塊空白。四個模組接口沒有入口——052-I 畫出來的四部位卡是唯讀的，卡片底下那行「部件混搭開放後，每個部位可換成別台機甲的同位部件」就是在等這個計畫；四個部位固定來自同一台機甲——右欄的四部位表整個被註解掉，註解逐字寫著「等部件混搭開放後，這張表才開始回答『這一套是怎麼拼出來的』」。
地基早就鋪好，工程量不在「造」而在「接」：LoadoutDraft.parts / .modules 兩個欄位、codec v1 的 §PARTS / §MODULES 兩段、resolveChassis() 的 partOverrides 與 moduleLevelOf() 全部已實作且有測試——而全部處於「開了但沒接線」的狀態。而接線正是這個專案最會出事的地方：shareIndexes 的 module 那一行今天傳空陣列，component 剛因為同一個坑漏改了整整三個 Phase，症狀是元件被靜默濾出分享碼、encode 與 decode 兩邊的畫面都不說話，單元測試抓不到（codec 的測試自己建索引），是瀏覽器實地驗收才發現的。A-1 因此把「載入集合」與「接索引」綁成同一個工項。
2026-08-27 直讀正式 Firestore 四輪盤點，修正總綱決策六的四個數字：候選池 186（非 188）、Ⅰ型接口候選 42（非 41）、modules 241（非 242）、不綁機甲 198（非 199）。並發現總綱未點名的 mech.module4Id / module8Id / moduleFixedIds——天生模組住在這裡，而其中 112 顆的 boundMechId 是 null，一度看似會讓已裁決的候選規則撈進「別台機甲的天生模組」。查 source 才確定那不是漏洞而是機制本身：特性模組來源是「拆機甲／商店」、56 筆帶 dismantleMechIds，拆一台機甲把它的特性模組裝到自己機上就是這個玩法。決策六原封不動成立。
另兩處收斂：決策十三的同名消歧義在候選池裡已不存在（唯一的同名對手 mod_2030 是官方廢案、依決策一明著排除），該工項降級為可讀性的效果摘要；新增決策三——moduleAddLevel（31 顆通用模組Ⅱ型為 2、其餘 155 筆為 1）要做，使用者裁決「它就是接口槽的意義」，工作假說為 Σ 四接口決定天生模組等級（S 機四格全Ⅱ型 ⇒ 8，恰好是「8級模組」levels[] 的長度），假說未經實機驗證，E-3 專項驗收，通過前一律標「本站推算」。
⚠ 星夜女神四格全 Ⅰ 型已確認，是 256 格 S 級接口裡唯一的例外（16 台 A 級機甲清一色 Ⅰ／Ⅱ／Ⅱ／Ⅰ），依接口 gate 會變成「一台 S 機只能裝 A 級模組」——疑為 052-A 正規化時的誤改，B-0 回官方對帳。

PLAN-052 · 配裝模擬器改版 · 總綱

現行配裝模擬器的根本問題不是「功能不足」，而是資料模型只有兩個單值欄位（weaponId / backpackId）——連「左手一把、右手一把」都表達不了，更擋住雙肩、備用手、海莉絲的多套形態配裝、以及把元件掛到每一把武器上。本總綱把它換成多槽・多形態・可分享的 Loadout v2，並拆成 A–H 八個可各自出貨的子計畫。
紅隊拿官方整備截圖逐格對帳，發現五份獨立設計一致採用的公式都是錯的：備用武器組不是加總、是取較重者（先鋒形態加總會得 2625，官方 1825，誤差 44%）；機甲火力＝Σ四部位，而 mech.firepower 是爬蟲產物——實測 83 台的頂層值等於單一部位值，也就是站上現在顯示的火力是實際的 1/4；出力是 per-form 的（3675 vs 3375 差的 300 來自強襲者背包）。第四條（weapon.attack 是連擊總和、官方顯示每擊值且差 17–18%）已裁決延後至傷害計算。
落盤形狀拍板為 code-as-payload：users/{uid}/builds/{pilotId} ＋ slots map，每格內容就是一串分享代碼——因為 Firestore 規則沒有位元組長度運算子、不能對動態 key 迴圈、也沒有 count()，巢狀結構在規則層設不了上限；收斂成單一字串後 code.size() <= 1024 才是繞不過的硬牆，而 map key 白名單讓「每機師 5 套」變成結構性事實。儲存＝分享是同一串字，沒有第二套序列化會漂移。
⚠ 時間窗：users 集合實測 0 筆、builds 0 筆，現在改模型零遷移成本；一旦全面公開（已定案）就再也不免費。PLAN-047 由本計畫取代並歸檔——它 0/22 未動工、驗收數字全部過期（mechs 63→90、weapons 172→180），且決策十二①②④（不改 Build 成多槽／不做形態獨立配裝／不做部件混裝）皆已被使用者裁決推翻。

PLAN-050 · 首頁資訊架構重構

源自使用者反饋的兩個問題，追下去發現是同一個根因的兩種症狀：首頁把「離散的檢視選擇」綁在「連續的環境輸入」上，又把三種長寬比需求完全不同的內容塞進同一個 48vw 的框裡。
問題一不是「動畫該用什麼手勢」，是不該有這道門。Hero 裝的是站務履歷與團隊介紹（一次性內容），門後是每週回訪的版本資料——頻率決定版面，現況剛好相反。因此不做「隱晦的左右切換鈕」（隱晦＋必經＝發現性失敗），而是刪掉 scroll-snap 兩頁架構（PLAN-015 的產物，也正是誤觸的結構成因），Hero 降級為首訪展開／回訪收起的頂帶。站長明確表示「動畫不是必要的」「藏進 about 也可接受，功能優先」，故原判為不建議的「Hero 移至 /about」改列可選升級路徑而非否決。
問題二不是空間不夠，是空間花錯地方。實測：甘特＋卡片容器可用高僅 247px 而甘特區塊 532px，scrollHeight 1217px——只有兩成內容在畫面內，卡片流可見高度實測為 0px。更關鍵的是按下「展開版面」把寬度加倍（922→1843px、每週欄 123→277px），垂直預算一格沒變、多露出 0 張卡片：預算被砸在只有 6 個刻度的軸上，而長條的資訊上限是一行截斷文字。寬度不是瓶頸，列數才是。根因是甘特（寬而扁）與卡片流（窄而長）長寬比正交卻共用同一條捲動軸，解法是主從分割成兩條獨立軸。
三個檢視改 routed tabs（/versions/:view）＋導覽列新增「版本情報 ▾」：一次拿到深連結、上一頁與分流統計——現況三個 tab 全記成 /，「Gray Ops 有沒有人看」「行動端佔比多少」目前無從得知，而後者直接決定 Phase C/D 誰先做。故 Phase A 刻意單獨上主站跑 1–2 週收數據再定序。
P0 止血（移除 scroll-snap-stop、補 overscroll-contain、寬度下限 780px）已於 2026-08-19 完成推送，不在本計畫範圍。整個計畫零資料模型變更、不需 bump 版本。

PLAN-049 · 問題回報與功能建議

站上資料由爬蟲蒐集後人工修正，錯誤無法避免，但目前沒有任何回饋迴路——玩家看到錯的數值，除了私訊維護者以外無處可去。2026-08-18 補上的 GitHub issue 模板服務的是「會用 GitHub 的人」，一般玩家不會為了回報一個數值去註冊帳號，預期回報率趨近於零。本計畫做站內表單，涵蓋資料錯誤 / 功能異常 / 功能建議三類，共用一個 feedback 集合與一套狀態機。
拍板一律需登入（訪客看得到入口但不能提交），這個決定的連鎖效應比表面上大——它讓本計畫不需要動用 Cloudflare Worker。與 PLAN-046 使用統計正好是對照組：統計要涵蓋訪客 ⇒ 不能要求登入 ⇒ client 直寫等於 create: if true（任何人可迴圈寫爆額度）⇒ 必須 Worker 代寫；回報要求登入 ⇒ create: if isAuthenticated() && uid 綁定 有身分可追溯 ⇒ client 直寫 + 規則守門即可，省下整個端點。寫入範式直接沿用 systemLog（PLAN-045）已驗證的 append-only + uid 綁定。
回報對象不另發明欄位，直接用既有的 EntityRef——其 RefType 已涵蓋 pilot / mech / weapon / module / backpack / component 等所有可能被回報的實體，於是詳情頁按下回報可自動預填對象（使用者只需填「哪裡錯、正確值是什麼」），後台則用現成 RefChip 渲染成可點連結。feedback 刻意不進 GameDataContext：三層快取是為版本化的靜態遊戲資料設計的，套在隨時被管理員更新的動態資料上只會讓使用者看到過期狀態。
限流正面回應 PLAN-045 決策四的顧慮：第一版只做登入門檻 + 規則層欄位長度驗證 + UI 節流 + 事後封鎖，不做規則層時間窗 rate limit（第二階段設計已備妥，屆時走獨立 feedbackThrottle 集合並強制 lastAt == request.time 使其無法偽造）。⚠ 封鎖標記不能放 users/{uid}/profile——現行規則只擋 role，其餘欄位本人可自由修改，被封鎖者能自己解封，須一併加入禁改清單，這是本計畫唯一動到既有規則之處。最大風險不是技術而是維運：回報堆積無人處理，故「讓回報有下文」的 adminReply 是必做而非加分項。
