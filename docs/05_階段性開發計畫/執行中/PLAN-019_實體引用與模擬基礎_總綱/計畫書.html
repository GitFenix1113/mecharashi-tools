定位
Master Plan（大綱）
一句話：一個實體的描述文字常引用其他實體（如天賦「悖想先驅」內含 [虛粒子形態]、[激發能]、[形態增益]、[粒子爆發]、[海莉絲]）， 但現行 description 都是純字串，系統看不見這些引用。本總綱把引用變成型別化、可解析、可模擬的資料， 並以此為大綱拆出子計畫。
Problem
問題背景 — PLAN-001/003/004/005 的同一個問題
已解決的一半（數值）：PLAN-001 已用 SkillEffect[]（stat/value/scope/condition）、 GameBuff（buffs 集合）、buffIds[] 表達技能的「可計算數值」。PLAN-003/005 補上武器側與專武強化。
未解決的一半（引用關聯）：description 內 [xxx] 這類跨實體連結被困在字串裡。 系統無法把它變成可點擊、無法驗證引用是否存在、無法在模擬器中把它當成語義邊處理。 PLAN-010 Phase B 其實發明了 EntityReference 解法（entityType+entityId、批次預載、點擊→Drawer）， 但只用在攻略文章。本總綱把它一般化到所有 description。
更深一層（使用者澄清）：引用不只是「顯示連結」。天賦/技能延伸的特殊效果， 可能是既有屬性（增傷/加子彈/加暴傷）、可能是特殊 BUFF、也可能是機師專屬的型態切換。 未來傷害模擬最合理的做法，是讓使用者設定的模組/機甲/機師去觸發特定 BUFF， 才不會發散出「不可能存在」的組合。因此抽象化比單純顯示更重要。
Architecture
核心架構：四層抽象
Layer 1 — 統一型別化引用 EntityRef（輕量、表單友善、可升級）
不把 description 改成節點樹（採「先表單」路線）。description: string 維持遊戲原文唯一真相 （[xxx] 標記原樣保留，符合 PLAN-005「原文不動」），外掛一份解析側錄 descriptionRefs。 顯示層寫一個 <RefText> tokenizes [xxx] → 查表命中渲染可點擊（點擊開 Drawer，複用 PLAN-010）； 未命中原樣顯示，優雅降級。日後換 TipTap 時，節點 attrs 即是 EntityRef，資料零浪費。
// src/types/index.ts —— 已落地 export type RefType = | 'buff' | 'skill' | 'pilot' | 'mech' | 'weapon' | 'module' | 'backpack' | 'component' | 'stat' | 'term' | 'neuralDrive' // 🆕 PLAN-023 指向 neuralDriveAbilities | 'form' // 🆕 PLAN-041 指向 forms 機師形態 export interface EntityRef { refType: RefType refId: string // buffs/{id}、pilots/{id}、glossaryTerms/{id}，或 stat key 'dmg' label?: string // 顯示文字；預設取目標 name level?: number // 🆕 PLAN-034 指定階梯 buff 的級別 fixedLevel?: boolean// 🆕 PLAN-034 鎖級，不吃神驅算力覆寫 } // description 內 [xxx] → 對應實體。key = 括號內文字，如 "虛粒子形態" export type DescriptionRefs = Record<string, EntityRef>
為何「混合」而非單一詞條庫或純型別化： 增傷/加子彈/加暴傷 = refType:'stat'（既有屬性 key）；特殊增益/狀態 = 'buff'； [海莉絲] = 'pilot'/'mech'；[固定傷害] 這種無數值歸宿的機制關鍵字 = 'term'（glossaryTerms）。 一個 resolver 依 refType 分派；glossaryTerms 只收「無專屬集合可放」的關鍵字。
2026-08-22 現況：Layer 1 已完全落地並持續長大。RefType 由原設計 10 種擴為 12 種 （PLAN-023 加 neuralDrive、PLAN-041 加 form），另有兩個待做的擴充掛在其他計畫下： summon（PLAN-026）與 backpackSkill（PLAN-043 N2）。
引用 token 本身也長出第二種：PLAN-022 的 數值引用 <refId.attr>（含 PLAN-024 的 .lvN 段），與 [xxx] 實體引用同用一套 <RefText> 解析迴圈。
DescriptionRefs 的 key 語意也由 PLAN-039 補上同名消歧 （"駐陣|skill" 後綴），舊資料不需遷移。 ⚠ 新增 RefType 值要補的窮舉消費端共 5 檔 6 處，完整清單維護在 src/types/common.ts 的 RefType 註解上。
Layer 2 — BUFF / 形態 的模擬可達性圖（抽象優先） 2026-08-22 訂正
⚠ 原設計的「形態」機制已作廢，勿照本節舊文補資料。 本節原本規定：形態（型態切換）= GameBuff with buffType:'state' + mutexGroup:'<pilotId>_forms'，同群一次只能存在一個。 PLAN-041 實測發現 全庫 0 筆 buff 曾經填過 mutexGroup——這套引擎從上線到被拆為止一次都沒渲染過， 卻仍在 BuffAdmin 誘導維護者把形態建到錯的地方。因此整套已被移除： GameBuff.mutexGroup 欄位、reachableBuffs 的 FormGroup 收斂、SimulatorPage 的 activeForms、 BuffAdmin 的互斥群組選擇器，全數刪除（見 src/types/buff.ts 的刻意留註）。 形態改由 PLAN-041 的獨立 forms 集合承載，日後真要做形態互斥應以 forms 為準，不要把 mutexGroup 找回來。
仍然成立的核心（Layer 2 的真正價值）：觸發來源圖 = 沿用既有 buffIds[] 作為唯一真相的「賦予邊」：凡會產生 BUFF 的 技能/天賦/神經驅動/模組/武器/背包技能，其 buffIds[] 即宣告「我能賦予這些 buff」。 模擬器建立反向索引，可用 buff = 當前配裝所有實體 buffIds[] 的聯集 —— 只有「來源在配裝中」的 buff 才會出現， 這條杜絕不可能組合的規則未受影響。引擎為純函式 src/utils/buffPool.ts + reachableBuffs.ts（附單測）。
收斂機制（現況，PLAN-024 + PLAN-041 後）：原規劃的「兩種分立互斥機制」現在只剩一種——
① mutexGroup 形態互斥 → 已移除（PLAN-041，改走 forms）；
② 同 buff 多 level：階梯取最高（PLAN-024 把「同概念多階梯 buff」由「N 份文件 + 共用 mutexGroup」改為「單一文件 + levels[]」，天然互斥；buffIds 以 id@N 賦予指定級）。
另有 excludeFromPool（標在 utils/entityRefs.ts 的 buffIds 站點上，不是標在 buff 本身）：形態站點是戰鬥期狀態、神驅 buffUpgrades 是「升階」而非「賦予」，兩者收進 buff 池會誤判「無條件可達」，故於 runSpec 內強制排除。
// GameBuff 現況（src/types/buff.ts） export interface GameBuff { // ... 既有：id/name/description/icon/buffType/maxStack/duration/effects ... descriptionRefs?: DescriptionRefs levels?: BuffLevel[] // PLAN-024 階梯各級；同 buff 多 level 天然互斥取最高 // ⚠ 刻意**沒有** mutexGroup —— PLAN-041 移除，形態改走 forms 集合 } // Module 擴充：補上 buffIds（武器/技能/天賦/神經驅動已有） interface Module { /* ... */ buffIds?: string[] }
模擬器可達性流程（現況）： 使用者配裝 機師 + 機甲 + 模組×N + 武器 + 背包 │ 收集各實體的 buffIds[]（可帶 @N 指定階梯級） ▼ 可用 buff 池 = ⋃ buffIds[] ← 只有「來源在配裝中」的 buff 才會出現 │ 收斂：同 buff 多 level → 取最高 │ 排除：excludeFromPool（形態 / 神驅 buffUpgrades） ▼ 使用者勾選 active → SkillEffect[] 依 stat 加總 → Buff 面板輸出 │ └─ 最終「傷害數字」不在本總綱範圍 → 未來傷害模擬 PLAN（見 docs/02 傷害公式）
Layer 3 — BOSS / 關卡資料模型 2026-06-28 descope → 移轉 PLAN-010
已 descope（不在本計畫實作）：BOSS 機制／關卡打法為各關獨特的敘事內容、可重用的結構化引用（重複 BUFF）相對少，把它建成 bosses/stages 結構化集合的投報率低。 決定整層移交 PLAN-010 攻略系統——以攻略 CMS 自由圖文撰寫各關打法、用 Phase B 實體嵌入承載偶發 buff 卡片。 掉落索引 src/data/bossDrops.ts 維持現狀（續餵 BossDropTooltip 顯示元件掉落來源），不遷移、不建集合。下方原始設計保留作歷史參考。
（原始設計，已 descope）現行 src/data/bossDrops.ts 是靜態的 元件→關卡→掉落索引。一般化為 Firestore 集合 bosses / stages，並複用既有結構（ArmorType、MechPart 數值面、SkillEffect、EntityRef）。 BOSS 技能描述同樣吃 Layer 1 引用層 → 零額外機制即可點擊查詞條。遷移保留相容檢視函式給現有 BossDropTooltip。
// bosses/{id}、stages/{id}（已落地型別） interface Boss { id; name; armorType?; parts?; skills: BossSkill[]; descriptionRefs?; weakness?[] } interface Stage { id; name; category; bossIds: string[]; mechanics?; mechanicsRefs?; drops?: StageDropEntry[]; guideIds?: string[] } // guideIds → PLAN-010 攻略

Verification

  1. 型別：npm run build（tsc -b && vite build）通過；新欄位皆選填不破壞既有頁面。
  2. 引用層：天賦填 descriptionRefs（"虛粒子形態"→{refType:'buff',refId:'buff_虛粒子形態'}），前台該詞可點擊開 Drawer；未填的詞原樣顯示不報錯。

  6. 維護者流程：非 OWNER 的 ADMIN 帳號用表單 + 詞條挑選器新增 glossaryTerm 並在前台引用，全程不碰程式碼。
