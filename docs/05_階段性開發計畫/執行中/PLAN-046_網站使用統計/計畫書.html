Problem
問題背景
問題一：只看得到 Firestore 用量，看不到「誰在用哪一頁」
目前唯一的觀測手段是 Firebase 主控台的讀寫次數統計。它能回答「花了多少額度」，但完全無法回答 「哪些頁面有人用、哪些沒人用」——而後者才是決定改版投資順序的依據。 站上已有 20 餘個前台頁面與大量待補資料，優先序目前全憑直覺。
問題二：PLAN-029 的中國訪客策略成效無從驗證
為了中國訪客，PLAN-029 做了 Worker 同源代理、字體自託管、邊緣 SPA 改寫，投入不小。 但至今沒有任何數據能證明它有沒有效——只能說「應該有用吧」。 request.cf.country 是 Worker 白拿的欄位，一個維度就能給出答案。
問題三：Firestore 寫入額度長期閒置
本站是讀多寫極少的資料站，每日寫入額度（免費 20,000）幾乎沒用到。 統計是少數能把這份閒置資源轉成決策資訊的用途。
⚠ 為什麼不能靠既有的 Cloudflare 請求日誌反推
本站的兩項架構優化剛好讓被動日誌結構性地測不準：
① SPA 路由不產生伺服器請求——使用者從 /pilots 點進 /pilots/ada，瀏覽器一個請求都沒發；
② 三層快取讓資料請求與瀏覽次數脫鉤——回訪使用者整場 session 可能發出 0 次 /api/data（見 CLAUDE.md §6.2），Worker 邊緣快取再吃一層。
結論：必須主動埋點，沒有捷徑。快取做得越好，被動日誌越測不準。
Design
設計決策
決策一：自建，不用 GA4（Q1 裁決）
三個本站特有條件讓 GA4 不划算：
① 中國訪客完全統計不到——googletagmanager.com 牆內不可達，等於用一把測不到目標客群的尺；
② 廣告攔截器預設封鎖，遊戲工具站使用者裝機率偏高；
③ entity 級（哪個機師最熱）仍要自己埋自訂事件，設定成本不低於自建。
自建走同源 /api，攔截器擋不掉、中國訪客照樣統計得到。
另平行開啟 Cloudflare Web Analytics 作為免費對照組（Phase C-1），但它同樣可能測不到中國訪客，只能回答總量趨勢。
決策二：三層識別碼去重，閒置窗口 10 分鐘（Q2 裁決）
層存放生命週期擋掉哪種重複
visitorIdlocalStorage永久同一人今天已算過一次 UV
sessionIdlocalStorage + lastActiveAt10 分鐘閒置或跨午夜界定「一次造訪」＝去重的作用域
已報頁面 SetlocalStorage（隨 sessionId）隨 session同一 session 內同一頁只計一次 UPV
· sessionId 放 localStorage 而非 sessionStorage：後者每個分頁一份，開三個分頁比較機甲會被算成三次造訪。
· 已報頁面 Set 必須持久化，否則 F5 重整就重新計數；並設 50 筆上限防止無限成長。
⚠ 決策二連帶：「閒置」必須由活動訊號判定，不能只看路由變更
10 分鐘窗口下，若只把「換頁」當活動訊號，認真讀一頁 12 分鐘的人（慢慢調配裝、逐條看天賦）會被判定閒置 → sessions 灌水，且該頁去重被重置，UPV 往 PV 漂回去，反而削弱原本要的去重效果。
做法：lastActiveAt 由路由變更、click、keydown、scroll（後三者節流 60 秒，只寫 localStorage、不發任何網路請求）、 visibilitychange → visible 共同刷新。
語意即為站長原意：「真的離開 10 分鐘沒動作，回來才算新的一次查詢」，而非「10 分鐘沒換頁就算走了」。
決策三：PV 與 UPV 雙軌並存（Q2 裁決）
兩者存在同一份文件的相鄰欄位，成本完全相同（不多一次寫入），而比值本身就是資訊： PV / UPV 越高代表該頁被反覆折返查看，通常意味「資訊沒一次給足，使用者要跳來跳去比對」。 機師列表 ↔ 詳情頁若比值特別高，就是改版訊號。
決策四：資料經 Worker /api/collect 寫入，前端不直寫 Firestore
訪客也要記 → 直寫就得開 allow create: if true，後果：任何人可用迴圈寫爆共用額度、數字可任意灌水， 且與 PLAN-029「真鎖直連、只留 Worker 一扇門」的方向牴觸。
走 Worker 則白拿既有基礎設施：service account、同源 /api、antiScrapeBlock() 反爬守門、 request.cf.country / asn。IP 只在邊緣用於判定，絕不落地。
⚠ 決策四的兩條不可妥協鐵律（本計畫最重要的安全約束）
此舉讓 Worker 從「100% 唯讀」變成「有一條匿名可觸發的寫入路徑」。service account 本來就有完整寫入權限， 新增的不是權限而是觸發它的路徑——在此之前 Worker 有漏洞最壞是資料外洩，之後最壞是資料被寫壞。
// 鐵律① payload 絕不參與決定「寫哪一份文件」 const docPath = `analyticsDaily/${todayKeyUTC()}` // ← 伺服器時間算出來的 // ✗ const docPath = `analyticsDaily/${body.date}` ← 絕對不可以 // 鐵律② 欄位路徑一律由程式碼組出，payload 只能提供「數字」 { fieldPath: 'pv', increment: clampInt(body.pv, 0, 200) } // ✗ 不可把 body 的字串直接當 fieldPath —— 那等於讓任何人指定要改哪個欄位
只要這兩條成立，攻擊者能造成的最壞後果被限縮為「統計數字變髒」，不會碰到 pilots / mechs / users 任一集合。
決策五：預聚合文件，不存原始事件流
原始事件流（一次瀏覽一份文件）看一個月報表要數萬 reads、寫入量與流量線性成長； 預聚合則是看 30 天＝30 reads、儲存約 1.8 MB／年，可永久保留不需 TTL。
// analyticsDaily/{YYYY-MM-DD} —— 一天一份，只增不減 { date: '2026-08-08', pv: 1240, upv: 820, sessions: 210, visitors: 168, byRoute: { pilots: { pv: 190, upv: 96 }, pilot_detail: { /* … */ } }, byAuth: { guest: 145, user: 65 }, byDevice: { mobile: 130, desktop: 75, tablet: 5 }, byCountry: { TW: 120, CN: 48, HK: 22, other: 20 }, // ← Q5 裁決納入（網路位置） byLang: { zh_tw: 90, zh_cn: 55, en: 48, ja: 9, other: 8 }, // ← 決策十一（受眾語言） byRef: { direct: 150, google: 30, bahamut: 18 }, writes: 210, // ← 熔斷器的燃料表（決策七） truncatedAt: null, // ← 熔斷發生時間，儀表板據此標示資料不完整 updatedAt: Timestamp } // analyticsEntity/{YYYY-MM} —— 高基數資料拉長到月粒度，避免撐爆日文件 { month: '2026-08', pilots: { ada: 320, … }, mechs: {…}, weapons: {…}, modules: {…} }
· 容量：entity 約 40 B／key，四類合計 1,500 個 id 也僅約 60 KB，遠低於單文件 1 MiB 上限。
· 路由 key 必須消毒：Firestore 巢狀欄位路徑以 . 分隔，含 / : 的字串會被誤解析；/pilots/:id 須轉為 pilot_detail。
· 用「路由樣板」而非實際網址，否則 map 會長出上百個 key；個別機師熱度另存 entity 文件。
· 單文件持續寫入軟上限約 1 次／秒；本設計每 session 才寫一次，日 session 數穩定超過 5,000 再考慮分片（現在做是過度設計，但程式碼要留註解說明門檻）。
決策六：一個 session 離站時批次寫一次
寫入量與「逛幾頁」完全脫鉤——逛 5 頁還是 50 頁都是同一次寫入。以 1,000 sessions／日估約 1,500 writes／日。
flush 時機：visibilitychange → hidden（主力，行動裝置上唯一可靠）、pagehide（桌機補強）、 每 5 分鐘定時（防長時間停留資料全丟）、session 換手時。
不用 beforeunload——iOS Safari 不可靠。 送出用 navigator.sendBeacon ＋ text/plain Blob（屬簡單請求，不觸發 CORS preflight）； 失敗則進 localStorage 佇列下次補送，佇列直接沿用 PLAN-045 的 src/lib/diag/queue.ts 模式。
決策七：寫入預算熔斷器 ＋ kill switch（站長追加要求）
站長為 Blaze 方案，額度耗盡不會停擺、小額超支可接受，但要求單日計數超出免費寫入額度時自動暫停。
做法：analyticsDaily 這份文件本來每次就要寫，順手加一個 writes 欄位自增，它就是當日寫入次數的權威來源—— 不需要 KV、不需要 Durable Objects（後者要付費方案）、不需要任何新服務。
const DAILY_BUDGET = Number(env.COLLECT_DAILY_BUDGET ?? 50000) // ↑ 取向已於 2026-08-08 調整：從「省錢優先(15,000)」改為「資料完整優先(50,000)」。 // 理由見下方 warning-block —— 低預算會在最該量測的那一天把資料切斷。 // isolate 層級快取（多 isolate ⇒ 近似值，對熔斷器足夠） let cache = { dateKey: '', known: 0, knownAt: 0, localSince: 0 } const est = cache.known + cache.localSince // 自適應回查頻率：<50% 預算查 10 分鐘一次、<80% 查 2 分鐘、逼近時 30 秒 // 正常情況約 1,440 reads/日（10 isolate × 144 次），佔免費讀取額度 2.9% if (est >= DAILY_BUDGET) return new Response(null, { status: 204 }) // 熔斷：安靜丟棄
四層防線：① Cloudflare Rate Limiting（WAF 層，早於 Worker，被擋下的請求不消耗 Worker 請求額度） → ② Worker payload 驗證 → ③ 寫入預算熔斷器 → ④ COLLECT_ENABLED=false kill switch（改一個 secret、不用 deploy）。
損失上限＝當日統計資料；絕不損失網站可用性、遊戲資料、後台編輯能力。
⚠ 熔斷預算的取向：低預算會在最該量測的那一天把資料切斷（2026-08-08 修訂）
站長補充：維護夥伴願意共同分擔費用，小額超支不是問題。這讓「省額度」不再是首要目標，而暴露了低預算設定的真正缺陷—— 熔斷會在流量暴增日觸發：中國宣傳鋪開、被大站轉發、遊戲改版當天…… 那些正是你最想知道「多少人來、他們看什麼」的日子，卻剛好是資料被切斷的日子。
費用面完全不構成理由：Firestore 文件寫入約 US$0.18／10 萬次， 就算單日衝到 50,000 次寫入（＝現況的 250 倍流量），超出免費額度的部分也只有約 US$0.05。
因此改為：預算提高到 50,000，第一道通知改用 Firebase 用量告警（設在 20,000）， 熔斷器退居「防惡意攻擊的最後防線」。 告警讓你「知道並決定」，熔斷讓你「不知不覺失去資料」——順序不能顛倒。 若日後偏好回到省錢優先，改 COLLECT_DAILY_BUDGET 一個環境變數即可，不需改程式。
⚠ 熔斷之後不能讓數字默默說謊
最危險的不是熔斷，是「熔斷了但報表看不出來」——某天下午三點熔斷、之後資料全丟，儀表板卻照樣畫出完整曲線， 你會拿一個看起來正常但少了半天的數字去做決策，這比沒有統計更糟。
因此：熔斷時放行最後一次寫入記下 truncatedAt；儀表板讀到就把該日資料點改為紅色虛線並標註 「當日統計於 HH:MM 因寫入預算熔斷而中止，數字不完整」；趨勢圖與 TOP N 自動排除被截斷的日子。
決策八：Worker 端不放頁面白名單 —— 避免重演 PLAN-043 事故
workers/src/index.ts 的 ARRAY_COLLECTIONS 上方有一段血淚註解：漏一個 key 的症狀是該集合在 正式站回 404 而本機完全正常，PLAN-043 就是這樣漏掉 backpackSkills（本機、模擬器、build、測試全綠，上線才炸）。
若 /api/collect 也放一份頁面 key 名單，就是原封不動再造一次同樣的陷阱，而且更難發現——它不報 404，只是數字少了。
改用無名單防護：驗格式與數量，不驗身分。
const KEY_RE = /^[a-z][a-z0-9_]{0,39}$/ // 格式：小寫英數底線，≤40 字 Object.entries(body.byRoute ?? {}) .filter(([k]) => KEY_RE.test(k)) // 格式不合 → 丟這一筆，不是丟整包 .slice(0, 50) // 單包最多 50 種頁面 .map(([k, v]) => ({ k, pv: clampInt(v.pv, 0, 200), upv: clampInt(v.upv, 0, 50) }))
名單式防護問「這個 key 合法嗎」→ 需要知識 → 需要同步 → 會腐化； 格式式防護問「這個 key 會不會造成傷害」→ 不需要知識 → 永遠不用改。
代價僅是報表可能多一列看得懂的雜訊（不會撐爆文件，有數量上限），後台用前端 ROUTE_LABELS 對照，對不到的歸「其他」。 把不同步的後果從「資料遺失」降級成「顯示雜訊」。
決策九：頁面 key 自動推導 ＋ 測試把關，杜絕靜默失敗
key 由 useMatches() 的路由樣板自動推導（新增頁面 +0 行）， 並寫一支 node --test 斷言「App.tsx 的前台路由集合 ⊆ 統計標籤表」。
效果：忘記登記新頁面 → npm test 直接紅並指名是哪條路由 → pre-push hook 擋下，不可能靜默上線。 把最糟的失敗模式（幾週後看報表才發現某頁一直沒統計）轉成 build 期錯誤。 專案已有 node --test 基礎設施，不需新工具。
決策十：不記錄個別登入使用者（Q4 裁決）
只保留 guest / user 加總，看不出是誰。站長理由：要看的是全站統計，個別 USER 行為並非重要資訊。
連帶好處：整個方案不產生任何可識別個人的行為資料，隱私敘述 「本站只統計匿名彙總數字，不記錄任何個人的瀏覽紀錄」字面上為真，不需要任何但書。
決策十一：加入「瀏覽器語言」維度 —— byCountry 單獨無法描述本站受眾（2026-08-08 追加）
站長補充的受眾實況推翻了原本「有 byCountry 就夠」的假設： 本站主要客群是國際服（EN）與中國（CN）玩家，台港澳反而少數。而
維度量到的是對本站的失真
byCountry
request.cf.country		網路位置 高 ①「EN 服玩家」不是一個國家——他們散布在 SEA／NA／EU，會被拆成十幾個小數字，看不出這是同一群人；
② CN 玩家常經 VPN／代理，顯示為 US／JP／HK，系統性低估 CN
byLang
navigator.language		使用者的閱讀語言 低 直接對應站長心中的分群方式（EN／CN／TW），且不受 VPN 影響
分桶為 zh_tw / zh_cn / zh_other / en / ja / ko / other——低基數 map，與其他維度同一次寫入，成本為零。 兩個維度並存互補：byCountry 看「連線從哪來」（驗證 PLAN-029 的邊緣可達性）， byLang 看「誰在讀」（驗證受眾組成）。
◈ byLang 的衍生價值：把語言門檻的軼事變成可決策的數字
站長訪談得知：EN 使用者認為本站設計較好，但因閱讀難度仍傾向使用另一位作者的 EN WIKI（純網頁翻譯體驗差）。 這目前是軼事，無法回答「值不值得投入 i18n」這種昂貴決策。
byLang = en 的訪客配合頁／造訪與單頁跳出比例，可以量化三件事：
① 有多少 EN 使用者真的來了；② 來了之後逛多深（若明顯低於 zh 使用者 → 語言門檻確實在勸退）； ③ 他們停在哪一頁（若集中在數值表格頁 → 或許只需翻譯欄位標籤，不必全站 i18n）。
註：_local-notes/ 目前沒有任何 i18n 評估文件，代表這題尚未開始評估。本維度正好為它準備前置資料。
刻意排除的流量： 所有具後台存取權的角色（ADMIN／OWNER，以及 PLAN-042 規劃中的 EDITOR）、/admin/* 路由、 import.meta.env.DEV（順帶解決 StrictMode 雙跑）、 localStorage['analytics_optout'] === '1'、 navigator.webdriver 與 document.prerendering。
⚠ 這在小流量站是嚴重問題而非小事： 目前日均僅約 93 次造訪，站長與維護夥伴若各自每天巡站看幾十頁， 就足以構成 10–20% 的噪音，且會系統性地把「後台編輯者常看的頁面」推上熱度排行—— 那正好是最不該影響改版決策的偏差來源。角色判定必須用白名單以外全部排除的寫法， 日後新增角色不會漏掉。
Scope
實作範圍與不在範圍內
在範圍內：
  • Phase A（先做）：session／去重模組、usePageTracking、Worker /api/collect、 firestoreRest 寫入能力、寫入預算熔斷器、Firestore 規則、Cloudflare Rate Limiting 設定
  • Phase B（兩週後）：後台 /admin/analytics 儀表板——總量卡片、每日趨勢、頁面熱度、 訪客組成（登入/訪客・裝置）、國家分布、熱門機師／機甲／武器 TOP N（Q3 已併入第一期範圍）
  • Phase C：Cloudflare Web Analytics 對照組、兩週後的資料驗收
不在範圍內：
  • 個別使用者行為追蹤（Q4 已裁決不做）
  • 路徑分析、留存曲線、A/B 測試、即時看板——個人專案規模下這些數字不會改變任何決定
  • 停留時間估算——SPA 下算不準，寧可不給假數字
  • 引進圖表函式庫——為幾張長條圖付出約 100 KB gzip 不划算，對中國訪客載入成本尤其不利；手刻 CSS 長條 ＋ 簡單 SVG 折線
  • 計數器分片（sharding）——日 session 數穩定超過 5,000 再說，現在做是過度設計
  • 把熔斷事件寫進 systemLog——該集合規則要求 uid == request.auth.uid 而 Worker 沒有 auth context， 不值得為記一筆 log 去動已穩定的稽核規則；用儀表板標註即可
◈ 實測基準線（2026-08-08，Cloudflare Web Analytics 已運行 14 天）
過去 24 小時：造訪 93 次 · 頁面瀏覽 397 次（約 4.3 頁／造訪）。以此推算 PLAN-046 上線後：
項目推算值額度佔比
每日 session 數（10 分鐘閒置切分後略高於 CF 的「造訪」）約 110–150—
每日 Firestore 寫入（一 session 一寫 ＋ 中途 flush）約 150–220免費 20,000 的 ~1%
每日新增 Worker 請求約 150–220免費 100,000 的 ~0.2%
後台儀表板讀取約 32 reads／次開啟免費 50,000 的 <0.1%
結論：自然流量要成長約 90 倍才會碰到 Firestore 免費寫入額度，約 400 倍才會碰到 Workers 請求額度。 正常使用不可能把額度灌爆，熔斷器純粹是防惡意攻擊與意外暴衝的保險。
⚠ Workers 請求額度：風險真實，但今天就已經存在，不是本計畫帶來的
已確認站長使用 Workers 免費方案（100,000 requests／日，超出後回 Error 1027 至 UTC 午夜重置）。 /api/collect 與 /api/data、/api/versions 共用此額度。

但關鍵事實是：任何人現在就能用 curl 猛打 /api/data 燒掉這 100k。 antiScrapeBlock() 雖然會回 403，但 Worker 已經執行過了，請求照樣計數。 因此 /api/collect 不是新增一類風險，只是在已暴露的攻擊面上多一個端點—— 真正的防線是 zone Rate Limiting，而那件事與統計無關、本來就該做。

PLAN-029 Step 4 已規劃過這條規則（starts_with(http.request.uri.path, "/api/")、60 req／分／IP、Block）， 若當時已建立，/api/collect 自動被涵蓋、無須新增規則（Free 方案僅含 1 條 Rate Limiting 規則，共用路徑條件正是當初這樣寫的原因）。 A-6 只需確認它確實存在並生效。
補充：60 req／分／IP 換算單一 IP 上限約 86,400 請求／日，仍接近 100k。若日後真的遭遇持續攻擊， 把上限調到 30 req／分（約 43,200／日）即可留出一半餘裕；現階段不必預先調整，以免誤傷首訪使用者（首訪約需 13 次 /api 請求）。
