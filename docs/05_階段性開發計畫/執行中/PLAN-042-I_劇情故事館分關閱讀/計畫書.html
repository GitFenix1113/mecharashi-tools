◆ PLAN-042-I

劇情故事館分關閱讀 一關一頁 · 常駐關卡列 · 下一關 · 閱讀進度

Problem
問題背景
一章一條長捲軸，目錄只在頁頂
現行 StoryBookPage 把整章所有關卡一次畫出、三段預設全展開（最長的兩章是 1,850 行與 1,917 行）。 關卡目錄是頁頂的一排膠囊，不會黏住：讀完 Chapter-I 的 1-3 想跳 1-5，要先往上捲約 4 個螢幕回到目錄再點。 捲動時看不出目前在哪一關；讀完一關沒有「下一關」；離開再回來要重找。
目錄雜訊：「22 關」裡有 15 場是遭遇戰
主線的關卡數包含沒有編號的遭遇戰／突襲戰（WayPointType 3）。Chapter-Ⅳ 標「22 關」，其中正關只有 7 個、遭遇戰 15 場，膠囊目錄全部平鋪。
正文底下壓著館內底圖
.lore-shell 的 bg-paper.webp（官網切版：MECHARA 浮水印與建築線稿）直接墊在對白底下，長時間閱讀的對比偏低。
主線關卡長度（260 關）中位數九成以內最長
每關對白行數40159393

一關約 1–4 個螢幕，天然適合當「一頁」；最長的一關也不需要再分頁或收合。

Design
設計決策
決策一：一次一關，關卡寫在網址路徑上 /lore/story/:id/:part
（實作註：原稿寫 :stage。App.tsx 明訂故事館路由參數一律 :id／:part——entityHits 依參數名讀值——所以沿用 :part，網址形狀不變。）
沿用機師館與機甲館章節 /lore/pilots/:id/:part 的慣例。:stage 是關卡 key（w108／l…／m…），取自遊戲設定 ID，改版重跑匯入也不會變。 用路徑而不用錨點，是為了直接套用 LoreLayout 現成的「換 pathname 就捲回頂端、按返回就還原捲動位置」（決策 (I)），本頁不必自己 scrollIntoView。 目前在哪一關由網址推導（純衍生值），元件不持有 activeIndex state，這是 PLAN-050 與 LoreChapterPager 共用的規則。 路徑仍在 /lore 前綴下，不必動 Cloudflare 白名單；但 seo.ts 要登記頁名，並決定進不進 sitemap（測試會擋）。
決策二：書根 /lore/story/:id 就是第一關，不做扉頁；有進度只提示、不自動跳
完整書頭（章名、簡介、互相參照）只放在第一關上方，其餘關只留精簡書頭（書名＋關卡碼）。從館首頁點進來不會多一步。 讀過的書在書根頂端出現提示列「上次讀到 3-5 機修師的尊嚴 → 繼續」，但不自動跳轉，免得想從頭讀的人被帶走。
決策三：關卡列用手風琴收納，不開第二層垂直捲動（地雷 M-08）
全部攤開的話，最長的一本要 28 列（event-20：5 幕＋23 關），768px 高的桌機放不下。收納規則：
  • 遭遇戰／突襲戰縮排掛在前一個正關底下，只展開目前所在的那一組，其餘正關後面標「＋2」這類數字。
  • 支線另外歸成一組，加上「支線」標題。
  • 活動分幕（stage.group）只展開目前那一幕。
收納後主線最多約 13 列，桌機視窗放得下，關卡列不必自己捲動。關卡列只在 ≥ 1024px 出現，用 position: sticky 黏在館內唯一的 scrollport .lore-scroll 裡。
（實作追加：沒有分幕的長串也會超出——event-8 有 22 個正關，攤開 808px，大於 1366×768 的 scrollport 722px。 因此不分幕、超過 14 列的段切成「1～10」「11～20」一截一截，只展開目前那一截。storyNav.test.ts 對全部書、每一關斷言 ≤ 20 列，實際最多 15 列。）
決策四：換關只接「明確意圖」的輸入：按鈕、← →、水平滑動；不接滾輪
照 LoreChapterPager 的規則，絕不劫持滾輪：館內只有一個 scrollport，吃掉滾輪會讓人在正文中段捲著捲著突然跳關。 ← → 沿用 PilotLorePage 全域鍵盤的分流方式，並排除輸入框。水平滑動的門檻是位移 48px、水平分量要比垂直大 1.5 倍以上，而且不 preventDefault。
（實作註：同一本書內換關用 replace、跨到隔壁那一本用 push——照 LoreChapterPager「章節之間用 replace」的慣例；一本二十幾關，用 push 的話上一頁要一關一關退回去。）
決策五：閱讀進度只存在本機 localStorage
記錄「上次讀到哪一關」與「哪幾關讀完」，關末出現在畫面上就算讀完。這是個人便利功能：不花 Firestore read、不必登入； 讀不到時（無痕視窗、資料被清除）就當沒讀過，頁面照常運作。鍵名沿用站內 mecharashi_* 前綴，所有讀寫都包 try/catch。跨裝置同步不在本案。
決策六：三段（開場／戰鬥中／結尾）改成段落小標，不再用 <details> 收合
單關最長 393 行，不需要收合，「全部收合／展開」按鈕一起拿掉。 .lore-story-stage 的 content-visibility，以及目錄跳轉時「多等兩個 frame 再補捲一次」的補丁，都是為了整章長頁才加的，單關模式下一併移除（若決策八保留整章模式，就只留在整章模式裡）。
決策七：閱讀欄改實心紙面，順手做兩個排版小修
閱讀欄沿用 .lore-sheet 的做法（紙紋上蓋 0.86 不透明的紙色），浮水印與建築線稿不再壓在字底下；行寬 ≤ 760px。 StoryLines 的兩項小修：同一人連續發言時省略名字（遇到戰中分隔就重新顯示），手機上能省下大量垂直空間；戰中觸發之間的虛線分隔改成淡點線。
決策八（待定）：要不要保留「整章連續」檢視
單關模式的代價是沒辦法在整章裡 Ctrl+F，也不能一口氣捲完整章。模擬頁有「單關／整章連續」切換可以比較。 本案把它列為選配 D-1，等 B 段驗收後由站長決定。要做的話路徑用 /lore/story/:id/all（all 不會跟 w／l／m 開頭的關卡 key 撞名），關卡列改成跟著捲動位置高亮。
舊連結相容
現行書頁用的是 #w108 這種頁內錨點，可能已經被分享出去。書根收到錨點時，以 replace 導向 /lore/story/:id/w108；不認得的 :stage 一律以 replace 回到書根。
Scope
實作範圍與不在範圍內
在範圍內：
  • 關卡路由、舊錨點相容、頁名與 sitemap 登記；分頁標題改成「1-3 全頻道阻塞｜日沉谷日沉 劇情」
  • 純函式 storyNav.ts（關卡列結構、上一關／下一關，含跨書）與 storyProgress.ts（本機進度），各附 node:test
  • 單關閱讀畫面、桌機常駐關卡列、關末導覽、← → 與水平滑動、手機底部換關列＋共用 BottomSheet 關卡清單
  • 閱讀進度：繼續閱讀提示列、關卡列已讀標記、館首頁卡片顯示「已讀 N／M」
  • 閱讀欄紙面、連續發言省略名字、戰中分隔改淡點線
  • 文件：故事館頁面規劃、更新履歷、PLAN-042 總綱子計畫表
不在範圍內：
  • 方案 C 場景條＋說話者頭像：要改 import-story.mjs，並匯入約 140 張劇情 CG。評估報告建議接在本案之後，另開子計畫。
  • 方案 B 選章舞台（音遊選曲式換章）：建議放在方案 C 之後，因為它的底圖沿用方案 C 匯入的 CG。
  • src/data/story/ 書檔與 scripts/import-story.mjs：本案一行不動。
  • 閱讀進度跨裝置同步（要進 Firestore 並綁帳號）。
  • 整章連續檢視：見決策八，列為選配 D-1，等站長決定。
