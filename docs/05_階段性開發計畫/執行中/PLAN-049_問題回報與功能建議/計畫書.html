◆ PLAN-049

問題回報與功能建議 · Feedback · 站內表單 · 登入制 · 後台分流

讓登入使用者直接在站內回報資料錯誤、功能異常與功能建議；回報自動帶上實體引用定位，後台統一分流處理並回覆狀態。

一句話：本站的資料由爬蟲蒐集後人工整理，錯誤無法避免，但目前沒有任何回饋迴路——玩家看到錯的數值，除了私訊維護者以外無處可去。本計畫補上這條迴路，並把「功能建議」一併納入同一套流程。
Problem
問題背景
一、資料錯誤只能靠維護者自己發現
遊戲資料來自爬蟲 + 人工修正（如 PilotTalent.manual 對抗官方 API 的滿晶片污染值），改版後必然出現落差。 但目前發現落差的唯一途徑是維護者自己比對，看站的玩家比維護者多得多，卻沒有管道把發現的錯誤送回來。
二、GitHub issue 對玩家門檻過高
2026-08-18 已補上 .github/ISSUE_TEMPLATE/ 的資料錯誤 / bug 回報模板，但那服務的是「會用 GitHub 的人」。 一般玩家沒有 GitHub 帳號，也不會為了回報一個數值去註冊，實際回報率預期趨近於零。
三、功能建議散落在聊天訊息裡
目前許願都走 Discord 私訊或頻道閒聊，沒有狀態、沒有去重、會被洗掉。 幾週後回頭想找「當初有人提過的那個功能」往往已經翻不到。
四、回報缺少定位資訊，處理成本高
即使收到回報，「艾達的攻擊力好像怪怪的」這種描述仍需來回確認是哪一頁、哪個欄位、什麼條件下的值。 回報當下的頁面脈絡若沒被一起帶走，處理成本就轉嫁給維護者。
Design
設計決策
決策一：一律需登入才能提交，訪客不能留下資訊
使用者拍板。訪客看得到回報入口，但按下後顯示「登入後即可回報」的引導（本站已有 Google 一鍵登入）。

這個決定的連鎖效應比表面上大——它讓本計畫不需要動用 Cloudflare Worker，見決策二。 其他附帶好處：回報者可追蹤自己回報的處理狀態、濫用者可被封鎖、不需處理匿名資料的去識別化問題。
代價是門檻提高、回報量會低於匿名制；但以本站規模而言，回報品質比回報數量重要。
決策二：client 直寫 Firestore + 規則守門，不建 Worker 端點
這裡要和 PLAN-046（使用統計）明確區分，兩者看似都是「使用者產生的寫入」，架構卻相反：
計畫是否要涵蓋訪客若 client 直寫，規則會變成結論
PLAN-046 使用統計 要（訪客也要統計） create: if true — 任何人可迴圈寫爆額度 必須走 Worker 代寫，write: if false
PLAN-049 回報 不要（決策一） create: if isAuthenticated() && uid 綁定 — 有身分可追溯 client 直寫即可，省下整個 Worker 端點
寫入模式直接沿用 systemLog（PLAN-045）已驗證的 append-only + uid 綁定寫法，這是站內現成的範式。
決策三：三種回報類型共用一個 feedback 集合
type: 'DATA_ERROR' | 'BUG' | 'FEATURE'，不拆三個集合。
理由：後台一個列表就能看完全部待處理事項、狀態機三者共用、量級是每日個位數。 各類型的專屬資訊用選填欄位承載（如資料錯誤才有 currentValue / expectedValue）， 而非拆成 union 型別——後台表單與列表元件因此可以共用一套。
決策四：用既有的 EntityRef 定位回報對象，不另發明欄位
回報對象直接存 types/common.ts 的 EntityRef（refType + refId）， 其 RefType 已涵蓋 pilot / mech / weapon / module / backpack / component / buff / skill / term / neuralDrive / form / stat，正好是所有可能被回報的對象。

三個直接好處：
· 前台從詳情頁按下回報時自動預填對象，使用者只需填「哪裡錯、正確值是什麼」；
· 後台列表可直接用現成的 RefChip / EntityRefView 渲染，點擊即跳到該實體；
· 未來要做「這筆機師資料有 2 則未處理回報」的關聯查詢，用 refId 就能 where 出來。
決策五：feedback 刻意不進 GameDataContext 快取層
三層快取（記憶體 → localStorage → 遠端）是為版本化的靜態遊戲資料設計的，靠 meta/gameData 的版本號失效。 回報是高頻變動的動態資料，狀態隨時被管理員更新，套用版本 gate 只會讓使用者看到過期狀態。
因此 feedback 不加入 CollectionKey，走獨立的 src/lib/api/feedback.ts 直接查詢。
決策六：限流——第一版只做規則層欄位驗證，不做 rate limit
PLAN-045 決策四曾明確指出「放寬寫入到一般登入使用者會擴大寫入面並帶來限流需求」，這個顧慮在本計畫必須正面回應。

第一版的防線（由強到弱）：
1. 登入門檻——擋掉所有無帳號的腳本洪水，這是最有效的一道；
2. 規則層欄位驗證——欄位白名單 + 字串長度上限（防塞入大量文字灌爆容量）+ uid 必須等於 request.auth.uid；
3. 前端 UI 節流——送出後鎖定按鈕，防手滑連送；
4. 事後封鎖——管理員可標記濫用帳號停止其寫入。

刻意不做規則層的時間窗 rate limit（需額外 feedbackThrottle/{uid} 集合 + 每次寫入多一次 get() 讀取）。 理由：登入制下濫用成本已足夠高、Firestore 免費寫入 20k/日 遠高於預期量級、且真被濫用時可隨時改規則即時生效。 但第二階段的設計要先備妥（見下方「不在範圍內」），避免臨時應急。
決策六附記：封鎖標記不能放在 users/{uid}/profile/main
現行規則是 allow update: if isOwner(userId) && !affectedKeys().hasAny(['role'])—— 使用者可以自由修改自己 profile 的任何非 role 欄位。 若把 feedbackBlocked 放進 profile，被封鎖者可以自己把它改掉。
處理方式：把該欄位一併加入禁改清單 → hasAny(['role', 'feedbackBlocked'])。 這是本計畫唯一會動到既有規則的地方，實作時務必連同 emulator 測試一起補。
決策七：狀態機與回覆
NEW → IN_PROGRESS → RESOLVED / REJECTED / DUPLICATE。
只有管理員能改狀態（allow update: if isAdmin()），回報者不能改自己送出後的內容（append-only 精神，避免「送出後改內容」讓管理員的判斷與紀錄對不上）。
管理員可填一段 adminReply 回覆回報者，顯示在回報者的「我的回報」頁——這是讓人願意持續回報的關鍵：回報有下文，才會有下一次。
決策八：通知先做後台紅點，Discord webhook 列為選配
第一版在後台入口顯示未處理回報數（where status == 'NEW' 的 count，量小成本可忽略）。
Discord webhook 通知雖然更即時，但 webhook URL 不能進前端 bundle，需要 Worker 中轉——那會把決策二省下的 Worker 端點又加回來。 因此列為 Phase E 選配，等實際回報量證明「紅點不夠用」再做。
與 GitHub issue 模板的關係：單向連結，不做系統整合
兩條管道並存，服務不同對象：站內表單給玩家（資料錯誤為主）、GitHub issue 給技術使用者（程式 bug、fork 者、安全性回報）。
不把站內回報自動轉成 GitHub issue，因為兩者的修復路徑不同——資料錯誤修在 Firestore 後台，從頭到尾不碰 repo， 放進 GitHub 只會讓資訊與工作流分離，還得兩邊對帳。實作上僅在回報表單底部加一行「你是開發者？也可以到 GitHub 開 issue」。
Model
資料模型草案
// src/types/feedback.ts（新檔，需併入 types/index.ts barrel） // enum 依慣例放 src/types/enums.ts（不在 barrel 內，獨立 import 路徑） export interface FeedbackItem { id: string type: FeedbackType // DATA_ERROR | BUG | FEATURE status: FeedbackStatus // NEW | IN_PROGRESS | RESOLVED | REJECTED | DUPLICATE // ── 回報者（create 時規則強制 uid === request.auth.uid）── uid: string displayName: string // 快照，避免後台為了顯示名字去 join users // ── 內容 ── title: string // 上限 80 字（規則層驗證） body: string // 上限 2000 字 // ── 定位（決策四）── target?: EntityRef // 從詳情頁回報時自動預填 pageUrl?: string // 回報當下的 route，自動帶入 // ── DATA_ERROR 專屬（選填，見決策三）── currentValue?: string // 站上顯示的（錯的） expectedValue?: string // 遊戲內實際的（對的） gameVersion?: string // 回報者確認時的遊戲版本 // ── BUG 專屬（選填）── userAgent?: string // 自動帶入，省去問「你用什麼瀏覽器」 // ── 管理端（僅 isAdmin() 可寫）── adminReply?: string // 回覆給回報者，顯示在「我的回報」 adminNote?: string // 內部備註，不對回報者顯示 duplicateOf?: string // status=DUPLICATE 時指向的 feedbackId createdAt: Timestamp updatedAt?: Timestamp expireAt?: Timestamp // 見下方保留期限討論 }
保留期限待定：依「博物館原則」，判準是刪掉的東西還能不能再生。 已處理的回報屬於不可再生的使用者輸入（無法重爬、無法重建），傾向不設 TTL； 量級估算：單筆約 1–3 KB，一年一千筆也不到 3 MB，容量完全不是瓶頸。 expireAt 欄位仍先留著（比照 announcementDrafts 的做法：欄位有值但不掛政策），保留日後改變主意的餘地。 實作時請確認此判斷。
// firestore.rules 草案 match /feedback/{feedbackId} { // 讀：管理員看全部；一般使用者只看得到自己送的 allow read: if isAdmin() || (isAuthenticated() && resource.data.uid == request.auth.uid); // 建：登入即可，但 uid 必須是自己（防偽造嫁禍，同 systemLog） // 並驗證欄位白名單、長度上限、狀態必須為 NEW allow create: if isAuthenticated() && request.resource.data.uid == request.auth.uid && request.resource.data.status == 'NEW' && request.resource.data.title.size() <= 80 && request.resource.data.body.size() <= 2000 && !isFeedbackBlocked(); // 改 / 刪：僅管理員（回報者送出後不可修改，append-only 精神） allow update, delete: if isAdmin(); }
Scope
實作範圍與不在範圍內
在範圍內：
  • FeedbackItem 型別、FeedbackType / FeedbackStatus enum
  • feedback 集合的 Firestore 安全規則 + emulator 規則測試
  • users/{uid}/profile 規則調整：feedbackBlocked 加入禁改清單
  • 前台回報 Modal（三種類型共用，依 type 顯示不同欄位）
  • 兩個入口：實體詳情頁的「回報這筆資料」（自動預填 target）＋ 全站固定入口
  • 後台管理頁 /profile/admin/feedback：列表、篩選、狀態流轉、回覆
  • 後台入口未處理數紅點
  • 使用者端「我的回報」：查看自己送出的回報與管理員回覆
  • docs 同步：資料模型頁 + Firebase 資料庫設計文件新增 feedback 集合頁
不在範圍內（本期刻意不做）：
  • 訪客／匿名回報——決策一已拍板需登入
  • 圖片上傳——Storage 成本尚可，但開放一般使用者上傳等於承接內容審查責任與濫用面。第一版改以文字描述 + 外部圖床連結。日後可再議
  • 自動同步到 GitHub issue——理由見決策八上方的 info-block
  • 公開的回報看板 / 投票 / 留言串——那是論壇，會帶來審查與社群經營成本，且未處理的資料錯誤公開展示反而造成混淆
  • 規則層時間窗 rate limit——決策六，第二階段才做。屆時的設計：獨立 feedbackThrottle/{uid} 集合，規則強制 lastAt == request.time 使其無法偽造成過去時間，feedback 的 create 以 get() 檢查間隔（batch 內 get() 讀的是交易前狀態，可行）
  • Discord webhook 通知——Phase E 選配，需 Worker 中轉
  • Email 通知回報者——需寄信服務，成本與維護不成比例
Risk
風險與對策
風險程度對策
登入門檻使回報量過低，功能形同虛設 中 入口要顯眼且脈絡化（詳情頁就地回報，而非藏在頁尾）；上線後觀察一個月，若量趨近零再檢討是否放寬
登入使用者惡意灌爆寫入額度 低 決策六四道防線；真發生時改規則即時生效，並封鎖該 uid
回報堆積無人處理，使用者失望後不再回報 高 這是本計畫最大的實際風險，且是維運問題不是技術問題。對策：後台紅點提醒 + adminReply 讓回報有下文；寧可快速標 REJECTED 並附理由，也不要放著不回
使用者用回報表單洗版辱罵或張貼不當內容 低 登入制可追溯；管理員可刪除並封鎖。內容僅管理員與本人可見，不公開展示，波及面小
