召喚單位展示 · Summon · 迷你機兵 · 引用層接線

部分機師的特殊召喚單位（如薩普莉婭的咕咕）有自己的技能、型態與裝備；建立獨立 summons 集合並在機師頁以條件式分頁展示，天賦正文的 [咕咕] 接進引用層變成可解析實體。

Problem
問題背景
特殊召喚單位無處展示
部分機師的天賦會「出擊時自動部署」一個獨立戰鬥單位（薩普莉婭的 咕咕）。這個單位有自己的技能組、型態切換與裝備，本質上是一個「迷你機兵」，但目前機師頁完全沒有承載它的地方，玩家只能從天賦一行文字腦補。
天賦正文的 [咕咕] 降級成純文字
天賦正文已寫成「出擊時自動部署[咕咕]…繼承[薩普里婭]75% 最大耐久值和 100% 的其餘屬性」。其中 [薩普里婭] 能解析成 mech，但 [咕咕] 在引用層（PLAN-019）沒有對應的 refType，只能原樣顯示成純文字，無法懸停、無法點開。
召喚單位資料 WIKI 也查無
官網 API 與外部 WIKI 都沒有召喚單位的結構化資料，只能人工維護。目前全遊戲僅兩個機師有召喚單位，屬長尾、低頻但深度內容。
Design
設計決策
決策一：獨立 summons 集合，而非塞進 Pilot 文件
召喚是 AI 戰鬥單位，結構近似 bosses（技能＋部件＋型態），比一般欄位重。關鍵理由是接進 RefType 系統：新增 summon refType 後，[咕咕] 在任何 description 都能解析、進 ReferenceContext 懸停浮窗——一份資料源、兩處渲染（天賦內懸停 + 分頁內展開）。比照 pilotSkills / neuralDriveAbilities 的「集合＋ID 引用」慣例，ensureLoaded(['summons']) 只在機師詳情頁載入，不增前台首屏；召喚改動各自 bumpDataVersion('summons')，不必動 pilots 版本。
決策二：機師頁條件式第 4 分頁「召喚單位」
比照專武面板的條件式渲染——只有擁有召喚的機師才顯示這個 tab（天賦 / 技能 / 神經驅動 / 召喚單位）。分頁內版面全部複用現有元件：技能卡＝「技能」分頁的 skillrow；型態切換＝專武的「階段 I / II」切換器；裝備＝ WeaponDetailContent 懸停浮窗。幾乎不用做新元件。
決策三：屬性繼承「只顯示公式」（本期不對機兵求絕對值）
召喚數值是「機兵屬性 × 繼承比例」動態算出（咕咕：最大耐久 75%、其餘屬性 100%）。本期只顯示比例公式（「來源 [薩普里婭] · 耐久 75% · 其餘 100%」），不讀機兵屬性求絕對數值。SummonInheritance 結構已預留 ratios/defaultRatio，未來模擬層（PLAN-019）可再對實際機兵求值。
決策四：後台手動維護（managedBy:'manual'）
因為召喚單位無外部資料源，走後台手動 CRUD，比照 Boss / 手動機師（PLAN-025）的 manual 慣例——不進爬蟲補丁流程，不會被洗掉。需要一個 SummonAdmin 編輯器。技能／型態文本由管理員逐筆人工輸入，屬長期維護尾巴。
邊界：技能沿用「string | 物件」過渡型別
Summon.skills 比照 PilotSkill，可為 ID 引用（skill_xxx）或內嵌物件。初期以內嵌為主（召喚技能多為專屬、不共享），需要時再抽到 pilotSkills 集合共用，向後相容。

Scope
實作範圍與不在範圍內
在範圍內：
  • Summon 系列型別 + summons 集合接線（Context / api / barrel）
  • 引用層新增 summon refType，[咕咕] 可解析、可懸停
  • 機師頁條件式第 4 分頁「召喚單位」（繼承公式列 / 型態切換 / 技能卡 / 裝備，複用現有元件）
  • SummonAdmin 後台編輯器（手動 CRUD，managedBy:'manual'）
  • 人工補建現有兩個機師的召喚單位資料（長期維護尾巴）
  • 同步 docs/02_技術文件/ 資料模型與 Firebase 集合文件
不在範圍內：
  • 對實際機兵求召喚絕對數值（留待模擬層 PLAN-019）
  • 爬蟲自動抓取召喚資料（無外部資料源，一律人工）
  • 召喚單位參與傷害模擬計算（模擬層再處理）
