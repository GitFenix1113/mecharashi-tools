◆ PLAN-042-E

機師資料分家與故事館編輯台圖鑑只留功能 · 人物檔案歸故事館 · 外觀管理

機師圖鑑只保留跟數值、機制有關的資料；簡介、人物檔案、英文名全部搬進 pilotLore。故事館編輯台擴充成一個地方就能編完一位機師的所有故事資料，外觀的名稱、隱藏、順序也改在後台管理。

本計畫的依據：_local-notes/2026-10/2026-10-13_機師資料分家_圖鑑與故事館評估.html（在 _local-notes，不進版控）， 內含逐條勘誤、欄位歸屬總表、後台線框、外觀資料流與搬遷步驟。資料數字取自 _local-notes/db-backup-2026-10-12_1847/（機師 92 份、pilotLore 34 份）。 站長同日回覆評估的四個問題：Q1 全名、陣營留在 pilots（陣營日後會有遊戲機制作用）；Q2 圖鑑保留故事館入口連結； Q3 故事編輯者角色先不做；Q4 孤兒欄位 fullPortrait 在收尾時刪除。
Problem
問題背景
問題一：一位機師的故事資料分住兩處，編輯要跑兩個畫面
簡介、性別／身高／血型、自訂欄位、英文名在「機師管理 › 個人資料」分頁（PilotAdmin.tsx:1670-1698）； 章節、旁白、扉頁署名、陣營徽章在「故事館編輯台」（/admin/lore）。故事館的扉頁同時讀兩個集合，編輯台的預覽也因此做不出來。
問題二：圖鑑混入了非功能資訊
站長 2026-10-13 定調：機師圖鑑只做「功能性」，也就是數值、機制、天賦、技能。現在詳情頁標頭的資訊格最多 11 列，其中 6 列是人物檔案（PilotDetailPage.tsx:1046-1054）， 頁尾另有一張「機師故事」卡（:1309-1336）。
問題三：總綱決策二的前提已經失效
決策二「誰是權威來源」不搬 lore／profile 的兩個理由：① 圖鑑浮窗讀 pilots.lore，但 2026-10-09 浮窗已改列天賦（EntityRefView.tsx:95）； ② 爬蟲每次補丁會重寫，但 2026-10-11 官網爬蟲已退場。現在所有資料都是人寫的，「誰寫的」這條判準已經分不出任何東西。
問題四：外觀的名稱和隱藏只能改 JSON 再部署
042-D 讓 37 位、42 套外觀上站，名稱與隱藏設定放在 scripts/lib/pilotSkinMeta.json，由 generate-art-index.mjs 在 build 時讀取。 維護人員要幫外觀命名，就得改 repo 裡的檔案並等部署。目前這個 JSON 的 name／hidden 一筆都沒填（唯一的一筆是 owner 歸屬），前台全部顯示「外觀 N」。
問題五：兩處資料形狀的遺留問題
① 34 篇扉頁署名仍黏在 pilots.lore 正文尾端，每次渲染都靠 stripTrailingSource 切掉； ② additionalInfo 是 map，Firestore 不保證鍵的順序。總綱決策二當初就把「additionalInfo 的顯示順序」列為 lore 集合要承擔的事，但一直沒有落地。
Design
設計決策
決策一：新判準「與數值、機制有沒有關係」，取代總綱決策二
有關的留在 pilots，其餘全部歸 pilotLore。邊界案例依站長 Q1 裁決：全名 fullName、陣營 faction 留在 pilots。 全名是圖鑑標題；陣營現在用於圖鑑搜尋和卡片，日後還會有遊戲機制上的作用。
欄位（pilots）去向填寫率說明
lore→ pilotLore.intro89／9251.0 KB。0 篇含 [xxx]。搬遷時把黏在尾端的署名切掉
profile.gender／height／bloodType→ pilotLore.dossier92／92保留固定欄位：LoreDossier 拿身高當紅色標籤
profile.additionalInfo→ pilotLore.dossier.extra83／92147 筆、103 種鍵名，每人最多 3 筆；改成有序陣列
nameEn→ pilotLore.nameEn90／92只有故事館讀（扉頁草書、卷宗、名冊搜尋）
pilotSkinMeta.json 的 name／hidden→ pilotLore.skins0 筆沒有資料要搬；JSON 收斂成只管匯入用的 owner／note
fullPortrait刪除82／92舊爬蟲的 _Raw 路徑，src／workers／scripts 都沒有讀取點（Q4）
name／fullName／faction留—身分與分類，兩館共用（Q1）
class／license／rarity／masterLevel／debutVersion、gameId／artKey／portrait／pairedMechId、數值類留—功能性欄位。預設外觀＝artKey，圖鑑頭像也在用，所以不由故事館管
決策二：單向依賴，圖鑑不跨進故事館
圖鑑只讀 pilots；故事館讀 pilotLore，另外從 pilots 讀身分欄位（名字、全名、職業、陣營、立繪）。 這樣一來，故事館壞掉、資料還沒填，或日後又要收起入口，都不會影響圖鑑。 依站長 Q2，圖鑑保留一顆不帶任何文字內容的「故事館 ▸」入口連結，不必載入 pilotLore。92 位機師都有故事館頁，所以連結不會連到空頁。 故事館入口旗標 useLoreEntry.ts（LORE_INTERNAL_ONLY=false，原定穩定後刪除）在本計畫刪除：圖鑑已經沒有簡介可以退回顯示，這個旗標的退路也就不存在了。
決策三：不新增集合，只擴充 LoreDoc
pilotLore 的 CollectionKey、Worker 白名單、rules、entityRefs SPECS、changeHistory 都已接好，所以不會碰到「新增集合要連動九處」的陷阱。 搬遷後 pilotLore 整包約 6.8 KB → 70 KB（不含之後增加的章節），仍留在 NO_LOCAL_CACHE_KEYS（collectionKeys.ts:54）。 Worker 的邊緣快取 key 已帶版本號，額外的 Firestore 讀取可以忽略。
// src/types/lore.ts export interface LoreDoc { id: string name?: string intro?: string // 扉頁簡介（原 pilots.lore），署名已切掉 frontSource?: string nameEn?: string // 原 pilots.nameEn dossier?: { // 原 pilots.profile gender?: string; height?: string; bloodType?: string extra?: { label: string; value: string }[] // 原 additionalInfo，陣列順序＝顯示順序 } skins?: { key: string; name?: string; hidden?: boolean }[] // 外觀顯示設定，陣列順序＝顯示順序 factionLogos?: string[] chapters: LoreChapter[] } export interface LoreChapter { /* 既有欄位不變 */ draft?: true // 前台不列出；資料仍會整包下載（站長：外洩無妨） }
決策四：搬家時順便修正資料形狀
① 欄位名用 intro，不沿用 lore，避免和集合名、型別名混淆。 ② additionalInfo 改成 {label, value}[]，順序由編輯者決定，存檔時檢查同名標籤；搬遷時照備份裡的現有順序轉換。 ③ 34 篇署名在搬遷時一次切乾淨，執行期的 stripTrailingSource 就可以拿掉，不必每次渲染都重新猜一次。
決策五：草稿只做章節層的 draft 旗標，進度由資料推導
站長裁決草稿外洩沒關係，所以不另開只有編輯者讀得到的集合。草稿章在前台不列出、章節網址導回扉頁，館首頁的章節數也不計入。 簡介和檔案都是短欄位，沒有「寫一半」的問題，不做草稿。 不存文件層的 status：後台進度總覽的「有沒有簡介、檔案幾欄、章節數、草稿數、外觀命名數」全部從資料推導。 這是 PLAN-041「0/5 定律」的教訓：選填的狀態欄位最後沒人會填。
決策六：外觀分成靜態層和動態層
靜態層（build 時決定，仍走腳本＋部署）：圖檔本身、owner 歸屬（決定檔案放進哪位機師的資料夾）、檔案清單 gameArtIndex.ts， 以及 NPC 圖庫的歸屬 npcArtNotes.json。
動態層（後台存檔就生效）：pilotLore.skins 的名稱、隱藏、順序，由 pilotSkins() 在執行期合併。 已經有圖、DB 卻沒有設定的外觀照舊顯示「外觀 N」；DB 有設定、圖卻不存在的 key 直接忽略。
決策七：先複製、再切換、觀察後才刪，不寫雙讀退路
任何時間點，正在跑的程式都讀得到它要的資料：資料先複製到 pilotLore（舊程式不認得新欄位，所以不受影響）→ Worker 先部署 → 網站一次切換 → 觀察一週後才刪除 pilots 的舊欄位。 不寫「新欄位讀不到就退回舊欄位」的程式碼：那種退路實際上會一直留著，結果變成兩個資料來源。 C 段（讀取端）必須和 D-1（移除 PilotAdmin 個人資料分頁）、D-2（編輯台加欄位）同一次部署，否則在舊分頁改的內容會沒有地方去。
決策八：故事編輯者角色先不做
站長 Q3。目前的維護人員都是 ADMIN，這和總綱「EDITOR 角色降級為備案」一致。 要做的時候，需要改 role 值、rules（pilotLore 和 changeHistory 的寫入）、AdminRoute，編輯台直讀 pilots 也得改走 Worker，再加一個指派角色的介面。屆時另立小計畫。
⚠ 已知地雷
  • 舊 AdminLorePage 存檔是整份覆寫：從複製資料到網站部署完成之間，如果有人在舊後台存檔，剛搬進來的 intro／dossier 會被洗掉。這段期間要凍結編輯，F-2 的對帳腳本負責抓遺漏。
  • Worker 分享卡會在沒有錯誤的情況下退化：/lore/pilots/* 的 description 現在讀 pilots.lore（socialPreview.ts:249）。沒改到的話，回應一樣是 200、一樣有 og:image，只有描述文字退回預設值。
  • pilotLore 讀不到時，降級的結果變差：現在讀不到時扉頁仍有正文（來自 pilots），搬遷後只剩名字、職業、陣營。要明確顯示「故事資料載入失敗」，不能讓人以為是空白資料。
  • 還原舊歷史快照會把舊欄位帶回 pilots：G-1 之前的 pilots 快照仍含 lore／profile。G-3 處理。
  • hidden 的意思會變：以前代表不寫進 build 清單（打包檔裡完全沒有），改由 DB 控制後打包檔仍有路徑，只是前台不列出。依「劇透不是顧慮」可以接受。
  • 例行流程要能不靠 AI：import-game-assets.mjs --skins 報告的「下一步」清單（:727）現在寫著「編輯 pilotSkinMeta.json 的 name／hidden」，E-3 要改成指向後台的外觀分頁。
  • 註解和文件裡多處寫著「扉頁正文住 pilots.lore」（lore.ts:68-73、AdminLorePage.tsx:387-389／551、LoreDossier.tsx:18、LoreHomePage.tsx:17-19、PilotDetailPage.tsx:1317-1324），C-5 要一起改寫，否則會誤導下一個人。
Scope
實作範圍與不在範圍內
在範圍內（25 項開發者任務＋1 項站長部署）：
  • A 資料模型（3 項）：擴充 LoreDoc、Pilot 型別拿掉遷出欄位、人物檔案純函式＋測試
  • B 搬遷腳本（3 項）：備份、複製（dry-run → apply → bump）、對帳
  • C 讀取端切換（6 項）：故事館元件、圖鑑清理＋入口連結、entityRefs 站點、Worker 分享卡、註解改寫、測試 fixture
  • D 故事館編輯台（5 項）：移除 PilotAdmin 個人資料分頁、編輯台分頁化（扉頁／人物檔案／章節）、進度總覽、即時預覽、章節草稿旗標
  • E 外觀管理（3 項）：pilotSkins() 合併 DB 設定、外觀分頁、build 腳本與 JSON 收斂
  • F 部署與驗收（3 項，F-1 為站長）：部署順序、驗收、文件同步與更新履歷
  • G 收尾（3 項）：刪除 pilots 舊欄位（含 fullPortrait）、封存一次性腳本、還原快照排除遷出欄位
不在範圍內：
  • 機甲側的 mechs.lore（MechDetailPage.tsx:429）：同一種問題，等 042-B 機甲故事館動工時套用同一套判準
  • 故事編輯者角色（決策八）
  • 外觀圖檔上傳：圖檔放在 GitHub Pages，後台沒辦法新增檔案，仍走 import-game-assets.mjs --skins 再部署
  • NPC 圖庫歸屬（npcArtNotes.json）改到後台：後台選立繪的 NPC 分組也在用它，列為日後候選
  • 由故事館切換預設外觀：預設外觀是 pilots.artKey，圖鑑頭像也在用，留在機師管理
  • 042-D H 段的站長資料作業（造型名稱、台版白名單、逸聞 OCR 清理）：本計畫完成後改在後台外觀分頁做，不必再改 JSON
