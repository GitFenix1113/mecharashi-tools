架構安全網與維護性改善 — CI 測試 · 原子寫入 · 變更歷史 · 備份 · 實體登錄表 · 故事館動畫

爬蟲 10-11 退場後，Firestore 成了人工資料唯一的一份。很多防線是在「壞了可以重跑爬蟲」的前提下設計的，這個前提已經不成立。本計畫補上寫入、測試、備份、部署這幾層安全網，收斂「新增一個集合要改 20 處」的散落結構，並整理故事館的動畫架構。

Problem
問題背景
問題一：人工維護的核心資料沒有安全網
  • 變更歷史只接了一半。只有 6 個集合走 saveWithHistory（buffs、pilotSkills、glossary、forms、backpackSkills、pilotLore）。 pilots、mechs、weapons、modules、components、backpacks、neuralDriveAbilities、grayOps 只做 writeDoc 加 bump，沒有任何歷史（例：src/lib/api/pilots.ts:17-21）。 AdminVersionEditorPage.tsx:401 甚至直接呼叫 setDoc。
  • 當初不接的理由已經失效。pilotLore.ts:26-28 寫的理由是「其餘集合重跑爬蟲就有」，但爬蟲已經退場。PLAN-030 的「其餘 8 個集合各補一行即可接上」也一直沒有補。
  • 有歷史也無法還原。有接歷史的集合只存 changedFields，沒有改前內容（changeHistory.ts:192-200）。
  • 整份覆寫、沒有並行檢查。firestoreCore.ts:63 的 setDoc 不帶 merge，版本號每個 session 也只讀一次。 早上就開著的後台分頁一存檔，會把下午用腳本批次修好的內容蓋回去。草稿還原（useDraftAutosave.ts:117-125）不記錄基準版本，被級聯清掉的引用會在還原舊草稿後被寫回去。
  • 沒有自動備份。backup-firestore.mjs 只在本機，而且被 gitignore；.github/workflows 裡沒有任何排程匯出。
問題二：版本 bump 不是原子操作，失敗會被吞掉；腳本端各自重寫
  • src/lib/api/* 有 12 處 bumpDataVersion(...).catch(() => '')，都是先寫文件、再另外 bump。 Worker 的邊緣快取以版本號當 key，所以 bump 一旦失敗，所有訪客都會一直看到舊資料，編輯者這邊卻沒有任何提示。
  • cascadeDelete.ts 和 restore.ts 已經把 bump 併進同一個 batch。正確寫法早就存在，只是一般存檔沒有用它。
  • 腳本端有 5 份各自手寫的 bump，其中 derive-composite-backpack-skills.mjs:247-252 記錄自己寫錯過：版本寫到頂層欄位，畫面印出「已 bump」，快取卻完全沒失效。
  • 唯一正式的 scripts/bump-data-version.mjs 被 .gitignore:92 擋掉，README.md:61,109 卻還在教人跑它。
問題三：守門測試寫得很好，卻沒有任何自動流程會跑
  • deploy.yml、preview.yml、.githooks/pre-push 都只跑 npm run build。
  • 專防 PLAN-043 那種正式站 404 的 collectionKeys.test.ts、路由登記的 routeKeys.test.ts、分享碼 codec 的 golden fixture，都只在有人手動跑 npm test 時才有用。
  • routeKeys.ts 的註解寫「pre-push hook 會擋下」，但這件事並不成立。
  • 部署環境是 Node 20，跑不了 node --test "src/**/*.test.ts"。repo 也沒有 engines 或 .nvmrc。
  • 2026-10-13 在 Node 22.22、沒有 node_modules 的環境實測：1401／1407 通過，失敗的 5 個都只是缺套件（sharp 等），1 個 skip。
問題四：新增一個集合要改約 20 處，存檔流程在 13 個編輯器裡各抄一份
  • GameDataContext.tsx 單一檔就有 9 處要改，其中包括 4 個 switch（第 150、177、260、293 行）。
  • collectionKeys.test.ts:82 只檢查整個檔案裡有沒有出現 case 'k':，4 個 switch 只寫了 1 個也會通過。
  • 後台的存檔、取消、新增前檢查各手抄了 12–13 次。新增前檢查只有 3 份會確認「資料已載入完成」。
  • 潛在地雷：saveWithHistory 用 Firestore 集合名去 bump（changeHistory.ts:190），但 bump 需要的是 CollectionKey。 目前兩者剛好同名；接上 grayOps（集合 grayOps、key grayOpsRoster）時，就會靜默 bump 到錯的 key。
問題五：全站沒有 ErrorBoundary，首包也帶著用不到的程式碼
  • 任何一筆格式異常的文件都可能讓整站白屏、導覽列消失。全站只有兩段註解提到這件事（ModuleBoundPart.tsx:18、MechAdmin.tsx:735）。
  • App.tsx 仍然靜態 import AdminPage（14 個分頁，閉包約 33k 行）、LoadoutPage、PilotDetailPage，首包約佔全部原始碼的 83%。
  • lib/firebase.ts:56 在模組頂層初始化了從未使用的 Storage。
  • 約 180 KB 的更新履歷透過 HomePage 打進首包。
問題六：資料模型的歷史包袱
  • 同一個關係在兩邊各存一份。Module.boundMechId 與 Mech.moduleFixedIds 分別在兩個後台頁維護，沒有任何東西負責同步。
  • 用顯示名稱當引用。patchVersions 的 pilots／mechs／weapons／backpacks 都是名稱陣列；另有 hasBuff、enhancesTalentName。
  • 讀取時沒有正規化。fetchCollection 直接 as T，程式裡因此寫了 91 處 ?? []。
  • 三種雙格式過渡至今還在。Pilot.skills 是 string|PilotSkill、Weapon.skills、NeuralDriveLevel 的引用與內嵌並存，而當初保留它們的理由（爬蟲）已經消失。
  • patchVersions 有兩份來源。靜態 TS 停在 3.3，Firestore 已經到 3.7，靜態那份卻仍是首屏初始值與讀取失敗時的備援。
  • localStorage 快接近上限。已用 4.2–4.5 MB，上限約 5 MB。
問題七：關鍵維運知識只存在站長電腦和 CF Dashboard 上
  • 被 gitignore 的關鍵工具：bump-data-version.mjs、check-nd-minsum-drift.mjs、.claude/skills/data-patch/、backup-firestore.mjs。換電腦或雲端 session 都拿不到。
  • 封存路徑寫死在 E:\（scripts/lib/gameDump.mjs:17,19）。
  • Worker、firestore.rules、Transform Rule 白名單都靠手動部署。白名單已漏過兩次（PLAN-043、PLAN-050）。
  • CLAUDE.md 說白名單「16 條」，App.tsx 實際有 21 個頂層路徑段。wrangler.jsonc:40 說 /lore/ 也要排除社群爬蟲 UA，CLAUDE.md 卻沒寫。
  • public/debug/*.json 被 gitignore 卻仍在追蹤，會部署到正式站。
  • CHANGELOG 自動化在淺層 clone 裡截斷過整份檔案（dc4b5bc），最近 50 個 commit 裡有 23 個是它的自動 commit。
問題八：故事館的動畫時序分散在三套機制，靠手動對齊數字
  • 三套機制：CSS keyframes 加狀態 class；JS 計時器（PilotLorePage.tsx:130-133 的 1050／1250／1600／3200、LoreStage.tsx:38 的 DRESS_MS=1000）；LoreSwitcher.tsx:197-260 的 14 處 WAAPI。
  • 數字之間有隱性綁定：JS 的 1000 必須等於 CSS 的「170ms 延遲加 820ms」。只要調了其中一邊，動畫就會被腰斬或閃一下，而且不會有任何錯誤訊息。
  • 故事館 CSS 佔全域 index.css 的 74%（約 780／1057 行），每一頁都要下載；色票重複兩套，另有約 45 處寫死的 rgba。
  • 卷宗的 width／margin 過場、每個捲動幀寫進根元素的 --sy，都會觸發 layout 或整棵樹的樣式重算。
Design
設計決策
決策一：分段原則是「先止血、再收斂結構、最後整理」
  • A 段全部是半天內可完成的小改，彼此獨立，可以一次 push。
  • B 段是本計畫的核心：一份登錄表加一個統一存檔函式，一次修好問題一、二、四。
  • C、D 段在 B 段之後依序處理資料模型與維運。
  • E、F 段屬於整理，排程上配合其他計畫，不急。
決策二：ENTITY_REGISTRY 是「集合」這個概念的唯一登錄處
新檔 src/lib/entityRegistry.ts 以 kind 為鍵，登記 Firestore 集合名、CollectionKey、歷史種類、顯示標籤、fetch 函式、空值，以及能否刪除。 GameDataContext 的 4 個 switch、changeHistory 的 3 張對照表、AdminHistoryPage 的 TARGET_OPTIONS、saveEntity，全部改成查這張表。 型別用 mapped type 從登錄表推導，漏登記時由 tsc 報錯，不再依賴字串比對的測試。
collectionKeys.ts 維持零依賴，因為 Worker 的漂移測試要讀它；登錄表再 import 它，不取代它。
// src/lib/entityRegistry.ts（示意） export const ENTITY_REGISTRY = { pilots: { collection: 'pilots', key: 'pilots', history: 'pilot', label: '機師', fetch: getPilots, deletable: true }, grayOps: { collection: 'grayOps', key: 'grayOpsRoster', history: 'grayOps', label: '灰域行動', fetch: getGrayOps, deletable: false }, // …每個集合一行；漏登記 → tsc 錯誤 } as const satisfies Record<EntityKind, EntitySpec>
決策三：saveEntity() 是後台唯一的存檔入口，用一個 transaction 包住四件事
  1. 讀現況，與編輯器開啟時的基準比對；不一致就拋出 ConcurrentEditError，並列出被別人改過的欄位。
  2. 寫入文件，沿用 stripUndefined 與寫入被拒的診斷。
  3. 在同一個 transaction 裡寫 meta/gameData.versions.<key>。bump 不再是另一個請求，也不再 .catch(() => '')。
  4. 寫入 changeHistory，帶上改前快照 before。
任何一步失敗就整筆失敗，並把錯誤顯示給編輯者。12 個 update* 和 saveWithHistory 都收斂到這裡。 腳本端（Admin SDK）另建 scripts/lib/dataVersion.mjs，5 份手寫的 bump 都改用它。
⚠ 決策三推翻 PLAN-030 決策十，需要站長確認（Q1）
PLAN-030 決策十規定「log 寫入失敗絕不可擋住主操作」，當時的前提是資料可以重新產生。現在核心資料只有一份，「存進去了、卻沒有紀錄也救不回來」比「這次存不進去」更糟。 建議：歷史寫入併進 transaction，沒有歷史就不准存。
代價是 changeHistory 的規則（actorUid == request.auth.uid）出問題時，所有存檔都會失敗。B-4 要先用 emulator 測試釘住這條規則。 改前快照的大小依現況估計：單筆機師文件約 10 KB 上下，遠低於 Firestore 1 MB 的文件上限；TTL 沿用兩年。
決策四：並行檢查的基準用「正規化後的內容雜湊」，不新增 updatedAt 欄位
編輯器開啟時，對它拿到的文件算一次雜湊（穩定排序鍵，並先做 stripUndefined）。存檔時在 transaction 裡對伺服器現況算同樣的雜湊，兩者不同就擋下。
  • 這個做法同時涵蓋兩種情境：別的分頁改過，以及自己讀到的是過期快取。
  • 不加 updatedAt：既有文件都沒有這個欄位，腳本也不會記得寫，這是 PLAN-041 的「0/5 定律」。
  • 草稿（StoredDraft）也記下基準雜湊。還原草稿時若現況已經不同，就先警示，不再直接覆蓋。
⚠ 雜湊的正規化陷阱
Worker 會把 Firestore Timestamp 轉成 ISO 字串（workers/src/firestoreRest.ts:33），直連則拿到 Timestamp 物件。雜湊前必須把兩者統一成同一種表示，否則經過 Worker 讀到的文件永遠會被判定為「別人改過」。 另外 getPilots 有 orderBy、Worker 不排序，這只影響陣列順序，不影響單筆文件，但 F-3 會一併統一。
決策五：後台只抽「外框」，不做依 schema 自動產生表單的通用 CRUD
後台大部分程式碼是各實體專屬的子編輯器：天賦算力變體、神驅分區、模組等級引用表、武器製作鏈。通用表單只會到處開例外。
  • useEntityEditor(kind) 只負責編輯中狀態、草稿、新增前檢查（含「資料已載入」）、存檔、取消確認與刪除。
  • 驗證寫成每個實體一支 validateX(doc, ctx) → {errors, warnings} 純函式，由 saveEntity 呼叫，腳本的 dry-run 也能共用。
  • 不在 firestore.rules 裡做欄位驗證：只有 admin 能寫，維護成本遠高於收益。
決策六：ID 不遷移，改用 branded 型別擋住新的錯誤
技能 id 大小寫兩制並存、模組有 6 種形狀、背包與元件新舊兩制。全面遷移會牽動分享碼、引用與快取，成本遠大於收益。 改為 type PilotId = string & { readonly __brand: 'pilot' } 這類型別，讓 tsc 抓「把 mechId 塞進 pilotId 欄位」的錯誤。舊資料不動。
決策七：故事館動畫的時序只有一份來源
  • 新增 src/components/lore/loreMotion.ts，定義每段過場的時長、延遲與 easing。
  • 由 .lore-page 根元素把它們寫成 CSS 變數，keyframes 讀變數，WAAPI 也 import 同一份。
  • 過場收尾改成等 el.getAnimations() 的 finished，不再用 setTimeout 猜時間；只在沒有動畫（reduced-motion）時退回立即執行。
  • 故事館 CSS 拆成 src/pages/lore/lore.css，由 lazy 載入的故事館頁面 import，不再每一頁都下載。
決策八：與 PLAN-042-E 的排程
  • A 段、B-1～B-5、C、D 段和 042-E 不衝突，可以隨時做。
  • B-6 遷移 pilots 與 pilotLore 編輯器：042-E 正在改 PilotAdmin 的個人資料分頁和故事館編輯台，所以排在 042-E 的 C／D 段部署之後。 如果 B-4 先完成，042-E 的編輯台改寫可以直接用 saveEntity。
  • E 段（故事館動畫與樣式）排在 042-E 完成之後，避免兩邊同時改 src/components/lore/*。
  • loreArtTuning.ts 搬進 pilotLore 的提議，建議直接併入 042-E 的 LoreDoc 擴充（E-4）。
決策九：漂移檢查搭上備份的便車
B-1 的每週備份 workflow 已經握有唯讀 SA 和全集合 JSON，可以接著離線執行各種一致性檢查，不必再各自連 Firestore：
  • 專屬模組雙存（C-3）
  • 名稱引用斷鏈（C-4）
  • 既有的 check-*-drift 系列
有問題就讓 workflow 失敗，並用 GitHub 的失敗通知提醒站長。
