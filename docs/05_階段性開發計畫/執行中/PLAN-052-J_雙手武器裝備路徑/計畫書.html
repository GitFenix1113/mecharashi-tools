Problem
問題背景
全庫 40／182 把雙手武器，在新模擬器裡沒有任何入口裝得上
2026-08-26 做 052-I Phase B 時在瀏覽器實測確認。點開任何一格手部， 清單裡一把雙手武器都不會出現——不是灰掉、不是附原因，是整批被 omit， 使用者看不到它們存在過。
成因：兩個各自正確的決定撞在一起
① loadoutRules.ts 的 canEquipWeapon() 第一條槽位檢查是 if (weapon.equipSlot !== ref.slot) reject('SLOT_MISMATCH')， 而 SLOT_MISMATCH 的 tier 是 'omitted'（連列都不列）。
② mechSlots.ts 的 enumerateSlots() 刻意不產生 dualHand 座標——這個決定是對的：雙手武器佔的是兩格 singleHand， 不是第三格手部；產生它會讓畫面同時渲染出「一把雙手武器」與「兩個空著的手格」。
於是 weaponChoices(ctx, { slot:'singleHand' }) 把 40 把 equipSlot:'dualHand' 的武器全部濾掉，而 dualHand 的座標 又從來不會被產生去問一次。兩條路都不通。
證據：作者原本就預期它會出現在手部清單裡（同檔內留著死碼）
· LoadoutPage.tsx 的 replaceNote() 有一整條 w.equipSlot === DUAL_HAND 分支，負責提示「裝上將同時取代左右手」——今天永遠跑不到。
· LoadoutRig 特地用 slotHasCandidates(ctx, dualRef) 避免把手部畫成「沒有可裝的武器」，也就是它假設 dualRef 問得出東西。
· 規則層與重量層其實早就全部認得 dualHand：mountCoverage() 會把它攤成左右兩格、slotsOverlap()／withoutSlot()／ slotExists()／isHandSlot() 一應俱全。 唯一擋住的就是上面那一行早退。
為什麼現在修，不能拖
052-C 剛讓使用者能存本機書架、發分享碼。 今天存下來的每一份配裝，都不可能包含雙手武器—— 等修好之後，這批已經發出去的分享碼會顯得莫名其妙地缺一整類武器， 而分享碼是只進不出的。愈晚修，愈多既成事實。
目前唯一畫得出雙手格的路徑是形態鎖定（ctx.lock.mounts）—— 那條路不經過 canEquipWeapon()，所以看得到。 這也解釋了為什麼這個 bug 撐到 052-I 才被發現： 有雙手武器的形態畫面看起來完全正常。
Design
設計決策
決策一：修規則層，不讓 enumerateSlots() 產生 dualHand 座標
保留「雙手佔兩格 singleHand」這個模型——它是對的，槽位圖也是照它畫的。 改成：手部座標願意接受雙手武器，由規則層在內部把座標換成 dualHand。 反方向（產生第三格手部）會讓 SlotCapacity、槽位圖、匯出圖、 分享碼 codec 四處同時要處理一個不存在的格子。
決策二：新增單一入口 mountRefFor(weapon, ref)
回傳「這把武器裝在這一格時，實際會佔住的座標」： 雙手武器 ＋ 手部座標 ⇒ { bank, slot:'dualHand' }（無 side），其餘原樣回傳。
canEquipWeapon() 內部用它做佔用／重量判定， UI 派發 equipWeapon 時也用它。預覽與落地必須是同一支函式算出來的， 否則會出現「清單說裝得上、按下去卻不是那樣」。這與 loadoutWeightSet() 「假想異動與實際落地共用一支」的既有原則同源。
決策三：reducer 幾乎不用動
placeWeapon() 已經用 slotsOverlap() 過濾被取代的 mount， 而 slotsOverlap() 走的是 mountCoverage()—— 餵它一個 dualHand ref，它本來就會同時擠掉左右手兩把、並寫入 slot:'dualHand'。所以 reducer 只要收到正確的 ref 就對了。 這是為什麼本計畫的改動面遠小於它的影響面。
決策四：side 一律不寫
dualHand 的 SlotRef 不帶 side（slotAcceptsSide() 對它回 false）。 寫了會讓 slotKey() 產出 main:dualHand:left 這種 永遠對不上 mountCoverage() 產物的鍵，症狀是「裝上去了但那一格顯示還是空的」。
邊界一：備用組（backup bank）
強襲者背包給的備用手是 0 或 2 格，slotExists() 對 dualHand 的判斷 （capacity ≥ 2）兩個 bank 通用，已經是對的。 但重量帳是主手組與備用組取較重者——一把雙手武器落在備用組時， 仍走 isHandSlot() 進 backupHand，需有測試釘住。
邊界二：固定武裝佔住其中一手
只要左右任一格被固定武裝佔住，雙手武器就該是 SLOT_OCCUPIED（灰掉並說明原因，不是 omit）。 canEquipWeapon() 的佔用檢查已經 for (const key of mountCoverage(ref))， 換上 dualHand ref 後自動涵蓋兩格。
邊界三：從雙手換回單手
手上是雙手武器時，往左手裝一把單手武器，slotsOverlap() 會擠掉那把雙手、 右手變空。這是對的行為，但提示文案要說得出來—— LoadoutPage.tsx 的 replaceNote() 那條死碼正是為此寫的，本計畫讓它復活。
Scope
實作範圍與不在範圍內
在範圍內：
  • loadoutRules.ts：新增 mountRefFor()； canEquipWeapon() 的槽位早退改為「雙手武器可進手部座標」； weaponChoices() 與 slotHasCandidates() 跟著走同一條
  • UI 派發端（LoadoutPage / 挑選器）改用 mountRefFor() 產出的 ref
  • 讓 replaceNote() 的 DUAL_HAND 分支真正跑得到，並確認文案正確
  • 槽位圖：一把雙手武器橫跨左右兩格的呈現（mountCoverage() 已提供依據）
  • 測試：40 把雙手武器可選、佔兩格、擠掉左右手、備用組重量、固定武裝佔手時灰掉附原因
不在範圍內：
  • 分享碼 codec 不動——codec.ts 的 SLOT_OF 早就有 1: 'dualHand'，格式本來就編得出來，只是至今沒有資料走到那條路
  • 元件（052-D）、雲端存檔（052-E）、形態分頁（052-F）、模組槽（052-G）
  • 已發出的分享碼不做任何回溯處理——它們本來就是合法的配裝，只是少了一類選擇
