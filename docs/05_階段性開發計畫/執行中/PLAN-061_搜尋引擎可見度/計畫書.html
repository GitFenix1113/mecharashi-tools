◆ PLAN-061

搜尋引擎可見度 SEO · 網頁標題 · sitemap

搜尋「鋼嵐」「Mecharashi」時不容易找到本站。站名維持「米赫瑪超吉情豹站」，把遊戲名放進網頁標題的最前面，替每一頁加上自己的標題，並補上 robots.txt、sitemap.xml 與網站名稱的結構化資料。

Problem
問題背景
一、網頁標題裡沒有遊戲名
原本的 <title> 是「米赫瑪超吉情豹站 — Milkhama PawInfo Station」，沒有「鋼嵐」也沒有「Mecharashi」。 在網頁本身能控制的項目裡，標題對排名影響最大；「鋼嵐 Mecharashi 繁中資料站」只寫在 meta description，而 Google 已說明 description 不計入排名。
二、全站只有一個標題
src/ 裡沒有任何地方依頁面設定標題，幾十個機師頁、機甲頁在搜尋結果與瀏覽器分頁裡長得一模一樣。 資料站最有機會拿下的「鋼嵐 ＋ 機師名」這類搜尋，因此對不上任何一頁。
三、沒有 robots.txt 與 sitemap.xml
public/ 底下兩個都沒有。後台、PR 預覽站（/preview/<branch>/，正式站的複本）也沒有擋，預覽站被收錄會和正式頁面搶排名。
未在本計畫處理：頁面全部在瀏覽器端產生
原始 HTML 只有空的 <div id="root">，內容要等 JS 從 Worker 抓資料。Google 會執行 JS，但排程較晚；Bing（Yahoo 奇摩搜尋的結果大致來自 Bing）處理 JS 較弱。 是否真的影響收錄，要等 Search Console 的「網址審查」看 Googlebot 渲染出來的畫面才知道（進度表 B-2），再決定要不要做預先渲染（見下方「後續選項」）。
期望值
只搜「鋼嵐」兩個字時，第一頁幾乎一定是官網、App Store／Google Play、巴哈姆特、維基百科與 YouTube，同好站叫什麼名字都很難擠進去。 本計畫的目標是長尾搜尋：「鋼嵐 資料站」「鋼嵐 配裝」「鋼嵐 ＋ 機師／機甲名」。
Design
設計決策
決策一：站名不改，標題加上遊戲名（站長 2026-10-14 指定）
網頁標題定為「鋼嵐 Mecharashi 資料站｜米赫瑪超吉情豹站」：關鍵字在前、品牌在後。品牌 2026-08 才正名過，不必再動。 src/lib/siteMeta.ts 新增 SITE_SEARCH_NAME（鋼嵐 Mecharashi 資料站）與 SITE_DOC_TITLE（完整標題）； SITE_TITLE（頁尾、配裝分享圖浮水印）維持原樣。og:title／twitter:title 一起換成新標題，讓不認識站名的人從分享卡片也看得出是鋼嵐的資料站。 Worker 的逐頁分享卡片（PLAN-038「海莉絲｜米赫瑪超吉情豹站」）不動。
決策二：每頁標題 =「頁名｜站台標題」
例：「機師圖鑑｜鋼嵐 Mecharashi 資料站｜米赫瑪超吉情豹站」「海莉絲 機師資料｜鋼嵐 Mecharashi 資料站｜米赫瑪超吉情豹站」。標題太長時 Google 會截掉尾端，被截的是品牌，關鍵字都在前面。
  • 路由預設頁名：src/lib/seo.ts 的 PAGE_TITLES，以路由樣板為鍵，沿用 analytics/routeKeys.ts 的 ROUTE_PATTERNS（已由測試與 App.tsx 綁住）。新增頁面不必接線。
  • 詳情頁覆寫：src/contexts/PageTitleContext.tsx 的 usePageTitle()。機師／機甲／武器詳情頁與故事館機師頁，資料到了以後換成「名稱 ＋ 類別」。
  • 覆寫記錄自己屬於哪個 pathname：換頁時就算舊頁的 cleanup 還沒跑，也不會把上一頁的名字套到新頁。
為什麼不用 React 19 的 <title> 元素
React 19 會接管 index.html 原有的 <title>，元件卸載時把那個元素整個移除（已對照 react-dom 原始碼確認）。 換到沒有宣告標題的頁面，文件就沒有標題了。所以改用一個 Provider 統一寫 document.title。
決策三：robots.txt 只擋沒有公開內容的路徑
擋 /admin、/profile、/debug/、/connectivity、/preview/。 不擋 /docs/：白名單複製出去的文件含遊戲機制說明，對玩家有用。Disallow 只是不爬，真正的權限仍在 AdminRoute 與 Firestore 規則。
決策四：sitemap.xml 在 build 時產生，只收 16 個固定頁
vite.config.ts 的 plugin 依 seo.ts 的 SITEMAP_STATIC_PATHS 產出 dist/sitemap.xml；PR 預覽（base 不是根路徑）不產。 詳情頁不列：列表頁都是 <a href> 連結，搜尋引擎會順著爬到。 要把詳情頁直接列進來，得在 build 時讀到實體清單，但 /api/* 有反爬守門（要求 Origin／Referer），Firestore 公開集合也已收成 read: if isAdmin()，build 讀不到—— 只能改由 Worker 在邊緣補上，那需要另外部署 Worker，先看 Search Console 的收錄狀況再決定。
決策五：首頁加 WebSite 結構化資料
Google 從首頁的 WebSite 結構化資料讀「網站名稱」（顯示在搜尋結果標題上方）。 name 用品牌「米赫瑪超吉情豹站」，alternateName 列「鋼嵐 Mecharashi 資料站」與英文名，讓搜尋引擎知道它們指的是同一個站。
決策六：用測試把「忘了做」變成紅燈
src/lib/seo.test.ts：每條路由都要有頁名、都要決定進不進 sitemap（SITEMAP_STATIC_PATHS 或寫理由進 SITEMAP_EXCLUDED）、每一頁的標題都要含「鋼嵐」與「Mecharashi」、sitemap 裡的頁不能被 robots.txt 擋掉。 src/lib/siteMeta.test.ts：index.html 的標題、og:title、twitter:title 與 JSON-LD 和 siteMeta.ts 一致（順手修正舊測試只找 content="…"、任一標籤對了就整組通過的漏洞）。
Scope
實作範圍與不在範圍內
在範圍內：
  • 網頁標題、og:title、twitter:title 改為「鋼嵐 Mecharashi 資料站｜米赫瑪超吉情豹站」
  • 每頁獨立標題（路由預設＋四個詳情頁的實體名稱）
  • public/robots.txt、build 產出的 sitemap.xml
  • 首頁 WebSite 結構化資料
  • 站長的上線後設定：Search Console、Bing Webmaster Tools、提交 sitemap（進度表 B 段）
不在範圍內（後續選項，看 Search Console 的結果再決定）：
  • 預先渲染（SSG／prerender）：若「網址審查」顯示 Googlebot 渲染出來的是空白頁，或詳情頁長期「已檢索，尚未建立索引」，再評估在 build 時把公開頁輸出成靜態 HTML。工程量大，而且資料只能從 Worker 讀。
  • 詳情頁列入 sitemap：由 Worker 接 /sitemap.xml，取 origin 的靜態版再補上 pilots／mechs／weapons 的網址（以資料版本號當邊緣快取鍵）。需要 wrangler deploy。
  • 每頁 meta description、canonical：Google 多半自己改寫摘要，效益低；網址也沒有明顯的重複版本，先不做。
  • 站外連結：巴哈姆特哈啦板、FB 社團、Discord 的連結對排名影響很大，這是站長的社群經營，不是程式工作。
