A-5   TTL 政策（取代 Cloud Function）
Firebase Console / gcloud
待開始
設定 expireAt TTL 政策 + 單欄位索引豁免
在 changeHistory 集合群組上設一條 TTL 政策指向 expireAt 欄位，保留兩年（決策九）。 同時要為 expireAt 設單欄位索引豁免——官方明確警告索引 timestamp 會造成寫入 hotspot，而此欄位從不參與查詢，保留自動索引純屬有害。 三個已知行為：① TTL 不受安全規則約束（是後端程序），與 A-3 的 append-only 完全相容； ② 刪除延遲約 24 小時，過期文件在實際清除前仍會出現在查詢結果； ③ TTL 刪除只計 delete 費用、不計 read——這正是不寫 Cloud Function 的理由。

src/lib/api/restore.ts
待開始
反向套用 ReversePatch[] + 衝突跳過並報告
逐筆反向套用：arrayRemove → 加回陣列、mapKeyDelete → 加回 map key、fieldClear → 寫回純量。 這三種天然冪等——只需檢查「該欄位現在還缺不缺這個值」，缺就補、已有就跳過， 不需比對整份文件是否未被改動（決策七）。 textFreeze 是唯一非冪等的：需比對現值是否仍等於凍結後文字，不符則跳過並列入報告。 來源文件若已不存在（例如整個機師被刪）同樣跳過並報告。 還原結束回報「成功 N 筆／跳過 M 筆」與跳過原因。

F-4   模擬器端到端驗證（AGENT 執行）
Phase 0 環境
待開始
在隔離環境跑完整刪除→還原往返
用 Phase 0 的模擬器環境與資料切片，由 AGENT 操作管理介面實測。必驗場景：
① 正常往返：刪除一個被多處引用的 BUFF → 確認引用全清、數值 token 已凍結 → 還原 → 確認引用全數復原；
② 衝突跳過：刪除後先編輯某個引用來源文件，再還原 → 確認該處被跳過並列入報告，而非硬蓋；
③ 來源消失：刪除後把某個引用來源整份刪掉，再還原 → 確認跳過並報告；
④ ID 已被重建：刪除後手動新建同名項目，再還原 → 確認中止並提示，不可無聲覆蓋；
⑤ 安全規則：以非管理員帳號嘗試讀 log、以管理員嘗試改／刪 log → 皆須被擋（驗證 A-3 的 append-only）；
⑥ 原子性：驗證 batch 失敗時不留半殘狀態、超過 500 操作會被攔截。
這是本專案第一個非純函式測試——現有 5 個測試皆無 mock、無 async、不碰 Firestore，需自行建立 setup/teardown 模式。
