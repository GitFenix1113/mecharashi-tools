◆ PLAN-030

資料變更歷史 — Change History · 級聯清除 · 快照還原

後台 BUFF／技能／詞條補上刪除功能：刪除時級聯清乾淨全站引用、不留混亂資料；刪除快照同時記下「被刪的文件」與「被移除的每一處引用」，可一鍵還原。所有異動寫入僅可新增的 changeHistory 集合，依「集合 × 操作」雙軸分類，並以 Firestore 原生 TTL 自動保留兩年。

一句話：先蓋好稽核，再開放刪除，而且刪除要刪得乾淨、也救得回來。新增一個只能寫入的 changeHistory 集合作為所有後台資料異動的黑盒子；刪除實體時級聯清除全站對它的引用，並把「被刪文件 + 每一處被移除的引用」一併寫進快照，形成一份可反向套用的還原單。底層做成集合無關，日後其餘 8 個集合各補一行即可接上。
規模提醒：本計畫在初版（純 log + 刪除按鈕 + 警示）之上，追加了級聯清除與快照還原兩項要求，工程量約為初版的兩倍，且從「單文件寫入」升級為「跨集合多文件交易」。Phase C／F 是全新增加的核心複雜度來源，若需要縮減範圍，這兩個階段是唯一有意義的切點（見文末「分期取捨」）。
Problem
問題背景
① 後台從來沒有刪除功能
三個管理分頁（BuffAdmin / SkillAdmin / GlossaryAdmin）目前只有新增與編輯。全 repo 唯一的 deleteDoc 出現在 src/lib/userApi.ts 的 deleteBuild()（使用者刪自己的配裝），11 個遊戲資料集合一律沒有任何刪除路徑。誤建的 BUFF、測試用詞條、改版後作廢的技能只能放著或改名重用，垃圾資料逐月累積且會出現在引用挑選器的候選清單裡干擾維護。
② 任何資料異動都無跡可循
現行寫入是 setDoc(ref, data) 不帶 { merge: true }，等於整份文件覆寫，舊值在寫入當下就消失。誰、在什麼時候、改了哪個 BUFF、改動了哪些欄位，系統裡沒有留下任何痕跡。
③ 引用散布在 9 個集合，刪除會留下大量斷裂關聯
BUFF／技能／詞條是被大量引用的底層實體。實際盤點後，可能持有引用的欄位散布在 pilots（天賦、技能、神驅等級三處）、pilotSkills、buffs（BUFF 互相引用）、weapons、modules、backpacks、components、glossaryTerms、neuralDriveAbilities 共 9 個集合。刪除若不處理引用，這些關聯全部變成指向空氣的死連結。
④ 「新增」與「修改」在程式上分不出來
updateBuff / updatePilotSkill / updateGlossaryTerm 沒有獨立的 create 函式——建立與修改是同一個 setDoc 呼叫，UI 只在建立前用 docExists() 擋同名碰撞。稽核若要分辨這兩種操作，API 層必須自己取得寫入前的舊文件。
⑤ log 會無限成長
每次存檔都寫一筆記錄，且 append-only 規則下前端無法清理。若不設保留策略，這個集合只會單調增長，最終拖累儲存成本與查詢效率。
Design
設計決策
決策一：獨立頂層集合 changeHistory，完全隔離在快取層之外
不做成各集合的 subcollection，也不註冊進 CollectionKey。理由：前台永遠不需要讀這份 log，而 GameDataContext 的版本 gate 三層快取是為「整包載入、長期不變的靜態遊戲資料」設計的；log 是持續成長、只查最近幾頁的資料，塞進那套快取只會白白撐爆 localStorage。因此它是專案裡唯一一個「後台專用、走伺服器分頁、不進 GameDataContext」的集合。
決策二：append-only 規則 — 連管理員都不能改自己的 log
現有集合一律是 allow write: if isAdmin();，而 write 涵蓋 create／update／delete。log 若沿用這套，管理員就能竄改或抹除自己的操作記錄，稽核價值歸零。改用：
match /changeHistory/{docId} { allow read: if isAdmin(); // 僅管理員可讀（不像遊戲資料公開） allow create: if isAdmin(); // 只能新增，寫下去就定型 allow update, delete: if false; }
決策三：雙軸分類用兩個獨立欄位，不用複合字串
分類軸為集合類型（target）×操作類型（action）。關鍵是這兩者必須是各自獨立的 top-level 欄位，不能圖方便寫成 'buff:create' 這種複合字串——Firestore 的 where 只能對獨立欄位做等值比對，複合字串一旦寫死，就永遠無法查詢「所有集合的刪除記錄」。
// src/types/changeHistory.ts export type ChangeAction = 'create' | 'update' | 'delete' | 'restore' export type ChangeTargetKind = 'buff' | 'pilotSkill' | 'glossaryTerm' // 可擴充 export interface ChangeHistoryEntry { id: string // Firestore 自動 ID（log 無自然 slug） target: ChangeTargetKind // 分類軸一 action: ChangeAction // 分類軸二 targetId: string targetName: string // 去正規化，查 log 免 join actorUid: string actorName: string // displayName 快照（改名後仍看得懂是誰） at: Timestamp // serverTimestamp() expireAt: Timestamp // at + 2 年，交給原生 TTL（決策九） changedFields?: string[] // 僅 update snapshot?: DeleteSnapshot // 僅 delete（決策六） restoredFrom?: string // 僅 restore：來源 log 文件 ID }
需要三組複合索引：(target, at↓)、(action, at↓)、(target, action, at↓)。
決策四：寫入前先讀一次 pre-image，用「舊文件是否存在」判定 create / update
針對問題④。寫入前多做一次 fetchDocument()：回傳 null → create；有值 → update，並用這份 pre-image 做淺層 key 比對算出 changedFields。
成本：每次存檔 +1 read。已確認可接受——後台編輯與刪除都不是經常性行為。
不採用：從 UI 傳 isNew 旗標（省 1 read，但拿不到 pre-image，等於放棄 changedFields，且同一 helper 無法供刪除快照複用）。
決策五：級聯清除引用 — 引用是「側錄表」設計，可外科手術式移除
盤點後發現一個決定可行性的關鍵事實：引用採錨點與綁定分離的側錄表設計。[虛粒子形態] 這個錨點在文案字串裡，但真正的綁定關係存在獨立的結構化欄位 descriptionRefs：
// src/types/common.ts export type DescriptionRefs = Record<string, EntityRef> // key = 括號內文字，value = { refType, refId, label?, level? } // 實際儲存形狀 description: "進入[虛粒子形態]，可疊加<buff_凝勢.lv3.maxStack>層" descriptionRefs: { 虛粒子形態: { refType: 'buff', refId: 'buff_虛粒子形態' } } // └─ 結構化 map，delete refs[key] 即可，完全不必動文案
因此四類引用全部可機械移除：descriptionRefs map key、buffIds[] 陣列元素、termRef 純量欄位、abilityId 純量欄位。
但「外科手術式」只成立於資料語意層，不成立於寫入機制層（C-2 實作後補充）： 上面那句 delete refs[key] 即可 描述的是記憶體中的操作。真要把它送進 Firestore 時， 原本設想的 arrayRemove() / deleteField() sentinel 大部分站點用不了—— Firestore 的 FieldPath 不能穿越陣列：'talents.2.buffIds' 會被解讀成 map key '2'， 而非 talents 的第 3 個元素。C-1 盤點的站點中帶陣列索引的佔多數 （talents[] / skills[] / neuralDrive[].levels[] / weapons.skills[] / *.levels[]）。 C-2 因此統一改為「載入文件 → 記憶體內修改 → 只寫回被動到的頂層欄位」， 並刻意不對少數可走 sentinel 的站點特例化（混用兩套機制，Phase F 就得寫兩套逆運算）。 連帶影響兩處：① 寫入是該頂層欄位的 last-write-wins，故 C-4 必須用「當下重讀」的文件建 plan，不可餵 GameDataContext 快取； ② 同文件多處命中已合併成單筆 update，batch 500 上限的計算基準由「站點數 + 1」變為「文件數 + 1」。
與 buildBuffPool 的關係（C-1 實作後更正）：本計畫初稿寫「buildBuffPool() 已經在走訪全站每一個 buffIds 站點來建反向索引，traversal 完全相同」——這句話高估了它。 實際上它只有一處呼叫（SimulatorPage.tsx:861），傳入的是單一套配裝（一個機師、幾個模組、一把武器、一個背包），產出「這套配裝能拿到哪些 buff」，完全沒有迭代任何集合； 而且它只處理 buffIds，不碰 descriptionRefs / termRef / 數值 token——而那三者才是真實資料裡引用的主體。
因此可共用的是站點路徑定義（哪些欄位持有引用），不是走訪函式本身：buildBuffPool 是「單配裝 → BuffSource[]」，findReferences 是「全資料庫 → 誰引用了 X」，形狀不同。 C-1 的做法是把站點定義抽成 src/utils/entityRefs.ts 的 registry，兩者各自消費同一份定義。
決策五之附帶地雷（實作務必注意）
① buffIds 帶 @N 等級後綴：陣列元素可能是 "buff_傷害提升@3"（PLAN-024）。用字串相等過濾會讓它在刪除 buff_傷害提升 後存活下來變成死連結。必須先用既有的 parseBuffRef()（src/utils/buffRef.ts）解析出 buffId 再比對。
② Pilot.skills 是 (string | PilotSkill)[] 聯合型別：PLAN-004 遷移中途狀態，同一陣列裡可能混有「ID 字串」與「內嵌物件」兩種形態，走訪必須兩種都處理。buffPool.ts:62-68 有現成的處理範式可抄。
③ 引用站點清單必須與 buffPool.ts 保持同步：兩處各走各的會逐漸偏移。實作時應讓級聯清除與 buildBuffPool 共用同一份站點定義。
C-1 實作時發現的第三顆地雷：ChangeTargetKind 與 RefType 是兩套不同字串
這顆比 @N 更容易犯，且症狀完全一樣（靜默漏清）：
// src/types/changeHistory.ts type ChangeTargetKind = 'buff' | 'pilotSkill' | 'glossaryTerm' // src/types/common.ts type RefType = 'buff' | 'skill' | 'term' | … // ↑ 不同名！ ↑
findReferences('pilotSkill', …) 若直接拿 kind 去比對 EntityRef.refType，所有技能與詞條引用都會零命中， 而且不會拋錯、不會有任何警告。已加 REF_TYPE_OF 顯式映射表並以單元測試 D0~D3 鎖住。
另外兩個同類約束（皆已納入實作）：
· descriptionRefs 的 map key 是使用者輸入的中文，可能含 . → ReversePatch.path 是 . 分隔字串， C-2 若用 path.split('.') 還原 FieldPath 會拆錯。故 RefHit 同時帶 segments（陣列，權威）與 path（字串，顯示用），C-2 只准用 segments。
· 索引式路徑不是穩定識別子 → 還原時 talents[] 若已被重排，patch 會套到錯的天賦上。故每個站點盡量帶 anchor（by name / level / minSum）， 讓 Phase F 能「先按 index 找、對不上則按 anchor 重新定位」。這個格式是 C-2/F-2 的契約，現在不加之後補不上。
C-1 盤點發現的第四類引用：nameSoftRef（以名稱而非 ID 關聯）
原本假設所有引用都是 ID 型，盤點後發現 SkillCondition.hasBuff（src/types/buff.ts:43）存的是 buff 的「名稱」而非文件 ID，散布在 11 處路徑（機師天賦 / 專武強化效果 / 技能 / 神驅各級 / BUFF 自身 / BUFF 各級 / 武器技能…）。
ID 型級聯無法處理它：刪除 buff_凝勢 時掃不到 hasBuff: '凝勢'，改名也會靜默斷鏈。 PilotAdmin.tsx:100 是純文字輸入框、無任何校驗。
處置：掃描器認得這 11 條路徑，但命中結果進 softWarnings 而非 hits——只在對話框列出讓管理員自行處理，不自動清除。 自動清除一個「靠名稱字串比對」的欄位風險過高（同名不同義、部分匹配）。
實測全站 0 筆，屬「型別在、資料無」的類別。
Phase 0 實測發現：buffIds 在正式資料裡幾乎沒被填
匯出模擬器切片時實際統計正式資料，結果與規劃時的假設有明顯落差：
來源buffIds 陣列非空
pilots（2 名機師，含引用最密的兩位）38 個0
pilotSkills705 個1（["buff_虛粒子形態"]）
整份切片中的 @N 等級後綴0 個
正式資料的引用實際上幾乎全走 descriptionRefs 側錄表與文案內嵌數值 token。buffIds 是典型的 「集合會被填滿、選填欄位不會」——欄位存在、有型別、有 UI，但實際維護時沒人填。
三個後果：
① @N 後綴仍是必須寫對的程式邏輯（資料隨時可能開始被填），但真實資料一個實例都沒有 → F-4 整合測試撞不到它，C-6 單元測試從「建議」變成唯一覆蓋手段。
② 級聯清除的實際主戰場是 descriptionRefs + 數值 token 凍結，測試素材（梅利莎 numRef=20、艾達 refId=15）正好覆蓋這兩者。
③ 複用 buildBuffPool() 走訪邏輯的決策仍然正確，但要知道它目前走的是一個近乎空的欄位—— 這也解釋了為何 buffIds 相關的既有功能不易察覺問題。
決策六：數值 token 用「凍結」而非移除，讓文字層也變成可機械處理
唯一不可機械移除的是內嵌在文案字串裡的數值 token：<buff_凝勢.lv3.maxStack>。要移除它就得改寫文案，風險高。
解法：既有的 resolveNumRefs(text, lookup)（src/utils/numRefs.ts）本來就能把 token 換算成實際數值——刪除前先對受影響文案跑一次，把最後已知數值烘焙進文字：
// 刪除 buff_凝勢 之前 "可疊加<buff_凝勢.lv3.maxStack>層，持續<buff_凝勢.lv3.duration>回合" // 凍結後（token 就地變成常數，不再依賴已刪的 BUFF） "可疊加5層，持續3回合"
這個函式原本是為 DiffHighlight 預處理寫的，但它正好就是「在來源消失前把值固定下來」所需要的原語，幾乎是一行呼叫。
「幾乎是一行呼叫」是錯的（C-3 實作後更正）：resolveNumRefs 無差別替換正文裡的所有 token， 不分它指向哪個實體。真實文案常有多個 token 指向不同 BUFF（上面那個例子只是剛好兩個都指向 buff_凝勢）， 直接套用會把無辜的引用一併烘焙成死數字——日後那些 BUFF 改了數值，正文不會跟著更新， 而且事後完全看不出它曾經是引用，連修補單都沒記（因為那些 token 不屬於本次刪除的命中）。 C-3 因此在 numRefs.ts 新增 freezeNumRefs(text, targetId, source)， 只烘焙指向被刪實體的 token，其餘原樣保留；內部仍借用 resolveNumValue 共用 registry 與 .lvN 取級邏輯。
取捨：凍結後的文字失去動態連動（日後改 BUFF 數值不會跟著變），但來源都要被刪了，本來也連動不了。凍結前的原始文字必須存進快照，否則還原時無法復原成 token 形式。
不採用「留著讓它顯示 ?」：系統確實有優雅降級（未解析的 token 顯示為淡色 ? 加 tooltip），但那個 ? 對管理員與使用者而言看起來就是 bug，不符合「不造成資料混亂」的要求。
決策七：刪除快照 ＝ 文件本體 ＋ 反向修補單，且反向修補單天然冪等
初版快照只存被刪文件本身，那不足以還原引用。改為三段式：
export interface DeleteSnapshot { doc: Record<string, unknown> // ① 被刪文件完整內容 patches: ReversePatch[] // ② 每一處被移除的引用 } export interface ReversePatch { coll: string // 'pilots' docId: string // 'pilot_艾達' path: string // 'talents.2.buffIds' / 'talents.2.descriptionRefs.凝勢' op: 'arrayRemove' | 'mapKeyDelete' | 'fieldClear' | 'textFreeze' value: unknown // 被移除的原值（textFreeze 存凍結前原始文字） }
關鍵性質：前三種 op 的還原都是「把元素加回集合」，天然冪等。這讓還原不需要比對整份文件是否未被改動（那等於做時光機），只需檢查「該欄位現在還缺不缺這個值」——缺就補、已有就跳過。衝突處理因此從「時光機」降級為「補一個缺項」，複雜度大幅下降。
textFreeze 是唯一非冪等的（覆寫字串），還原時需比對現值是否仍等於凍結後的文字，不等於就跳過並報告。
決策八：刪除是跨集合多文件交易，用 WriteBatch 保證原子性
一次刪除實際包含：1 次目標文件 deleteDoc + N 次引用來源 update + 1 次 log 寫入。若非原子，中途失敗會留下「文件刪了但引用還在」或反之的半殘狀態——比不做級聯更糟。
做法：用 writeBatch() 把目標刪除與所有引用清除包成單一原子提交。
硬限制：Firestore batch 上限 500 個操作。需防呆：引用站點數 + 1 若超過 500，中止操作並提示管理員（實務上單一 BUFF 被 500 處以上引用極不可能，但不能無聲截斷）。
log 寫入刻意排在 batch 之外：沿用決策十的原則，log 失敗不得回滾已成功的資料操作。
決策九：log 保留策略用 Firestore 原生 TTL，不寫 Cloud Function
針對問題⑤。雖然已有 Blaze 方案可用 Cloud Function，但原生 TTL 在這個場景嚴格更優：
項目原生 TTLCloud Function 排程
找出過期文件不需查詢要 query，每筆計 read
刪除計 delete計 delete
執行成本無Function 調用 + Cloud Scheduler
程式碼零，純設定要寫、部署、維護
官方文件明載「TTL delete operations count towards your document delete costs」，且不另計 read——而 Function 方案必須先讀出來才知道刪誰。你擔心的流量負擔在 TTL 方案下基本不存在。
做法：寫入時多存 expireAt = at + 2 年，在 changeHistory 上設一條 TTL 政策指向該欄位。因此「筆數上限」的備案不需要了。
決策九的兩個關鍵細節（容易踩雷）
① TTL 與 append-only 規則不衝突。安全規則只約束 client SDK；TTL 是後端程序，不受 allow delete: if false 影響。兩者可以同時存在——這正是理想組合：前端永遠刪不掉，但系統會自己過期清理。
② TTL 欄位要設單欄位索引豁免。官方明確警告索引 timestamp 欄位會造成寫入 hotspot。expireAt 從不參與查詢（只有 TTL 程序讀它），保留自動索引純屬浪費且有害。
③ 刪除延遲約 24 小時，過期文件在被實際清除前仍會出現在查詢結果。對 log 檢視而言無影響。
④ TTL 一併帶走還原能力：兩年後 log 被清除，快照也隨之消失。誤刪兩年後才想還原並不現實，屬可接受取捨，但需明確知道。
決策十：log 寫入失敗絕不可擋住主操作
順序固定為「主寫入成功 → 才寫 log」，且 logChange() 不被 await、內部 .catch() 吞掉錯誤只在 console 警告——沿用既有 bumpDataVersion(...).catch(() => '') 的慣例。
理由：稽核 log 是輔助設施。若因規則未部署、索引缺失或網路瞬斷導致 log 寫入失敗就讓存檔丟出錯誤，管理員會誤以為資料沒存進去而重複操作。
代價：極端情況下會漏記。但刪除是例外——刪除的 log 承載還原用的快照，漏記等於永久失去救回能力，因此刪除路徑的 log 採先寫 log、再執行 batch 的順序，log 寫失敗則中止刪除。
決策十一：GameDataContext 補上 removeCollectionItem
現有的 patchCollectionItem 是 upsert-only。刪除後若不做對稱處理，被刪項目會殘留在記憶體 state 與 localStorage 快取，直到手動 reload。
級聯清除讓這件事變複雜：被改動的不只目標集合，還有多達 9 個引用來源集合。逐一 patch 不切實際，做法是對所有被觸及的集合呼叫 bumpDataVersion，讓其餘 client 自然失效；編輯者自己則直接對受影響集合走一次 reload。正確性優先於 read 數最佳化——刪除是低頻操作。
決策十二：測試用 Firebase Emulator Suite，不在網站埋開發後門
Phase C／F 是本計畫風險最高的部分，需要 AGENT 能進入管理介面實測。曾考慮「埋一個開發用旗標讓 AGENT 免登入 ADMIN」，評估後否決，改用官方模擬器：
比較項開發後門Emulator Suite
資料隔離 無——繞過驗證後動的仍是正式資料庫 完全隔離，本機獨立實例
安全規則 未受測——繞過驗證＝isAdmin() 不執行 原封不動執行，真的測到
production 風險 永久存在——import.meta.env.DEV 是編譯期旗標，build 模式設錯即為線上活後門 零——不留任何東西在 prod
關鍵：需求其實有兩個——① AGENT 要能進管理介面 ② 不要影響真實資料庫。後門只解決①，而模擬器兩個一起解決。更要命的是本計畫正好要新增一組全新的 append-only 規則（A-3），其核心就是 isAdmin()；用「關掉待測機制」的方式去測試待測機制，等於沒測。
為什麼這個專案用模擬器特別便宜（三個關鍵事實）
① role 存在 Firestore 文件而非 custom claim。路徑是 users/{uid}/profile/main（src/lib/userApi.ts:18），所以「偽造管理員」＝寫一份 JSON 文件，不需要 mint token、不需要 setCustomUserClaims、不需要 client 端 claim 刷新。
② firestore.rules 的 isAdmin() 讀的是同一份文件。因此規則檔原封不動就能在模擬器運作，種一個 role: 'OWNER' 同時滿足 client UI 與規則兩邊。
③ 所有寫入腳本都走 Admin SDK。firebase-admin 會自動識別 FIRESTORE_EMULATOR_HOST / FIREBASE_AUTH_EMULATOR_HOST 環境變數，匯出兩個環境變數即改指模擬器，零程式碼改動。
另：docs/02_技術文件/04_Firebase/Firebase設定與資料更新指南.html 已提議過 VITE_USE_EMULATOR 旗標，本決策與既有意圖一致，非另起爐灶。
決策十三：把可測邏輯盡量推成純函式，模擬器只驗證真正需要資料庫的部分
盤點後發現 Phase C／F 的高風險邏輯絕大多數是純函式，不需要驗證、不需要資料庫：
純函式（node --test 即可）需要模擬器（整合測試）
findReferences() 全站掃描
@N 後綴比對（風險表 HIGH 項）
反向修補單產生
修補單冪等重加（還原核心）
數值 token 凍結 		WriteBatch 原子性
500 操作上限攔截
append-only 安全規則
端到端刪除→還原往返
左欄涵蓋了還原正確性的主要風險，而且專案已有 5 個純函式測試（src/utils/*.test.ts）可直接沿用其模式與 fixture 寫法。這讓 Phase F 的風險在模擬器就緒前就能先降下來。
注意：模擬器整合測試會是本專案第一個非純函式測試——現有 5 個測試皆無 mock、無 async、不碰 Firestore。這是在建立新模式而非延伸既有模式，需自行處理 setup/teardown。
Scope
實作範圍與不在範圍內
在範圍內：
  • changeHistory 集合：型別、API、append-only 規則、三組複合索引、TTL 政策 + 索引豁免
  • 集合無關的 saveWithHistory / deleteWithHistory 通用 helper

  • 數值 token 凍結（刪除前烘焙最後已知值，原文存快照）
  • 反向修補單與還原引擎（冪等重加 + 衝突跳過並報告）
  • 刪除確認對話框（列出將被清除的引用清單）與三個分頁接線
  • 變更歷史檢視頁：雙軸篩選、伺服器分頁、快照展開、還原入口
  • 本地 Firebase Emulator 環境：連線分支、模擬器管理員種子、真實資料切片匯入、AGENT 可獨立操作
  • 純函式單元測試（掃描／@N 比對／修補單產生與冪等重加）與模擬器整合測試
不在範圍內：
  • 其餘 8 個集合的接線——底層已通用，日後每集合各補一行
  • 修改操作的還原——只有 delete 存快照，update 僅記 changedFields（見下方取捨）
  • 還原被凍結文字的自動重新連動——還原會把文字還原成 token 形式，但若期間 BUFF 數值已變，值會直接跟著新值走
  • 前台任何呈現——純後台功能，規則層即擋住非管理員
  • Cloud Function——決策九已論證原生 TTL 更優，本計畫不引入 Function
  • 任何形式的開發後門 / 免驗證管理員捷徑——決策十二已否決，改用模擬器。此項明列於此以免日後又被當成待辦撿回來
  • 正式資料庫的寫入測試——所有 Phase C／F 的破壞性驗證一律在模擬器進行；對 prod 僅有一次唯讀匯出（資料切片）
  • 爬蟲／migrate 腳本寫入的稽核——走 Admin SDK 不經前端 API 層；批次寫入逐筆記 log 會瞬間灌爆集合
  • 未上線的 bosses / stages 集合——型別已存在但無規則、無 CollectionKey、無 API，掃描站點暫不涵蓋（PLAN-019 Layer 3 上線時補）
為什麼 update 不存 before 快照：BUFF／技能含 levels[] 等巢狀結構，每筆修改存完整前後快照會讓 log 迅速膨脹，而修改的追溯需求通常「知道誰動了哪些欄位」就足以定位。刪除則是不可逆操作，必須留完整後路。若日後發現不夠用，加一個選填 before 欄位即可，不影響已寫入的舊 log。
