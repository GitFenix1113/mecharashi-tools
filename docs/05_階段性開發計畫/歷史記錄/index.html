PLAN-052-L · 匯出圖改版與技能配置

團隊 2026-08-29 提出八項回饋，本計畫承接其中的 2–8 共七項。逐項查過原始碼與正式庫之後，它們不是同一種東西：五項是匯出圖的版面問題、兩項要動資料模型與分享碼、而第一項（三碼三圖）根本不是圖的問題——它的正解是分享連結 OG 卡，歸 PLAN-052-H 既有範圍。
三個要修的現況：① 圖上今天印的是 statText()，而候選池 186 顆模組有 119 顆（64%）滿級數值欄全為 0 ⇒ 三分之二的模組在圖上只有一個名字，而且它會漏掉觸發條件卻看起來像完整答案（猛擊裝置的「格鬥傷害+15%」省略了「有 70% 的概率發動」）；② gammaPairCap = 23 是雙區共用預算，但有 10 位 1.0 老角只有單一個 γ 區（天花板 16），他們的圖上印著 16 / 23，像「還差 7 沒點滿」而那 7 點永遠不存在；③ 裝備條列表與遊戲整備畫面對不起來，而螢幕版早就是位置化的——這一項是把已裁決過三次的空間語彙搬到印刷品上，不是重新設計。
兩個新欄位（方案備註、攜帶技能三格）都走分享碼的 TLV 追加段（NOTE=6／SKILLS=7），舊 client 會跳過不拒收 ⇒ 零遷移。技能候選池 ＝ pilot.skills − 職業單元（unitType === '6'，天生自帶不佔格）——⚠ 計畫書原訂還要再減 manual，但那個旗標記的是「這筆資料誰建的」而不是「要不要攜帶」，且會讓 3.3+ 那七位機師的候選池歸零，已於 2026-08-30 依使用者裁決拿掉（見 D-4）；第四格「改」技能只開欄位不開 UI（站上沒有這份資料，而分享碼只進不出）。
Phase A～F 全數完成（進度 41／41）：模組改印官方敘述、四格 Stat 收成一條窄帶（順手修掉上面第 ② 個線上錯誤），裝備區則從四欄條列表換成與遊戲整備畫面同構的十字（幾何走新的 rigLayout() 純函式，螢幕版與匯出圖共用同一套「畫面左欄＝機體右側」裁決）。C 又補上方案備註（100 碼點／6 行，走分享碼的 §NOTE 追加段、舊 client 跳過不拒收 ⇒ 零遷移），並把書架去重改成比「去掉名稱與備註之後的本體」。D 讓玩家第一次選得動機師技能（三格自由替換，走 §SKILLS 追加段；853 筆技能因 doc id 是純名稱而全部走 shareId 別名區，由對帳腳本 append-only 自動續號）。E 補上回饋 1 的本站那一半：一顆「複製摘要」把同一套配裝輸出成可搜尋、可 Ctrl+F、可貼進 wiki 的純文字（PNG 這三件都做不到），圖底則同時保留完整碼與新的 QR（給只拿到「別人螢幕截圖」的人掃）；為了讓文字與圖不漂移，模組列、γ 分區過濾、槽位座標三處抽成共用函式。F 的驗收在真的瀏覽器裡量完：匯出 787ms（A-1 那條「固定燒滿 5 秒」確實消失）、最壞情況圖高 2,792 CSS px（離 iOS 的 canvas 上限還有 33%），而縮圖壓到 156px 之後只有 HERO 與重量色帶活著——「縮圖只負責讓人點開」因此從假設變成量過的裁決，主版面不動。

PLAN-052-M · 模組算力加成與 α／β 鎖定

補一個一直缺的模型：有些模組會加神經驅動算力。強擊模組的 LV.MAX 寫著「已解鎖的神經驅動分區中最低的區域算力+3」，而站上先前只把它當一段文字印出來 —— 條上的格數、匯出圖的能力清單、純文字摘要的分區等級全部少一級。這不是理論問題：機甲疾嘯天生帶的 8 級模組就是它，四部位各 2 級剛好湊滿 LV.MAX，玩家什麼都不用做加成就在（換掉一個部位就掉到 6 級、加成消失）。
計畫真正的內容是把一個量拆成兩個：投入算力（玩家點的、吃 23 的預算、存進分享碼）與生效算力（含加成、決定哪些能力亮著、印在圖上）。先前兩者是同一個數，一旦不相等（投入 23 可以生效 26），任何一處混用都不會報錯，只會讓格子與數字對不起來。加成因此一律不落盤 —— reconcileNdLevels() 有一條「γ 合計超過 23 就整份丟掉」，落盤會讓合法的 26 被靜默洗回預設值。
兩條裁決：α／β 鎖死在滿級不開放調整（只有 3 級、人人點滿，鎖掉之後加成的落點自動只剩 γ）；γ1 與 γ2 平手時加在 γ1（站長實機測出來的，官方文案沒講）。

PLAN-052-E · 雲端存檔與配額

登入者的存檔能力從 0 變成「每位機師 5 格、換一台裝置也看得到」。落盤形狀沿用總綱決策二 （users/{uid}/builds/{pilotId} ＋ slots map，每格就是一串分享代碼）—— 儲存＝分享，沒有第二套序列化。
安全規則是本計畫唯一不可逆的部分：身分、頂層 key 白名單、slot key 白名單 （⇒「每機師 5 格」是結構性事實而不是會漂移的計數欄位）、每格 size() <= 4096。 ⚠ 第五件擋不住：文件份數 —— 規則沒有 count()，也驗不了 {pilotId} 是不是真的機師。 A-3 裁決接受這個殘餘風險，並把「哪一條沒被守住」寫進規則註解本體，不假裝擋住了。
上限 1024 → 4096 是實測改出來的：B-4 量到「號碼全滿 ＋ 4 套獨立形態」＝ 1051 字元， 1024 在那裡就破了（每多一套形態約 +160 字元）。而上限只能放寬不能收緊，挑小了才是不可逆的錯； 4096 同時與 codec 的解碼上限對齊，消掉「解得開卻存不了」那段落差。
v1 Build 整條刪除而非遷移：A-1 直讀正式庫復驗 builds 實測 0 筆 （順帶訂正總綱「users 0 筆」—— 那是量測假象，父文件是空殼，實際有 42 個帳號）。
訪客書架是匯入不是搬移：localStorage 那 10 格不清空（同一個瀏覽器可能有別人在用）， 成功的改標「已在雲端」——而那個標記是比對代碼字串算出來的，不存旗標（旗標會在雲端那邊被刪後繼續說謊）。 兩種配額語意不同 ⇒「塞不下」是正常結果，逐筆回報而不是一句「匯入完成」。
⚠ 四個 bug 是實地驗收抓到的、單元測試全都抓不到：模組索引漏傳別名表（每套帶模組的存檔被誤判成「已下架」）、 AuthModal 的 z-index 蓋不住書架（按登入像沒反應）、匯入摘要重複計數、以及 離線時 setDoc 永遠不 settle（SDK 把寫入排進佇列，UI 永久停在「存入中…」）。

PLAN-052-K · 天生模組逐部位化

一顆天生模組的等級 ＝ 四個部位各自貢獻的等級加總（＋插槽貢獻 × 部位倍率），而站上把它存成 mech 頂層的三個 id、沒有部位也沒有等級。052-G Phase D 讓玩家能換部位之後， 「自帶 4」那一列就開始說謊了 —— 換掉滿階帕斯卡的右臂，遊戲裡〈彙編矩陣〉整顆消失、 〈蓄能模組〉8→6、〈出力模組〉4→3，站上卻一顆都不動，而且不報錯。
核心決策：矩陣不落盤，用規則推導。90 台 × 4 部位 ≈ 1500 格全是規則的產物，落盤只會在改版時過期 （加上 0/5 定律，1500 格選填欄位必然腐爛）。滿配假設下規則表只有九個數字， 已用 57 台 SSR × 兩端點 × 四部位驗過：8 級模組與副模組 57／57 全中。 專屬模組的逐部位等級更是零新欄位——(boundPart, levels.length) 就推得出來，24 顆零例外， 其中彌造者〈帕姆斯陣列〉「軀幹 LV1～3 為 1 級、LV4 彩為 2 級」由站長實機確認。
但重心不在爬蟲，在後台。站上 90 台已到 v3.6，官方 aircraft_data 只有 83 台、停在 v3.2 —— v3.3 之後的 7 台官方完全沒有資料，全靠維護者人工建檔。所以 Phase C（ModuleAdmin 兩個新欄位、 MechAdmin 的推導預覽＋逐格覆寫入口）不是順便加欄位，是這個計畫能不能長期活下去的關鍵； 對帳腳本只能覆蓋官方有的 83 台，是輔助不是主力。
另外三個機制目前在資料模型裡根本不存在：部位倍率（破曉者-02〈匯流樞紐〉的「某部位插槽等級翻倍」 只存在描述文字裡，而且兩顆同名效果不同，用名稱查表必撞）、 觸發式模組（限制解除 6 顆 —— 復仇女神 ×4 的觸發者是別顆模組〈迸發模組〉LV.MAX， 它們自己的描述裡沒有「限制解除」四個字，掃自己描述的做法會全數漏掉）、 以及專屬模組的逐部位等級。
⚠ 順帶結案一條：052-G E-3「延後」的前提已經不成立——當初的理由是「滿階下 Σ 是常數」， 但滿配假設擋掉的是「品質階」這個維度，擋不掉「來源機甲」這個維度。
✅ 全部完成（2026-08-29，33/33）——推導層、資料補完、後台維護介面、模擬器接線、對帳與驗收都已上線： 換掉一個部位，「機甲自帶」那一列會跟著改變（連效果文字都跟著降階），觸發式模組失效時 顯示為停用態並講出原因而不是消失。 關鍵修法是把六處各自呼叫的 moduleStacks() 收成單一的 ctx.stacks —— 只補其中一處的話，右欄的 Lv、四部位卡、可用出力與匯出圖會各說各話。
對帳腳本 check-part-module-drift.mjs 跑出 83 台 × 932 格逐格全中，規則表一格都不用動； 它 import 站上真正在跑的那份實作，不另寫一份規則。已掛進 data-patch skill 的檢查清單。
⚠ 順帶浮出兩筆與本計畫無關的資料問題，兩筆都在 E-3 當天（2026-08-29）修完：
① sub_mod_防爆模組 的 name 是「防暴」，而官方與它自己的 doc id 都是「防爆」 （效果文字「被暴擊率降低」裡的「暴」是暴擊，與模組名無關）——判定為手動輸入的錯字 ⇒ 改資料，不在腳本裡登記例外。 改名前先驗過全庫沒有第二顆同名（moduleFamilyKey 用的就是名稱，撞名會靜默併族）。
② U+FFFD 截斷字全庫實際是 23 個欄位，不是 2 筆（modules 2 ／ pilots 18 ／ weapons 3）。 根因是各爬蟲的 fetchJson() 寫成 res.on('data', c => data += c) 卻 沒有先 res.setEncoding('utf8') —— chunk 是 Buffer、+= 逐塊 toString， 中文字剛好跨在邊界就碎掉一個字。所以它不是某次改版壞掉，而是每次重抓都可能在不同欄位長出一個新的。 ⇒ 六支爬蟲 ＋ 兩支對帳／補值腳本，共 8 支已補上（圖片下載那兩條走 chunks.push(Buffer)，刻意不動，設了會壞）。 既有資料由 repair-fffd-descriptions.mjs 23／23 全數修復、0 筆需人工，三個集合已 bump、fixture 與 slice 已重出。
⭐ 修法刻意不用猜的：把壞字串切成前綴＋<FFFD>＋後綴回官方 detail 比對， 只接受「長度剛好、前後綴完全吻合」且恰好一個的候選 —— 猜出來的字沒有來源， 而錯字混在一堆正確文字裡就再也查不出來。

PLAN-052-G · 模組槽與部件混搭

模擬器僅存的兩塊空白。四個模組接口沒有入口——052-I 畫出來的四部位卡是唯讀的，卡片底下那行「部件混搭開放後，每個部位可換成別台機甲的同位部件」就是在等這個計畫；四個部位固定來自同一台機甲——右欄的四部位表整個被註解掉，註解逐字寫著「等部件混搭開放後，這張表才開始回答『這一套是怎麼拼出來的』」。
地基早就鋪好，工程量不在「造」而在「接」：LoadoutDraft.parts / .modules 兩個欄位、codec v1 的 §PARTS / §MODULES 兩段、resolveChassis() 的 partOverrides 與 moduleLevelOf() 全部已實作且有測試——而全部處於「開了但沒接線」的狀態。而接線正是這個專案最會出事的地方：shareIndexes 的 module 那一行今天傳空陣列，component 剛因為同一個坑漏改了整整三個 Phase，症狀是元件被靜默濾出分享碼、encode 與 decode 兩邊的畫面都不說話，單元測試抓不到（codec 的測試自己建索引），是瀏覽器實地驗收才發現的。A-1 因此把「載入集合」與「接索引」綁成同一個工項。
2026-08-27 直讀正式 Firestore 四輪盤點，修正總綱決策六的四個數字：候選池 186（非 188）、Ⅰ型接口候選 42（非 41）、modules 241（非 242）、不綁機甲 198（非 199）。並發現總綱未點名的 mech.module4Id / module8Id / moduleFixedIds——天生模組住在這裡，而其中 112 顆的 boundMechId 是 null，一度看似會讓已裁決的候選規則撈進「別台機甲的天生模組」。查 source 才確定那不是漏洞而是機制本身：特性模組來源是「拆機甲／商店」、56 筆帶 dismantleMechIds，拆一台機甲把它的特性模組裝到自己機上就是這個玩法。決策六原封不動成立。
另兩處收斂：決策十三的同名消歧義在候選池裡已不存在（唯一的同名對手 mod_2030 是官方廢案、依決策一明著排除），該工項降級為可讀性的效果摘要；新增決策三——moduleAddLevel（31 顆通用模組Ⅱ型為 2、其餘 155 筆為 1）要做，使用者裁決「它就是接口槽的意義」，工作假說為 Σ 四接口決定天生模組等級（S 機四格全Ⅱ型 ⇒ 8，恰好是「8級模組」levels[] 的長度），假說未經實機驗證，E-3 專項驗收，通過前一律標「本站推算」。
⚠ 星夜女神四格全 Ⅰ 型已確認，是 256 格 S 級接口裡唯一的例外（16 台 A 級機甲清一色 Ⅰ／Ⅱ／Ⅱ／Ⅰ），依接口 gate 會變成「一台 S 機只能裝 A 級模組」——疑為 052-A 正規化時的誤改，B-0 回官方對帳。

PLAN-051 · 管理員 profile 讀取收斂

安全性收斂。firestore.rules 的兩條 profile 讀取規則原本帶著 || resource.data.role in ['ADMIN','OWNER']，而這個條件沒有任何 auth gate——用意是讓首頁的維護團隊區塊在未登入時也顯示，代價卻是：Firestore 的授權單位是文件而非欄位（沒有 field-level read mask），讀得到文件就是拿到整份 UserProfile，其中 email 是必填。結果是每一位匿名訪客進首頁，瀏覽器裡就有全部管理員的 email。嚴重度中而非高：email 不是憑證，後台入口仍是 Google 帳號 ＋ isAdmin()；值得修是因為它降低了針對管理員的釣魚門檻。

PLAN-045 · 登出診斷與系統日誌

三個缺陷是實測抓到、單元測試全綠卻漏掉的：① 草稿接在列表層監聽 editing，但使用者打字改的是編輯器內部的 form——提示會正確跳出、還原拿回的卻是原始資料，比沒有草稿更糟；② Firebase 會自動重建 firebaseLocalStorageDb，使該探針恆為 present，導致 idbEvicted 永遠產生不出來，更讓每個第一次進站的匿名訪客被判成 storageCleared 而跳出登出橫幅；③ onAuthStateChanged(null) 每次重新載入都會再觸發，未登入狀態下重整幾次就多幾筆重複記錄。修正後判定只採用不受 Firebase 干擾的兩顆哨兵，探針改為檢查 firebase:authUser:* 記錄（名實相符）並降為佐證欄位。本期刻意不修登出問題本身，先取得證據分布再開對策計畫，以免重蹈上次先修再猜的覆轍。

PLAN-039 · 引用標記同名消歧

新角色天賦正文「可使用指令[駐陣]…若處於[駐陣]狀態」——前者是技能、後者是 BUFF，但 DescriptionRefs 的 key 就是「括號內文字」，同名必然同指，後台也只看得到一列可指派。要區分只有兩條路：不動正文（只能靠「第幾次出現」的序數）或動正文（把消歧資訊寫進括號）。序數被明確否決——numRefs.ts 早已把「編號對齊」的脆弱性刻意限制在編輯期、entityRefs.ts 地雷 c 也拒絕索引式識別子，寫進持久層等於讓正文插一句話就靜默錯位。故採 [駐陣|skill] 語意化後綴，由既有的 RefChip label ?? inner 機制把前台文字還原成 [駐陣]。舊資料零遷移——不加後綴本來就是「沿用同一筆引用」。分隔符必須是 |：# 是 maxTriggers 的 sigil，[駐陣#2] 會被 compileSugar 當語法糖改壞正文（已有三筆守門測試存證）。執行中修掉兩個規劃時漏看的問題：其一，「填了後綴卻忘記指派」時 RefText 與 DiffHighlight 的優雅降級會把內部語法直接印給使用者；其二，RefPicker 收的是 description 與 descriptionMax join 後的字串，同名計數會把本案例報成「出現 4 次」而誤觸發按鈕上限——改為分段陣列逐段取最大值。B-3 的原始設計「改寫第 2 次以後」也在實作中作廢：實際要加後綴的是第一處，改為逐處各一顆按鈕由維護者明確指定，序數不再是推測。
