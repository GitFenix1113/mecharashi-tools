PLAN-038 · 社群連結預覽（Open Graph）系統

站長回報網站在 LINE 有連結預覽、Discord 完全沒有。根因單一且已證實：index.html 從未放過任何 og:* 標籤——Discord 的預覽爬蟲不執行 JS、也沒有 <title> fallback，找不到就整張卡片都不顯示；LINE 則退而抓標題撐出陽春卡，於是有「LINE 有、Discord 沒有」的落差。Tier 1（全站靜態標籤 ＋ scripts/generate-og-image.mjs 合成的 1200×630 品牌圖，64KB）獨立上線即解決「有沒有卡片」；Tier 2 由 Cloudflare Worker 在邊緣用 HTMLRewriter 改寫，讓機師／機甲／武器詳情頁顯示各自的立繪與名稱，素材全部重用既有 portrait／icon 欄位，不另開美術維護線，缺值一律 fallback 預設圖。
最大的意外在 Cloudflare 的處理順序：Redirect Rules → Transform Rules → Workers → Cache → Origin。PLAN-029 那條 SPA fallback 的 Transform Rule 已先把 /pilots/xxx 改寫成 /index.html，於是 mecharashi.wiki/pilots/* 這條 route 一次都不會命中（首次部署後 wrangler tail 實測：Discordbot 請求零事件，同時段 /api 正常）。解法是給該規則加例外，而例外必須同時綁路徑與 UA——只看 UA 會讓爬蟲抓 /news、/pilots 列表頁時「不改寫、也沒人接手」直接落到 GitHub Pages 404，比沒做還糟。route 也刻意只掛三條詳情頁而非整站 /*：實測單次冷啟動瀏覽會從 3 次計數變 66 次（76% 是圖片），且與 /api 共用同一個免費額度池。

完成日期：2026-08-22 · 11 / 11 任務

PLAN-048 · 時間線甘特圖改版

甘特圖的三個結構性問題都不是調 CSS 能解的：tooltip 被裁切是因為容器 overflow-y-auto 而浮窗 absolute bottom-full 永遠往上長（z-index 對 overflow 裁切無效，實測 11 層 clipping ancestor，只有 portal 有效）；一週活動只剩一個 12px 圓點，因為 activityToColumns() 把起點量化到下一個週界（實測 27/75 筆＝36%）；而「打了很多資料卻看不到」根本不是顯示問題 —— TimedActivity 沒有描述欄位，獎勵只能硬塞進 name。方案定調 「甘特＝索引，卡片＝內容」：甘特降級為日精度概觀、續與週次表共用同一條軸，內容改由同一捲動容器內的卡片流承載，並做甘特↔卡片↔週欄三向連動。評審抓到的四案共同盲點也一併兌現：玩家三個問題裡有兩個半能從既有 startDate + weeks 直接算出，零欄位、零維護成本。
兩項超出原訂範圍的追加：① 計畫書估固定資訊表 234px、實測 383px，壓列密度後甘特＋卡片區只有 186px，核心目的仍落空 —— 使用者看過成果後提出「版本內容可收合」，實測資訊表 337 → 123px、甘特＋卡片區 186 → 488px（2.6 倍），計畫書「未解問題」第 1 項實質解除；② 刪掉 PLAN-014 宣告取代卻從未移除的四個死碼元件（ActivityTimeline 等，實測零 import）。
台版公告管線落地：實測台版是靜態 JSON（副檔名 .html 但內容是 JSON），不需 Playwright，266 篇公告全量歸檔完成、0 失敗 —— 這 258 篇此前只存在於前代理商網域 ma.tentree-games.com（代理權 2026-01-05 已移轉），站一收掉即不可逆，該風險已解除。後續建 staging 雙集合 + /admin/announcements 審核工作檯 + GitHub Actions 每週自動抓取，首灌 43 篇草稿 / 96 筆待審（排除儲值促銷後留 67 筆），一次補齊近五個月台版活動史；帶外驗證確認 patchVersions 版本號未被 bump，證實爬蟲只碰 staging。TTL 政策建立、驗證後刻意關閉 —— 容量壓力不存在（一年 <0.5MB vs 1GiB 免費額度），而 rawText 是公告原文的唯一備份，刪了不可再生。

PLAN-040 · 固定武裝

「無法更換的武器」在資料層根本不存在：帕斯卡兩個手臂模組的描述引用了［衝擊炮］，但 weapons 集合 172 筆裡沒有這把武器，而引用層只檢查 token 在不在 refs、不檢查 refId 解不解析得到，於是 chip 照樣可點、點下去顯示「找不到對應資料」。彌造者的耀星／隕星／千星同樣 0/172，讓 PLAN-041 機師形態第一天就會卡在「無物可引」。
實機查證後固定武裝從 4 種訂正為 6 種，多出破曉者-01 的嵐質儲能艙與霸王的多功能彈倉這兩種純封鎖型——無數值、無技能、遊戲連數值區塊都不渲染，唯一作用是把雙肩焊死。它們逼出本計畫最關鍵的決策 naStats：ammoCount: 0 在本站已被佔用為「無限彈藥 ∞」（172 筆中 129 筆靠這條規則），照舊填 0 會把「沒有彈藥」渲染成「無限彈藥」——一個與遊戲相反的肯定陳述；改為 DB 仍存 0、渲染層對列入 naStats 的欄位一律顯示「—」。
三個在動工時才浮現、計畫書沒寫的東西：① WeaponAdmin 的種類下拉是 WEAPON_KIND_BY_TYPE[type] ?? ALL_WEAPON_KINDS，「特殊」無對應項會 fallback 到全部 17 種而其中沒有「固定武裝」——六筆在後台根本建不出來，且完全靜默；② B-3 自己列的同步清單漏了三處消費端、又點名了一處不存在的 icon map；③ 六筆一旦寫進 Firestore 就對所有人生效（新訪客冷快取直接抓 Firestore，不受 bump 影響），因此實際交付順序改為 Phase D 先上線、部署完成後才寫資料，否則會有一段時間顯示「彈藥量 ∞」。
另含四項資料衛生（修 6 筆 moduleFixedIds 斷鏈讓模擬器讀得到帕姆斯陣列、3 筆 boundPart 型別違規順帶修好一個現存的後台整頁崩潰、全庫僅存 2 條懸空引用、新增八類檢查的 validate-module-binding.mjs 長期守門）。三個死武器槽改為凍結加註而非刪除——取代品的形狀已知（PLAN-047 掛 MechPart.fixedArmament），刪了再加回來是白工。

PLAN-045 · 登出診斷與系統日誌

維護者持續回報「編輯資料到一半被登出」，但站上沒有任何持久化診斷記錄，每次回報都只能靠猜——先前為此加的 navigator.storage.persist() 至今從未被證實是對的方向。而「被登出」其實混雜三種故障：Auth 真的失效、仍登入著但寫入被 permission-denied（使用者誤以為登出）、資料快取失效（無害）。
關鍵約束是登出當下沒有權限寫 Firestore（規則全站 isAdmin()，此時 currentUser 已為 null），故改為 localStorage 佇列 ＋ 下次登入後 flush。成因判定靠雙哨兵（localStorage ＋ cookie，兩者存活條件不同）：先回答「這台裝置究竟登入過沒有」，才分得出「儲存被清」與「從未登入」。另含只有 OWNER 看得到的系統日誌頁（read: isOwnerRole()，全站唯一 read 比 write 嚴格的集合，因為日誌含裝置指紋不該讓 ADMIN 互看）、登出當下的白話橫幅、12 個後台編輯頁的草稿本機暫存與還原，以及把 12 個模組各自的 setDoc 收攏成 writeDoc 統一入口以攔截寫入被拒。
三個缺陷是實測抓到、單元測試全綠卻漏掉的：① 草稿接在列表層監聽 editing，但使用者打字改的是編輯器內部的 form——提示會正確跳出、還原拿回的卻是原始資料，比沒有草稿更糟；② Firebase 會自動重建 firebaseLocalStorageDb，使該探針恆為 present，導致 idbEvicted 永遠產生不出來，更讓每個第一次進站的匿名訪客被判成 storageCleared 而跳出登出橫幅；③ onAuthStateChanged(null) 每次重新載入都會再觸發，未登入狀態下重整幾次就多幾筆重複記錄。修正後判定只採用不受 Firebase 干擾的兩顆哨兵，探針改為檢查 firebase:authUser:* 記錄（名實相符）並降為佐證欄位。本期刻意不修登出問題本身，先取得證據分布再開對策計畫，以免重蹈上次先修再猜的覆轍。

完成日期：2026-08-08 · 27 / 27 任務 · 單元測試 344 項全綠（含 diag 22 項）、模擬器 12 套件 55 項全綠 · 五種成因逐項瀏覽器實測通過 · 已知限制：多分頁主動登出會產生假 tokenRevoked（留待日後）

PLAN-039 · 引用標記同名消歧

新角色天賦正文「可使用指令[駐陣]…若處於[駐陣]狀態」——前者是技能、後者是 BUFF，但 DescriptionRefs 的 key 就是「括號內文字」，同名必然同指，後台也只看得到一列可指派。要區分只有兩條路：不動正文（只能靠「第幾次出現」的序數）或動正文（把消歧資訊寫進括號）。序數被明確否決——numRefs.ts 早已把「編號對齊」的脆弱性刻意限制在編輯期、entityRefs.ts 地雷 c 也拒絕索引式識別子，寫進持久層等於讓正文插一句話就靜默錯位。故採 [駐陣|skill] 語意化後綴，由既有的 RefChip label ?? inner 機制把前台文字還原成 [駐陣]。舊資料零遷移——不加後綴本來就是「沿用同一筆引用」。分隔符必須是 |：# 是 maxTriggers 的 sigil，[駐陣#2] 會被 compileSugar 當語法糖改壞正文（已有三筆守門測試存證）。執行中修掉兩個規劃時漏看的問題：其一，「填了後綴卻忘記指派」時 RefText 與 DiffHighlight 的優雅降級會把內部語法直接印給使用者；其二，RefPicker 收的是 description 與 descriptionMax join 後的字串，同名計數會把本案例報成「出現 4 次」而誤觸發按鈕上限——改為分段陣列逐段取最大值。B-3 的原始設計「改寫第 2 次以後」也在實作中作廢：實際要加後綴的是第一處，改為逐處各一顆按鈕由維護者明確指定，序數不再是推測。

PLAN-034 · 神驅算力 BUFF 階覆寫層
