A-4   canEquipComponent()：五條合法性規則
src/utils/loadoutRules.ts
已完成
總槽 · 分項 · W 型 · 武器種類 · 同族互斥
① 總槽：觸 ＋ 應不超過 componentLimit（SS／S+ ＝ 4、S ＝ 3、其餘 0）
② 分項：觸不超過 triggerSlots、應不超過 effectSlots —— 讀欄位不寫死 3（決策八）
③ W 型只給 dualHand ／ back 武器（實測符合條件的武器 49 把）
④ allowedWeaponTypes 過濾 —— 空陣列或長度大於等於全部種類數皆視為不限 （沿用 052-I componentBlockReason() 已寫對的那條，資料無須補丁，見決策七）
⑤ 同族互斥，範圍是單把武器內（使用者裁決，決策一）：只看 mount.setup 這一個物件，不掃全套 mounts。
⚠ conditionType 不參與可裝性判定 （決策五）：always 103 筆、dualWield 3 筆，而「同時使用兩把武器攻擊」是戰鬥中的 出手指令、不是配裝狀態，配裝層判不了。
實作時發現的坑：不能用 slotOccupant() 取「這一格上的武器」—— 它比對的是 slotKey(ref)，而雙手武器的 mountCoverage() 產出的是兩格 singleHand 的鍵、不含 main:dualHand 自己； 拿 weaponRows() 給的 dualHand 座標去問它，會得到「這一格是空的」—— 症狀是雙手武器的元件面板永遠顯示 0 個槽。改寫一支 weaponSiteAt()（比對 slotsOverlap() 的覆蓋交集）， 固定武裝／全鎖形態／玩家配的三種來源一視同仁。已加測試釘住。
另一項：測試 fixture 的武器預設 triggerSlots／effectSlots 由 0／0 改為 3／3（實測 limit>0 的 135 把恆為此值）， 固定武裝則明著設為 0／0／0。

B-2   reconcile 的元件級聯
src/pages/simulator/simReducer.ts
已完成
逐 mount 掃 setup，不合法的移除
在既有的「逐格掃武器」之後補一段掃 setup：換了武器種類、換了機甲、 或元件 doc 被後台刪掉時，不再合法的元件要移除。
⚠ 本計畫最危險的一條（決策六）： components 尚未載入時整段跳過，不可照抄武器那條 「查不到就刪」。草稿可能在 components 到齊之前就被 loadDraft 灌進來（分享碼、localStorage 書架、052-E 雲端存檔都走這條）， 照抄的症狀是貼一次分享碼、元件就被靜默清空一次。
換武器本身不需要額外程式：placeWeapon() 建新 mount 時不帶 setup，元件自動清空（決策四）—— 但要有測試釘住，否則哪天有人為了 「換同型武器保留配置」加一行，就會變成靜默繼承。
實際交付：reconcileSetups() 的作法是清空後逐顆重裝， 而不是逐條寫「哪些情況要拿掉」—— 重裝走的就是 canEquipComponent()， 於是五條規則自動全套適用、順序也與玩家手動裝時一致 （與 reconcile 掃武器時「把它自己先拿掉再問」是同一個手法）。 外部來源把同一顆掛兩次時另行擋下：canEquipComponent() 對已裝的那顆是 放行的（面板要畫得出「已裝上」），所以重複必須在級聯這一層自己判。
載入 gate 已驗證：測試用兩個世界對照 —— WORLD_LOADING（components 尚未載入）下同一份草稿 原樣保留且一個字都不說；WORLD 下同族兩顆會被正確移除一顆。 第二則測試存在的理由是證明第一則不是因為規則沒接上。

逐項實測，不目測推斷
比照 052-I F-2 與 052-J 的作法，用 Chrome DevTools 逐項實測而非目測推斷：
① SS 武器裝到第 5 顆被擋（總槽 4）；② 觸元件裝到第 4 顆被擋（分項 3）； ③ W 型元件在單手武器上摺疊、在雙手武器上可裝； ④ 警戒族在非射擊武器上摺疊並寫出原因； ⑤ 同族第二顆灰掉並附「卸下 X」按鈕，按下去真的只卸下； ⑥ 換武器後元件清空並且跳 toast，[復原] 能還原； ⑦ 雙手武器的元件面板只出現一次； ⑧ 主手與備用各裝同型武器，元件互不影響； ⑨ 貼一段含元件的分享碼，元件完整還原（含刻意在 components 載入前貼的競態）； ⑩ 匯出圖印得出元件。
十項全數通過，並抓到一個單元測試看不到的破口 ——
⚠ 第⑨項抓到：component 的分享碼索引是空的 LoadoutPage 的 shareIndexes 寫著 buildShareIndex('component', [])（052-C 留的，當時頁面沒有 components 資料）。 A-3 已把 components 加進 equip 階段，但這一行漏改了整整三個 Phase： encode 時 toShareId() 回 null ⇒ 元件被靜默濾掉，分享碼裡根本沒有它們； decode 時 toDocId() 回 null ⇒ 進 unresolved 被丟掉。 玩家配好元件、複製連結、貼給別人，對方收到一套沒有元件的配裝，而兩邊都不會說任何話。
單元測試抓不到這種事：codec 的測試自己建含元件的索引，壞掉的是頁面這一層的接線。 052-C 當初的註解甚至已經寫明「052-D 動工時把對應集合加進 equip 階段即可」—— 集合加了，索引那一行沒接上。這就是實地驗收存在的理由。
順帶補的一項：換掉一把帶元件的武器時，toast 原本只說「已由 X 取代」。 元件隨 mount 一起走、不各自進 removed，於是那一行讀起來像只換掉一把武器， 而玩家配的四顆元件也一起沒了。現在補成「已由 X 取代（連同 N 顆元件）」， 一句話講完、不必為此在清單上多列四行。
競態那一項由結構保證而非時序運氣：stage 在有 pending 時 直接跳 equip，而還原的守衛是 if (pending && !loading) —— loading 為 false 就代表 equip 階段的每個集合（含 components）都到齊了。 reconcile 那一層的載入 gate 另有兩個世界對照的單元測試（B-2）。
其餘實測數字：背部武器可裝 201／208（W 型可用）對比手盾 124／208（W 型整批摺疊）； 分享碼還原後武器列顯示「元件 2 / 4 · 觸元件W-背水・應元件W-增幅」； 匯出圖印出「元件 2／觸元件W-背水・應元件W-增幅」； 主手與備用各裝一把夾心曲奇、各帶不同觸元件，落盤後兩者互不影響。
