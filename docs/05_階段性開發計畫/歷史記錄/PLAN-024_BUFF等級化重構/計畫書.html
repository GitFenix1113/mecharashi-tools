◆ PLAN-024

階梯式 BUFF 等級化重構 · Leveled Buff · levels[] · 引用 .lvN · 去重 68%

把同概念、多等級的 BUFF / DEBUFF 由「N 份獨立文件 + mutexGroup」合併為「單一文件 + levels[]」，用 level 表示各等級能力（比照 Module 的 ModuleLevel）；順手把全空的數值結構化，為傷害模擬鋪路。

📐 本計畫源自評估 _local-notes/buff-等級化vs屬性覆寫_評估.md 的「問題二」，經盤點腳本 scripts/scan-graduated-buffs.mjs 量化後拍板執行。 與其正交的「問題一（屬性覆寫 BuffMod）」由 PLAN-023 處理，不在本計畫。 本計畫深化 PLAN-022 的引用語法（新增 .lvN 段），趁引用 token 尚未全站鋪開的時間窗口定案。

一句話：「傷害提升 I~V」「凝勢 I/II/III」這種一個概念被切成 N 份 buff 文件的現象，全站有 27 族、85 份文件。把每族塌縮成一份文件 + levels[]（省 58 份、68%）， level 承載各等級能力、天然互斥取代 mutexGroup、數值引用收斂為單一 .lvN token， 並順手把全空的 effects（0/266）結構化進 levels[]，給未來傷害模擬一個乾淨的數值來源。
Problem
問題背景
問題一：一個概念被切成 N 份文件，改一處要同步多份
盤點（scan-graduated-buffs.mjs，266 個 BUFF）顯示：同詞幹、僅尾碼不同（羅馬數字）的「階梯族」有 27 族、共 85 份文件，塌縮成單一文件可省 58 份（68%）。 現行每一級各存一份 GameBuff，名稱／描述／圖示／數值各自為政，改一個概念要逐份同步——典型的單一事實來源缺失。
傷害提升 I 傷害提升 II 傷害提升 III 傷害提升 IV 傷害提升 V ← 5 份文件、一個概念 凝勢 I 凝勢 II 凝勢 III ← 3 份文件 + mutexGroup 綁定
問題二：數值引用被迫寫三份 token，且引用窗口即將關閉
PLAN-022 的 <buff_凝勢I.maxStack> 因每級是獨立 refId， base/≥10/≥13 三處被迫寫 <buff_凝勢I/II/III.maxStack> 三個不同 token。目前這類 token 只在艾達凝勢撒了一例—— 趁全站尚未鋪開，現在改成 <buff_凝勢.lv3.maxStack> 是最便宜的時間點；越晚改、要遷移的既有 token 越多。
問題三：數值全空，傷害模擬無結構化來源
盤點顯示 effects 已結構化的 buff = 0 / 266——所有數值（傷害提升 5%/10%…）目前只活在描述文字裡， 沒有任何可被模擬器消費的結構化欄位。等級化正好是把這些數值一次結構化進 levels[].effects 的天然時機， 填 27 份 levels[] 取代散填 85 份頂層 effects。
問題四：散落模型讓資料缺漏難以察覺
健檢揪出 9 族含「無尾碼成員」（失穩、威壓光環、短路、膽怯…）與 3 族缺階（整葺從 2 起、迴避率提升從 3 起、迴避率降低從 2 起）。 這多半是早期維護人員輸入習慣不一致造成的漏填／重複——散在 N 份文件時難以發現。 收斂成 levels[] 後，「這個 buff 有哪幾級、缺哪級」一目了然，結構化本身就是資料健檢與後續補登的基礎。
盤點關鍵結論（決定本計畫成本的核心數字）： 27 族裡「結構型」只有凝勢 1 族（per-level 連 maxStack(5/7/7) 都變、且 II→III 加暴擊）， 其餘 26 族全是「數值型」（含 debuff 程度遞增，per-level 只差一個數值）。 換言之——最複雜的「各 LV 能力不同」case 全站僅一個，工程主體是最單純的那種，風險可控。
Design
設計決策
決策一：GameBuff 加選填 levels[]，比照 ModuleLevel；普通 buff 零影響
階梯 buff 把各等級收進 levels: BuffLevel[]；沒有 levels 的普通 buff（266 中的多數）完全不受影響， 沿用既有頂層欄位。結構型（凝勢）levels[] 填滿 maxStack/effects；數值型（傷害提升）只填 level + effects， 同一個 BuffLevel 結構通吃，數值型只是少填欄位。
// 【改】GameBuff —— 新增選填 levels[]（無 level = 普通 buff，行為不變） export interface GameBuff { id; name; description; buffType; // 既有欄位不動 maxStack?; duration?; effects; // 普通 buff 仍用頂層欄位 descriptionRefs?; icon?; mutexGroup?; levels?: BuffLevel[]; // 階梯 buff：各等級能力 } // 【新】BuffLevel —— 一個等級的能力（結構型填滿、數值型只填 level/effects） export interface BuffLevel { level: number // 1,2,3…（= 羅馬尾碼數值） description?: string // 該級描述（選填） maxStack?: number // 結構型各級不同（凝勢 5/7/7） duration?: number effects?: SkillEffect[] // 數值型各級數值（傷害提升 5%/10%…） icon?: string }
決策二：level（靜態強度階）與 stack（runtime 疊加層）兩維度嚴格分離
這是成敗關鍵。凝勢同時有兩個維度，絕不能混：
buff_凝勢.levels = [ { level: 1, maxStack: 5 }, // 算力 base { level: 2, maxStack: 7, effects: [暴擊+…] }, // 算力 ≥10 { level: 3, maxStack: 7, effects: [暴擊++…] }, // 算力 ≥13 ] level（強度階）：來源（神驅算力）決定掛哪一級 ── 靜態、資料驅動 stack（疊加層）：戰鬥中累積到該級的 maxStack ── runtime 執行期狀態
傷害提升只有 level 維度、沒有 stack。levels[n] 決定 maxStack/effects，執行期再去疊 stack，互不干涉。
決策三：mutexGroup → level 的 max() 收斂
同一個 buff 的不同 level 天然互斥（不可能同時是凝勢 II 又是凝勢 III）；「取最高」變成 level 的 max() 運算。 因此階梯 buff 不再需要 mutexGroup 樣板——可廢除凝勢的 pilot_038_艾達_凝勢 群組。 淨收益 非階梯的「形態互斥」（虛粒子⟷實粒子）仍保留 mutexGroup，兩者不衝突。
決策四：numRef 新增選填 .lvN 段，向後相容；輸入靠 RefPicker 兜底
沿用既有「token 自描述、不依賴出現位置」哲學，中間插一個選填具名段。正則僅 numRefs.ts 一處改：
現在：<buff_x.maxStack> // 普通 buff，照舊合法 新增：<buff_凝勢.lv3.maxStack> // 階梯 buff 指定第 3 級 正則：<([^<>.]+)(?:\.(lv\d+))?\.([A-Za-z]\w*)> 解析：有 lv 段 → lookup(refId).levels[n-1] 取屬性；無 → 取頂層（普通 buff）
維護人員不手打：RefPicker 偵測到選中的是階梯 buff 時，跳出 level 下拉（Lv1/Lv2/Lv3，與產品 UI「Lv.」語彙一致），選完按鈕代入。
決策五：buffIds 帶 level 的表達（賦予哪一級）
技能/天賦/神驅以 buffIds 賦予 buff 時要能指定等級（「賦予傷害提升 III」）。 採與 numRef 一致的尾綴語法 buff_傷害提升@3（保持 string[] 形狀、解析時拆出 level）， 避免動到所有 buffIds: string[] 消費端的型別。未指定 level = 賦予 base / 該 buff 預設級。 需評估 確切分隔符（@3 / #3）於 Phase A 與 numRef 一併定案，全專案一致。
決策六：雙格式過渡 + dry-run + __REVIEW__，比照成熟模式
沿用 pilotSkills / PLAN-023 的安全過渡：前端先支援「讀 levels[]」， 遷移腳本以詞幹去重（已有 scan-graduated-buffs.mjs 為輸入）產生合併草案，同名衝突／無尾碼污染／缺階一律進 __REVIEW__ 報告人工確認， 確認後才寫入、再 flip。遷移前先做資料庫靜態備份（backup-firestore.mjs）作回滾安全網。
遷移要人工裁決的已知雜訊（來自盤點健檢）：
  • 暴擊率提升的「無尾碼成員」帶 stack=3、而 I~IV 皆無 stack → 高度疑似另一個獨立 state buff，不應併入階梯。
  • 9 族含無尾碼成員（失穩／威壓光環／短路…）：多為漏填尾碼或重複，逐族確認該無尾碼文件是「某一級的別名」還是「獨立 buff」。
  • 3 族缺低階（整葺從 2 起…）：確認是遊戲本就無低階，還是維護漏登 → 後者於 levels[] 補位。
合併前後對照
── 之前（N 文件 + mutexGroup）── ── 之後（1 文件 + levels[]）── buff_凝勢I { maxStack:5, mutex:… } buff_凝勢 { buff_凝勢II { maxStack:7, mutex:… } ──► levels: [ {lv1,max5}, {lv2,max7,…}, {lv3,max7,…} ] buff_凝勢III { maxStack:7, mutex:… } } <buff_凝勢I.maxStack> / II / III ──► <buff_凝勢.lv1.maxStack> / .lv2 / .lv3
Scope
實作範圍與不在範圍內
在範圍內：
  • 資料模型：BuffLevel 型別 + GameBuff.levels?；資料模型 docs 同步（skills-buffs.html / skills_buffs.html）。
  • 數值引用層：numRefs.ts 加 .lvN 段（正則 / parseNumRefs / resolveNumValue / NumRefSource.levels）＋單測；前台 RefText 解析。
  • buffIds 帶 level：賦予指定等級的解析（@N 尾綴），相容既有無 level 的 string[]。
  • 後台：BuffAdmin 的 levels[] 編輯（比照 ModuleAdmin 各 LV）＋ RefPicker level 下拉；階梯 buff 的 mutex 欄位簡化。
  • 遷移：詞幹去重遷移腳本（dry-run + __REVIEW__）；buffIds / 艾達 ndVariants 既有引用更新為 .lvN；bump 版本。
  • 端到端驗收：凝勢（艾達天賦 .lv3 引用 + DiffHighlight）＋ 一支數值型（傷害提升）。
不在範圍內（標為後續）：
  • SKILL（pilotSkills）等級化：結構上可套用同一 levels[] 模式，但尚未盤點規模。本計畫先把 BUFF 做成範本，技能等級化另跑盤點後比照（可能併入或另開 PLAN）。
  • 補登全部 effects 數值：本計畫只建「容器」（levels[].effects 結構），把 0/266 的數值填滿是後續資料工作（可走 data-patch）。
  • 屬性覆寫 BuffMod（幹勁 maxStack→8）：正交機制，由 PLAN-023 處理，不可用 level 表達（會組合爆炸）。
  • 傷害模擬計算核心：屬 PLAN-019-B / 未來模擬器 PLAN；本計畫只提供乾淨的結構化來源。
