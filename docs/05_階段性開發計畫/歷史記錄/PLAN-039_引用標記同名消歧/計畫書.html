◆ PLAN-039

引用標記同名消歧Disambiguation · descriptionRefs · 正文內穩定識別子

同一段正文出現兩個 [駐陣]，一個是 BUFF、一個是技能。以正文內的消歧後綴取代序數識別，前台顯示完全不變、零資料遷移。

一句話： descriptionRefs 的 key 是「括號內文字」，因此同一段正文裡兩個 [駐陣] 必然指向同一個實體。 本計畫讓 key 可以帶一段語意化消歧後綴（[駐陣|skill]）， 並由既有的 EntityRef.label 顯示機制把前台文字還原成 [駐陣]。 不改資料模型、不動舊資料、不引入位置型識別子。
Problem
問題背景
同名 [xxx] 無法指向不同實體
新角色的天賦正文（官方原文）：
同時裝備大盾和噴火器時,可使用指令[駐陣];行動開始時,若處於[駐陣]狀態, 使用噴火器對攻擊範圍內所有目標,造成0.5倍傷害;使用噴火器攻擊時,每命中1個目標,獲得1層[戎火]。
第一個 [駐陣]（「可使用指令」）是技能； 第二個（「若處於…狀態」）是 BUFF。 這是天賦賦予的角色獨有技能，並非可學習技能——但 pilotSkills 早已是全站技能字典 （84% 的引用目標無任何機師持有），故技能側直接建一筆文件即可，不需掛給機師。

問題在於 DescriptionRefs = Record<括號內文字, EntityRef>（src/types/common.ts）， RefText 以 refs[m[1]] 查表 —— 兩個 [駐陣] 讀到的必定是同一筆 EntityRef。 管理者在後台 RefPicker 也只會看到一列可指派（extractTokens 以 Set 去重）。
規模界定：這是第一個案例。 既有全站資料中尚未出現「同名不同義」的 [xxx]；舊資料的所有同名重複都是同名同義， 一對一命中即為正確行為。這個事實直接決定了方案選型 —— 值得為單一新案例付出的成本，遠低於為它改造全站持久層。
Design
設計決策
決策零：這是一個邏輯上的二選一，沒有第三條路。
要區分同一段正文裡的兩個 [駐陣]，可用的資訊只有兩種：
① 不動正文 → 唯一的區分依據是「第幾次出現」（序數）；
② 動正文 → 把消歧資訊寫進括號內。
任何「正文保持純淨又能穩定區分」的設計都不存在。故決策的實質是： 要犧牲識別子穩定性，還是要犧牲正文與官方原文的字面一致？
決策一：採方案 ②（正文內消歧後綴），格式 [顯示文字|消歧鍵]
以實際案例為例，正文改寫為「可使用指令[駐陣|skill]…若處於[駐陣]狀態」—— 裸 key 留給 BUFF、帶後綴的標成技能（消歧鍵定為 skill）， descriptionRefs 因此自然有兩個相異 key。

為什麼不選序數（方案 ①） —— 本專案已對序數識別子明確表過態，且不只一次：
  • numRefs.ts 開頭：「語法糖 $n 永不落地， n = 描述中第 n 個有引用的 [xxx]，僅在編輯當下成立… 『編號對齊』的脆弱性被限制在編輯期」；
  • entityRefs.ts 地雷 c：「索引式路徑（talents.2.buffIds） 不是穩定識別子——還原時陣列可能已被重排」，故每個站點盡量帶 anchor。
採序數等於把一個被反覆拒絕的東西寫進持久層：正文中間插一句話、調換語序， 所有引用即靜默錯位——沒有錯誤訊息，只有指錯的浮窗。
決策二：分隔符必須是 |，絕不能用 #（地雷）
# 是 NUM_ATTRS.maxTriggers 的語法糖 sigil。若寫成 [駐陣#2]：
// detectLeftoverSugar 的正則會把 #2 認成「未代入的語法糖」 const re = new RegExp('[' + '$%#' + ']\\d+', 'g') // ← 命中 "#2" // 接著 compileSugar 會把它替換掉，正文當場被改壞： "獲得[駐陣#2]" → "獲得[駐陣<buff_XXX.maxTriggers>]"
| 與現有三套語法（[xxx] 引用、<refId.attr> 數值 token、 $n/%n/#n 語法糖）皆無交集，且在中文遊戲文案中不會自然出現。
附帶好處：| 後接的是語意（skill / buff）而非序號， 正文改寫、語序調換都不會使它失效。

RefChip.tsx:39 早就是 entity.label ?? inner。 整條引用鏈逐層檢查後，加了後綴的 key 天然成立：
環節加了 |skill 後綴的行為需改動

未命中路徑：原「原樣顯示 [xxx]」的優雅降級會把整串內部語法印出來 A-3 實測發現		 3 行
RefChip 顯示 label ?? inner；補一層剝後綴 fallback 後恆顯示 [駐陣] 1 行
RefPicker.extractTokens 靠字串去重 → 自動變成兩列獨立指派 零

A-3 實測修訂（2026-08-02）： 上表原本把 RefText 與 DiffHighlight 都列為零改動， 實作時發現漏看了未命中的降級路徑——「填了後綴卻還沒指派」時， 兩者原本的「原樣顯示 [xxx]」會把 [駐陣|skill] 這種內部語法印給使用者看。 兩處均已補上剝後綴的降級，且都以 disp !== inner 為條件 （無後綴時分支不觸發），舊資料的渲染輸出 byte-identical。 兩處必須改成一致，否則同一段天賦正文會隨「差異高亮：開／關」顯示出不同的字。
刻意不自動預填 label：剝後綴的 fallback 已是安全網， 再自動塞一份 label: '駐陣' 只會在 Firestore 存冗餘欄位， 並模糊 label 的原本語意（「原文用別名時覆寫顯示文字」）。
決策四：零資料遷移 —— 舊資料的「同上」是預設行為
初步構想曾提到「所有引用都獨立、相同者勾『同上』，現有資料全部處理成同上」。 在本方案下這件事不需要做：不加後綴 = 沿用同一筆 EntityRef = 就是「同上」。 只有真正需要區分時才付出「正文多幾個字」的代價，成本只落在有歧義的那一處。
決策五：與「一鍵拆分」相關的邊界（B-3）
  • 語法糖必須先代入。拆分會改變 orderRefsByFirstMention 的編號， 正文中尚未代入的 $n / %n 會指到錯誤的引用。 故偵測到 detectLeftoverSugar 非空時，拆分按鈕停用並提示「請先代入數值」。 已實作
  • 序數改寫在 3 次以上出現時做不到。 任何「改寫第 N 次以後」的機械規則在第 1、3 次同義而第 2 次不同義時都會出錯， 故只服務「出現 2 次」的情境。
B-3 實作修訂（2026-08-02）：第二點作廢。 該限制的前提是「機械規則決定改寫哪一處」。實作採的 UI 是逐處各給一顆按鈕 （「標記第 1 處」「標記第 2 處」…），由維護者明確指定——序數不再是推測，而是選擇。 3 次以上照樣可用，只在 >4 次時改提示手動編輯，理由純粹是按鈕排不下。
實際案例正好印證這個修訂的必要：要帶後綴的是第一個 [駐陣]（指令＝技能）， 不是第二個。原設計「改寫第 2 次以後」在這個案例上根本用不了。
決策六（B-3 實作時發現）：多欄位面板必須傳「分段正文」，不能傳 join 後的字串
RefPicker 的 text prop 原本是單一字串，天賦面板傳的是 [description, descriptionMax].join('\n')。同名計數若直接數這個合併字串， 本計畫的實際案例會被報成「出現 4 次」（初始版 2 次 ＋ 滿星版 2 次）—— 而 4 次會誤觸發按鈕上限，讓一鍵拆分在最需要它的地方不可用。

根因是 join 後無法分辨「同一個 [xxx] 在兩個版本各出現一次」與 「在同一版本出現兩次」，而這兩者對同名消歧的判定完全相反。 故 text 改為 string | (string | undefined)[]：
  • 陣列 → 逐段計數取最大值（非合計）。兩段是同一段能力的平行版本，不是連續文字。
  • 字串 → 視為單段，既有 8 個消費端行為完全不變。
只有天賦與 ndVariant（PilotAdmin ×2）需要改傳陣列。刻意不加第二個 prop—— text 與 segments 並存會製造兩個 source of truth，遲早不同步。
爬蟲覆寫風險：已被既有機制涵蓋。 正文加後綴後最大的疑慮是「下次重抓被官網原文洗掉」。掃過 scrape-pilots-v3.js 後確認兩層保護都在：
  • 技能（第 587 行）：Firestore 的 description 與官網不同即視為 「管理者手動覆寫過」，直接保留；
  • 天賦（第 625 行）：manual: true 時保留 description / descriptionMax——這正是既有的正文去污染流程 （官方 API 天賦文本為滿晶片狀態），後台勾選框旁已有明確提示；
  • descriptionRefs（第 622 行）：無條件保護，補丁永不覆寫。
唯一新增的操作紀律：在天賦正文加消歧後綴時，務必一併勾選 manual。
Scope
實作範圍與不在範圍內
在範圍內：
  • 新增 src/utils/refKey.ts：splitRefKey / displayKeyword / formatRefKey + 單元測試
  • RefChip 顯示層剝除消歧後綴（忘填 label 也不會漏到前台）
  • RefText 與 DiffHighlight 的未命中降級一併剝後綴 （A-3 實測補入，見決策三修訂）
  • RefPicker：token 列顯示原文 + 標註消歧鍵；偵測同名重複並提示
  • 一鍵拆分輔助（選配，含決策五的兩道防護）
  • 引用鏈全路徑回歸驗證（前台渲染 / 差異高亮 / 級聯刪除 / 還原 / 數值語法糖）
  • 實際案例（[駐陣]）填值驗收 + docs/02_技術文件/ 資料模型說明同步
不在範圍內：
  • 改動 DescriptionRefs 型別（維持 Record<string, EntityRef>）
  • 任何既有資料的遷移——舊資料一律維持現狀（見決策四）
  • 序數 / 陣列型引用（見決策一，明確否決）
  • 把消歧後綴自動同步進 EntityRef.label（見決策三）
  • 爬蟲端對消歧後綴的特殊處理——既有 manual 與差異保留機制已足夠
順手修掉的既有缺口 B-3 已完成
WeaponAdmin 的 RefPicker 原本只接 skill.description， 漏了同屬該技能的 enhancedTalentDescription（PLAN-022 遺留）—— 後者的 [xxx] 無法在後台指派、語法糖也不會被代入， 但 entityRefs.ts 的 WEAPONS.textUnits 確實會掃它。
原列為選配，實作時因 text prop 正好改成支援多段而一併補上（兩段同步套用 transform， 與 PilotAdmin 的天賦一致）。這是修正而非回歸： 武器技能面板的 token 列表會因此多出 enhancedTalentDescription 內的標記—— 那些標記本來就該在這裡指派。
