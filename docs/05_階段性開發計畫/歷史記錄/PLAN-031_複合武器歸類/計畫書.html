◆ PLAN-031

武器製作關係層 · 進階鏈 · 複合武器歸類 · 正交 facet 投影

用單一 upgrade 關係同時表達「炬塔·改→熠光」的武器進階與「熠光+背包→裁決者」的複合製作；讓武器頁看得見前置與後續，讓複合武器在背包圖鑑正確並列——不搬集合、不改 refType。

Problem
問題背景
使用者回報：「裁決者」歸類錯了
「裁決者」在工具站是武器（SS · 戰術 · 電磁炮 · 肖妮專屬）， 但遊戲內它是在【背包製作 → 特種背包製作】用背包圖紙做出來的， 與「捍衛者背包 / 征服者背包 / 隱匿者背包 / 主宰者背包 / 拯救者背包」並列在同一份清單。 使用者因此在背包圖鑑找不到它。
但事實查核推翻了「官方歸類是背包」這個前提。
官方 API 兩張表的歸屬沒有模糊空間：weapon_data 命中裁決者（ID 50116121）， backpack_data（180 筆）查無； 它有 InitiativeSkill / NumberOfBullets / WeaponBasicAttackingPower 這些背包表根本不存在的欄位。

「特種背包製作」是製作台的位置，不是裝備分類。 那份清單是混合清單——同時列出兩張資料表的產物：22 個 SSSR 特種背包（backpack_data） ＋ N 把複合武器（weapon_data）。 所以這是「呈現／發現路徑」問題，不是「儲存歸類」問題。
而且這不是孤例，是一個持續增長的家族
複合武器母武器機師融合技能
裁決者 weapon_115 · 電磁炮熠光 weapon_102肖妮首攻強化Ⅲ
糖衣毀滅者 weapon_146 · 電磁炮草莓通心粉 weapon_132菲婭首攻強化Ⅲ
天燼審判 · 浮游炮 已確認在 live諸神黃昏—首攻強化Ⅲ
複合武器 = 母武器 + 多掛一條背包系被動，其餘欄位（含重量 1100、icon）完全相同。 家族已跨電磁炮／浮游炮兩系——而這兩系正好就是全部 20 把 equipSlot:'back' 武器的組成。 推測「背後武器 + 背包」複合是一條長期產線，故任何實作都不可對「裁決者」做特判。
第二層問題：全站 42 條武器製作關係完全沒有被表達
S+ 武器是 SS 武器的製作材料（來自武裝討伐關卡的材料另計），但工具站完全沒有這層關係—— 玩家看不出「我這把能升成什麼」「這把的前置是誰」。

【實測】這層關係可以從既有資料完美推導（鍵 = skill.name，取極大真子集）：

站長舉的兩個例子皆驗證通過：夜魘·改 → 終末之嘆、炬塔·改 → 熠光 （live dry-run 4 個回歸抽查全過）。
而這兩層問題其實是同一件事——這是本次範圍擴大的決定性依據。
42 條邊裡，SS→SS 的邊恰好只有 3 條，而且差集都是 首攻強化Ⅲ：
// 純武器進階（39 條，S+→SS，|delta|=2） 炬塔·改(S+) → 熠光(SS) delta = {充沛, 鼎新} // 複合製作（3 條，SS→SS，|delta|=1，且該技能帶 6 開頭背包 buffId） 熠光(SS) → 裁決者(SS) delta = {首攻強化Ⅲ} buffId 600433 草莓通心粉(SS) → 糖衣毀滅者(SS) delta = {首攻強化Ⅲ} buffId 600433 諸神黃昏(SS) → 天燼審判(SS) delta = {首攻強化Ⅲ} buffId 600433（浮游炮系）
同一次計算同時產出：(a) 進階圖　(b) 複合武器判別　(c) 融合技能　(d) 母武器。 原計畫的 craft.baseWeaponId 只是這 42 條邊裡的 3 條， 若兩者分開實作，同一個關係會有兩個欄位表達 = 第二份真相。

Design
設計決策
決策一：weapons 為唯一真相，不搬集合
儲存歸類跟著資料源與資料形狀（官方 weapon_data）， 官方介面歸類另以正交欄位表達。

四個獨立方案經 3 個評審鏡頭（資料正確性／實作成本／UX 與長期擴充）評分： 不搬集合 7.67 ＞ 製作關係一等公民化 7.17 ＞ EquipmentBase 抽象 6.67 ＞ 搬進 backpacks 3.67（三鏡頭一致低分）。
為什麼「搬進 backpacks」被否決——一擊致命
SimulatorPage.tsx:317：
const handleSaveBuild = useCallback(async (buildName) => { if (!user || !state.pilotId || !state.mechId || !state.weaponId) return // ← silent return
Build.weaponId 是必填。搬集合後裁決者變成 backpackId、weaponId = null → 配裝按下儲存毫無反應、且沒有任何錯誤訊息； :154 的 incomingBuild?.weaponId ? 'result' : 'pilot' 又會讓讀取舊配裝掉回第一步。 整個 round-trip 斷裂。
其餘否決理由：與上游爬蟲永久對抗（weapon_data 會一直吐回來）、 Backpack 集合語意永久模糊、effectiveWeapon 是每個未來功能的永久稅。
決策二（v2 改寫）：WeaponCraft 作廢，併為單一 Weapon.upgrade
v2 變更 原 craft 型別整個作廢。 upgrade 包含 craft——複合製作只是「進階邊上多帶一個背包材料」。
/** 武器製作／進階關係。有值 = 此武器由 fromWeaponId 製作而來。 * 只存「事實」，不存 UI 顯示決策，也不存任何可推導值。 */ export interface WeaponUpgrade { /** 母武器 doc id（必填——實測 42 條邊皆有母武器） */ fromWeaponId: string /** 官方製作工作台。未填 = 一般武裝生產；'specialBackpack' = 特種背包製作 */ station?: 'specialBackpack' /** 融合進來的背包 doc id（複合武器專用），如 '60102405' */ fusedBackpackId?: string } export interface Weapon { // …既有欄位全部不動… upgrade?: WeaponUpgrade // 不改變本武器的儲存集合、doc id 或 refType }
三個原欄位被刪除的理由（全部是「可推導的不存」）：
原欄位處置理由
baseWeaponId→ 改名 fromWeaponId同一概念，升格為 42 條邊共用
fusedSkillName刪除，前端 derive ＝ 子武器 skills − 母武器 skills 的差集。實測 fan-out 0、邊唯一，推導安全。
額外好處：PLAN-032 把技能改成引用後，差集自動換算，本計畫零改動。
fusedBackpackType刪除，由 fusedBackpackId 查表 它就是決策二自己否決的 displayBackpackType 換皮。背包圖鑑本來就載入了 backpacks，查表零成本
同樣刻意不加：upgradeTo（反向索引前端 derive，雙向欄位失同步時沒有任何機制會發現， 且 fan-out 一旦出現就得改成陣列）、officialCategory、isComposite: boolean。
製作材料的擴充點——現在不做，但位置已經免費留好
站長明示材料（武裝討伐關卡掉落）「太細枝末節、想保留可能性、分階段執行」。 不要現在加 materials?: CraftMaterial[]——它需要 items 集合與掉落表，兩者皆不存在， 必然 0 筆被填（0/5 定律）。
但擴充點已經存在：upgrade 是物件不是字串，未來加 materials? 是純新增選填欄位、零 migrate。要做的「保留」只是在 weapons.html 寫一句： 「製作材料是 upgrade 邊的屬性，不是武器的屬性；未來加在 WeaponUpgrade.materials?: { itemId, qty }[]。前置條件：items 集合與武裝討伐掉落資料。」
決策三：「特種背包製作」是正交 facet，不是 BackpackType 的一個值
背包圖鑑篩選列在既有的「稀有度」「類型」之外，新增一顆可交叉的 facet， 打開後 = 22 個 SS 特種背包 ＋ N 把複合武器 = 遊戲內那份清單。

背包側完全 derived（rarity === 'SS'），不在 Firestore 存任何推論值。 投影條目的 type 用 craft.fusedBackpackType，讓功能維度誠實歸位—— 使用者按「出力」篩選也找得到裁決者。
為什麼不能新增 BackpackType.Composite
使用者要並列的那 5 個背包，type 分屬 5 個不同值： 拯救者 Heal、征服者 MovePointAdd、捍衛者 Interference、 主宰者 Flow、隱匿者 Invisible。沒有一個會是 Composite → 新增後點「複合」只會看到 2 筆，反而讓它們更孤立，與訴求正好相反。
且 BackpackType 是 API BackpackMainType 的鏡像， scrape-backpacks.js 會用 API 值直接覆寫 type，自創值會被沖掉； 還要同步 enums.ts / BACKPACK_TYPE_CONFIG / ALL_BACKPACK_TYPES 三份會漏改的硬編白名單。
決策四（v2 改寫）：用進階圖本身當複合武器判別式
v2 變更 原本的兩個字串啟發式被更精確的圖結構判別取代：
// 主判別式：進階圖上的「同稀有度邊」 edge.from.rarity === edge.to.rarity // SS→SS，實測全站恰好 3 條，零偽陽性 // 交叉驗證：差集技能帶背包命名空間 buffId delta.some(s => s.buffIds.some(id => String(id).startsWith('6'))) // 武器 buff 為 5303xx，背包 buff 為 6xxxxx → 恰好同樣命中那 3 把
推導腳本應同時跑兩者並要求一致，不一致才需人工介入。
判別式命中評價
SS→SS 邊（|delta|=1）裁決者、糖衣毀滅者、天燼審判主判別式零偽陽性，且順帶產出母武器與融合技能
skills[].buffIds 有 6 開頭裁決者、糖衣毀滅者、天燼審判交叉驗證零偽陽性
weapon.description 含「背包」裁決者、糖衣毀滅者、天燼審判輔助零偽陽性，但必須是 weapon.description
技能描述含「背包」馬哈利姆之力 陷阱這是偽陽性——它的技能文字提到「修理背包的 0.35 倍」， 那是引用背包數值而非由背包合成。絕不可搜尋技能描述。
仍成立 Weapon 沒有存官方數字 ID（doc id 是中文 slug）， 所以「官方 ID 第 5 碼 = 6」對現有文件不可用，只能在爬蟲內部用。
決策六（v2 新增）：推導的鍵是 skill.name，絕不可用 skill.icon
這是 v1 調查寫錯、v2 實測糾正的一點：
方向結果判定
name → icon124 個相異技能名，0 個對到 >1 個 icon1:1，可當鍵
icon → name107 個相異 icon，11 個對到 2–3 個不同技能名非 1:1，不可當鍵
反例：Icon_skill_passive_5186 → 凝神待發／靈光一現； Icon_skill_passive_5136 → 擴容火力／追蹤調律／扞拒。 icon 是共用美術素材，不是技能 ID；拿它當鍵會把三個無關技能合併成一筆。
資料填寫的兩個陷阱
① 官方 description 是錯的，不可用來推導 fusedBackpackType。 裁決者寫「將干擾背包與機載電磁炮合二為一」、糖衣毀滅者寫「通用強化背包」， 但站長實機截圖確認材料是 出力強化背包·首攻（PowerAdd）。一律以實機製作介面為準。

② 命名陷阱：DB 有兩個名字只差「出力」二字的背包。
名稱idraritytype
正解 出力強化背包·首攻60102405S+PowerAdd
陷阱 強化背包·首攻60600404SEnhance
評估文件的初版草稿就填錯過這一格。
決策五：必須寫進資料模型文件的架構判準
這是本計畫真正的長期價值——沒有它，下一把複合武器出現時會整輪重吵一次：
跨界實體（官方製作介面歸類與資料形狀不一致者）： 所屬集合與 refType 依「資料形狀／官方 API 來源表」決定； 官方介面歸類另以 craft 這類正交欄位表達， 並在對應圖鑑以投影方式呈現，不改變 refType。

不在範圍內（各自另立計畫）：
  • 武器技能引用化 → PLAN-032（本次辯論裁決另開）。 兩者零欄位重疊：本計畫碰 Weapon.upgrade、PLAN-032 碰 Weapon.skills。 但不建議同時開工——在 src/types/weapon.ts、WeaponAdmin.tsx、 WeaponDetailPage.tsx 有檔案級交集。建議本計畫先行。
  • 製作材料（武裝討伐掉落）——擴充點已留在 WeaponUpgrade（物件形態）， 但現在不建欄位（0/5 定律）。前置條件：items 集合與掉落資料。
  • back 槽互斥修正——站長已實機確認「背部永遠只能裝一個，無論背包或武器」， 而 SimulatorPage 兩邊都不看 equipSlot，影響全部 20 把背後武器。 回歸面與本計畫完全不同，不可綁同一個 commit。
  • /backpacks/:id 詳情頁與背包合成展示——站長決定另開背包 Detail 頁處理。 本計畫仍存下 fusedBackpackId（事實欄位，零成本）， 先渲染為純文字「融合自 出力強化背包·首攻」，待該頁上線再換成連結，資料不用重做。
  • 武器主動指令技能（InitiativeSkill 從未被爬蟲讀取）——站長決定以後再處理。 與本計畫零耦合：融合技能改為前端 derive 差集後，母子武器日後同時獲得主動技能時差集不變。
  • 搬集合、新開第三集合、EquipmentBase 大抽象、legacyEntityAliases （線上 refType:'weapon' 引用實測 0 筆）。
本計畫的風險性質： 0 筆文件搬移 · 0 個 doc ID 變更 · 0 個 refType 變更 · 0 筆 userBuilds 遷移 · 只 bump 1 個版本號。
回退 = git revert + bump；Firestore 上殘留的 upgrade 是惰性資料，沒有任何消費端。 工程量估 約 2.5–3 人日（v1 為 1.5–2，因併入進階鏈而增加；但覆蓋率從 3 把複合武器提升到 42 條邊）。
第一個出貨點的建議（個人專案的可停性）
本計畫在寫入資料前使用者可見價值為 0。若晚上時間有限，建議把 patch 拆成兩次寫入： 先只寫 upgrade.fromWeaponId（42 條邊全部）—— 這時武器頁的進階鏈就全部可點，覆蓋率是「3 把複合武器」的 14 倍，而人工成本更低 （推導 0 歧義，複合武器那 3 筆才需要實機確認背包）。 之後再補寫 station / fusedBackpackId 與背包圖鑑投影。
Pitfalls
已知實作陷阱
  • weapon 卡務必用 WeaponIcon，不可用背包側圖示元件—— BackpackBadges.tsx 會強制拆檔名拼 /images/backpacks/{filename}， 武器圖示必然 404 → remote fallback 再 404 → 顯示「背」佔位字。
  • 投影條目的技能圖示要走武器側路徑解析—— BackpacksPage 內的 SkillIcon 拼的是 /images/skills/， 而 WeaponSkill.iconLocal 是 /images/weapons/skills/，直接沿用會 404。
  • src/components/BackpackSkillCard.tsx 是死碼（全庫零 import， 且沒接 RefText、圖示路徑規則與現行不一致）——別誤當可複用元件。
  • 讀取量取捨：BackpacksPage 加 useWeapons() 後， 冷快取新訪客直接落地 /backpacks 會多付約 169 筆 doc read（之後走 localStorage）。 若在意免費額度，改成點該 facet 時才 lazy ensureLoaded(['weapons'])。
  • 腳本一律用 doc id 比對，絕不用 name—— mechs/mech_037_裁決者 是一台真實機甲， patchVersions/base.ts 名單裡的「裁決者」指的也是機甲。
  • 武器圖鑑的 badge 是必做不是可選——熠光與裁決者數值全同、 連 icon 都共用同一張圖（Icon_weapon_50100401.png）， 不給視覺區隔會讓玩家在武器圖鑑困惑。
  • v2 新增推導腳本不要放進 scripts/temp_scripts/——該目錄在 .gitignore， 既有的 migrate-plan001／plan023／plan024／derive-debut-version 全部未進版控、只存在單一台機器。
    upgrade 是 Weapon 上第一個人工維護欄位（現有 168 筆全部來自 API）， 沒有可重跑的腳本，它會在下次改版後變成無人維護的死欄位。 推導腳本請放進版控的 scripts/。
  • v2 新增推導鍵用 skill.name 不用 skill.icon （見決策六）。用 icon 會把 11 組無關技能合併。
  • v2 新增判別式只搜 weapon.description， 不可搜技能描述——後者會誤中「馬哈利姆之力」（它的技能引用了背包數值，並非由背包合成）。
