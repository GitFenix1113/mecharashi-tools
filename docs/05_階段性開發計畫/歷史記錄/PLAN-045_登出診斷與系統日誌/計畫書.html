◆ PLAN-045

登出診斷與系統日誌 · Diagnostics · SystemLog · Draft Autosave

維護者「編輯到一半被登出」查無實據。用三態哨兵在登出當下留下證據、暫存草稿避免損失，並開一頁只有 OWNER 看得到的系統日誌。

Problem
問題背景
維護者持續回報「編輯資料到一半被登出」，但完全查不到原因
回報者不會看瀏覽器主控台，也講不出當下的環境細節。目前站上沒有任何持久化的診斷記錄， 每次回報都只能靠猜。過去已針對「Chrome storage eviction 清掉 IndexedDB」的假說， 在 src/lib/firebase.ts 加了 navigator.storage.persist() 申請持久化儲存， 但那個假說從未被證實——問題仍在發生，我們不知道是修錯了方向，還是修對了但涵蓋不全。
「被登出」很可能是三種不同故障的統稱
使用者只會說「我被登出了」，但底下其實混雜著性質完全不同的三件事：
症狀實際發生的事使用者看到
A. Auth 失效 本機儲存被清除，或 refresh token 被撤銷 真的變回未登入狀態
B. 寫入被拒 仍登入著，但 setDoc 收到 permission-denied 「存檔沒反應」，誤以為被登出
C. 資料快取失效 gameData 版本 bump，重新抓資料 畫面閃一下，其實不影響編輯
只記 A 會抓不到真兇。B 尤其容易被誤報成登出，且它會直接造成編輯內容丟失。
不論成因為何，編輯內容都是直接蒸發的
12 個後台編輯頁的草稿全部只存在 React state（const [editing, setEditing] = useState<T|null>(null)）， 沒有任何本機暫存。無論是被登出、寫入被拒、或單純誤觸重整，未存檔的編輯一律歸零。 對填了半小時數值的維護者而言，這才是真正的損失——查明原因是手段，止血才是目的。
Design
設計決策
決策一：不能在登出當下寫 Firestore——這是整個設計的形狀來源
被動登出時，onAuthStateChanged 拿到 null 的那一刻 auth.currentUser 已經是 null， 而 firestore.rules 全站要求 isAdmin()，所以此時寫任何 log 必定 permission-denied。 因此不能照 PLAN-030 changeHistory 那套直接 addDoc。

改為兩段式上報：登出瞬間寫進 localStorage 佇列 → 下次登入成功後 flush 到 Firestore。 維護者被登出後幾乎都會馬上重登，實務延遲通常只有幾秒。

已評估但不採用的替代方案：加開 Cloudflare Worker /api/log 端點即時上報。 優點是不依賴重新登入，缺點是要動 Worker 程式碼、新增未授權寫入面、需額外限流防灌爆。 唯一多涵蓋的情境是「使用者被登出後再也沒回來」——而那種人本來就不會回報問題。 保留為日後需要時的擴充點（見「不在範圍內」）。
決策二：雙哨兵判定——用兩顆哨兵 + 一個旗標把成因收斂到唯一解
（本決策被實作與實測各修正過一次，經過見下方兩個警告框。定稿如下。）

我方呼叫過
signOut()		localStorage
哨兵		cookie 哨兵判定 reason
✓ 是 — — explicit
主動登出（正常，不記錄、不告警）
✗ 否 ✓ 在 — tokenRevoked
quota storage 完好卻登出 → 改密碼 / 停用 / 撤銷
✗ 否 ✗ 不見 ✓ 在 storageCleared
裝置確實登入過 → quota storage 被清
✗ 否 ✗ 不見 ✗ 不見 neverSignedIn
查無登入痕跡 → 不產生事件
判定順序不可調換：explicit 必須最先判，它是我方自己設的旗標， 可信度高於任何環境推測。
判定邏輯寫成純函式（src/lib/diag/sentinel.ts），用 node --test 窮舉全部 54 種輸入組合。
// 兩顆哨兵都在登入成功時種下，且刻意「不」在登出時清除—— // 它們的價值正是在於「儲存被清時會跟著消失」。 const SENTINEL_KEY = 'mecharashi_diag_sentinel' // { uid, plantedAt, lastSeenAt, sessionId } const SENTINEL_COOKIE = 'mr_diag' // 僅存 uid 前 8 碼，回答是非題就夠
🐛 實測推翻：IndexedDB 探針測不到任何東西（成因 idbEvicted 因此退場）
初版讓「Firebase 的 firebaseLocalStorageDb 還在不在」參與判定。瀏覽器實測發現 那顆探針恆為 present：該 database 會在 SDK 初始化時自動重建， 所以等 onAuthStateChanged(null) 觸發、探針執行時，就算前一秒手動刪光整個 database，它也早就回來了。

兩層後果，都在實測中重現：
① idbEvicted 永遠產生不出來（條件是「IDB 不見」，而它不會不見）；
② 更嚴重——原本「cookie 沒了但 IDB 還在 → 證明登入過 → storageCleared」這條，會讓 每個第一次進站的匿名訪客（哨兵、cookie 都沒有，IDB 由 SDK 剛建好） 被判成 storageCleared 並跳出登出橫幅。正是決策二之補要防的誤報，卻被從側面繞過。

修正：判定只採用不受 Firebase 干擾的兩顆哨兵；探針改為檢查 firebase:authUser:* 記錄是否存在（名實相符），保留為佐證但不參與判定。

單元測試為什麼沒抓到：它測的是「給定探針值 → 判定是否正確」， 而錯的是探針值本身測不到真實狀態。那一層只有真實瀏覽器測得出來。
決策二之補：為什麼一顆哨兵不夠——匿名訪客誤報
只用 localStorage 一顆哨兵時，「哨兵不見了」有兩種截然不同的解釋：儲存被清， 或這台裝置根本沒登入過。而前台匿名訪客每次載入都會觸發一次 onAuthStateChanged(null)，全部會被判成 storageCleared —— 日誌會被訪客雜訊淹沒到失去用途。

關鍵在於必須先回答「這台裝置到底登入過沒有」，而這個問題不能問正在被懷疑的那個儲存機制。 故第二顆哨兵種在 cookie：它不屬於 quota-managed storage，Chrome 的 eviction 清不到它， 所以「localStorage 沒了但 cookie 還在」就是儲存被清的鐵證。

已知取捨：Safari ITP 會連 cookie 一起清，故 Safari 的儲存清除會落到 neverSignedIn 而非 storageCleared。這是刻意的—— 寧可漏報也不要誤報，且 Safari 情境可由日誌裡的 UA 分布另行辨識。
決策三：Safari 根本不給 persist()——現有防護對 Safari 使用者完全無效
現有的 navigator.storage.persist() 只在 Chrome 系有意義。Safari 一律不核准 （除非站台被加入主畫面），而 Safari ITP 的政策是7 天無互動就清除 script-writable storage， 包含 localStorage 與 IndexedDB。若有維護者用 iPhone 或 Mac Safari， 他們被登出是必然而非偶然，且現有修法完全擋不住。

這正是本計畫要證實的關鍵假說之一——所以日誌必須記錄 UA / 平台 / persisted() 結果， 否則無法區分「Chrome 空間壓力」與「Safari ITP 定時清除」這兩個需要完全不同對策的成因。
決策四：systemLog 沿用 changeHistory 的集合形狀，但讀取權限收到 OWNER
與 changeHistory 同構：獨立頂層集合、append-only、伺服器分頁、刻意不註冊進 CollectionKey / GameDataContext（沿用 PLAN-030 決策一：持續成長、只查最近幾頁的資料， 塞進「整包載入 + localStorage」的版本快取只會撐爆快取）。

差異在權限：changeHistory 是 read: isAdmin()， systemLog 收緊為 read: isOwnerRole()——日誌含 UA、儲存用量等環境指紋， 屬於維護者的裝置資訊，不該讓其他 ADMIN 互看。
match /systemLog/{docId} { allow read: if isOwnerRole(); allow create: if isAdmin() && request.resource.data.uid == request.auth.uid; allow update, delete: if false; }
create 維持 isAdmin()：本計畫只追蹤維護者，一般 USER 被登出不影響資料， 放寬到 isAuthenticated() 只會擴大寫入面並帶來限流需求。
決策五：日誌不只記登出，也記寫入被拒（症狀 B）
攔 permission-denied，記成 kind: 'writeDenied' 的事件。這類事件 當下通常仍登入著，可以直接寫 Firestore，不必走佇列——但仍共用同一個事件型別與同一頁檢視， 因為對 OWNER 而言「維護者存不進去」與「維護者被登出」是同一個問題的兩種面貌。

（實作修正：原本以為 firestoreCore.ts 已有寫入路徑可以直接攔， 實際上該檔只有讀取函式，寫入分散在 12 個模組的 update* —— 8 個各自 setDoc、4 個走 saveWithHistory。故先新增 writeDoc / writeDocRaw 統一入口再全數改接，順帶讓 stripUndefined 不會再有人漏掉。）
決策五之補：診斷在非瀏覽器環境一律停用
reportWriteDenied() 開頭即檢查 typeof window === 'undefined' 並返回。 模擬器整合測試與 scripts/ 的 migrate 腳本都會走到 writeDoc， 而破壞性測試更是刻意製造 permission-denied —— 讓診斷在那裡開火只會產生 無人閱讀的雜訊記錄，還可能干擾計算寫入次數的測試。
另外，寫入被拒本身就可能意味著憑證已失效（那樣連診斷記錄也會被拒）， 故直接寫入失敗時退回 localStorage 佇列，證據不會因此丟失。
決策六：草稿暫存做成統一 hook，而非逐頁改寫
盤點 12 個後台編輯頁後發現慣例高度一致：一律是 const [editing, setEditing] = useState<T|null>(null) 搭配 handleSave(updated)。 因此可在 shared.tsx 加一個 useDraftAutosave(kind, editing, setEditing)， 每頁只需接一行，不需要動各頁的表單結構。

草稿存 localStorage（debounce 寫入，避免每次按鍵都寫），存檔成功後清除。 重新進入該頁時若偵測到未清除的草稿，顯示「偵測到未儲存的編輯，要還原嗎？」讓使用者選擇。 不自動套用——自動覆蓋使用者當前選取的項目比丟失草稿更難解釋。
決策七：被登出當下就要跳橫幅，不能只寫進 OWNER 才看得到的日誌
維護者不看主控台，也看不到系統日誌頁。若只做後台記錄，對他們而言體驗毫無改善， 仍然是「莫名其妙被登出」。因此登出當下要直接顯示橫幅，用白話說明推定原因與 草稿是否已保住，例如：
⚠ 你被登出了 推定原因：瀏覽器清除了本站的儲存資料（裝置空間不足或隱私設定） 你未儲存的編輯已暫存在這台裝置，重新登入後可還原。 [ 重新登入 ]
決策八：佇列要有上限，日誌要有 TTL
localStorage 佇列上限 20 筆、超過丟棄最舊的——若使用者長期沒登入回來， 佇列不該無限增長把 localStorage 配額吃光（那反而會誘發我們正在追查的儲存問題）。

Firestore 端沿用 PLAN-030 的 expireAt + Firestore 原生 TTL 政策， 但保留期縮短為 90 天（changeHistory 是 2 年）——診斷日誌的價值隨時間急遽衰減， 半年前的登出記錄對排查今天的問題沒有意義。
TTL 在 firestore.indexes.json 的 fieldOverrides 以 "ttl": true 宣告，隨 firebase deploy --only firestore:indexes 一併生效， 不需要到 Firebase Console 手動設定。
決策九：草稿暫存自己不能變成故障來源
這一條在實作時才浮現，但它是本計畫最容易自相矛盾的地方：我們正在追查「localStorage 被清空」， 而解法之一是往 localStorage 寫更多東西。
因此草稿寫入在配額滿時，會清掉自己的草稿再放棄，而非重試或保留： 寧可失去暫存能力，也不能讓暫存機制把配額撐爆、反過來誘發我們正在追查的儲存清除。 診斷佇列的 20 筆上限也是同一個理由。
Scope
實作範圍與不在範圍內
在範圍內：
  • 診斷採集層 src/lib/diag/：哨兵讀寫與三態判定、環境證據採集、localStorage 事件佇列、登入後 flush
  • systemLog 集合：型別、API 層（append-only + 伺服器分頁）、firestore.rules、TTL 政策、複合索引
  • OWNER 系統日誌頁 /admin/system-log：依 kind / reason 雙軸篩選、展開看完整環境證據
  • 登出橫幅：被動登出當下以白話說明推定原因與草稿狀態
  • 草稿本機暫存與還原：useDraftAutosave hook + 12 個後台編輯頁接線
  • 寫入被拒記錄：firestoreCore 寫入路徑攔 permission-denied
不在範圍內：
  • Worker /api/log 即時上報端點——見決策一，保留為日後擴充點
  • 一般 USER 與匿名訪客的登出記錄——本期只追蹤 ADMIN / OWNER
  • 實際修復登出問題——本計畫是「取得證據」，對策要等日誌累積出真實成因分布後再開新計畫。 先修再驗證，等於重蹈 navigator.storage.persist() 那次的覆轍
  • 前台使用者的錯誤回報 / Sentry 類全站錯誤追蹤——範圍完全不同
驗收標準：本計畫的成敗不看「登出問題有沒有解決」（那是下一個計畫）， 而看下次維護者回報被登出時，OWNER 能不能在系統日誌頁上直接看出原因， 以及該維護者的編輯內容有沒有保住。
