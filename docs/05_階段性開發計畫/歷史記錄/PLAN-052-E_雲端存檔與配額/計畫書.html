Problem
問題背景
① 登入使用者今天的存檔能力是 0，而管理者的測試配裝正躺在 localStorage 裡
052-C 給的是訪客本機書架（mecharashi_loadout_shelf，全站共用 10 格）。 它的檔頭第一句就寫著「未登入者唯一的存檔方式，直到 052-E 的雲端存檔上線」—— 而登入者今天用的也是同一個，因為沒有第二條路。 後果：清一次瀏覽器資料、換一台電腦、換一個瀏覽器，配裝就沒了，而且沒有任何預警。 目前管理者測試期配出來的每一套都在這個處境。
② users/{uid}/builds 的安全規則今天沒有任何上限
firestore.rules 現行只有一行 allow read, write: if isOwner(userId)—— 那是 PLAN-011 時代為 v1 Build 寫的，不驗形狀、不驗大小、不驗份數。 一個登入帳號可以往自己的子集合塞近 1 MiB 的合法 JSON、塞無限份文件，全部合法。 這正是總綱決策二選擇 code-as-payload 的理由：Firestore 規則沒有位元組長度運算子、 不能對動態 key 迴圈、也沒有 count()，巢狀結構在規則層根本設不了上限。
③ v1 Build 那條路徑還活著，而且從模擬器一路接到 ProfilePage
types/user.ts:59 的 Build 仍是總綱判死的兩個單值欄位模型 （weaponId / backpackId）；userApi.ts 的 getUserBuilds／saveBuild／deleteBuild 三支還在； ProfilePage 的「我的配裝」tab 還在讀它，並用 navigate('/simulator', { state: { build } }) 送進 LoadoutPage 的 legacyBuildToDraft()（LoadoutPage.tsx:103／:206／:294）。 三層都還在，只是因為集合是空的所以永遠走不到。 再放著，它會變成「兩份都聲稱自己是存檔格式」的第二個真相源。
④ 時間窗正在關 —— 這是本計畫排在 052-H 前面的唯一理由
總綱寫得很直白：users 集合實測 0 筆、builds 0 筆， 「現在改模型零遷移成本；一旦全面公開（已定案）就再也不免費」。 SIMULATOR_INTERNAL_ONLY = true 讓這個窗還開著， 而使用者已裁決「全部功能完成並校正後再開放」——所以窗會一直開到本計畫做完。 對照組是 052-H（站內熱門配裝）：它的輸入是流量，內部測試期只有幾位管理者在配， 聚合出來的「熱門」是自己人榜、OG 卡沒有對外連結可預覽，做完了驗不了， 真實分布一進來還得重來。E 先於 H 不是重要性排序，是可行性排序。
Design
設計決策
決策一：落盤形狀沿用總綱決策二，本計畫不重新討論
users/{uid}/builds/{pilotId}，一位機師一份文件， slots 是 '0'～'4' 的 map，每格內容就是一串 base64url 分享代碼。
三條理由原封不動成立：(1) 收斂成單一字串後 code.size() <= 1024 是規則層唯一精確且繞不過的上限；(2) map key 白名單讓「每機師 5 套」變成 結構性事實而不是一個會漂移的計數欄位；(3) 儲存＝分享是同一串字， 沒有第二套序列化。
⇒ 本計畫是接線與把關，不是重新設計資料模型。
決策二：規則要擋的是四件事，而第五件擋不住 —— 明著寫出來，不假裝擋住了
擋得住：① 頂層 key 白名單（hasOnly(['slots','updatedAt'])）； ② slot key 白名單（slots.keys().hasOnly(['0','1','2','3','4'])）⇒ 5 格是結構性事實； ③ 每格 code.size() <= 4096（B-4 實測後由 1024 上調，見下）；④ isOwner(userId)。
擋不住的第五件：文件份數。規則沒有 count()，也驗不了 「{pilotId} 真的是一位存在的機師」。一個帳號可以開任意多份 builds 文件。
⇒ 處置：用 doc id 正規式把面縮小（buildId.matches('^pilot_[0-9]{3}_.*')）， 並接受份數無界這個殘餘風險。理由：每份有界（5 × 4096 ＋ overhead ≈ 20 KB）， 要塞出有意義的量需要極大量寫入，而寫入本身受 Firebase 專案配額與計費保護。 這條要寫進規則的註解——下一個讀規則的人必須知道哪一條沒被守住。
⚠ string.size() 回的是字元數不是位元組數。base64url 全為 ASCII， 所以 4096 字元 == 4096 bytes 剛好成立。這是巧合不是保證， 註解要寫明「這一格只准放 base64url」，否則哪天有人往裡面塞中文，上限就悄悄變成 16 KB。
✅ B-4 實測後把 1024 改成 4096（2026-08-29，使用者裁決）：「號碼全滿 ＋ 4 套獨立形態」量到 1051 字元，1024 在那裡就破了，而每多一套形態約 +160 字元。依本決策自己的規矩「上限只能放寬不能收緊」，挑小了才是不可逆的錯。4096 同時與 codec 的解碼上限 LIMITS.codeChars 對齊，消掉「解得開卻存不了」那段落差。
✅ A-3 已裁決（2026-08-29）：接受殘餘風險 —— 走 doc id 正規式縮小面，不上 Cloud Function 計數器（那會把「存一套配裝」從一次 client 寫入變成一條需要冷啟動、需要監控、會失敗的後端路徑，為了一個沒有實際攻擊者的風險）。B-4 的交付物因此包含那段「份數沒守住」的註解，不是選配。
決策三：v1 Build 走「刪除」而不是「遷移」—— 但動手前要再驗一次 0 筆
builds 實測 0 筆 ⇒ 沒有東西要遷。Build／UserBuild 型別、 userApi 三支、legacyBuildToDraft()、pending.legacy 分支、 ProfilePage 的 v1 BuildCard 全數刪除。
⚠ 這是本計畫唯一的破壞性動作，而它依賴的「0 筆」是 2026-08 盤點的數字。 A-1 必須直讀正式 Firestore 復驗，不可以只信文件上的數字—— 052-G 的四輪盤點就修正過總綱四個看起來很確定的數字。
✅ A-1 已復驗（2026-08-29）：builds 確認 0 筆 —— collectionGroup('builds') 全站掃描 0 筆、逐 42 個 uid 複查加總 0 筆，兩種算法互相對上。決策三成立，零遷移成本。（scripts/temp_scripts/count-user-builds.mjs，唯讀）
⚠ 但總綱那句「users 集合實測 0 筆」要訂正：實際有 42 個帳號。那不是筆誤而是量測假象 —— users/{uid} 父文件是空殼（只有子集合、無欄位），getDocs 看不到這種 missing document（listDocuments() 42 個參照、其中真的存在的 0 個）。本決策不受影響（關鍵數字是 builds），但「站上沒有使用者」這個推論是錯的，B 段之後凡是引用「使用者數」的地方都要用 42 而不是 0。
決策四：訪客書架是「匯入」不是「搬移」—— localStorage 那 10 格不清空
三條理由：① 同一個瀏覽器可能有多人用（家用電腦），清空等於替別人做決定； ② 匯入到一半失敗時清空 ＝ 資料消失；③ 兩種配額語意不同—— 訪客是「本機書架 7/10」（全站共用），登入是「海莉絲 3/5」（每機師）， 10 套完全可能全是同一位機師。
⇒ 「塞不下」是正常結果不是錯誤，必須逐筆回報而不是整批成功／失敗。 localBuilds.ts:17 的檔頭註解早就預告了這一條（「UI 文案要分開寫」）。
決策五：方案名稱不加登入 gate —— 推翻 052-I E-1 的預告
052-I E-1 寫著「命名與雲端保存需登入，登入 gate 的實作掛 052-E」。 那個前提在實作落地時就已經不成立了：name 今天對訪客完全開放、 已經編進 codec 的 §NAME 段（codec.ts:59／:430）、 已經印在匯出圖最大的一行上。
回頭 gate 它的代價是訪客既有的分享碼與匯出圖會失去名稱，換來的好處是零—— 名稱不佔 Firestore、不是特權、也不是配額。052-I 當初的假設是「命名是雲端保存的一部分」， 實際落地後兩者分開了。⇒ 只有「存到雲端」需要登入。 ✅ A-2 已裁決（2026-08-29）：不加 gate，本決策定案。 loadoutName.ts 檔頭第 6 行已補上下落註記。
決策六：載入 gate 接既有那一份，不新寫第五份
052-G 決策六那條 gate 對雲端存檔同樣適用——草稿會在集合載入完成前就被 loadDraft 灌進來，而空 Map 不等於「查不到」。
052-G Phase D 已經把它補到第四份（元件／模組／形態／部件）。 雲端書架與分享碼走的是同一條解碼路徑（classifyBuild() → decodeLoadout()）， 所以這裡要做的是接上而不是再寫一份。
⚠ 052-G E-1 ⑤ 踩過一次：在 ?b= 冷開頁注入 fetch 延遲攔不到 Firestore （SDK 走自己的 WebChannel），那樣只是「看起來測過了」。 真正的觸發條件是在還沒選機師的空頁面上開雲端書架。
決策七：雲端書架用 getDocs 一次抓，不用 onSnapshot
跨裝置同步的實際需求是「換一台裝置打開時看得到」，不是「A 裝置存、B 裝置立刻跳出來」。 onSnapshot 會讓每個開著模擬器的分頁長期佔一條連線並持續計費讀取， 換來一個沒有人在等的即時性。符合 CLAUDE.md 的 Firestore 慣例 （靜態資料 getDocs 一次抓、需即時才 onSnapshot）。
⚠ 這是模擬器的第一次 Firestore 寫入
useSimulatorEntry.ts 的檔頭明著寫：目前「模擬器全程沒有任何 Firestore 寫入 （書架走 localStorage、分享碼是純前端 codec）」——那句話正是當初決定「不 revert、 只收起入口」的依據之一。本計畫做完之後它就不成立了，該檔註解要一併訂正。
連帶影響：讀寫額度、離線行為、規則被拒的錯誤呈現，三者從本計畫起才第一次在模擬器上存在。
Scope
實作範圍與不在範圍內
在範圍內：
  • 安全規則：users/{userId}/builds/{buildId} 四條 gate ＋ 殘餘風險註解
  • src/lib/buildsApi.ts（新檔）：雲端書架的讀／寫／刪，零 React、零 UI 文案（比照 localBuilds.ts）
  • 雲端書架 UI：與本機書架同一個對話框的兩個分頁，共用 classifyBuild() 三態
  • 每機師 5 格的槽位選擇與覆寫確認（覆寫時要說出被覆寫的是哪一套，不是「確定嗎？」）
  • 訪客書架匯入：逐筆預覽、勾選、逐筆回報、idempotent、不清空 localStorage
  • v1 Build 全鏈刪除：型別 ／ userApi 三支 ／ legacyBuildToDraft() ／ ProfilePage 舊卡
  • ProfilePage「我的配裝」重寫成雲端書架
  • emulator 規則測試：擴充 scripts/test-emulator-rules.mjs（Auth emulator 換真 token 打 REST）
  • 常駐橫幅文案訂正：拿掉已經不成立的「部件混搭、雲端存檔尚在後續階段」
不在範圍內：
  • 開放模擬器（SIMULATOR_INTERNAL_ONLY = false）——使用者已裁決「全部功能完成並校正後再開放」，那是獨立的一次決定，不夾帶在本計畫裡
  • 052-H 站內熱門配裝與 OG 卡——需要真實流量才驗得了
  • 即時同步 / 協作編輯（決策七）
  • 配裝的公開瀏覽（「看別人的雲端書架」）——雲端存檔是私有的，公開走分享碼
  • Cloud Function 計數器擋文件份數（決策二已裁決接受殘餘風險）
  • 方案名稱的登入 gate（決策五推翻）
