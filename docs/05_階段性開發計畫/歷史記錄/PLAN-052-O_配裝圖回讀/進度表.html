目標效果： PC 玩家拿到別人的配裝圖，Win+Shift+S 截下來、切回模擬器 Ctrl+V，站上自己從圖裡讀出分享連結、 走既有的預覽 → 套用；原始匯出圖靠 PNG 內嵌 100% 精確、不受碼長上限，二手截圖靠 QR。 圖片從頭到尾不離開瀏覽器：零上傳、零 Firestore read、零 Worker 請求。
施作順序： A → B 是主線（做完就能從圖讀碼）；C 是匯出端的補強 （tEXt 內嵌補上「長碼不畫 QR」與「二手壓縮」兩個缺口；原列的整數間距吸附評估後否決，見 C-2）， 不做 C，A＋B 對舊圖照樣有效。D 收尾——文件與 Playwright e2e（18／18）皆已完成，計畫已於 2026-10-11 歸檔。
Phase A
解碼核心 —— 兩支純函式，Node 測試裡跑得動
零 DOM、零 React。這一階做完，任何一段 bytes 進來都能問出「裡面有沒有本站的連結」，但還沒有人呼叫它。
✅ 2026-09-08 完成（3／3）。 解碼器選型在這一階定案：jsQR 對本站匯出圖（QR 方塊 420 實體 px、v21 以上每模組 3.07–3.85px） 從 1000 字元起全數失敗；zxing-wasm 36／530／1461 字元全部解回（54／26／28 ms）， 模擬二手截圖 36 字元縮 25%＋q40、530 字元縮 40%＋q60 仍 OK，經驗門檻每模組 ≥ 約 1.9 實體像素。 4000×3000 純雜訊 67 ms 回空陣列、同框兩個 QR 兩個都回。 實驗腳本 _local-notes/2026-09/2026-09-08_qr-sanity*.mts。

⚠ 兩條在這一階釘死的不變式：insertPngText() 絕不 throw（它跑在匯出流程尾端，一個例外＝整張圖存不下來）； decodeQrTexts() 在 wasm 載入失敗時刻意 throw（「載不到解碼器」與「圖裡沒有 QR」是兩句不同的話，吞成空陣列會把前者誤報成後者）。
A-1   pngText.ts —— PNG tEXt 寫入／讀取
src/utils/loadoutCode/pngText.ts
已完成
insertPngText / readPngText / crc32 / isPng / dataUrlToBytes
keyword mecharashi-loadout、值＝完整分享連結。IHDR 之後插入（讀取時走不到幾步就命中，不必掃過幾 MB 像素）。
⚠ 讀取要能吃任何位元組：使用者丟進來的可能是 JPEG、WebP、截斷的檔、甚至不是圖片——每一步先驗界限再讀， 不能假設 chunk 宣告的長度是誠實的（宣告超長時回 null、不 throw）。
⚠ 只收 Latin-1、不做 iTXt；keyword 不合規（空、≥80 字、前後空白）或 text 含非 Latin-1／NUL 一律 null， 不偷偷改寫——規格外的 chunk 會讓某些看圖軟體判整張圖壞掉。
⚠ 改 keyword ＝ 升格式版本：已流出的匯出圖會全部讀不到內嵌碼（退回走 QR）。

Phase B
對話框接線 —— 三個入口、三層順序、九句話
本階段做完，玩家就能貼圖。這是整個計畫的價值所在；C 做不做都不影響它對舊圖的效果。
✅ 2026-09-08 完成（3／3）。 對話框只做一件事：把讀到的整串塞進 textarea，後面全走既有流程——預覽、套用覆蓋警示、 舊快取誤判防護、「資料還在載入不給套用」一行都不必重寫，也不會長出第二條套用路徑。

⚠ 原生 BarcodeDetector 的覆蓋率比想像中窄（2026-09-08 查證 Chromium 原始碼與 MDN BCD）：Chrome 只在 macOS／ChromeOS／Android 暴露它， Windows／Linux 的 Chrome 自 88 起連這個類別都沒有（83–87 曾有類別但 getSupportedFormats() 回空）；macOS 13 在 Chrome 113 之前靜默失敗； Safari 17 起藏在 feature flag「Shape Detection API」後預設關閉、iOS 18 起壞掉未修（WebKit bug 281848）；Firefox 完全沒有。 對本站主要客群（Windows PC 玩家）zxing 就是正式路徑，原生偵測器只是 macOS／Android 上的 0 KB 加速—— 程式碼仍先查 getSupportedFormats() 含 'qr_code'，回空或丟例外一律往下走。

程式碼已還原：loadoutQr.ts 沒有任何吸附欄位、ShareQr 仍鋪滿 210 CSS px 方塊。決策留在計畫書決策五，免得日後再走一次同樣的彎路。
