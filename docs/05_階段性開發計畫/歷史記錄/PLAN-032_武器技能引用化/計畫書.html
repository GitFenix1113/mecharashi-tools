◆ PLAN-032

武器技能引用化 · 技能庫吸收 · 消滅重複維護面

把散落在 82 把武器內的 170 份技能拷貝收斂成 124 筆共用定義，改一處全站生效——沿用 PLAN-004 已驗證的漸進遷移路徑。

前置依賴
建議 PLAN-031 先行（檔案級交集，非欄位耦合）
立案背景：站長觀察到「當初個別在武器上輸入技能是考慮不周，現在技能庫已經非常龐大」， 提議把武器技能改為「連結引用」單獨管理，目的是未來調整技能效果時有更完善的機制。
本計畫由 19 個 agent 的對抗辯論（3 個分案立場 × 3 個紅隊鏡頭）裁決從 PLAN-031 分離獨立—— 理由：它改變的是「同一事實用什麼識別方式書寫」，與 PLAN-031 的「同一事實由哪個欄位表達」正交， 可延後且零欄位重疊。
Problem
問題背景
同一個技能存了很多份，而且已經開始漂移
【實測】170 個武器技能實例 → 僅 124 個相異技能，重複率 27.1%； 44 個技能名被 2 把以上武器共用。

漂移已經發生——S+ 武器是 SS 武器的材料，兩者持有同一個技能，但兩份拷貝的文字已經不同步：
起爆　　（icon = Icon_skill_passive_1115，同一個官方技能） [凱旋·改 S+] 「造成傷害時，對命中的部位造成15%武器攻擊力的固定傷害」 [獵器 SS ] 「造成傷害時，對命中的部位造成15%武器攻擊力的[固定傷害]」 ← 只差方括號 凝神待發（icon = Icon_skill_passive_5186，同一個官方技能） [赤狐·改 S+] 「普通攻擊前，若沒有移動過，本次攻擊可以瞄準，每回合最多發動3次」 [魔笛 SS ] 「普通攻擊前，若沒有移動過，本次攻擊可以[瞄準]，每回合最多發動3次」
差異是 PLAN-019 引用方括號只補了一份。這正是引用模型要消滅的東西—— 技能只有一份定義，就不可能左右不一致。
沒有「改一處全站生效」的機制
目前要調整一個被 3 把武器共用的技能效果，必須逐把武器編輯 3 次， 且沒有任何機制會提醒你「還有兩把沒改」。技能庫化後這是單筆編輯。
Design
設計決策
決策一：不新開 weaponSkills 集合，併入既有技能庫 —— 反駁站長偏好
站長原提議「單獨列一個武器技能分類，後台管理跟一般技能分開（或你認為不分開也可以反駁我）」。 本計畫反駁「分集合」，接受「分類」。

決定性證據：pilotSkills 早就不是「機師的技能」，它已經是全站技能字典。
實測項結果
全庫 refType:'skill' 引用目標89 個
其中沒有任何機師持有的75 個（84%）
pilotSkills 中無機師持有的孤兒 doc83 筆
集合裡已經存在的武器技能 關鍵SKILL_故障植入、SKILL_態勢優化 ——維護者自己已經把武器技能放進去了，且描述與武器側幾乎逐字相同
分開建立新集合，等於在資料層宣告一條「現況已經被打破、而且是被維護者自己打破」的邊界。

成本差距同樣是壓倒性的：
面向併入技能庫另開 weaponSkills
RefType／EntityRefView／RefChip／RefPicker 0 處9 處（部分是 Partial<Record>，TS 抓不到漏改）
GameDataContext（CollectionKey 八處手改）0 處 7 處 switch（applyData 漏 case 完全不報錯）
firestore.rules／api 層／barrel0 處3 處
後台編輯面板既有頁 +約 30 行篩選 複製一份 SkillAdmin ≈ 330 行
＝第二份維護面，正是本計畫要消滅的病
武器技能可被 [起爆] 引用當天免費獲得要自己接
唯一代價是集合物理名 pilotSkills 變成誤稱。這是純美觀問題， 不值得為它做 collection rename migration —— 在 docs 裡把它正名為「技能庫」即可。
決策二：用 domain 欄位分類，後台同頁加篩選（採納站長的「有分類即可」）
// src/types/pilot.ts — PilotSkillDoc 只加選填欄位，既有 646 筆零改動 export interface PilotSkillDoc { // …既有欄位全部不動… /** 技能所屬領域。未填 = 'pilot'（向後相容） */ domain?: 'pilot' | 'weapon' }
後台技能庫頁加一顆 domain 篩選（機師／武器／全部）。 不建 SkillType 新 enum 值——實測 170/170 武器技能的 type 全是「被動技能」，零鑑別力，分類該用 domain 而非 type。
決策三：引用條目不能是裸字串——activation 是真實的每武器變異
PLAN-004 的機師版是 (string | PilotSkill)[]，但武器版不能照抄。 【實測】44 個重複技能名群組中，38 個在 activation 上衝突：
凝神待發： [赤狐·改 S+] activation = 'carry' // 攜帶即生效 [魔笛 SS ] activation = 'use' // 僅使用該武器時生效
這是遊戲規則造成的真實差異，不是資料漂移（S+ 一般武器 39/39 全為 carry）。 所以掛載側必須有地方放 activation：
// src/types/weapon.ts /** 武器對技能庫的掛載關係：只承載「這把武器怎麼用這個技能」 */ export interface WeaponSkillRef { skillId: string activation: 'carry' | 'equip' | 'use' // 實測 38/44 重複名在此衝突 → 必留掛載側 } export interface Weapon { /** 過渡期雙格式：WeaponSkillRef = 已遷移；WeaponSkill = 未遷移內嵌 */ skills: (WeaponSkillRef | WeaponSkill)[] }
鑑別鍵：'skillId' in entry（內嵌 WeaponSkill 沒有這個欄位）。
決策四：WeaponSkill 內嵌型別「刻意永久保留」，不是待清死碼
這與 PLAN-004 的情況不同：PLAN-004 的 union 是「該收斂卻沒收斂」， 本計畫是設計上不收斂——爬蟲抓到全新武器時仍會產出內嵌格式， normalize 步驟才把它轉成引用。這點必須寫進型別註解，否則日後會被誤當死碼刪掉。
決策五：去重鍵用 skill.name，絕不可用 skill.icon
方向結果判定
name → icon124 個相異技能名，0 個對到 >1 個 icon1:1，可當鍵
icon → name107 個相異 icon，11 個對到 2–3 個不同技能名非 1:1，不可當鍵
反例：Icon_skill_passive_5136 → 擴容火力／追蹤調律／扞拒； Icon_skill_passive_5198 → 蹁躚／故障植入（且與機師技能跨域碰撞）。 icon 是共用美術素材，不是技能 ID。
決策七（實作階段補充）：專武強化兩欄放定義側，不放 WeaponSkillRef
決策三只盤點了 activation，漏了 enhancesTalentName 與 enhancedTalentDescription（原 WeaponSkill 的專武欄位， 而 PilotSkillDoc 沒有它們）。實作 M1 時才發現必須先裁決。

裁決：兩欄移入 PilotSkillDoc。判準不是「哪邊比較整齊」，而是誰跟誰一起被消費：
// PilotDetailPage.tsx:1022 —— 同一份 refs 解析兩段正文 map.set(sk.enhancesTalentName, { text: sk.enhancedTalentDescription, refs: sk.descriptionRefs, // ← 綁在一起 })
descriptionRefs 一定住在技能庫 doc（它是技能正文的側錄表）。把 enhancedTalentDescription 留在掛載側，等於讓「正文」與「它的引用表」分居兩個文件—— 症狀是強化後天賦文字裡的 [虛情實意] 突然不會亮，且不會報錯。
而且它與 activation 的情況正好相反：專武與機師 1:1， 「此技能強化哪個天賦」天然無跨武器變異，沒有 38/44 那種衝突。
→ M2 影響：合併規則要把這兩欄一併納入衝突檢查。預期 0 衝突， 但腳本應該斷言而非假設——本計畫的其他「0 衝突」都是實測出來的，這兩欄沒測過。
決策六：文字漂移的收斂規則——有 descriptionRefs 的那份勝
合併同名技能時，description 取已補過 PLAN-019 方括號的那一份 （即 descriptionRefs 非空者）為正本，因為它資訊量嚴格較多。
effects / buffIds 實測 0 衝突，任取一份即可， 但仍保留「空殼不得覆蓋有值」的保護。
Scope
實作範圍與不在範圍內
在範圍內：
  • 前置修補：技能庫 ID 大小寫撞號防呆（見進度表 M0）
  • PilotSkillDoc.domain? + WeaponSkillRef 型別 + src/utils/weaponSkills.ts 相容層
  • Stage 1 遷移：建立 124 筆武器技能 doc（完全不動 weapons）
  • 前台雙格式解析上線（行為不變）
  • 後台：技能庫加 domain 篩選；WeaponAdmin 技能編輯改為挑選引用
  • 爬蟲 normalize：新武器技能自動建 doc 並掛引用
  • Stage 2 flip：82 把武器的 skills 換成引用
  • docs 同步（含把 pilotSkills 正名為「技能庫」）+ siteChangelog
不在範圍內：
  • 武器主動指令技能（InitiativeSkill）——爬蟲從未讀取，全站 170 筆武器技能 100% 是被動。 這是資料缺口不是結構問題，另立計畫。 好消息本計畫完成後，補進來的主動技能天生就是引用格式。
  • 技能庫 ID 正規化（134 筆 SKILL_ 大寫前綴改小寫）—— 要同步改所有引用它的 refId，成本高得多。本計畫只做防呆（M0），正規化另立 follow-up。
  • 集合實體改名（pilotSkills → skills）——純美觀，不值得做 rename migration。
  • 機師技能側的任何行為改變——本計畫對既有 646 筆 doc 一個位元組都不動。
與 PLAN-031 的關係： 零欄位重疊（本計畫碰 Weapon.skills、PLAN-031 碰 Weapon.upgrade）， 但在 src/types/weapon.ts、WeaponAdmin.tsx、WeaponDetailPage.tsx 有檔案級交集。建議 PLAN-031 先行、不要同時開工。 ✔ PLAN-031 已於本計畫開工前歸檔，此約束已解除
順帶一提：PLAN-031 把「融合技能」設計成前端 derive 差集而非存欄位， 正是為了讓本計畫 flip 之後零改動自動換算。
Pitfalls
已知實作陷阱
  • M3 必須早於 M6。雙格式前端要先上線，否則活站讀到新格式會整區空白。 （migrate-plan004-pilots.mjs 已把這句寫進互動提示，照抄該形制。）
  • 有 5 6 處 tsc 抓不到、會靜默壞掉：對 union 取 .length 兩個成員都合法。 WeaponsPage／WeaponDetailPage／PilotDetailPage（3 處）／ 實作時補上BackpacksPage（PLAN-037「包含武器」之後才長出來的消費端）的 weapon.skills.length > 0 必須改成 gate 在解析後的陣列， 否則技能庫尚未載入時會渲染出一個空的「武器技能」區塊。
    實作時新發現還有第 7 個靜默壞點不在 .length 之列： BackpacksPage 的搜尋 it.data.skills.some(s => s.description...)—— 引用化後那裡只拿得到 { skillId, activation }， 「用技能正文搜武器」會永遠 0 筆命中，無任何錯誤。 找這類壞點不能只 grep .length，要 grep 整個 .skills。
  • 計畫書漏列引用掃描層必須加 weapons.skills[].skillId 站點（entityRefs.ts）。 沒有它，M6 flip 之後從技能庫刪一個武器技能，級聯掃描器會回報 「零引用、可安全刪除」，然後所有掛它的武器靜默少一塊技能。 這正是 PLAN-043 為 backpacks.skillIds[] 做過的同一件事，武器側漏了。 且三個既有站點（buffIds／textUnits／softSites） 都要排除引用分支，否則與技能庫那份雙計。
  • ID 撞號地雷（M0 必須第一個做）：技能庫現有 SKILL_ 大寫 134 筆 / skill_ 小寫 512 筆，而後台撞號防呆只查小寫形式。 本次以 name 去重會直接踩爆——故障植入／態勢優化 已有大寫 doc， 腳本會再建一份小寫的，變成同名兩份，正是本計畫要消滅的東西。
  • 遷移腳本要進版控。scripts/temp_scripts/ 在 .gitignore， 既有的 migrate-plan001／plan023／plan024 全部未進版控、只存在單一台機器。
  • 遷移後武器技能失去自動補丁能力（與機師端同病）：normalize 只保證「新技能會被建 doc」， 不保證「既有技能的效果變更會被補丁」。這是引用化的固有代價， 改版後改由 data-patch 的報告提醒去後台核對。
