模組圖鑑內嵌改版等級滑桿 · 採用機甲縮圖 · 共用元件層

把藏在懸浮視窗裡的逐級效果搬到卡片上，順勢把兩頁重複的模組渲染碼收成一組共用元件

一句話： 模組的 levels[] 早就存了每一級的完整正文與數值，但前台只在 hover 出來的浮窗裡看得到；卡片本身顯示的永遠是滿級快照。本計畫改成 EN WIKI 那種「卡片內嵌一條等級滑桿」的讀法，並在動刀時把 ModulesPage 與 MechDetailPage 之間逐字重複的整套浮窗機制收斂成一組 src/components/module/ 共用元件。
Problem
問題背景
問題一：逐級資料被藏在互動後面，等於沒發佈
卡片上的描述吃的是 mod.description（頂層＝滿級快照），數值標籤吃的是 mod.dmg / mod.crit_rate 等頂層欄位。 Lv.1～7 的正文與數值只存在於浮窗中——搜尋引擎與站內搜尋抓不到、截圖分享帶不走、行動裝置得再點一次 BottomSheet 才看得見。 資料庫裡躺著 8 倍的內容，前台預設只露出 1/8。
問題二：同一套浮窗機制在兩個檔案裡各寫了一份
LevelTooltipRows、LevelTooltip、TooltipPortal、computePos、TooltipState、PART_LABELS、RARITY_STYLES 在 ModulesPage.tsx 與 MechDetailPage.tsx 中逐字重複，各自再配一組 hoverTooltip / pinnedTooltip / sheetMod 狀態與四個 handler。 兩頁合計約 240 行，做的是同一件事。任何一次調整（樣式、定位、行動裝置行為）都必須記得改兩個地方，而且沒有任何機制會提醒你漏了哪一個。
問題三：數值標籤是手寫 11 欄展開，抄了兩份，而且漏了一半欄位
ModulesPage.tsx:445-458 與 MechDetailPage.tsx:177-194 各自把 11 個屬性欄位一行一個硬寫出來（前者用純 <span>、後者包成 ModStat chip）。 但 ModuleLevel 型別實際有 32 個數值欄位——所有 dmg_blade / dmg_missile / dmg_counter 之類的武器類別與情境增傷，前台從來沒顯示過。 諷刺的是 STAT_LABELS（utils/moduleStats.tsx）早就備好了 25 筆對照，只有浮窗在用，卡片沒用。
問題四：ModuleBadges.tsx 是零消費者的死碼
src/components/ModuleBadges.tsx 已經提供 SLOT_LABELS / ModuleSlotBadge / ModuleRarityBadge， 但全站沒有任何檔案 import 它；同一組 slot 標籤表與稀有度樣式表在 ModulesPage.tsx:13-35 又被抄了一次，MechDetailPage 再抄一次稀有度表。 等於是「已經做好的抽象放著長灰塵，同時三份拷貝在各自漂移」。
問題五：「對應機甲」與「採用機甲」兩個詞讓人以為是兩種資料
ModulesPage.tsx:426 依機甲數量切文案（adopterNames.length > 1 ? '採用機甲' : '對應機甲'）， 但兩者來自同一個反查索引 mechsByModuleId，語意完全相同。 這是 2026-06-19「單機甲 → 多機甲共用」改版時為了讓單台情況讀起來自然而保留的舊詞，代價是每個讀者（包含站長本人）都會停下來想「這兩個差在哪」。
Design
設計決策
決策一：內嵌「單一等級 + 滑桿」，不是把 8 級全部攤平
浮窗方案唯一的優點是「卡片矮、一頁塞得多」。若把 8 級全部展開會直接毀掉這個優點。 採用 EN WIKI 的做法：卡片一次只顯示一級，用一條滑桿切換，卡片高度只增加約 40px。 副作用是得到浮窗給不了的東西——可以把兩張卡並排比較（pinnedTooltip 是單一值，天生互斥）。
┌──────────────────────────────────────────────────┐ │ [圖] 蓄能模組 S 8級模組 │ ← 標題列（改用 ModuleBadges） │ │ │ 採用 [頭像] [頭像] [頭像] （軀幹） │ ← 採用機甲縮圖列（可點進機甲頁） │ │ │ ├──┴──┴──┴──┴──┴──┴──┴──● Lv.8 / 8 │ ← 等級選擇器（預設滿級） │ │ │ 主動攻擊前，若移動距離 2 格以內，傷害 +18%； │ ← levels[i].description │ 行動結束時立即獲得 1 AP。此效果 1 回合觸發一次。│ （RefText 已內含數字著色） │ │ │ 傷害+18% 暴擊+6% │ ← levels[i] 的數值標籤（跟著滑桿走） └──────────────────────────────────────────────────┘
決策二：滑桿預設落在滿級，且不做全頁連動
預設滿級＝維持現況語感（今天卡片顯示的就是滿級快照），也是玩家最常查的狀態；EN WIKI 截圖同樣是 8/8。
不做全頁連動（頂部一個總控同步所有卡片）：模組的等級上限不一致，通用模組可能只有 1～3 級、8 級模組有 8 級， 一個全域「Lv.5」對半數卡片是無意義的，還會讓「這張卡為什麼沒跟著動」變成新的困惑來源。等級狀態各卡獨立。
決策三：數值標籤改為「由當前等級偵測、查不到就不顯示」
這是內嵌化的必然要求——滑到 Lv.3 卻仍顯示 Lv.8 的數字會是明顯的 bug。改為：
① 讀 levels[curLv - 1]；② 值為 0 / undefined 的欄位整個不渲染（不顯示「+0%」也不顯示灰字佔位）；
③ 當前等級整組數值皆空時，連標籤列容器都不出現，不留空白區塊。
這同時解掉「某些等級只有描述沒有數值」的既有情況，不需要額外分支。
決策四：STAT_LABELS 改為型別窮盡（編譯期擋漏）
問題三的根因不是「忘了寫」，而是沒有任何機制會在漏寫時報錯。改法是把陣列改由 Record 派生：
// utils/moduleStats.tsx — 現況：StatKey 誤含非數值鍵，陣列可任意少寫 export type StatKey = Exclude<keyof ModuleLevel, 'level' | 'description'> // ↑ descriptionRefs 也被算進來了 export const STAT_LABELS: StatLabel[] = [ /* 25 筆，漏 7 筆沒人發現 */ ] // 改為：從型別自動挑出「數值欄位」，再用 Record 強制窮盡 type NumericKeys<T> = { [K in keyof T]-?: NonNullable<T[K]> extends number ? K : never }[keyof T] export type StatKey = NumericKeys<Omit<ModuleLevel, 'level'>> const STAT_META: Record<StatKey, StatMeta> = { /* 少一個就編譯失敗 */ } export const STAT_LABELS = Object.entries(STAT_META).map(...) // 順序仍由 STAT_META 決定
效果：日後 ModuleLevel 一加新欄位（例如新版本出現新的武器種類增傷）， npm run build 會直接編譯失敗並指名缺哪個 key，而不是靜默地在前台少顯示一項。 這正是本次要補上的 7 個漏網欄位（dmg_heavy_machinegun / dmg_funnel / dmg_sniper_light / dmg_fist / dmg_pile / dmg_chainsaw / dmg_flamethrower）當初漏掉的原因。
決策五：抽 src/components/module/ 元件家族，兩頁共用
沿用站上既有的 WeaponSkillCard / BackpackSkillCard 慣例（單一 domain card 元件放 components/）：
新元件 / hook職責取代掉什麼
ModuleCard 模組卡骨架（圖示／名稱／badge／等級選擇器／描述／數值標籤），以 variant 區分圖鑑版與詳情頁版 ModulesPage 的 inline JSX（約 90 行）＋ MechDetailPage 的 local ModuleCard
ModuleLevelSelector 等級切換；桌機 <input type="range">、行動裝置改 Lv chip 列（useIsMobile 分流）；maxLv ≤ 1 時自身不渲染 全新
ModuleStatTags 吃一個 ModuleLevel，走 STAT_LABELS map 產出標籤；variant: 'plain' | 'chip' 涵蓋兩頁既有的兩種視覺 兩份手寫 11 欄展開 ＋ ModStat
ModuleAdopters 採用機甲縮圖列（FallbackImage ＋ Link 進機甲頁；無圖時退回名稱 chip） ModulesPage 的「對應／採用機甲」文字列
ModuleBoundPart 綁定部位顯示，內含唯一一份 PART_LABELS 兩份重複的 PART_LABELS 表與各自的行內渲染
useModuleAdopters() 模組 ID → 採用機甲清單的反查索引（useMemo，零額外 Firestore read） ModulesPage 的 inline mechsByModuleId
ModuleBadges（既有） 啟用死碼 兩頁改 import ModuleSlotBadge / ModuleRarityBadge 三份重複的 SLOT_LABELS / SLOT_STYLES / RARITY_STYLES
決策六：預設篩選 S，清單依「特性 → 8級 → 通用」排序 2026-08-05 追加
預設 S：rarityFilter 初值從 null（全部）改為 ModuleRarity.S。 A 級模組多為過渡期裝備，玩家開圖鑑時絕大多數在找 S；預設全部等於每次都要先按一下篩選。「全部」按鈕保留，隨時可放開。
槽位排序：清單以 特性 → 8級 → 通用 排序（副模組勾選顯示時排最後）。 順序不另外寫死一份——直接沿用篩選按鈕已在用的 CATALOG_SLOTS 陣列順序， 由 compareModuleBySlot() 查表得名次，因此不可能出現「按鈕排一種、結果排另一種」。 同槽位內維持 Firestore 原始順序（Array.prototype.sort 自 ES2019 保證穩定排序），不引入第二層排序規則。
連帶的結構調整：為了讓「槽位順序」有個乾淨的家，把槽位資料（SLOT_LABELS / CATALOG_SLOTS / compareModuleBySlot） 移到新檔 src/utils/moduleSlots.ts，ModuleBadges.tsx 只保留 Tailwind class 對照與元件本身。 副作用是消掉了該檔案既有的 react-refresh/only-export-components lint 錯誤（元件檔不再匯出非元件）。
決策七：「對應機甲 / 採用機甲」統一為「採用機甲」
語意最準（這台機甲把它裝在身上），且與 docs/03_頁面規劃/06_模組/ 既有的區塊標題一致。 Phase C 改成縮圖列之後連標籤都可以省——一排機甲頭像本身就說明了「誰在用」，縮圖保留 title 與 alt 供辨識與無障礙。
邊界一：等級數不齊。 通用模組可能只有 1 級，副模組 levels 是空陣列。 maxLv ≤ 1 時 ModuleLevelSelector 必須整個不渲染，退回單純描述；否則會出現「Lv.1/1」這種無意義的滑桿。 levels 為空時描述退回 mod.description、refs 退回 mod.descriptionRefs（沿用浮窗既有的 fallback 規則）。
邊界二：Phase D 之前，滑桿與卡片點擊會打架。 B 階段上線時舊的 handleCardClick（釘選浮窗）還在，滑桿與縮圖的事件必須 e.stopPropagation()， 否則拖動滑桿會順手把浮窗釘起來。D 階段拆掉浮窗後這層防護仍應保留（縮圖是 Link，不該冒泡到卡片）。
邊界三：卡片高度不齊。 grid 每一列會被最高的卡撐開。若落差明顯，對描述區設 min-h 讓同列對齊即可； 不要用 line-clamp 截斷——那等於又把資訊藏起來，與本計畫的目的相反。
邊界四：缺 portrait 的機甲。 縮圖一律走 FallbackImage ＋ imageCandidates(mech.portrait, images/mechs/{name}.webp)（沿用 MechsPage.tsx:12-16 的既有慣例，會自動處理 PNG→WebP 漂移）。 最終 fallback 必須退回機甲名文字 chip，不可留白或破圖——否則「誰在用」這項資訊會憑空消失，比改版前更糟。
正向副作用：浮窗嵌套消失。 現行浮窗裡的 RefText 會再吐出 RefChip，而 RefChip 自己又有 hover 浮窗（ReferenceContext）——浮窗裡開浮窗，z-index 與釘選狀態長期互相干擾。 內嵌之後 RefChip 的浮窗直接開在頁面上，這層嵌套自然消失。需實測卡片的 overflow 不會裁掉 chip 浮窗。
Scope
實作範圍與不在範圍內
在範圍內：
  • STAT_LABELS 型別窮盡化，補上 7 個漏顯示的數值欄位
  • 新增 src/components/module/ 元件家族（ModuleCard / ModuleLevelSelector / ModuleStatTags / ModuleAdopters / ModuleBoundPart）與 useModuleAdopters hook
  • 啟用既有的 ModuleBadges.tsx，刪除三份重複的 slot／稀有度樣式表
  • 模組圖鑑：卡片內嵌等級選擇器、描述與數值標籤跟隨當前等級
  • 模組圖鑑：採用機甲改為可點的機甲縮圖列；文案統一為「採用機甲」
  • 模組圖鑑：稀有度預設篩選 S；清單依特性 → 8級 → 通用排序（決策六）
  • 機甲詳情頁：改用同一組共用元件（含等級選擇器）
  • 兩頁移除浮窗機制（TooltipPortal / LevelTooltip / 三組 state / BottomSheet 與 useDragOffset 的本頁用法）
  • 同步 docs/03_頁面規劃/06_模組/index.html
不在範圍內：
  • 「拆解來源機甲」的前台顯示（dismantleMechIds）——站長裁決：遊戲定律是「特性模組在誰身上，拆他就有」，屬玩家常識，不需要在介面上解釋。該欄位維持只在後台可編。
    連帶：docs/03_頁面規劃/06_模組/index.html:73 那句過期的「拆機甲來源另標注對應機甲名稱」在 D-3 直接刪除，不實作。
  • 全頁等級連動總控（決策二已否決）
  • 任何資料模型 / Firestore 變更——本計畫是純顯示層，零 schema 異動、零額外 read（mechs 早已由 useMechNameMap 載入並快取）
  • SimulatorPage 與 ModuleAdmin 的模組呈現（配裝／後台情境不同，暫不併入）
  • BottomSheet / useDragOffset 本身——另有 weapons / backpacks / components / EntityRefView 等 9 處在用，僅移除本計畫兩頁的用法
驗收條件： ① 模組卡可在不觸發任何浮窗的情況下讀到任一等級的完整正文與數值； ② 滑到 Lv.N 時數值標籤與描述同步變動，無值的欄位不佔版面； ③ 採用機甲縮圖可點進對應機甲頁，缺圖時退回名稱 chip； ④ 機甲詳情頁的模組區與圖鑑共用同一個元件，兩處視覺一致； ⑤ ModulesPage.tsx 與 MechDetailPage.tsx 均不再包含 LevelTooltip / TooltipPortal / PART_LABELS / RARITY_STYLES 的定義； ⑥ npm run build 通過，npm run lint 無新增警告。
