三處與原計畫的偏離，都已在程式碼註解寫明理由：
① 改讀單一文件而非重用 /api/data 整包快取。原計畫寫「沿用整包邊緣快取、不新增 Firestore read」， 但 pilots 那包是 1.3 MB，為一筆資料 parse 整包在免費方案 10 ms CPU 預算下不划算；改成單文件 ＋ 專屬 cache entry （key 一樣帶集合版本號），命中 0 read、未命中 1 read。
② 加了防迴圈保險絲（轉發回 origin 時蓋 x-og-passthrough 標記）。 同 zone fetch 照理不會重入 Worker，但這條路徑上的迴圈代價是整站頁面請求爆掉。
③ Tier 2 的 twitter:card 降級為 summary（方形小卡）並移除 og:image:width/height： 立繪是直式、武器圖示是方形，套 Tier 1 那組 1200×630 的尺寸宣告會被平台裁切得很難看。

已解除（2026-08-22 當日）：Transform Rule 先於 Workers 執行
部署後用 wrangler tail 觀察：三個 Discordbot 對詳情頁的請求 Worker 零事件，同時段 /api/* 的事件（含真實訪客流量）一切正常。 原因是 PLAN-029 Phase 5-1 的 SPA fallback Transform Rule 已把 /pilots/xxx 改寫成 /index.html，而 Cloudflare 的處理順序是 Transform Rules → Workers，Worker 看到的路徑不再是 /pilots/*，route 匹配不到。

解法（需站長在 Cloudflare Dashboard 操作，程式碼端已就緒）： 在該 Transform Rule 的條件加上「社群爬蟲 UA 不套用」的例外，例如 and not (lower(http.user_agent) contains "discordbot" or ...)。 這樣真人流量的路徑照舊由 Transform Rule 處理（Worker 完全不執行、額度零增量）， 只有爬蟲的請求會落到 Worker 手上做改寫。

程式碼端已配合改成 自行抓 /index.html 當骨架 （能進 Worker 的請求＝沒被改寫過，直接 fetch(request) 會拿到 GitHub Pages 的 404）。

⚠ 例外條件必須同時綁路徑，不能只看 UA。 第一版例外只寫「UA 是爬蟲就不改寫」，但那條 Transform Rule 管的是全部 15 條 SPA 路徑， 而 Worker route 只接管 3 條詳情頁 —— 爬蟲抓 /news、/pilots（列表頁）時 會變成「不改寫、也沒人接手」→ 直接落到 GitHub Pages 的 404，卡片比修之前更糟（連站名卡都沒有）。 正解是例外要求「是三條詳情頁 且 是社群爬蟲」兩者同時成立， 路徑帶尾斜線（/pilots/）好讓例外範圍剛好等於 Worker route 範圍。

上線後的最終運算式（規則存在 Cloudflare Dashboard、不在版控，重建時照抄）： 原本的 ((http.request.method eq "GET" and ( ...15 條 SPA 路徑... ))) 一字未改，後面接： and not ( ( starts_with(path,"/pilots/") or starts_with(path,"/mechs/") or starts_with(path,"/weapons/") ) and ( lower(http.user_agent) contains "discordbot" or ... facebookexternalhit / line-poker / linebot / slackbot / twitterbot / telegrambot / applebot ) )。 lower() 是必要的 —— Cloudflare 的 contains 區分大小寫， 實際 UA 寫的是 Discordbot、TwitterBot 這種混合大小寫。

兩處 UA 清單刻意不同步：Worker 端列 17 個、Transform Rule 只列 8 個主要平台。 沒列進規則的爬蟲（WhatsApp／Reddit／Pinterest 等）會照舊被改寫成 index.html、拿到 Tier 1 站名卡 —— 是安全的降級，不需要為了對齊而把規則寫長。

歸檔後 follow-up（2026-08-23）：WebP 讓 LINE 的卡片沒有圖
站長實測 LINE：標題與描述都是 Tier 2 的實體資料（改寫確實生效），但沒有圖。 排查後排除「被擋」（用 LINE 的 UA 抓那張立繪回 200）與「抓不到站」， 真因是 og:image 是 WebP —— Facebook 的 OGP 規格只吃 JPEG／PNG／GIF， LINE 同樣抓不出縮圖；Discord 是少數支援 WebP 的，所以只有它看起來正常。 資料層實測：pilots 87/88、mechs 88/89 是 webp（受影響），weapons 170/178 是 png（本來就正常）。

修法：新增 scripts/generate-og-entity-images.mjs，於 build／dev 前置把 177 張會被卡片用到的立繪各轉一份 JPEG 到鏡射路徑 （/images/pilots/曜/half.webp → /images/og/entities/pilots/曜/half.jpg， 帶 alpha 的立繪以站台底色 flatten），Worker 的 absoluteImage 據此推導。 產出物不進版控（約 4.1MB，可完全重現），所以新增機師／機甲零維護； generate-image-manifest.mjs 一併排除該目錄，免得後台選圖多出 177 筆雜訊。

那條推導規則是兩份檔案的約定（腳本的 SOURCES ↔ Worker 的 toPreviewSafeImage）， 資料層若把 portrait 指到別的 webp 檔名就會推導出不存在的路徑 —— 而那是靜默失敗 （卡片變破圖、沒有任何錯誤）。因此 Worker 在改寫前對推導出來的路徑做一次 HEAD， 不存在就退回預設圖。爬蟲請求每日幾十次量級、且吃 CF 邊緣快取，成本可忽略。
