◆ PLAN-038

社群連結預覽（Open Graph）系統 · LINE／Discord 分享卡片

診斷已確認 index.html 完全沒有 og:* 標籤，是 Discord 無預覽、LINE 僅陽春標題卡的唯一原因。分兩層修：Tier 1 全站靜態標籤先解決「有沒有卡片」，Tier 2 讓機師／機甲／武器詳情頁的分享卡片顯示對應肖像與名稱。

前置依賴
PLAN-029（Tier 2 需要其同源 Worker；Tier 1 無依賴，可獨立先做）
立案背景：站長回報網站在 LINE 有連結預覽，但在 Discord 完全沒有。診斷（對話內已產出視覺化說明）確認根因單一： index.html 目前沒有放任何 og:*／twitter:* meta 標籤（只有 <title> 和 favicon）。 Discord 的爬蟲不執行 JS、也沒有 <title> fallback，找不到 og:title／og:image 就完全不顯示卡片； LINE 的爬蟲則會退而求其次抓 <title> 撐出陽春卡片，才會有「LINE 有、Discord 沒有」的落差。

站長決定兩層都做，且明確要求 og:image 素材要有規劃、易於管理與選用，不要臨時拼湊——這是本計畫在 Tier 1 之外，額外把「素材策略」獨立列為設計決策的原因（見決策二、三）。
Problem
問題背景
index.html 完全沒有 Open Graph 標籤
現況只有 <title>米赫瑪超吉情豹站 | Mecharashi-Milhama PawInfo Station</title> 與 <link rel="icon">。社群平台的連結預覽爬蟲（Discordbot／LineBot 等）不執行 JavaScript， 只解析拿到的原始 HTML——而純前端 SPA 的 /pilots/123 這類路由，爬蟲收到的骨架跟首頁是同一份 index.html， 因為完整內容要等 main.tsx 掛載 React 之後才會「長出來」。
現有素材都不適合直接當 og:image
favicon cat_no_bg.png 是去背貓貼圖，透明區塊在深色底 App 上會變成一片黑； public/images/banners/ 內的版本更新宣傳圖（v2.7～v3.3，單張 0.7～3.6MB）尺寸比例與檔案大小都不合 og:image 建議規格（≈1200×630、盡量 <1MB）。目前沒有任何一張圖能直接拿來用。
Design
設計決策
決策一：Tier 1 與 Tier 2 分開上線，不綁定交付
Tier 1（全站靜態標籤）本身就是完整且正確的修復——沒有它，Discord 連基本卡片都沒有； Tier 2（逐頁動態）是在此之上的加值，不做也不會讓現況變得更差。 這點與 PLAN-033 的「A 若不與 B 綁定會是負優化」相反—— 這裡 Tier 1 是可以獨立上線的正優化，Phase A 完成即可先部署，不必等 Phase B。
決策二：Tier 2 的 og:image 一律重用既有實體圖片欄位，不為社群分享另外產美術
三個有詳情頁的實體都已經有圖片欄位可直接引用：
實體欄位來源
Pilotportrait: string / portraitUrl?: stringsrc/types/pilot.ts:240-241
Mechportrait?: string / halfPortrait?: stringsrc/types/mech.ts:63-65
Weaponicon?: string（本地路徑，如 /images/weapons/Icon_weapon_10001.png）src/types/weapon.ts:73-74
Tier 2 動態改寫時直接組這些欄位成絕對網址即可，不需要為分享卡片另外設計一套圖庫—— 這正是「有規劃」的核心：素材規則建立在既有資料模型上，而不是為了 OG 這個單一用途另開一條維護線。
決策三：非實體頁只做「一張全站預設圖」，刻意不預先拆分類橫幅
首頁、list 頁（pilots/mechs/weapons 列表）、功能頁（simulator／research／news／guides／tools）等 沒有對應單一實體的頁面，一律共用 Tier 1 的全站預設圖。

素材存放訂出清楚慣例：public/images/og/default.jpg（全站預設，1200×630）。 刻意不在本計畫內預先拆「依大分類各配一張橫幅」——目前沒有證據顯示使用者常分享 simulator／research 這類功能頁到 Discord，先做一張、觀察實際分享情境，之後真有需求再擴充目錄（同一慣例下新增檔案即可，不是重新設計）。 這是「好管理」與「過度設計」之間的分界：目錄慣例現在訂好，圖片數量按實際需求長。
決策四：實體圖片欄位缺值時，fallback 回 Tier 1 預設圖
portrait／icon 多為選填欄位，個別機師／機甲／武器可能還沒補上圖（沿用 既有專案對「選填欄位不會自動被填滿」的觀察）。 Tier 2 組 og:image 時若目標欄位為空，必須 fallback 到 default.jpg， 不能讓 og:image 整個消失——消失就是退回本計畫要修的壞狀態。
決策五：Tier 2 只認 pilots／mechs／weapons 三個 /:id 路由
依 src/App.tsx 路由表，目前只有這三個集合有獨立詳情頁（pilots/:id、mechs/:id、 weapons/:id）；backpacks／modules／components 目前都只有 list 頁、沒有 :id 詳情頁。 Tier 2 的路徑判斷與資料組裝範圍鎖定這三者，其餘一律吃 Tier 1 全站預設圖（見「不在範圍內」）。
決策六：Tier 2 沿用既有 Worker 慣例，不新增服務、不多打 Firestore
延伸 workers/src/index.ts，比照現有 antiScrapeBlock（PLAN-029 Phase 3-4）的寫法新增一個 社群爬蟲 UA allow-list 判斷；資料組裝直接重用既有 /api/data/:collection 路徑背後的邏輯與邊緣快取 （caches.default，版本號當 cache key），不另開端點、不新增 Firestore read。 非爬蟲 UA 的請求完全不進這段邏輯，SPA 行為零影響。
Scope
實作範圍與不在範圍內
在範圍內：
  • 訂定 public/images/og/ 存放慣例與命名規則
  • 產出全站預設 og:image（default.jpg，1200×630，站名＋吉祥物＋場景，控制在 1MB 內）
  • 撰寫站點簡介文案（og:description）
  • index.html 補 og:title／og:description／og:image／og:url／og:type／twitter:card／twitter:image
  • workers/src/index.ts 新增社群爬蟲 UA 偵測（Discordbot／LineBot／Slackbot／TelegramBot／facebookexternalhit 等）
  • pilots／mechs／weapons 三個 :id 詳情頁的動態 og:title／og:image（含缺值 fallback）
  • 用 query string cache-busting 對 Discord／LINE 實測驗證
不在範圍內：
  • backpacks／modules／components 的逐頁動態預覽——這三者目前沒有 :id 詳情頁，Tier 2 無標的可做；未來若開了詳情頁，屬於當時的 follow-up。
  • 依大分類拆分多張靜態橫幅——見決策三，先做一張 default.jpg，之後有需求再擴充。
  • 其餘 SEO 工程（sitemap.xml、schema.org 結構化資料等）——與 Open Graph 是不同的問題，不在本計畫範圍。
  • 微信／小程序等中國生態的卡片規格——不同技術生態，且與站長「中國盡量改善即可」的既有定位（PLAN-029）一致，不特別投入。
  • 為分享卡片另外委製美術素材——決策二已定調全部重用既有實體圖片欄位。
Pitfalls
已知實作陷阱
  • Transform Rule 跑在 Workers 之前，會讓 route 匹配不到（2026-08-22 實際踩到）。 PLAN-029 Phase 5-1 用 Transform Rule 做 SPA fallback，把 /pilots/* 這類深層路徑 改寫成 /index.html。Cloudflare 的處理順序是 Redirect Rules → Transform Rules → Workers → Cache → Origin， 所以 Worker 看到的路徑早就變成 /index.html， mecharashi.wiki/pilots/* 這條 route 一次都不會命中 （首次部署後 wrangler tail 實測：三個 Discordbot 請求零事件，只有 /api 有）。 必解：讓那條 Transform Rule 對本計畫的目標請求不生效 —— 建議加 UA 例外（社群爬蟲不改寫）， 真人流量完全不受影響、Worker 也不必承擔 SPA fallback 的可用性責任。 連帶結論：Worker 內不能 fetch(request)，能走到 Worker 的請求就是沒被改寫過的， 原路徑在 GitHub Pages 上是 404 —— 骨架必須自己抓 /index.html。
  • Worker 目前根本收不到 HTML 請求。 workers/wrangler.jsonc 的 routes 只有 mecharashi.wiki/api/*， 頁面 HTML 是 GitHub Pages 直出、不經 Worker。Phase B 的第一步其實是**新增 HTML route** （mecharashi.wiki/pilots/* 等三條，或整站 /*）。 取捨：三條路徑限縮命中面、省 Workers 每日請求額度（與 /api 共用同一池）； 整站 /* 則未來任何新詳情頁都自動涵蓋，但真人訪客的每一次頁面請求都會計次。 （2026-08-22 開工前實查補記）
  • antiScrapeBlock 會把要服務的爬蟲 403 掉。 workers/src/index.ts 現在是在 fetch() 最前面**無差別**執行反爬守門， 而 Discordbot／LineBot 不會帶 Origin／Referer／Sec-Fetch-Site。HTML 一旦走進 Worker， 現行邏輯會直接回 403 —— Phase B 的第二步必須先把這道守門限縮在 /api/* 之下， 否則等於親手擋掉本計畫要服務的對象。（2026-08-22 開工前實查補記）
  • 本地路徑必須補 origin 才是合法 og:image。portrait／icon 存的都是 /images/... 這種相對路徑，Worker 端組 og:image 時忘記補 https://mecharashi.wiki 前綴，等於重蹈本計畫要修的錯——爬蟲一樣讀不到相對路徑。
  • UA 判斷寫反會砍掉一般使用者的 SPA。HTMLRewriter 改寫只能作用在判定為「社群爬蟲」的那次回應； allow-list 邏輯若誤判一般瀏覽器為爬蟲，會讓真人訪客也拿到改寫過的簡化 HTML，等於整站變成靜態頁、SPA 掛不上去。 上線後務必先驗證一般 UA 的請求路徑完全未觸碰新增邏輯（見進度表 B-4）。
  • Weapon.icon 是小尺寸方形圖示，非 1200×630 橫幅。直接當 og:image 使用時 會被各平台依自己的裁切規則縮放／置中，不會是理想的橫幅構圖。先求「有圖」，成效不理想再考慮是否要另外處理， 不在本計畫內預先為武器加工二次構圖。
  • Discord 對同一條網址的 embed 結果會快取。Phase A／B 上線後測試時，用 ?v=1／?v=2 之類的 query string 讓 Discord 當成新網址重新抓取， 避免誤判「改了沒生效」。
  • public/images/banners/ 的版更宣傳圖不可誤用為 og:image。那批圖是站內公告用途， 尺寸比例與檔案大小都不符合本計畫的素材規格（見問題背景）。
