Problem
問題背景
問題一：tooltip 被裁切，且會蓋住上方週次表
甘特容器（VersionGanttPanel.tsx:431）是 overflow-y-auto overflow-x-hidden，而 tooltip（:208）是 absolute bottom-full——永遠往上長。 z-index 對 overflow 裁切完全無效，這是 CSS 的硬規則：只要祖先有非 visible 的 overflow，子元素就被切。實測從 tooltip 往上數共 11 層 clipping ancestor。 第一列活動的 tooltip 必被切，第二列以後則會往上蓋住週次表。
問題二：一週活動在甘特圖上只剩一個點
兩層原因：(a) :216 的 colSpan === 1 分支只畫一顆 12px 圓點，連名稱都不畫； (b) 更根本的是 activityToColumns()（:55-73）用 allWeeks.findIndex(w => w >= startDt) 把起點量化到下一個週界，活動實際在週內哪天開始／結束的資訊在渲染時就被丟掉。 實測 75 筆活動裡有 27 筆（36%）正好是 1 週——超過三分之一的資料在甘特上是啞的。
問題三：維護者打了很多資料，但詳細資訊看不到
這不是顯示問題，是資料模型缺欄位。TimedActivity 只有 { name, startDate, weeks, type, pilots?, mechs? }， 根本沒有描述欄位。維護者只能把獎勵硬塞進 name，於是資料長成 瑞歲百角戲(輕型通用改裝模組*1 仿生超導體*2)。不補欄位，改任何版面都只是把同一串字串換個地方顯示。
問題四：陸版官網常漏維護公告，台版不會
已量化證實。陸版與台版是同一套 CMS，但陸版「公告」頻道等同廢棄：總共 2 篇、最新一篇停在 2023-10-20。 所有內容擠進「新聞」，而版本更新公告在 2025-01-15 到 2025-12-17 之間整整空了一年，且 time 欄位連年份都沒有（"10-20"），要靠 URL 路徑回推。 台版同期則是 258 篇、117 篇週報、2024-03-25～2026-08-12 週更未斷。
四份設計方案共同的盲點（由評審指出）：把「資訊看不到」誤診成「資料不夠」。
四案合計提議新增 5–11 個選填欄位，卻沒人去算已經算得出來的東西。玩家最常問的三個問題 （「這週有什麼」「這個活動什麼時候結束」「這版有誰」）裡有兩個半完全不需要新資料—— 從既有的 startDate + weeks 就能導出「進行中/即將開始/已結束、第 N/M 週、剩幾天、末週警示、進度條」。 對照 0/5 定律（集合會被填滿、選填欄位不會），衍生值是唯一「零維護成本、上線當天 100% 覆蓋率」的資訊來源。
Design
設計決策
決策一：甘特＝索引，卡片＝內容（並存，不是取代）
四份提案在最小螢幕上全都偷偷退化成卡片清單——三位評審獨立指出這是收斂證據：卡片才該是內容主體，長條只是輔助。 但把甘特整個刪掉會弄丟「機師/機甲/專武 ↔ 週次」這條原始設計動機，所以是並存。 甘特降級成「日精度的一眼概觀」，內容由正下方、同一個捲動容器內的卡片流承載。
決策二：長條改「單一 colSpan={totalWeeks} 的 td + 百分比定位」，不改 CSS Grid
該 td 的寬度天生就等於整條週軸（tableLayout:fixed + 同一份 Colgroup），所以百分比定位與上方固定資訊表的欄界自動對齊，Colgroup 一行都不用動。 用 % 而非 px：不必量測 DOM、不必 ResizeObserver，Tab 展開／視窗縮放／橫捲時也不會有一幀錯位。
決策三：用專案已安裝的 @floating-ui/react，不自己刻定位
package.json 已有 @floating-ui/react ^0.27.19（BossDropTooltip.tsx 已是同一套 pattern）。 FloatingPortal 一次跳出全部 11 層裁切祖先；flip/shift 取代手刻的「放不下才翻上方 + 左右夾在視窗內」；autoUpdate 取代 scroll/resize 監聽。 placement 改成 'bottom'——現況永遠往上長才是「第一列必被切、又蓋住週次表」的直接成因。 手機走既有的 BottomSheet + useIsMobile。
決策四：splitActivityName() 做成前台 runtime fallback，不做後台一次性遷移
一次性遷移只救得了按下按鈕的那一次；runtime fallback 同時救了歷史資料與「未來維護者又用老方法打字」的情況，而後者一定會發生。 規則刻意保守：括號內沒有「符號 + 數字」就整串當名稱——實測 34 筆有括號的資料裡， 真正 A*1 B*2 形狀的只有 15 筆，其餘是外觀名（10）、機制說明（6，如「體力轉票券商店」）、空括號（1）。寧可少抽，也不要把機制說明寫成獎勵。
決策五：rewards 用 string[]，不做 { name, qty, refKey } 結構化
上述三種形狀塞不進 {name, qty}；refKey 更是純人工欄位，會複製 iconUrls 那種 0% 填充的命運。string[] 無損接住全部。
決策六：ActivityType 由硬 union 改成「開放字串 + 靜態登錄表」
新玩法出現時，硬 union 會讓 buffer 塞住、要等改 code + build + deploy 才能合併。 開放字串（KnownActivityType | (string & {})）讓維護者當天就能上線，甘特用中性色顯示；之後補一列 REGISTRY 給它顏色，零資料遷移。 string & {} 讓 TS 不把 union 塌成 string，IDE 仍自動完成已知值。順便補上實測第 2 高頻的 topUpEvent（「指定方式儲值」出現 109 次）。
決策七：buffer 的審核最小單位是「一個活動」，不是「一則公告」
一則公告十個活動，看得懂九個就先放行九個，剩一個留在 pendingActivities。 新玩法不該卡住整批——這正是「待處理 buffer」要解決的事。解析器抽不到的欄位留 undefined，絕不填預設值； 沒被任何規則認領的原文片段存進 unmatched[]，讓「這段我沒看懂」在後台自動浮出來。實測 buffer 流量是每月 2～4 筆新名稱，維護者實際要打的字是三顆按鈕。
邊界一：endsAtExclusive 的命名是刻意的，且延到 Phase 2
既有慣例一律是 exclusive（types.ts:27 註解「1 = 當週四到下週三」、VersionGanttPanel:61 的 addDays(start, weeks*7)、AdminTimedActivityEditor:31 的 computeEndDate 同）。 而三份提案各自把 endDate 定義成「含當日」「最後一天」「真實結束日」——典型的一日之差 bug。用命名把語意編碼進欄位名，再配單元測試同時擋掉。 且既有 75 筆全部週四起始、weeks 全整數 → 現在加對既有資料零收益，等台版公告給絕對起訖（「8/21 10:00 ～ 9/03 23:59」）時才有意義。
邊界二：爬蟲寫完 Firestore 必須 bumpDataVersion('patchVersions')
patchVersions 走 Worker 邊緣快取（workers/src/index.ts 以集合版本號當 cache key、max-age=86400）。 不 bump 就是「資料寫進去了、前台看不到、硬重整也沒用、查半天」，最長 24 小時。這條要寫進 data-patch skill 與 docs。
邊界三：合併寫入必須 runTransaction；buffer 絕不能做成 PatchVersion.inbox 欄位
AdminVersionEditorPage.tsx:377 目前是整份 setDoc、沒有 merge:true。 若把 buffer 塞成 PatchVersion 的欄位，腳本追加、管理員存檔 → 追加內容無聲消失。同型事故已有前例（scrape-pilots-v3.js:117）。必須是獨立 top-level 集合。
補充：9 色收斂成 5 族群色 + 第二編碼通道
實測角色池 #79c0ff／機甲池 #58a6d4／限時活動 #06b6d4 是三個相鄰冷藍， 而撞色的正好是語意上最需要分辨的角色池 vs 機甲池。收斂後靠端點形狀／虛線／永遠可見的型別文字標籤補足第二編碼通道 （色彩不該是唯一的資訊通道）。副作用：使用者會感覺「顏色變少了」。
Scope
實作範圍與不在範圍內
在範圍內：
  • Phase 0（約 5h · 零資料模型變更）：floating-ui 浮窗置換、日精度百分比長條、splitActivityName runtime fallback、誠實空狀態 + overscroll-contain、預設落在 isTwCurrent 版本、三支 node --test。另含台版公告全量歸檔（見下方紅字）。
  • Phase 1（約 16h）：垂直預算回收（列高 32px + ShopRow 併列）、活動卡片流、甘特↔卡片↔週欄三向連動、共用軸線層（週格線／上下半分界／今日線）、色彩系統收斂、TimedActivity 擴充 + 後台編輯器 + docs 同步、deprecated 欄位 legacy shim。
  • Phase 2（約 26h）：scripts/scrape-tw-announcements.mjs（純 fetch、無 Playwright）、announcementDrafts / pendingActivities 兩個後台專用集合、/admin/announcements 審核工作檯、runTransaction 合併 + bump、confidence 前台顯示、產出量監控。
不在範圍內（明確不做，附理由）：
  • 348px 常駐側欄——首頁卡片預設是收合的（lg:max-w-[48vw]，1366 上只有 655px），塞不下。「要靠使用者先按 ▶▶ 才成立」的資訊設計不能當主形態。它便宜的優點（週欄整欄打亮）照收，貴的缺點不要。
  • 獨立 /timeline 路由——60–70h 賭一個未驗證的導覽模型；且 HISTORICAL_BLANKS 產生的 v1.0–v2.7 共 17 個無日期版本在絕對時間軸上沒地方放。刪掉 VersionTimeline 也等於淨損失 clip-path 圓形展開與滾輪切版本。
  • 軌道併合 packLanes——與「一活動一列、可選取」的心智模型衝突；列數隨資料浮動（v3.0 六軌、v3.3 四軌），方向鍵連切版本時甘特高度會跳。
  • description 支援 [xxx] 引用標記——會把 patchVersions 反向耦合到 RefText／ReferenceContext 全站體系，且 chip 開 FloatingCard 會與活動浮窗互相蓋。純文字就夠。
  • shortName / lane / highlight / dataStatus——全是「開了就必須人工持續維護」的欄位，依 0/5 定律必然 0% 填充；lane 更糟，填了之後新增活動就失效需要重排。
  • activityTypes 開成新 CollectionKey——collectionKeys.ts 已註明要同步四處（Worker ARRAY_COLLECTIONS、bump-data-version.mjs、entityRefs.ts SPECS、測試 helper），PLAN-043 就是漏掉 backpackSkills 炸在正式站。升級觸發點：未登錄型別穩定超過 20 種時再開，屆時資料形狀已對齊，遷移是複製貼上。
  • 解析陸版公告——陸版公告頻道已廢棄（見問題四）。明確接受「台版自動化／陸版人工」的不對稱，用 confidence 讓兩者新鮮度可辨識。
  • 台版 infodata API 換官方繁中譯名——調查時挖到 ma-activity.tentree-games.com/common/infodata/mQuery.do?appkey=1705460260139，與 scrape-pilots-v3.js:42 是同一支 API 的台服實例，回傳 77 名機師的官方繁中譯名（可取代現行 OpenCC 簡轉繁猜譯名）。價值高但與本計畫無關，另立議題。
⚠ 比功能開發更急的一件事：台版公告檔案庫的存續風險
258 篇公告至今只存在於前代理商網域 ma.tentree-games.com。代理權已於 2026-01-05 移轉給亦樹遊戲，新網域沒有平行的公告站。 這是不可逆風險：站一旦收掉，2024-03 至今的所有版本史料一起消失。 全量歸檔的優先度高於本計畫的任何功能，因此排在 Phase 0（任務 0-0），不等排到 Phase 2。
