◆ PLAN-029

Cloudflare 化與 App Check 退場 — Edge Proxy · 反爬 · 加速

用 Cloudflare 一層邊緣基建接手「反白嫖 + 反爬 + 加速」，讓 App Check／reCAPTCHA 退場；公開遊戲資料改走 Worker 代理、Firestore 收成 read:if false，並順帶盡量改善中國讀取（不碰 ICP）。

一句話：不「拆牆」（關 App Check enforce）而是「換一整道更好的牆」。前端不再直連 firestore.googleapis.com，改打自有網域上的 Cloudflare Worker；公開資料由 Worker 用 service account 代讀，Firestore 遊戲資料規則收成 read: if false。App Check 那張「可被無頭瀏覽器繞過的票」，換成 Cloudflare 這道「自己站崗、附帶加速與反爬」的邊緣層。
Problem
問題背景
① App Check 維運成本高、且防護有上限
導入 App Check 過程踩過多個坑（reCAPTCHA Enterprise vs classic 不匹配、Firebase Browser API 金鑰白名單漏 App Check API 導致 API_KEY_SERVICE_BLOCKED、正式站 metrics 一度 88% 無效）。即便修好，它本質是「一張票」，執著者能用無頭瀏覽器在本站跑、或抽 token 繞過 —— 防護有天花板，維運心智負擔卻不低。
② 公開資料的白嫖／爬蟲，現有手段擋不住
firebaseConfig 公開在 bundle，爬蟲可直打 Firestore REST API（/v1/projects/<id>/databases/(default)/documents/pilots），不 clone 前端、不跑 JS。前端 rate limit／行為偵測對它無效；Firestore 安全規則看不到 IP、不能 rate limit、不能黑名單（現況遊戲資料全 read: if true）。目前唯一在擋直打 REST 的，就只有 App Check —— 這也是為何不能單純「關掉它」。
③ 中國讀取被「兩道牆」擋住
Firebase 於中國自 2014 整體被 GFW 封鎖：第一道牆是資料端點 firestore.googleapis.com 本身，第二道才是 App Check 換票端點 firebaseappcheck.googleapis.com。只放鬆 App Check 救不了中國用戶（第一道牆還在）；且 App Check enforce 無地區豁免、Web SDK 不支援自訂 service URL —— 中國要能讀，唯一的路是換一個中國連得到的端點去代讀。
共同解：以上三個問題指向同一個答案 —— 一層「你自己控管、站在 Firestore 前面」的邊緣代理。它同時：換掉 App Check（①）、成為能看 IP／做反爬的唯一著力點（②）、提供一個非 googleapis 的可達端點（③）。Cloudflare 正是這層基建的現成、免費、成熟選擇。完整評估另見本機評估文件（_local-notes/Cloudflare取代AppCheck_概念與費用評估.html 等，未進版控）。
Design
設計決策
決策一：整站掛 Cloudflare（自有網域 + proxy）
買一個自有網域，DNS 託管到 Cloudflare 並開 proxy（orange cloud）。前端（GitHub Pages origin）與資料 API、圖片都收攏到同一個 CF 網域後面，一次拿到 CDN 加速、DDoS 防護、隱藏 origin IP，以及後續反爬規則的施力點。前端先維持 GitHub Pages（CNAME），日後有需要再評估搬 Cloudflare Pages。
決策二：公開遊戲資料走 Worker 代理，Firestore 收成 read:if false
前端讀公開資料改打 yourdomain/api/...，由 Cloudflare Worker 用 Firebase service account 憑證代讀 Firestore、回 JSON。確認前端不再直連後，遊戲資料規則從 read: if true 收成 read: if false。這比 App Check 硬：App Check 是「驗票、票可能被繞」，read: if false + 只有 Worker（Admin 憑證繞過規則）能讀，是把「直連」這條路真的鎖死。
// 目標架構：兩條路徑，職責分離 // ── 公開遊戲資料（pilots / mechs / modules / ...） 瀏覽器 → 自有網域(CF proxy) → Worker /api/data/:collection → Firestore REST + service account → JSON（邊緣快取） ▲ Firestore 規則：read: if false（只有 Worker 能讀） // ── 用戶資料 / 後台寫入（users/* · admin write） 瀏覽器 → Firebase SDK 直連 Firestore（維持不變） ▲ 規則：isOwner / isAdmin（Auth 保護，不經 Worker）
決策三（關鍵切分）：用戶資料與後台寫入維持前端直連 Firestore + Auth
只有公開遊戲資料走 Worker。users/*（個人檔案、收藏、build）與後台管理員寫入，牽涉 Firebase Auth 登入態與即時寫入，維持前端直連 Firestore，靠既有 isOwner / isAdmin 規則保護。這條路本來就要登入、拿不到別人的資料，白嫖的威脅模型（公開資料被整包搬走）不適用它 —— 所以 App Check 可以整個拿掉，不必為用戶資料保留。
決策四：反爬用 Cloudflare 現成能力，不自寫
在 CF 邊緣做：WAF 自訂規則封阿里雲／騰訊雲機房 ASN（免費檔 5 條規則足夠涵蓋主要雲廠商 ASN，精準打「營利爬蟲最省事的機房直爬」、對真人玩家近乎零誤傷）＋ Bot Fight Mode ＋ 1 條 rate limit（per-IP）。對應使用者「信任玩家、不信任營利站」的切分 —— 真人從住宅／行動網路來，爬蟲從機房來。
決策五：邊緣快取（版本號 key），成本壓到近 $0
遊戲資料是靜態的（版本 gate、整包載入、改版才變）。Worker 對每個集合的 JSON 做邊緣／KV 快取，key 帶上 meta/gameData 的版本號，跟著既有 bumpDataVersion 機制失效。同一集合一天可能只真讀 Firestore 一次，服務再多訪客都命中快取 → Firestore read 量趨近零、不吃 50k/天 免費額度。
決策六：分階段灰度，每階段可獨立回退
先把站搬到 CF 後面（不動資料流）→ 再加 Worker 代理與直連並存（可灰度）→ 確認公開資料全部走 Worker，才收緊 Firestore 規則、拔 App Check。任何一步都能回退（DNS 改回、前端切回直連、規則改回 read: if true 即時生效）。降低「一次性大改」的風險。
邊界一：中國是「盡量改善」，不是「真的很快」
標準 Cloudflare（免費／Pro）節點在境外，IP 有時仍被 GFW 干擾降速，中國用戶打 CF 一樣可能不穩。本計畫對中國的價值是「有一個非 googleapis 的可達端點 + origin 就近 HK、盡量改善」，不是「買 CF 就解決中國」。要「真的很快」＝中國境內節點＝ Cloudflare China Network（Enterprise）＋ ICP 備案（需中國境內公司實體，含設立成本約 US$18k–93k），與個人非營利站不成比例，明確排除。
邊界二：Workers 不能跑 firebase-admin
Cloudflare Workers 是 V8 isolate 環境，無法直接用 Node 的 firebase-admin（依賴 Node API／gRPC）。Worker 讀 Firestore 要走 Firestore REST API + 自己用 service account 簽 JWT 換 access token（有現成輕量庫，或用 jose 簽）。這是實作上要處理的一步，不是障礙，但需納入 Phase 2 工時。
Scope
實作範圍與不在範圍內
在範圍內：
  • 自有網域 + Cloudflare proxy（前端 GH Pages 掛上）
  • Cloudflare Worker：公開集合的 Firestore REST 代理 + 邊緣快取（版本號 key）
  • 前端 GameDataContext／useFirestore 公開資料改打 /api（保留版本 gate 快取邏輯）
  • Firestore 遊戲資料規則收成 read: if false（保留 users/*、寫入規則）
  • 移除前端 App Check + reCAPTCHA 初始化（firebase.ts）
  • CF 反爬：ASN 封鎖（阿里雲／騰訊雲）+ Bot Fight Mode + rate limit
  • （可選／後續）R2 圖片鏡像；中國 origin 就近 HK
不在範圍內：
  • ICP 備案 / Cloudflare China Network —— 成本與門檻不成比例，明確排除（中國只做「盡量改善」）
  • 用戶資料 / 後台寫入改走 Worker —— 維持前端直連 Firestore + Auth
  • 傷害模擬後端邏輯 —— 屬未來計畫；本計畫只順勢建好「Worker + service account + 部署」骨架供其複用
  • 前端整體搬 Cloudflare Pages —— 先維持 GitHub Pages，非必要不動
