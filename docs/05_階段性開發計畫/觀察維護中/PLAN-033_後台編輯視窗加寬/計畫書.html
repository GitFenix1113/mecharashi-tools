後台編輯視窗加寬 · AdminModal · 容器查詢 · 資訊密度

後台編輯彈窗固定 672px 過窄，維護者卻只在 PC 上作業。加寬到 90vw，並把多出來的寬度轉成欄位密度而非胖輸入框。

來源分析： 本計畫由本機評估 _local-notes/後台編輯視窗加寬_工程量評估.html 升級而來。 該筆記含一份可拉的寬度互動示範（滑桿 ＋「只做 A」/「A＋B」切換）， 用 WeaponAdmin 數值頁的真實欄位重現「加寬但不改格線」的負優化效果。 寬度參數即由該示範實測定案：由初版提案的 80% 上修為 90%。
Problem
問題背景
1. 編輯彈窗固定 672px，為不存在的使用情境付代價
AdminModal（shared.tsx:253）的 maxWidth 預設為 max-w-2xl＝672px， 而 12 個後台分頁中有 10 個共用這層殼（Pilot / Weapon / Module / Mech / Buff / Backpack / Component / Glossary / Skill / NeuralDrive）。672px 是通用彈窗尺寸——對一個「維護者只在 PC 上、 一次要對照數十個欄位」的後台而言，等於把大半個螢幕留白。
2. 高度早就夠了，感覺到的「小」純粹是寬度
殼層已是 max-h-[90vh]。因此本計畫完全不動高度， 所有工作集中在水平方向。這一點先釐清，可以省掉一整條沒必要的改動路徑。
3. 關鍵發現：單純加寬是負優化
.input-field 是 width: 100% 且無上限（index.css:70）， 而 admin 目錄下 59 處 grid-cols-* 宣告有 58 處是固定欄數（僅 GrayOpsAdmin:95 有 rwd 前綴）。兩者相加的後果是： 多出來的寬度會 100% 變成「輸入框變胖」，而不是「一次看到更多欄位」。

最典型的是 WeaponAdmin 數值頁——6 個數字欄位被拆成 3 組獨立的 grid-cols-2（:321 / :325 / :329）。 加寬到 1728px 後，「連擊數 hitCount」這種一位數的輸入框會被撐到約 820px 寬， 標籤與輸入內容之間出現大片空白，眼睛橫掃距離暴增；而 6 個欄位仍然佔 3 排，一排都沒省。 掃視成本反而比 672px 時更高。
因此 A 與 B 必須綁定交付。 「只改一行預設值」看似是廉價的快速勝利，實際上會讓後台比現在更難用。 這是本計畫最重要的判斷，也是為什麼它值得立成 PLAN 而不是隨手改掉。
Design
設計決策
決策一：改單一旋鈕，不逐檔改寬度
10 個編輯器的寬度來自同一個 AdminModal 預設值，所以 Phase A 只動 shared.tsx 一處即可全數生效。maxWidth 這個 prop 本來就存在（型別宣告於 shared.tsx:262），不需要改動元件 API， 也不需要動任何呼叫端——除了刻意要維持窄版的那幾個（見決策五）。
決策二：寬度定為 max-w-[min(90vw,1920px)]（實測定案）
初版提案為 80vw，經來源筆記的互動示範實拉之後上修為 90vw。 外層再套一個 1920px 硬上限，純粹是防止超寬螢幕（3440px 以上）把彈窗撐到荒謬寬度； 在 2133px 以下的視窗中該上限完全不會觸發，行為就是單純的 90vw。 可調 若日後覺得上限礙事，拿掉 min() 只留 90vw 即可，無副作用。
⚠ 陷阱：絕對不要寫成 w-[90vw]
殼層目前是 w-full ${maxWidth}（shared.tsx:272）。 w-full 與 w-[90vw] 都在設 width， 勝負取決於 Tailwind 產生的 CSS 規則順序，而不是你寫的 class 順序——這會是個難查的雷， 且可能在改動其他 class 時毫無徵兆地翻轉。 走 max-w-* 則與 w-full 是不同屬性，行為完全確定。
決策三：格線用 CSS auto-fill 自動決定欄數 執行中修訂
本決策在 Phase B 開工時由「階梯式容器查詢」修訂而來，原因見下方兩個發現。

抽成單一共用常數（shared.tsx），全站套用：
export const GRID_AUTO_FIELDS = 'grid grid-cols-[repeat(auto-fill,minmax(220px,1fr))]' // 用法：保留各處原本的 gap <div className={`${GRID_AUTO_FIELDS} gap-3`}>
欄位多就排滿一列、欄位少就靠左留白不撐胖。因為量的是元素自身寬度而非視窗， 窄版彈窗與巢狀卡片內都會自動得到正確欄數，完全不需要斷點。

關鍵 是 auto-fill 不是 auto-fit——auto-fit 會收合空軌道、 讓現有欄位吃掉整列寬度，正好是本階段要消滅的胖輸入框。兩者只差一個字、行為相反。
發現一：階梯式斷點解不掉「欄位數本來就少」的區塊
原訂做法是 grid-cols-2 @3xl:grid-cols-3 @5xl:grid-cols-6。 但 WeaponAdmin 的「射程」分頁只有 minRange / maxRange 兩個數字欄位——再多的斷點也排不滿，兩個框仍會各撐到約 830px。 這種「欄位數少於欄數」的區塊在後台不少（射程、元件插槽、改裝方案…）， 而它們正是 Phase B 要解決的胖欄位問題本身。 auto-fill 一併解決：排不滿就留白，不把空間分給現有欄位。
發現二：@container 會打壞彈窗內的 IconPicker 浮層 已修正
A-1 一度在殼層加了 @container。它會套用 container-type:inline-size， 而該值隱含 contain:layout——layout containment 會讓該元素成為 position:fixed 子孫的 containing block。 MechAdmin、BuffAdmin、ModuleAdmin、SkillAdmin、 NeuralDriveAdmin、PilotAdmin 都在彈窗內使用 IconField（components/admin/IconPicker），該元件是 fixed inset-0 的全螢幕浮層——加了 @container 之後 inset-0 會改對齊彈窗的框而非視窗，浮層直接錯位。

改用 auto-fill 後不再需要容器查詢，該 class 已移除， 並在 shared.tsx 留下反向註解防止日後有人加回來。
決策四：判準是「同質短欄位 vs 異質長欄位」，不是全部改成多欄
59 處格線並非全部都要動，估計實際需要改的約 35 處。

決策五：不是所有編輯器都該變寬
GlossaryAdmin（:41）、NeuralDriveAdmin（:63）、 SkillAdmin（:64）欄位數少，撐到 1728px 只會讓兩三個欄位漂在一片空白裡。 這三個顯式傳回 maxWidth="max-w-2xl" 維持現狀。 順帶把 MechAdmin:344 那個與舊預設值重複的顯式覆寫拿掉，讓它吃新預設。
決策六：Phase C 延後，A＋B 先獨立交付
使用者已確認三階段全做，但 C 不急迫。A＋B 合計約半天、純 className 改動、 可獨立驗收；C（四個大編輯器的 Tab 版面重構）需 1～2 天且會動到元件結構與狀態，風險層級不同。 兩者之間沒有技術依賴，因此 C 標記為 LOW · 延後， 待 A＋B 上線實際用一段時間後，再依「Tab 切換是否真的造成困擾」決定是否啟動與採用哪個方案。
決策七：Phase C 方向修正（2026-08-02，B 完成後重估）
原 Phase C 是在 Phase B 動工之前寫的，假設「分頁很擠，需要更好的版面容器」。 B 把格線改成 GRID_AUTO_FIELDS 之後重新實測，兩個前提都變了：
  • 分頁不是等量的，是「三小三大」。多數分頁已縮到 1～3 排， 而彈窗內容區在 1080p 下約 760px ≈ 10～11 排——小分頁三頁疊起來還不到一屏的一半。 真正惱人的是天賦這類展開後長達兩屏的分頁。
  • 病因不是「容器不夠好」，是「沒吃到寬度」。那些長分頁根本沒有 grid-cols-*，是純 space-y-* 垂直堆疊 （兩個 min-h-[150px] textarea 上下疊 ＋ RefPicker ＋ 兩組效果清單）， 在 1700px 下只會變成超寬矮帶——寬度浪費、長度沒少。B 修的是格線，修不到它們。

因此兩個原方案的處置：
  • 方案一（左側直排 Tab）＝ 刪除。切換次數一次都沒減少， 還要吃掉 140～180px 橫向空間——而橫向空間正是 A＋B 剛拿到的東西。淨收益為負。
  • 方案二（雙分區同顯）＝ 保留，但用在對的位置。 不是跨 Tab 並排（哪兩個配對沒有普適規則、兩欄高度不等時捲動難看）， 而是在單一長分頁內部並排：左＝文本、右＝結構化資料。
  • 新增方案三（合併小分頁）＝ 採用為 C-1。 把 Tab 邊界降級成 section 標題 ＋ border-t 分隔，就在同一個捲動區裡。 這正是 B 已在單一分頁內做過的手法，只是把邊界從 Tab 提升到 section。
  • 新增 C-0（抽共用 AdminEditTabs）。原計畫未涵蓋： 四個檔案各寫一份幾乎相同的 Tab 列，其中 MechAdmin 樣式還不一致。純提取、零風險。

風險與工時同步下修：查核後確認 form 是 EditPanel 頂層的 useState、Tab 只是條件渲染，改版面不碰 state 也不碰 handleSubmit → patchCollectionItem——原估「會動到元件結構與狀態」 並不成立，工時由 1～2 天下修為約半天。
決策八：天賦／神經驅動「獨立 detail page」不納入本 PLAN
使用者提出的方向，直覺正確（這些東西確實不該擠在彈窗裡）但診斷後確認不是本階段該做的：
  • 治不到病因。detail page 只是把同一條垂直堆疊搬到更高的容器裡， 捲動距離一樣長，淨收益僅「多約 200px 高度」。垂直堆疊本身已由 C-2 治掉。
  • 會動到資料寫入路徑。talents / neuralDrive 是 內嵌在 pilot 文件的欄位（非獨立集合），而 updatePilot（src/lib/api/pilots.ts）是 setDoc 無 merge、整份覆寫。 開 detail page 會出現兩個都會整份覆寫同一份文件的編輯面，且從彈窗跳過去會丟掉未存檔草稿。 要做對得處理草稿交接 / merge 寫入 / 路由——與本 PLAN「只改版面」的定位和風險層級不同。
  • 順序反了成本差很多。C-2 半天可驗證，做完很可能發現已經夠了； 先做 detail page 則是先花一天賭它不夠。
啟動條件：C-2 上線後，天賦編輯仍需捲動超過兩屏 → 屆時另開 PLAN。
先例參考：技能的效果本體早就外移到獨立的頂層分頁 SkillAdmin （彈窗副標題即寫「效果於『技能管理』分頁編輯」）——本專案已走過一次「內容太大就外移」， 當時的結論是升級成頂層 admin 分頁，不是開 route。
Scope
實作範圍與不在範圍內
在範圍內：
  • Phase A · 殼層加寬（~15 分鐘）—— AdminModal 預設寬度改 max-w-[min(90vw,1920px)]、殼層加 @container、 三個窄版編輯器例外處理、清掉 MechAdmin 冗餘覆寫、 AdminPage 外層列表容器 max-w-6xl 一併放寬（選配）。
  • Phase B · 格線響應式化（2～3 小時）—— 依決策四的判準逐檔處理 Weapon(13) / Pilot(14) / Module(13) / 其餘(16) 的 grid-cols， 並在真實後台實測回調斷點階梯。
  • Phase C · 分頁精簡與長分頁雙欄化（約半天；2026-08-02 依決策七改寫， 原為「大編輯器版面重構 1～2 天」）—— C-0 抽共用 AdminEditTabs； C-1 合併小分頁（Weapon 6→4、Pilot 7→6、Mech 5→4，Module 不動）； C-2 把長到必須捲的分頁內部改雙欄（TalentItem 展開體、ModuleAdmin basic、 WeaponAdmin mods、NdZoneCard）；C-3 驗證。
不在範圍內：
  • 手機 / 平板適配——後台維護者只用 PC，已明確排除。 這也是本計畫敢於大幅加寬的前提。
  • 前台彈窗——AuthModal、RefPicker、 IconPicker 各有自己的殼，不受 AdminModal 影響，不動。
  • UserAdmin 與 GrayOpsAdmin——這兩個是 inline 版面、 不走 AdminModal。其中 GrayOpsAdmin:95 已經是響應式格線，無需處理。
  • 任何型別 / Firestore / 資料邏輯變更——全程只改 className， 不動 src/types/、enums.ts、firestoreApi.ts， 也不涉及任何 Firestore 讀寫。
周邊成本：幾乎為零
  • 不觸發 CLAUDE.md 規則 2 的文件同步——無型別 / enum / API 結構變更， docs/02_技術文件/ 完全不用碰；也沒有資料版本問題，不需 bumpDataVersion。
  • commit 類型——commit-msg hook 會擋下未一併修改 src/data/siteChangelog/ 的 feat|fix|perf|style|refactor。 但這是後台改動、一般使用者無感，依規則 1「摘要以使用者視角描述」的精神， 用 chore 類型 commit 即可豁免，不必硬塞一筆履歷。
  • 驗證方式——本機後台截圖須走 port 5173（Firebase referer 白名單） ＋ 獨立 profile 手動登入。
