背包技能集合與編輯強化backpackSkills · 等級化 · 刪除 · IconPicker

背包技能從 SS 專屬的內嵌欄位，升級為獨立、可等級化、可共用的字典集合；並補上背包後台缺席已久的刪除與圖示挑選。

一句話： 背包的技能目前只以「SS 專屬的單一內嵌物件」存在，那是爬蟲時代官方 WIKI 欄位形狀的殘留； 實際遊戲內連 B 級的「移動背包」都有被動技能「移動強化 Ⅰ」，資料層卻無處可放。 本計畫開一個獨立的 backpackSkills 集合承接，順帶補齊背包後台的刪除與圖示挑選。
Problem
問題背景
問題一：技能欄位的形狀是「官方 WIKI 有填什麼」，不是「遊戲裡實際有什麼」
Backpack.mainSkill（src/types/backpack.ts:35-49）是單一選填物件，且實務上只有 SS 稀有度填了值——因為當初 scrape-backpacks.js 只在官方 WIKI 的 SS 條目上找得到技能欄位。 但遊戲內截圖顯示，B 級的「移動背包」（重量 150、僅限輕型機甲）掛著被動技能「移動強化 Ⅰ」，效果為「移動力 +1 格；軀幹耐久 +10%、造成傷害 +5%」。 官方 WIKI 從未錄入這類技能 —— 維護團隊已決定放棄爬蟲、改為人工維護，資料模型必須先跟上這個決定。
問題二：內嵌 = 無法共用，而背包技能明顯是「族」
「移動強化 Ⅰ」的羅馬數字直接宣告了同族存在 Ⅱ / Ⅲ。若沿用內嵌，同一族技能會在每個掛載它的背包內複製一份正文與 buffIds， 這正是 PLAN-032 在武器技能上診斷出的病（170 份拷貝／124 個相異技能，且已開始漂移）。背包在資料量還小的時候就該避開。
問題三：背包後台無法刪除
全站目前只有 buffs / pilotSkills / glossaryTerms 三個字典集合有刪除（皆走 PLAN-030 的級聯刪除）。 背包後台的新增走手打 ID（BackpackAdmin.tsx:433-445，無 deriveId），打錯就是一筆永久躺在集合裡的垃圾文件，只能進 Firebase Console 手動清。
問題四：背包是全站唯二還在手打圖示路徑的後台
BackpackAdmin.tsx:167-174（背包 icon）與 :282-285（mainSkill.icon）都還是純文字 <input>， placeholder 寫著「填圖示檔名如 Icon_skill_passive_1234」——維護者得自己記住那串數字。 IconPicker／IconField（src/components/admin/IconPicker.tsx）早在 PLAN-019 就做好，機師／技能／模組／BUFF／機甲／神驅六個後台都接了，唯獨背包沒接。
Design
設計決策
決策一：新開獨立的 backpackSkills 集合，不併入 pilotSkills
這與 PLAN-032（武器技能）的裁決相反，是刻意的，理由記錄如下：
  • 維護者裁定——背包技能要獨立管理，不與其他實體混在同一份清單裡。這是本計畫的前提，不再重新論證。
  • 欄位形狀確實不同：PilotSkillDoc 帶 type／unitType／ap／cd／pp／weapon／variants，背包技能一個都用不到（截圖的「消耗 —／武器 —」證實）；反過來背包技能需要 levels[]，那是 PilotSkillDoc 沒有的。塞進同一份 doc 會讓兩邊的必填語意再稀釋一次。
  • ID 前綴衝突風險：pilotSkills 現存 SKILL_ 大寫 134 筆／skill_ 小寫 512 筆，後台撞號防呆只查小寫形式（SkillAdmin.tsx:208-214）。獨立集合＝獨立命名空間 bpskill_，直接繞開這個仍未修的洞。
代價已知並接受：需要在 GameDataContext 補 9 處、RefType／ChangeTargetKind 各補一組、複製一份約 300 行的 Admin 分頁。詳見下方影響表。
決策二：掛載側用陣列 skillIds: string[]，不用單一 skillId
目前實務上每個背包只有一個技能，陣列長度恆為 0 或 1。但改成陣列的成本只是渲染側多一層 map， 而若未來出現雙技能背包，單一欄位就得再走一次型別遷移 + 腳本 flip。先付一點點，省掉未來一整輪。
// src/types/backpack.ts export interface Backpack { // …既有欄位不變… /** 掛載的背包技能 doc id（PLAN-043）。目前實務長度 0 或 1。 */ skillIds: string[] // mainSkill?: {...} ← Phase E flip 後刪除 }
決策三：等級沿用 PLAN-024 的 levels[] 模式
一族一筆 doc，levels[] 承載各級差異，引用時以 <id.lvN.attr> 指定級、buffIds 以 id@N 賦予指定級 —— 與 GameBuff.levels（src/types/buff.ts）完全同構，維護者的心智模型不必分岔。
{ id: 'bpskill_移動強化', name: '移動強化', skillType: 'passive', levels: [ { level: 1, name: '移動強化Ⅰ', description: '機甲移動力增加1格；…', effects: [...] }, { level: 2, name: '移動強化Ⅱ', ... }, ] }
繼承 PLAN-024 的踩雷紀錄：階名 levels[].name 必須手填，不做羅馬數字自動推導——既有資料已知損壞（「失穩ⅠⅠⅠ」是三個 U+2160），推導在髒資料上必然失敗。 無等級的技能就是 levels 不填，行為退回頂層欄位，與 BUFF 完全一致。
決策四：一次性硬切遷移，但分兩段部署
資料量小（僅 SS 有 mainSkill），不值得養一套長期雙格式相容層（PLAN-004／032 那種 resolveXxx util）。但部署順序仍必須安全 —— PLAN-032 的教訓是「讀新格式的前端必須早於 flip 上線，否則活站整區空白」。故拆成：
  • Stage 1（Phase B）：腳本讀出 mainSkill → 建 backpackSkills doc → 同時寫回 Backpack.skillIds。不動 mainSkill，此時兩者並存但前台仍讀舊的，零風險。
  • Stage 2（Phase E）：確認前後台都改讀 skillIds、線上無誤後，第二支腳本 deleteField('mainSkill') 並從型別中移除。
兩支腳本都預設 dry-run、--apply 才寫，並在最後 bumpDataVersion（否則使用者讀到舊 localStorage 快取）。
決策五：圖示獨立資料夾 public/images/skills/背包技能/
背包技能圖示絕大多數是被動技能圖示，與 skills/被動技能/（現有 518 張）大量重複。維護者明示接受這份重複，換取圖庫在「未來會愈來愈龐大」時仍分得清來源。
零腳本改動：scripts/generate-image-manifest.mjs 是遞迴全掃 public/images/、無白名單（:35-49），新資料夾放進圖片後跑 npm run manifest:images 就會自動出現在 manifest.json，IconPicker 的資料夾下拉也會自動多一項。
唯一要注意的是 src/utils/assets.ts 的 normalizeSkillPath()：它會依檔名前綴（passive → 被動技能）把扁平路徑推回子資料夾。若背包技能圖沿用 Icon_skill_passive_* 檔名而放在背包技能/，需確認該函式對「已含子資料夾的完整路徑」是冪等的（不會被改寫回 被動技能/）——這是 Phase A 的一項驗證任務。
決策六：級聯刪除要補兩個 entityRefs 掃不到的硬外鍵 ⚠ 本計畫最容易靜默出錯之處
加入刪除本身很輕（ChangeTargetKind 加值 + 一行 cascadeDelete + 三個共用元件），GameDataContext.removeCollectionItem 的 backpacks case（:272）與 firestore.rules（write 已涵蓋 delete）甚至不用動。 但 cascadeDelete 只清 entityRefs.ts 站點模型內的引用，而背包被以下兩個位置用裸 id 硬引用，兩者都不在目前的 BACKPACKS spec 裡：
  • Weapon.upgrade.fusedBackpackId（複合武器融合的背包，PLAN-031）
  • Backpack.craft.prereqBackpackId（前置主背包鏈，PLAN-036）
不處理就會刪出斷鏈：前台 BackpacksPage 的 prereqNameOf 會靜默降級成「前置主背包待確認」（:166-169）。 對策：把這兩處加為 scalarSites，並在 ConfirmDeleteDialog 內以 blocker（而非自動清除）呈現——被別的背包當前置的背包不該能被順手刪掉，應該要求維護者先斷鏈。
決策七：入向引用（refType）本期不做
背包技能的出向引用照做——技能描述可寫 [虛粒子形態] 引用 BUFF／詞條，descriptionRefs 與 buffIds 皆保留，模擬器 buildBuffPool 也接上。 但讓別人寫 [移動強化] 反過來指向背包技能（需新增 RefType: 'backpackSkill' + EntityRefView 分支 + RefChip + RefPicker 選項）列為 N2： 目前全站沒有任何一段正文需要引用背包技能，先加等於做出零消費端的休眠站點。日後有需求再補，成本約半天。

Scope
實作範圍與不在範圍內
在範圍內：
  • 獨立 backpackSkills 集合：型別、API、快取註冊、安全規則、引用掃描站點
  • 技能等級化（levels[]，PLAN-024 同構）
  • Backpack.mainSkill → Backpack.skillIds[] 的兩段式硬切遷移（含兩支腳本與 bump 版本）
  • 後台新分頁「背包技能管理」（列表 / 搜尋 / 新增 / 編輯 / 級聯刪除 / IconPicker / RefPicker）
  • 背包後台：技能挑選器、兩個 icon 欄位接 IconField、刪除背包（含前置鏈與融合武器的 blocker）
  • 前台背包圖鑑：卡片 / tooltip / BottomSheet 改讀集合，支援多技能與等級顯示
  • 模擬器接線：SIMULATOR_KEYS 與 buildBuffPool 走新集合，行為不變
  • 圖示資料夾 public/images/skills/背包技能/ 與 normalizeSkillPath 冪等性驗證
  • docs 資料模型同步（CLAUDE.md 規則 2）
不在範圍內：
  • 併入 pilotSkills——已由決策一排除，不再重議
  • 武器技能引用化——那是 PLAN-032，兩者刻意不互相依賴
  • 入向 RefType: 'backpackSkill'——決策七，列 N2
  • 更新 scrape-backpacks.js 爬蟲——維護團隊已決定放棄官方 WIKI 抓取，背包技能改純人工維護。爬蟲若日後再跑，需注意它不會也不該碰新集合
  • 逐筆補齊 180 個背包的實際技能資料——這是長期維護任務，也是本計畫日後轉入「觀察維護中」的判定條件

  • 刪除功能的還原（undo）——PLAN-030 的 planRestore 既有機制若能直接吃就吃；若因新 kind 需額外工作則跳過，維護者已表明背包刪除是低頻操作、不可復原可接受
Risk
主要風險與對策
風險後果對策
GameDataContext.applyData 漏 case 靜默 不報錯，表現為「重整後背包技能全消失」 Phase A 完成後實際重整一次頁面驗證快取回填，不能只看 tsc 過
刪除背包時漏清 fusedBackpackId / prereqBackpackId 靜默 前台降級成「前置主背包待確認」，不會報錯 決策六：加 scalarSites 並以 blocker 呈現，強制先斷鏈
Stage 2 flip 早於前台改讀上線 高 活站背包技能整區空白 決策四的兩段部署；Phase E 是最後一個 Phase，且需人工確認線上正常才執行
遷移腳本以 icon 去重 中 不同技能被合併成同一筆 去重鍵一律用 name（PLAN-032 實測結論）
忘記 bumpDataVersion 中 使用者持續讀到舊 localStorage 快取 兩支腳本結尾都必須 bump backpacks 與 backpackSkills；寫進腳本而非靠人記
normalizeSkillPath 把「背包技能/」路徑改寫回「被動技能/」 中 圖片 404 或指到錯誤的同名檔 Phase A 先驗證冪等性；必要時在該函式加「已含已知子資料夾則原樣返回」的短路
