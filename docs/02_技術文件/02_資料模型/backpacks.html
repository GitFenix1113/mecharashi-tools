Schema
欄位定義
背包是獨立裝備，有自己的種類、稀有度、修理量，以及可裝備機甲類型限制。SS 稀有度背包另有 API 提供的附帶技能資料。

namestring背包名稱（如 "拯救者背包"）
iconstring?背包圖示 CDN URL（由腳本根據 ID 自動組裝）
格式：https://media.zlongame.com/media/pictures/cn/community/img/gl/gameInfo/pack/Icon_backpack_{ID}.png

Cross-Display
「特種背包製作」交叉顯示（複合武器投影）
遊戲內【特種背包製作】清單是混合清單：22 個 SS 特種背包（backpack_data）＋ N 把複合武器（weapon_data，如裁決者／糖衣毀滅者／天燼審判）。背包圖鑑（PLAN-031 B-2）以此重現該清單。
背包側完全不存任何欄位，全部 derived：
· 「特種背包製作」正交 facet 的判定 = rarity === 'SS'（isSpecialBackpackCraft，見 src/utils/weaponUpgrade.ts），不在 Firestore 存推論值。
· 打開 facet = SS 背包 ∪ 複合武器（upgrade.station === 'specialBackpack'）；facet 為可交叉的正交維度，與稀有度／類型／裝備並存。
· 複合武器投影條目的「類型」由武器的 upgrade.fusedBackpackId 查 backpacks 取 type（不存欄位）；armor 篩選由武器 mechRestriction 換算（英文 key，EN→EN，不涉模擬器 EN→ZH）。
· weapon 分支卡片務必用 WeaponIcon（背包側圖示元件會強制拼 /images/backpacks/ 而 404）；技能圖示走武器側 iconLocal 完整路徑。
· PLAN-037 呈現調整：原「特種背包製作」正交 facet 改為圖鑑上的「包含武器」toggle 且預設開（includeWeapons）；複合武器與背包共用同一組階層／類型／裝備篩選統一收斂，判定仍為 isCompositeWeapon（upgrade.station === 'specialBackpack'）。

複合武器的儲存歸類仍是「武器」（存 weapons、refType:'weapon'），此處僅為呈現層投影。完整判準見 weapons 資料模型的「跨界實體判準」。刻意不新增 BackpackType.Composite——要並列的 5 個背包分屬 5 種不同 type，做完反而更孤立，且爬蟲會用 API 值覆寫 type。
Classification
合成階層與「強化/干擾」軸（全部 derive，零欄位）
背包圖鑑（PLAN-035）把 180 件背包依合成階層分成素材/基礎/複合/特種四層，並提供「強化 vs 干擾」第二軸與變體篩選（落地預設只展開特種層，見 ① · PLAN-037）。階層與軸皆從既有 rarity＋名字字串 derive，不新增任何 Firestore 欄位、不 bump 版本。邏輯在 src/utils/backpackClassify.ts。
① 合成階層 ＝ rarity 的粗化（tierFromRarity，實測 1:1）：
　素材 = A + B（37）· 基礎 = S（23）· 複合 = S+（98）· 特種 = SS（22），合 180。
　背包圖鑑的階層 facet 取代原稀有度多選（tier 只是 A/B 合併的 rarity，兩者是同一分割，並存會有「SS×素材＝恆 0 筆」矛盾）；落地預設只展開特種（SS，22 件）、其餘階層手動打開（PLAN-037 改版：預設查詢量最小，DEFAULT_TIERS = ['special']；原 PLAN-035 的預設「基礎＋複合＋特種 143 件」已收斂）。

② 「強化/干擾」軸只存在於名字字串，type 欄位不編碼它：
　出力強化背包·首攻 與 出力干擾背包·攻擊 同 type=PowerAdd——強化/干擾差異只在名字。故 line 一律由 parseBackpackName 從 name 解析，不可用 type。
　名字文法 [基礎功能]?[強化|干擾]背包·[變體]：[基礎功能] 可省略——base 階（S/A/B）的 強化背包·首攻/干擾背包·攻擊 無功能前綴（對應 type=Enhance/EMP），只有 S+ 複合階才有 出力/移動… 前綴。
　line 以整個 強化背包/干擾背包 token 判別（非裸『強化』），避開 強襲者背包(SS) 被誤判。純功能背包與 SS 特種背包 line=null，強化/干擾軸只作用於含該軸的條目、其餘不因此被排除。
　變體清單由現有資料 derive（不硬編，避免改版漏改）、依所選線收斂。

刻意不加結構化欄位（tier/line/variant）——name-derive 經 scripts/audit-backpack-classify.mjs 對 live 全 180 名字驗證 unresolved=0、分佈 37/23/98/22 相符，證實够用。僅在 name-derive 被證實不够用、或要做「背包合成關係鏈」（PLAN-031 upgrade 模型的背包版）時才需結構化。
Craft Prereq
背包的前置主背包（craft.prereqBackpackId）
背包製作有「低一階前置」關係：SS 特種背包 ← S+ 前置、S+ 複合背包 ← S 前置。 Backpack.craft 只存前置主背包這一個 id（低一階背包），種類/線/變體皆由此 id 查表 derive。
前置主背包一律「低一階」：
· SS ← S+：無法從名字 derive（征服者背包 ← 某 S+），由後台 BackpackAdmin 手動選擇。
· S+ ← S：可從名字乾淨反推（出力強化背包·首攻 ＝ 出力背包(S) + 強化背包·首攻(S)，存變體背包「強化背包·首攻」）。實測 98/98 命中，由一次性腳本 scripts/temp_scripts/fill-backpack-craft.mjs 填入。
· 存檔走 updateBackpack（自動 bumpDataVersion('backpacks')）；候選為「低一階」背包，S+ 前置的 type 是 Enhance/EMP（變體線）非自身 PowerAdd。

其餘 derive / 固定文案：
· 種類＝查 prereqBackpackId 取 type（prereqBackpackType）；背包圖鑑「前置背包種類」facet 目前只作用於 SS，查不到關聯的 SS 在此 facet 下不顯示（優雅降級）。
· 圖紙＝derive（name + '設計圖'，blueprintName）；S+ 的另一材料「功能背包」（出力背包）由 base derive、不存；任意 3 個 S ＝固定文案、不存。
· 無前置階（S/A/B）一律不寫 craft；未關聯者前台當「未關聯」處理、不報錯。

能力循前置鏈（PLAN-037，backpackAbility）：SS／S+ 自身名字常無變體（如 主宰者背包），沿 prereqBackpackId 鏈遞迴到第一個有 line+variant 的 S 祖先（主宰者背包 → 飛行強化背包·首攻 → {強化, 首攻}），使 SS／S+ 也能被「強化/干擾＋能力」軸循線篩選；鏈底為功能背包（出力背包）者回 {line:null, variant:null}、不被命中。

刻意分流的後續：完整配方呈現；形態二「特種背包武器」（裁決者等，產物是武器，已由 PLAN-031 weapon.upgrade 涵蓋）；圖紙材料來源（武裝討伐資料庫）。
