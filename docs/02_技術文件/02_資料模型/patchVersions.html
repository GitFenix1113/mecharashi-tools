patchVersions版本時間線資料模型

靜態 TypeScript 資料檔，定義版本資訊（PatchVersion）、半版本（PatchHalf）、計時活動（TimedActivity）的完整欄位規格。PLAN-014 Phase A 擴充。

Overview
資料來源 & 用途
位置：src/data/patchVersions/

組成：每個版本各一份 v{N}.ts；型別定義集中於 types.ts； index.ts 匯總 PATCH_VERSIONS 陣列供前台元件使用。

用途：版本時間線（VersionTimeline → VersionDetailView → VersionGanttPanel， route /versions/timeline/:version）、版本速覽表（VersionQuickTable，route /versions/quick；舊稱「版本濃縮資訊」）。

PLAN-014 Phase B 計畫將此靜態資料遷移至 Firebase Firestore，並以 usePatchVersions() hook 取代靜態 import，屆時本文件中的欄位定義亦適用於 Firestore Document 結構。
PatchVersion
PatchVersion — 版本頂層
export interface PatchVersion { version: string // 如 "2.8"、"3.3" name?: string // 版本副標，如 "黃昏紀元" bannerImage?: string // 版本前瞻圖路徑（/images/banners/v2.8.jpg） upper: PatchHalf // 上半版本 lower: PatchHalf // 下半版本 crisisShop?: string[] // 危境重構可兌換機師 memoryStorm?: string // 記憶風暴說明 borderShop?: string // 邊境商店更新（如 "雷克斯(6/15)"） arenaShop?: string // 鬥技場更新（如 "銀閃(6/18)"） grayOpsUpdates?: GrayOpsUpdate[] // 灰燼行動機甲列表更新 notes?: string | string[] // 版本備註（多條；舊資料為單一字串，讀取端一律經 normalizeNotes() 攤平） isTwCurrent?: boolean // 此版本是否為台服當前版本（首頁標記用） iconUrls?: VersionIconUrls // 版本內容名稱 → 圖示 URL 對照（pilots/mechs/weapons/backpacks） entityIds?: VersionEntityIds // 版本內容名稱 → Firestore 文件 ID 對照（首頁圖示接引用浮窗用） }
欄位型別必填說明
version string 必填 版本號字串，如 "2.8"、"3.3"。PLAN-014 Phase B 將作為 Firestore Document ID。
name string? 選填 版本副標題，如 "黃昏紀元"，顯示於版本徽章與頁頭。
bannerImage string? 選填 版本前瞻圖路徑，相對於 public/，如 /images/banners/v2.8.jpg。
isTwCurrent boolean? 選填 台服當前版本標記，全局只有一個版本為 true，於首頁顯示 ★ 標記。
crisisShop string[]? 選填 危境重構商店中此版本新增的機師名稱列表。
grayOpsUpdates GrayOpsUpdate[]? 選填 灰燼行動公司機甲列表更新，參見 GrayOpsUpdate 型別。
iconUrls VersionIconUrls? 選填 版本內容圖示對照表（pilots / mechs / weapons / backpacks 各為「名稱 → 圖示 URL」），供時間線與展開面板渲染媒體；參見 VersionIconUrls 型別。
entityIds VersionEntityIds? 選填 版本內容文件 ID 對照表（名稱 → Firestore 文件 ID），首頁版本濃縮表用它把圖示接上引用浮窗；參見 VersionEntityIds 型別。
PatchHalf
PatchHalf — 半版本（上半 / 下半）
export interface PatchHalf { cnDate: string // 陸服起始日 YYYY/MM/DD（固定週四） twDate?: string // 台服起始日（可含 "約 " 前綴） twIsPredicted?: boolean // 台服日期是否為預測值 weeks?: number // 本半版本幾週；未填視同 3。上半優先用「下半起始日」推算 pilots?: string[] // 本半版本新機師 mechs?: string[] // 本半版本新機甲 pilotSelection?: string[] // @deprecated 改用 TimedActivity.selection；前台仍 fallback 讀 mechSelection?: string[] // @deprecated 同上 armamentRaids?: ArmamentRaid[] // 武裝討伐副本 battlePass?: BattlePass // 版本戰令 // ── PLAN-014 Phase A 新增：甘特圖活動 ── cnActivities?: TimedActivity[] // 陸服活動（起始日 + 週數） twActivities?: TimedActivity[] // 台服活動（獨立維護，與陸服無關） // ── 舊欄位（deprecated）：cnActivities/twActivities 存在時優先使用 ── /** @deprecated */ skinGacha?: string /** @deprecated */ rouletteEvent?: boolean /** @deprecated */ specialEvents?: string[] /** @deprecated */ revivedBanners?: string[] }
pilotSelection / mechSelection 已 deprecated（2026-08-18）

它們曾經是「這一期可以選誰」唯一的去處（活動只記「什麼時候開、辦多久」）。 名單寫在官方公告「活動內容」的括號裡（一次列 30～40 個名字），當時解析器沒有抓，由維護者手填。

現已改掛在活動上（TimedActivity.selection），且解析器 自 PARSER_VERSION 6 起會自動抓（規則見 scripts/lib/parseAnnouncement.mjs，比對 266 篇語料 9 篇命中、零副作用）。 前台仍顯示在版本資訊表的「角色自選 / 機甲自選」兩列（走 halfRows，上下半各自獨立 —— 名單每半期都不同，不像戰令橫跨整版），但那是 fallback 而非主要來源。

後台的「選配池」兩格自 2026-08-18 起只在有值時顯示：既有 8 個半版本的資料 改得動也清得掉，新半版本則天然不會出現這兩格 —— 否則遷移永遠追不上新增。 ⚠ 清空與搬移是兩個動作，順序必須是「先搬、再清」：清空後區塊即消失， 而 changeHistory 對 update 只記 changedFields 不存舊值，救不回內容。

⚠ 2026-08-18 起新資料請填在活動的 TimedActivity.selection： 同一半版本可能同時開兩個自選池（如復刻場與一般場並行），半期層級只有一份會被迫共用而顯示錯誤。 這兩個欄位降為 fallback——活動沒填 selection 時才讀， 既有資料因此不會失效；甘特上已有對應自選池活動時，資訊表那兩列會自動讓位不重複顯示。

⚠ 2026-08-17 之前這兩個欄位前台完全沒有讀取：舊註解寫「改用 cnActivities」， 但 legacyActivities 的相容層只翻譯 skinGacha/rouletteEvent/ specialEvents/revivedBanners 四個，這兩個不在其中 —— 遷移只做了一半，於是 8 個半版本的手填名單一筆都沒顯示過。
週軸長度：weeks 與跨版本活動

甘特週軸的長度由三者依序決定：① 下一段的開始日（上半用下半的 twDate／cnDate， 是實際日期而非慣例，最可靠）→ ② weeks（維護者手填的例外）→ ③ 預設 3 週（DEFAULT_HALF_WEEKS，官方慣例）。

⚠ 週軸絕不被活動撐長。舊版會拿最長的活動去延伸軸尾，於是 v3.1 下半（7/30 起、實際 3 週） 因為一條 6 週戰令而長出 8/20～9/3 三欄 —— 那三週其實屬於 v3.2。跨版本的活動改由 ganttGeometry.activityGeometry 在軸尾切平（clipEnd，長條右緣不收圓角）， 這才是「延續到下個版本」的正確表達。回歸測試在 ganttGeometry.test.ts。

陸台分離原則

同一活動在陸服與台服的時間不同，且台服有時調整順序，因此 cnActivities 與 twActivities 各自獨立填寫，不從陸服日期自動推算台服。

遷移策略：舊欄位（skinGacha、rouletteEvent 等）保留以維持向下相容； UI 優先讀取 cnActivities / twActivities，若不存在則 fallback 顯示舊欄位的文字清單。 Phase B 完成後可逐步移除舊欄位。

欄位型別說明

mechsRecord<string, string>?機甲名稱 → 文件 ID（如 mech_001_伊格尼特）
weaponsRecord<string, string>?武器名稱 → 文件 ID
backpacksRecord<string, string>?背包名稱 → 文件 ID
為什麼要存而不是前台推導：三個集合的文件 ID 都帶建檔當下的流水號 （pilot_001_亞瑟 / mech_001_伊格尼特 / weapon_003_xxx）， 從名稱推不回來。由後台「自動同步」在既有那趟 getDocs 裡順手記下，前台零額外讀取。

為什麼與 iconUrls 分成兩張表：兩者填入時機不同。武器常是資料先建檔、 圖片素材晚幾天才處理好；分開存，同步時才能各自「只補空缺」，前台也才做得到 「有 ID 就可點，有沒有圖是另一回事」——素材沒到位時退成可點的文字而非失去互動。

ID 的同步策略與 icon 不同：icon 受「強制覆寫」勾選框控制（保護人工修過的路徑）， ID 則永遠以資料庫為準覆寫——它是機器推導、不開放手動編輯，沒有使用者的值需要保護， 而資料庫重建導致流水號變動時必須跟上，否則連結會靜靜指向舊文件。

值的格式：<docId>，跨集合時為 <refType>:<docId>。 「顯示在哪一列」不等於「實體在哪個集合」：backpacks 列會出現複合武器 （天燼審判、裁決者、糖衣毀滅者 — PLAN-031），它們在官方資料層是武器、住在 weapons 集合， 玩家視角卻是特種背包製作的產物，因此記成 weapon:weapon_169_天燼審判。 同步時 backpacks 查無此名會自動回退去 weapons 找（PLAN-031 判定這是 「一條長期產線」，故做成規則而非特判），icon 也一併取武器的。 解析與寫入一律走 src/data/patchVersions/entityRef.ts 的 parseEntityIdValue / formatEntityIdValue。
TimedActivity
TimedActivity — 計時活動（甘特圖單筆）
設計背景：鋼嵐所有活動均以星期四為起訖單位。 活動可用「起始日（週四）+ 持續週數」完整描述。 結束時刻一律為 exclusive：endExclusive = startDate + weeks × 7， 即「最後一天的隔天 00:00」（weeks=1 → 當週四到下週三，下週四 00:00 結束）。 UI 元件自動計算，不需手動填入。
PLAN-048 Phase 1 擴充：新增 id / rewards / description / sourceUrl / confidence / typeLabel 六個選填欄位， 並把 type 由硬 union 改為開放字串 + 靜態登錄表。
另外，「進行中／第 N/M 週／剩幾天／末週」等狀態一律由 startDate + weeks 衍生 （src/components/timeline/activityStatus.ts），不存欄位 —— 凡是能算的就不要問維護者，那是唯一零維護成本、100% 覆蓋率的資訊來源。
export interface TimedActivity { // ── 既有欄位 ── name: string // 活動名稱，如「角雕刮刮樂」、「環島物流節」 startDate: string // 起始日 YYYY/MM/DD，慣例為星期四 weeks?: number // 持續週數（1 = 當週四到下週三）；缺＝公告只寫「起」，該筆必然 hidden type: ActivityTypeId // 開放字串；未登錄型別走中性色 + typeLabel pilots?: string[] // 關聯實體：卡池 UP 機師、戰令獎勵機師（bannerIsRerun 靠它判復刻） mechs?: string[] // 同上，機甲側。⚠ 特遣／海運的可選名單是 selection 不是這裡 // ── PLAN-048 Phase 1 新增 ── id?: string // 穩定識別子 act_<base36 時戳><亂數>；甘特↔卡片連動的錨點 rewards?: string[] // 關鍵獎勵，逐項純字串；未填則前台解析 name 括號 description?: string // 活動說明／規則，純文字，換行即分段 selection?: string[] // 自選池「這期可選誰」；解析器 v6 起自動抓，未填才 fallback 讀半期的 pilotSelection/mechSelection sourceUrl?: string // 官方公告連結 confidence?: 'confirmed' | 'predicted' // 未填視同 confirmed typeLabel?: string // 未登錄型別的顯示名（已登錄型別以登錄表為準） // ── PLAN-048 Phase 2 新增 ── hidden?: boolean // 前台一律不顯示（資料未齊，補完取消勾選即上線） note?: string // 後台備註：缺什麼、去哪裡查。前台永不顯示 editorNote?: string // 站方備註：官方沒寫但玩家該知道的慣例。前台以「備註」顯示 } // 通過前台顯示閘門的活動：保證有 weeks 且未被隱藏 export type VisibleActivity = TimedActivity & { weeks: number }
欄位型別必填說明
name string 必填 活動名稱，顯示於甘特條 hover tooltip，如「角雕刮刮樂」、「白夜凍鋒（復刻）」。
startDate string 必填 活動起始日，格式 YYYY/MM/DD，必須為星期四（遊戲固定週四更新）。
weeks number? 選填 持續週數，最小值 1。UI 自動計算 endDate = startDate + weeks × 7 − 1。
PLAN-048 Phase 2 起改為選填：台版官方公告有 31% 只寫「10:00 起」、 不寫結束時刻（實測 625 筆中 193 筆，幾乎都是卡池）。填一個「慣例上大概兩週」進來， 就再也分不出哪些是官方寫的、哪些是系統猜的 —— 所以缺就留空。
⚠ 不變式：缺 weeks 的活動必然 hidden。 甘特沒有長度就畫不出長條，而畫一條長度是猜的長條比不畫更糟。
type ActivityType 必填 活動類型，決定甘特條顏色，詳見下方 ActivityType 一覽表。
pilots string[]? 選填 僅 pilotMission 類型時填入，顯示於 tooltip，如 ['白夜凍鋒', '十字線上的明光']。
mechs string[]? 選填 僅 crossShipping 類型時填入，顯示於 tooltip。
id string? 選填 穩定識別子，後台新增活動時自動產生（act_<base36 時戳><亂數>）。 不是防禦性設計：甘特列與後台編輯器原本都以陣列 index 當 key，陣列一重排， React key 與「目前選取哪個活動」的狀態就一起錯位。舊資料未填時，前台退回 半段+序號+名稱+起始日 組成的複合 key。
rewards string[]? 選填 關鍵獎勵，逐項純字串（['輕型通用改裝模組×1', '仿生超導體×2']）。 刻意不做成 { name, qty, refKey }：實測 34 筆括號內容有四種形狀 —— 獎勵 15、外觀名 10、機制說明 6、空括號 1，結構化接不住後三種。
未填時前台以 splitActivityName() 解析 name 的括號 （src/data/patchVersions/activityText.ts）。那是 runtime fallback 而非一次性遷移， 所以舊寫法與「未來又用老方法打字」都照樣顯示得出來。
description string? 選填 活動說明／規則。純文字，換行即分段。 刻意不支援 ［］引用標記：會把 patchVersions 反向耦合到 RefText／ReferenceContext 全站體系，且 chip 開浮窗會與活動浮窗互相蓋。
sourceUrl string? 選填 官方公告連結，顯示於卡片右下角「官方公告 ↗」與詳情浮窗。台版公告管線（Phase 2）可 100% 自動填。
confidence 'confirmed' | 'predicted'? 選填 資料成熟度，未填視同 confirmed。predicted → 長條虛線邊框 + 卡片標「推估」。
這是回應「陸版官網常漏維護公告」唯一能在顯示層兌現的東西：缺的公告仍然缺， 但至少讀者分得出「查證過的」與「照慣例推的」。legacy shim 翻譯出來的活動一律標為 predicted。
typeLabel string? 選填 type 不在登錄表時的顯示名（新玩法零部署上線用）。 已登錄型別的顯示名一律以登錄表為準 → 日後補登錄某型別時，先前填的 typeLabel 會自動被蓋過，無需回頭清資料。
hidden boolean? 選填 前台一律不顯示這筆（甘特、卡片、首頁濃縮表全部略過）。PLAN-048 Phase 2 新增。
用途是「資料不完整但捨不得丟」：公告只寫了開始日、沒寫辦多久，那筆事實仍然有價值 —— 藏起來等補齊，好過整筆卡在待審清單裡被遺忘。補完資料後取消勾選即上線，不需要重跑爬蟲或審核流程。
這是顯示閘門，不是軟刪除：不想要的活動請直接刪掉。
note string? 選填 後台備註：缺什麼、為什麼藏起來、要去哪裡查。前台永不顯示。
與 description 的分工很明確：description 是給讀者看的活動說明， note 是給維護者看的待辦事項。混在一起的話，補完資料時得先分辨哪一段是要刪掉的施工註記。
後台 /admin/announcements 的「規則待擴充」分頁會把所有 hidden 活動連同 note 彙總成待補清單。
editorNote string? 選填 站方備註：官方沒寫、但玩家需要知道的補充。前台會顯示（甘特浮窗與活動卡片， 以青色「備註」標示，與抄自公告的說明分成兩塊）。
例：「角雕刮刮樂固定是出外觀的活動」—— 這種慣例官方公告從不寫，卻是讀者最想先知道的一句話。
三個文字欄位的分工：description 是官方寫的規則（多由解析器抄入）、 editorNote 是我們寫的補充（解析器永不填寫）、 note 是給維護者的待辦（前台永不顯示）。分開存才始終分得出來源。
⚠ 前台顯示閘門：activitiesOfHalf()（legacyActivities.ts）
這是前台讀取活動的唯一入口，也是「半成品不上首頁」的唯一保證點。它排除兩種活動， 兩個條件是同一件事的兩半、缺一不可：
① hidden === true —— 維護者明確標記「還沒好，先別上」。
② 缺 weeks —— 沒有長度就畫不出長條。這條不倚賴 hidden 有沒有被正確設定： 寫入端漏標的後果不該是前台畫出一條長度是猜的長條。
通過閘門後型別收窄為 VisibleActivity（保證有 weeks）， 下游 ganttGeometry / activityStatus 因此不必各自再防一次 undefined —— 「忘了過閘門」變成編譯錯誤，而不是執行期的 NaN。
另一半防線在寫入端：mergeIntoVersion 與後台活動編輯器都會在 weeks 為空時自動補上 hidden。
衍生狀態（不存欄位）：activityStatus(act) 從 startDate + weeks 導出 phase（upcoming／ongoing／ended）、 weekIndex（第 N 週，1-based）、daysLeft（含今天）、 isFinalWeek、progress（0–1）。 邊界以單元測試守住：最後一天仍是 ongoing，隔天才 ended。
ActivityTypeId
ActivityTypeId — 活動類型（開放字串 + 靜態登錄表）
PLAN-048 Phase 1 起改為開放字串。 硬 union 的問題是：新玩法出現時，待處理 buffer 會塞住 —— 要等工程師改 code + build + deploy 才能把該筆合併進版本。開放字串讓維護者當天就能上線（甘特以中性紫色虛線顯示、名稱走 typeLabel），之後在登錄表補一列給它配色即可，零資料遷移。
string & {} 讓 TS 不把 union 塌成 string，IDE 仍會自動完成已知值。

Gantt Rules
甘特圖週列計算規則

ActivityTimeline 元件計算邏輯

  • 週單位：以週四作為每週起始日（weekStart），一週 = 週四到下週三
  • 活動結束日：endDate = startDate + weeks × 7（exclusive）
  • 週格是否啟用：actStart ≤ weekStart < actEnd
  • 上半週列範圍：從 upper.cnDate（或 twDate）到 lower.cnDate（若活動延伸則擴展）
  • 下半週列範圍：從 lower.cnDate 延伸到最後一個活動的結束日（最少 3 週）
  • 跨半版本活動：上半活動延伸到下半的週格會在分界線兩側連續顯示色塊，不需特殊處理
  • Tracks（欄道）：upper + lower 所有 activities 合併為欄道列表；上/下半共用同一組欄道
台服 twDate 含 "約 " 前綴

台服預測日期格式為 "約 2026/06/25"，解析時需 strip 前綴後再拆解 YYYY/MM/DD。parseDate() 已處理此情況：str.replace(/^[^0-9]+/, '')。
