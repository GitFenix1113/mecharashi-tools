UPDATED v2.3 · variableStats
v2.0 更新（PLAN-003）
Schema 重構說明
PLAN-003 武器資料模型優化（2026-05-18 實施）

· 射程結構化：移除 range: string，改為三欄位：rangeType + minRange + maxRange
· 術語對齊：category → type（類型），type → kind（種類），typeCoefficient → kindCoefficient
· 稀有度強型別：rarity: string → rarity: WeaponRarity（SS / S+ / S）
· 機甲限制：新增 mechRestriction: MechRestriction 欄位
· SkillCondition：weaponCategory? → weaponType?，新增 weaponKind?
PLAN-007 武器 API 欄位映射修正（2026-05-20 實施）

· 基礎屬性修正：accuracy（WeaponHitPoint）、critValue（WeaponUnderstanding）、weight（WeaponWeight）原本因 API 欄位名稱查找錯誤而全部填 0，已修正
· 技能自動填入：skills[]（PassiveSkill[]）原本因欄位名查找錯誤而永遠為空，已修正；子欄位 buffIds（BufCarried）、icon（SkillIcon）、description（SpecificEffects）同步修正
· 裝備部位 / 機甲限制：equipSlot（RestrictionsPositionOfWeapon）、mechRestriction（LimitedModelOfWeapon）改由 API 直接取值，不再全部仰賴種類預設值
PLAN-040 固定武裝（2026-08-10 實施）

· 新增三個選填欄位：isFixedArmament?（無法更換的武器）、manual?（手建保護旗標）、naStats?（不適用的數值欄位清單）
· enum 擴充：WeaponType +「特殊」；WeaponKind +「粒子莢艙」（戰術）「固定武裝」（特殊），17 → 19 種
· 新增 6 筆手建武器（weapon_173 ~ weapon_178）：衝擊炮 / 嵐質儲能艙 / 多功能彈倉 / 耀星 / 隕星 / 千星，全部 manual: true，官方 API 與 WIKI 皆無此六筆
· RangeType 未動：千星的「扇形」是尚未定義的攻擊方式，移交傷害模擬範疇；其 rangeType 暫沿用 manhattan，此值已知不精確
· 元件側不同步：「特殊」不進 allowedWeaponTypes，程式端用 COMPONENT_WEAPON_TYPES（見 components.html）
v2.3 variableStats — 無固定值的數值欄位（2026-08-13 實施）

· 新增選填欄位：variableStats?（無固定值的數值欄位 key 清單，渲染層整格不顯示並附一行說明）
· 起因：維護者回報耀星／隕星／千星（彌造者 · 海莉絲虛粒子形態）的數值隨機甲當下裝備的武器變動——PLAN-040 建檔時填的 attack: 757 等只是某次觀測的搭配結果，不是武裝自身屬性
· 定案值：三把皆為 ['kindCoefficient','attack','accuracy','critValue','weight','ammoCount','hitCount']（＝除 minRange／maxRange 外的全部數值欄位；只有射程與射程型態是武裝本身固定的）
· naStats 未動、也不可合併：naStats =「沒有這個數值」顯示「—」；variableStats =「有值但不固定」整格收掉。對後者顯示「—」等於做出「這把武器沒有攻擊力」這個與遊戲相反的肯定陳述
· DB 觀測值保留不洗：只在渲染層攔下，原數字留作日後傷害模擬的樣本（補丁腳本 scripts/temp_scripts/patch-halisi-variable-stats.mjs 只加旗標、不改值）

類型 vs 種類 術語說明
武器分類有兩個層級，欄位命名與中文概念對齊。
type（類型）
大分類 — WeaponType enum
射擊 / 格鬥 / 突擊 / 戰術 / 特殊
kind（種類）
細分類 — WeaponKind enum
格鬥類 7 種 / 戰術類 5 種 / 突擊類 4 種 / 射擊類 2 種 / 特殊類 1 種
種類是模組條件篩選的關鍵維度
模組 SkillCondition 使用 weaponKind? 限定到種類層級（如「機槍」、「狙擊步槍」）， 讓計算器能正確判斷模組是否對當前武器生效。 使用 weaponType? 則限定到大分類（如「射擊」、「格鬥」）。

兩者都只服務固定武裝（無法更換的武器，全庫已窮舉 6 種）： 「固定武裝」對應衝擊炮／嵐質儲能艙／多功能彈倉（type 為特殊，雙肩）， 「粒子莢艙」對應千星（type 仍為戰術，背部）。
這些武器帶 isFixedArmament: true，不可被玩家配裝、不能裝元件， 圖鑑預設不顯示（須開啟篩選開關）。 元件的 allowedWeaponTypes 不含「特殊」，程式端請用 COMPONENT_WEAPON_TYPES。
EquipSlot
裝備部位說明（WeaponEquipSlot Enum）
武器裝備時佔用的機甲格位，計算器用於驗證裝備合法性。
Enum 值中文說明
singleHand單手佔用左臂或右臂其中一個；雙手可各裝一把
dualHand雙手同時佔據左臂與右臂（雙手武器）
shoulder肩膀佔用左臂或右臂的肩膀槽位
⚠ 原文「需機甲有肩膀欄位才可裝備」指的是已刪除的 Mech.leftShoulderSlot / rightShoulderSlot（PLAN-040 凍結、PLAN-052-A 移除，實測 0/90 台有填、前台零消費端）。現行槽位模型（PLAN-052-A）：容量由 mechSlotCapacity() 回答——肩槽只有中甲有 2 格，其餘機種 0 格（實測 25 把肩部武器 100% mechRestriction='medium'）；固定武裝掛 MechPart.fixedArmament，肩槽附屬於手臂（leftArm → 左肩槽）。
back背後佔用機甲背後槽位
⚠ 同上：原「需機甲有背後欄位」指已刪除的 Mech.backSlot。背槽全機種都有 1 格（mechSlotCapacity().back === 1）——它同時是背包的位置，給 0 會讓 35 個「僅輕型可裝」的背包永遠無處可裝。背部武器雖然 22 把全是 mechRestriction='medium'，但那是武器的限制、不是槽位的容量，兩者是不同的問題。

▎固定武裝（PLAN-040）
isFixedArmamentboolean?無法更換的武器。已窮舉 6 種：衝擊炮（帕斯卡）／嵐質儲能艙（破曉者-01）／多功能彈倉（霸王）／耀星・隕星・千星（彌造者 · 海莉絲虛粒子形態）。
供 badge 渲染與圖鑑／模擬器過濾；不編碼「來源」也不編碼「佔哪個槽」，箭頭永遠是「來源 → 武器」。槽位歸屬見 PLAN-047。
⚠ 命名刻意避開 fixedMod（固定改裝）；不可複用 isExclusive / exclusiveFor——那是「可選裝的機師專武」，語意相反，且會被渲染成金框專武並破壞 isExclusive ⇔ rarity === 'SS' 的不變式。
manualboolean?手建文件保護旗標。官方 API / WIKI 無這六筆、100% 手動維護，補丁腳本應略過。
對照 mechs.html / pilots 的同名欄位
naStatsstring[]?不適用的數值欄位 key 清單；渲染層對列入者一律顯示「—」，不顯示數字（DB 仍存 0）。
為什麼不直接填 0：ammoCount === 0 已被佔用為「無限彈藥 ∞」（172 筆中 129 筆靠此規則），填 0 會把「沒有彈藥」渲染成「無限彈藥」。旁證安全：全庫 attack === 0 與 weight === 0 皆 0 筆。
⚠ 只標「不適用」，不標「未知」——衝擊炮的 ammoCount: 1 與射程 3 是真值，不得列入。
定案值：衝擊炮 = ['attack','accuracy','critValue','weight','kindCoefficient']；嵐質儲能艙／多功能彈倉 = 全部數值欄位；耀星／隕星／千星 = 不需要（改用下方的 variableStats）。
variableStatsstring[]?無固定值的數值欄位 key 清單：有數值，但由當下掛載情境決定，不是這把武器自己的屬性。渲染層對列入者整格不顯示，並在區塊末尾附一行說明。
⚠ 與 naStats 是兩件事，不可合併：naStats「沒有這個數值」→ 顯示「—」；variableStats「有值但不固定」→ 收掉整格。併成一欄會讓「嵐質儲能艙沒有攻擊力」與「耀星的攻擊力不固定」變成同一句話。
⚠ DB 仍保留原觀測值（耀星 attack: 757 等），只在渲染層攔下——那是日後傷害模擬的樣本，洗成 0 就回不來了。
定案值：耀星／隕星／千星 = 除 minRange／maxRange 外的全部數值欄位（2026-08-13 維護者實測：三把是海莉絲虛粒子形態的形態武裝，數值繼承自機甲當下裝備的武器，連重量都不是自己的）。

▎武器技能 skills[]（PLAN-032 雙格式：WeaponSkillRef | WeaponSkill）
「定義 vs 掛載」判準（PLAN-032）：本陣列的元素有兩種形狀，以 'skillId' in entry 鑑別。
· WeaponSkillRef = { skillId, activation } —— 已引用化。 技能本體（名稱／正文／effects／buffIds）住在技能庫（pilotSkills 集合），改一處全站生效。
· WeaponSkill —— 尚未遷移的內嵌拷貝（下表）。 此型別刻意永久保留：官方 API 的 PassiveSkill 就是這個形狀，爬蟲抓到新武器仍會產出它， 由 scrape-weapons.js 的 normalize 步驟才轉成引用。不是待清死碼。

為什麼 activation 留在掛載側而非技能 doc：它是遊戲規則造成的真實每武器變異。 實測 44 個重複技能名群組中 38 個在此欄衝突—— 凝神待發 在 [赤狐·改 S+] 是 carry、在 [魔笛 SS] 是 use。 併進技能 doc 會強迫兩者二選一。
反之 enhancesTalentName / enhancedTalentDescription 已移入技能 doc（定義側）—— 它們與 descriptionRefs 是一起被消費的（同一份 refs 解析強化後天賦正文的 [xxx]）， 拆兩份文件會失同步；且專武與機師 1:1，天然無跨武器變異。

⚠ 前端一律以 resolveWeaponSkills(weapon.skills, skillMap) 解析， 且顯示 gate 必須接在解析後的陣列上——對 union 取 .length 兩個成員都合法（tsc 抓不到）， 技能庫未載入時會渲染出一塊空的技能區。用 hasWeaponSkills()。

Architecture
跨界實體判準（複合武器歸類）
當某實體的官方製作介面歸類與資料形狀／來源表不一致時（如「裁決者」在遊戲內於【特種背包製作】做出、與 SS 特種背包並列，但官方 weapon_data API 命中、有 attack/ammoCount 等背包表沒有的欄位），依此判準處理，避免每次新複合武器出現時整輪重吵。

官方介面歸類另以 upgrade.station 這類正交欄位表達；
並在對應圖鑑（背包圖鑑）以投影方式呈現（PLAN-031 B-2「特種背包製作」facet），不改變 refType、不搬集合、不新開集合。

否決「搬進 backpacks 集合」的一擊致命理由：SimulatorPage 的 handleSaveBuild 硬性要求 weaponId（silent return），搬完配裝直接存不了且無錯誤訊息；另與上游爬蟲永久對抗（weapon_data 會一直吐回來）。四方案評分：不搬集合 7.67 ＞ 搬進 backpacks 3.67。

Range
射程型態說明
武器射程有三種型態，對應不同的遊戲機制。
manhattan — 菱形射程
採 Manhattan 距離（|dx|+|dy|），可打斜格，但斜格計距更遠。
攻擊格：minRange ≤ |dx|+|dy| ≤ maxRange
大多數武器使用此型態（機槍、狙擊、霰彈、格鬥等）。
例："2-4" → rangeType:'manhattan', minRange:2, maxRange:4
例："1-3" → rangeType:'manhattan', minRange:1, maxRange:3
orthogonal — 十字直線
只能攻擊上下左右四個方向的直線格，不可打斜格。
攻擊格：(dx=0 XOR dy=0) AND minRange ≤ |dx|+|dy| ≤ maxRange
目前僅電磁炮使用。特定角色技能可解鎖斜格攻擊（射程 -1）。
例：電磁炮 → rangeType:'orthogonal', minRange:0, maxRange:5
ring — 環形 N 圈
以持有者為中心，向外擴展 N 圈的方形覆蓋區域。
N 圈 = (2N+1)×(2N+1) 方格（含自身格，無最小限制）。
採 Chebyshev 距離（水平、垂直、斜角均計 1 格）。
例："2+" → rangeType:'ring', minRange:0, maxRange:2
例："1+" → rangeType:'ring', minRange:0, maxRange:1

0 = 持有者位置；■ = 攻擊範圍格；2圈 = 5×5 = 25 格（含自身）
計算機開發備注：
· ring 判斷：Math.max(Math.abs(dx), Math.abs(dy)) <= maxRange
· manhattan 判斷：minRange <= Math.abs(dx) + Math.abs(dy) && Math.abs(dx) + Math.abs(dy) <= maxRange
· orthogonal 判斷：(dx === 0 || dy === 0) && dx !== dy && minRange <= Math.abs(dx) + Math.abs(dy) && Math.abs(dx) + Math.abs(dy) <= maxRange
