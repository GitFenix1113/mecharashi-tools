架構說明
前端部署於 GitHub Pages；Firebase Firestore 統一管理所有遊戲資料與用戶資料。管理者透過網站後台直接讀寫 Firestore，無需 CI/CD。
🔄 v2.0 架構重大調整：靜態 JSON → Firebase Firestore 舊架構：Google Sheets → GitHub Actions → Static JSON → 前端讀取。
新架構：管理後台 → Firestore 遊戲資料 → 前端即時讀取。
優點：資料即時更新、複雜關聯（模組↔機甲、技能↔BUFF）可直接透過 Document ID 引用、型別枚舉化消除不一致。

遊戲資料讀取

前端透過 Firebase SDK 直接查詢 Firestore Collections（pilots / mechs / weapons 等），使用 React Hooks 封裝資料讀取邏輯，支援快取策略。

👤

用戶資料讀取

Firebase Auth 取得 UID 後，讀取 users/{uid}/profile 與 users/{uid}/builds。未登入用戶的科研設定暫存於 localStorage。

🛠️

管理後台寫入

管理員登入後，透過 AdminPage 直接對 Firestore 進行 CRUD 操作。角色驗證透過 Firebase Auth custom claims 實作。

src/utils/ 共用工具
抽象化原則：只有「跨兩個以上頁面重複」的東西才抽出，並依性質分家：
・純資料 / 純函式（標籤表、排序規則、格式化）→ utils/
・帶 JSX 的呈現邏輯 → components/
這條界線同時避開 react-refresh/only-export-components——元件檔一旦匯出非元件就會觸發該 lint 規則。
※ 早期曾把 UI 元件留在各頁面「等需求穩定再抽」，實測代價是同一份實作在兩頁各長一份並各自漂移（PLAN-044 收斂了模組卡的兩份拷貝）。現行做法是第二個使用者出現時就抽。

◆ STAT_LABELS 的型別窮盡設計（PLAN-044）
它不是手寫陣列，而是由 Record<StatKey, StatMeta> 派生。ModuleLevel 日後新增數值欄位（例如新版本出現新的武器種類增傷）卻忘了補標籤時，npm run build 會直接編譯失敗並指名缺哪個 key。
先前沒有這道保險，dmg_heavy_machinegun 等 7 個欄位在資料庫有值卻從未在前台顯示過。
武器相關標籤直接引用 WeaponType / WeaponKind enum（label: `${WeaponKind.Rod}傷害`），與武器圖鑑用語保證一致、不會再漂移。
src/components/ 分類
元件依職能分資料夾，扁平層不再放檔案。分兩種歸類軸，混用是刻意的：
・UI 種類（badges/、icons/、cards/、common/）——同一種視覺元件跨多個領域重複出現，放一起才找得到、樣式才不會各自漂移。
・功能領域（module/、planner/、timeline/、refs/…）——彼此緊密耦合、只服務單一頁面或機制的元件家族。
※ 判斷法：問「這個元件會不會被第二個領域拿去用」。會 → 依 UI 種類；不會 → 依功能領域。

module/ModuleCard 模組卡骨架。variant="catalog"（圖鑑：大圖示、含槽位標籤與來源）／"detail"（機甲詳情頁：小圖示、緊湊）。等級狀態放在卡片內部，各卡獨立、預設滿級

GitHub Pages

前端靜態資源部署至 GitHub Pages。推送 main 分支自動觸發 GitHub Actions 建置並部署。

SPA 路由支援：由於 GitHub Pages 是靜態伺服器，直接訪問子路徑（如 /modules）會 404。解法：public/404.html 將路徑編碼至 query string 後跳轉回根目錄；index.html 在 React 載入前以 history.replaceState 還原正確路徑，使 React Router (BrowserRouter) 正常運作。

🔥

Firebase

Firestore、Auth 使用 Firebase Spark（免費方案）起步，流量成長後可升級至 Blaze 計費方案。

☁️

Cloudinary

用戶頭像圖片上傳與托管。前端直接以 Unsigned Upload Preset 上傳至 Cloudinary，取得 secure_url 後寫入 Firestore；不使用 Firebase Storage。
