台版公告解析規則活動如何被篩出來

官方公告是人手打的，格式會漂移。這份文件說明解析器如何從一則公告裡篩出活動、 哪些東西被刻意丟掉、以及每一次規則修補背後踩到的坑 —— 給未來擴充規則的人看。

Overview
這份文件在講什麼
程式位置：scripts/lib/parseAnnouncement.mjs（純 JS，無型別）
型別契約：src/types/announcementStaging.ts（本檔是契約的文件面）
單元測試：scripts/lib/parseAnnouncement.test.mjs —— 每一組回歸測試都對應一個真實踩過的錯
回歸語料：scripts/fixtures/tw-announcements-2026-08/（266 篇公告純文字快照）
目前版本：PARSER_VERSION 7

台版公告站（ma.tentree-games.com）的內容是營運人員手動編寫的， 沒有結構化 API。同一件事在不同月份可能有不同寫法，欄位偶爾漏字、日期分隔符偶爾換成點或反斜線。 因此這個解析器的核心問題不是「怎麼抽資料」，而是「怎麼在格式漂移時仍然知道自己漏抓了」。

⚠ 這條管線的失效模式一律是「安靜地少抓東西」，不是拋錯。
HTTP 200、程式不崩、待審清單少了兩筆 —— 沒有人會發現。 所以規則設計的每一處都在回答同一個問題：出錯時要怎麼被看見。 這也是為什麼有 unmatched（沒看懂的原文）與 warnings（產出量監控）兩層自我體檢。
Principles
五條設計原則

前四條寫在解析器檔頭、都有 266 篇語料的實測支撐；第五條是實作過程中兩次踩坑才學到的。

①

由時間錨點反向找名稱

不是由 【】 正向切塊。全語料有 3052 個【】區塊，79.7% 是樣板噪音 （【招募一次】【購置十次】…），正向切塊會產出四倍垃圾。 而 620 個時間錨點幾乎 1:1 對應真實活動 —— 樣板【】一律出現在時間行「之後」， 從時間往回找，噪音天然被跳過。

②

段落標題決定型別

「機師征招招募活動」「機甲獲取海運活動」「活動中心」「特殊活動」四個段落標題 在 2024–2026 全程穩定（實測 78/79/102/107 次），比句型可靠得多。 名稱關鍵字只在段落內做二選一 —— 計畫書當初點名的漂移句型 「本期機師征招『X』」在 2024/2025 出現 0 次。

③

解析得出來 ≠ 要收錄

儲值促銷擋在解析層而非顯示層（產出來再讓人逐筆忽略是白工）， 但仍計入產出量統計 —— 不然「少收 30%」會被誤讀成「解析率掉了 30%」， 自己的過濾規則會污染自己的體檢報告。

④

抽不到就留空，絕不填預設值

填了預設值就再也分不出「官方真的是這樣」與「我沒抽到」。 開放式檔期（「10:00 起」，實測 191 筆）的 weeks 因此是缺的， 由後台表單顯示建議值供人按一下套用 —— 建議值不會自己進資料。

⑤

「不是標題」與「不是邊界」是兩回事

isHeadingCandidate() 同時被「找活動名」與「切內文區塊」兩處使用。 把某種行排除在標題之外時，如果順手拆掉它的邊界身分，內文就會灌進 description。兩次修補都踩到這個坑， 修法一律是「照樣截斷，但把整段認領掉」。

Pipeline
一則公告如何變成活動

輸入是一則公告的純文字，輸出是 0..n 筆待審活動 ＋ 整篇的 unmatched / warnings。以下每一步都可能丟掉東西 —— 丟掉是設計的一部分，重點是丟得有理由、而且丟掉的東西看得見。

STEP 0
正規化
解 HTML 具名實體（decodeEntities）。歸檔階段只解了最基本六個， 這裡補完剩下的 —— 尤其 &ndash; 是卡池標題的破折號分隔符， 不解掉就抽不出「主題名 vs 實體名」。
STEP ①
標記段落標題（SECTIONS）
建立「行號 → 所屬段落」對照。登錄表分兩種：
· 會產活動：機師征招招募活動 / 機甲獲取海運活動 / 活動中心 / 特殊活動 / 限時活動
· 認得但不產活動（kind: null）：維護時間、維護計畫、修正與優化、新增內容、新增商品、注意事項、特別提醒、已知問題、領獎範例、回報流程、參考格式、本週推出內容…
丟掉：kind: null 段落的整段內容（v7 起）
STEP ②
找出所有時間行（錨點）
樣式支援三種：絕對區間、⟨日期⟩ 起（開放式）、裸日期（2024 年有 5 筆）。 日期與時刻之間可夾星期註記（2026/08/13(四) 04:50:00起）。
有幾個時間行，就有幾個活動候選。
丟掉：「維護計畫／維護時間」段落裡的時間行 —— 那是停機時間不是活動
STEP ③
從時間行往回找活動名
往回掃，不跨過上一個時間行、也不跨過段落標題。途中的欄位行 （➤活動內容：…）一律吃掉繼續往上。找到第一個「標題候選」即停。

實體名（UP 的機師／機甲）有三道退路，是三次句型漂移各補一道：
1. 標題行本身的 「」
2. 時間行之前的 ➤活動內容：S級機師「科林」招募概率提升
3. 時間行之後的 本期機師征招「X」開放【特選】S級戰術家「哈達威」！（2026/07 起的新句型）
STEP ④
判定型別（三層優先序）
活動名關鍵字 › 段落標題 › 公告標題關鍵字 › 認輸標未知
名稱關鍵字優先於段落，因為同一個「機師征招」段落裡既有卡池也有【角雕特遣】， 只看段落會把兩者一律歸成卡池。比對範圍含 【】 內容 —— 型別關鍵字常只出現在括號裡（【環島密令】「謀海魅影」賽季 的名字是「謀海魅影」，看名字永遠認不出戰令）。
認不出型別時不猜：標 unknownActivityType flag，型別留原始段落標題
STEP ⑤
檔期與 flags
絕對區間 → startDate + weeks（整週吸附：實測 424 筆區間 93.2% 恰為整週）。 開放式（只寫「起」）→ weeks 留空，標 openEnded。 起始日非週四 → 標 nonThursdayStart。
任何一個 flag ⇒ 該筆落在 needsReview，不會自動放行。
STEP ⑥
切內文區塊 → description / rewards
區塊從時間行的下一行開始，終點取「下一個時間行」與以下四種邊界的最早者：
· 段落標題
· 下一個標題候選
· 【X】補充說明（v7）—— 抽獎條文的起頭
· 機體故事的型號行 「LTX-AB01君權」（v7）
丟掉：編號條列、※／➤ 起頭行、含「概率／保障／請見遊戲」的行
STEP ⑦
排除層（解析得出來但不收錄）
目前只有 topUpEvent（儲值促銷）。它是產出量第 2 高的型別 （96 筆裡 29 筆，30%）—— 不擋掉的話每三筆待審就有一筆要按忽略， 審核工作檯的訊噪比會被拖垮。但仍計入產出量統計。
STEP ⑧
未認領原文（自我體檢之一）
掃過全篇，把「沒有被任何活動認領、而且看起來有訊號」的行收進 unmatched， 後台「規則待擴充」分頁會標紅。只收帶 【】「」 或日期的行 —— 全收會被抽獎規則說明淹沒，滿頁都紅等於沒有紅。單篇上限 30 行。
STEP ⑨
整篇告警（自我體檢之二）
lowYield（週報抽出 < 2 個活動）、 pilotSectionNoName / mechSectionNoName（有卡池段落卻抽不到實體名）、 yieldRegression（整體解析率比前次低 20% 以上）、 contentSelectorMiss（抓不到正文容器 ＝ 官網改版）。
Filters
篩選規則一覽：什麼會被丟掉

依「丟在哪一層」排列。要新增排除規則時，先確認該丟在哪一層 —— 丟太早會連帶影響邊界，丟太晚等於讓人工去按忽略。

規則丟掉什麼為什麼
SECTIONS
（kind: null）		 維護時間／注意事項／新增商品／特別提醒／領獎範例／回報流程等段落的整段內容 段落標題已經宣告「這裡不產活動」，內容當然也不必再看。v7 之前只認領標題行本身，內容全數落進未認領清單（1713 那 6 行商店上下架公告就是這樣來的）
EXCLUDED_TYPES topUpEvent：指定方式儲值、物資空投、多爾沙龍 純儲值促銷，對「這版有什麼玩法、檔期多長」零資訊量。多爾沙龍是台版對儲值滿額活動的固定專名，標題不出現「儲值」二字，v4 才補上
BOILERPLATE_NAMES 【特選招募】【購置十次】【版本前瞻】 等樣板小標 抽獎規則說明的小標，不是活動名。這是段落標題缺席時的第二道防線
RE_FIELD_LINE ➤活動內容：…／活動時間：… 這類欄位行 ⚠ ➤ 前綴不能當唯一判準：2026/04 有整批公告漏掉 ➤，結果「活動內容：…」被誤當標題、產出「活動內容 招募概率提升」這種名字，而且不觸發任何 flag
isHeadingCandidate 超過 40 字、含 ，。；、不含 【】「」 的行 標題是短句、不帶句讀。沒有這道閘時，內文因為含「」而被當成活動名，真正的 【物資空投活動】 反而落進未認領
RE_MECH_MODEL_LINE 機體故事的型號行 「LTX-AB01君權」（v7） 三條標題判準全中，於是被誤當「下一個活動的標題」。仍然是區塊邊界，只是不再是標題，且連故事正文一起認領
RE_SUPPLEMENT_LINE 【X】補充說明 以下整段抽獎條文（v7） blockEnd 停在這一行之後，其下十餘行沒有任何活動認領。修法必須是「照樣截斷，但整段認領」，不能只是讓它不算標題
NOISE_LINE 「回新聞列表」「《鋼嵐後勤小組》」「詳情可見官網活動公告」等整行樣板 頁尾與制式句，不進未認領清單
unmatched 篩選 不含 【】「」 或日期的行、以數字或 ※➤ 起頭的行 未認領清單要保持訊噪比。全收會被抽獎規則淹沒 —— 滿頁都紅等於沒有紅

How-to
要擴充規則時的標準流程
三條鐵律，違反不會報錯但會靜默出錯：
① 改完必跑 266 篇 A/B　② 必 bump PARSER_VERSION　③ 寫一條回歸測試
  1. 先確認根因，不要照句型加規則
    未認領清單裡看起來獨立的好幾組，常常是同一個根因的下游。 v7 的第 4/5/6/8 組（跨域海運抽獎條文）全部出自第 3 組 （【X】補充說明 截斷區塊後那些行落在區塊外）—— 它們根本不是「被誤當標題」， 逐條加樣式會加出四條沒必要的規則。
    判斷方法：把那幾行丟進 isHeadingCandidate() 看是不是標題候選。
  2. 改規則前先存一份 A/B 基準
    逐篇餵 scripts/fixtures/tw-announcements-2026-08/ 進 parseAnnouncement()，把每篇的 activities / warnings / unmatched 數輸出成 JSON。 改完再跑一次，比對兩份。
    要看的四個數字：完全相同的篇數、未認領行增減、 活動數變動（必須是 0，除非你就是要改它）、description 變動。
  3. 判讀差異：是進步還是回歸
    語料快照當時是 PARSER_VERSION 3，所以「跟當年不同」很可能是進步。 判準是方向：未認領減少、活動數不變 ＝ 好； 出現 0 → N 的反向惡化、或 description 憑空多出上百字 ＝ 踩到邊界了。
  4. bump PARSER_VERSION，寫回歸測試
    測試要寫成「錯的時候會怎樣」而不只是「對的時候是什麼」—— 既有測試每一組都對應一個實際踩過的錯，註解裡寫著當初的症狀。
  5. 跑 --reparse 讓既有草稿套用新規則
    node scripts/scrape-tw-announcements.mjs --reparse（先加 --dry-run 預演）。
    它不會覆寫 merged / rejected 的收據（刻意的）， 但會把「規則改變後不再產生」的待審標成 superseded 退出清單。
常用指令
node scripts/scrape-tw-announcements.mjs — 增量抓取（只掃前 3 頁）
… --backfill=2026-01 — 回填該月之後的公告
… --reparse — 不連外網，用既有 rawText 重新解析
… --dry-run — 只解析並印報告，不寫 Firestore
… --from-archive — 讀本地歸檔而非連線（離線驗證）
… --fail-on-warn — 結構性異常時 exit 1（排程用）
Open
已知未解與未來方向
◆

官方用 <h3> 標好了活動標題

實測 266 篇歸檔 HTML（241 篇有 <h3>）： 週報裡解析器抓到的活動名有 99%（363/368）落在 h3 內， 而未認領行中有 16%（55 行）其實是 h3。

也就是說我們一直在用文法猜官方已經標好的東西。 但要用它得改抽取層（rawText 丟了標籤）、既有草稿要 --backfill 重抓、 語料要從 raw/*.html 重產。另外 2024 年的公告把「補充說明」也放進 h3， 所以 h3 仍需搭配「後面有沒有時間行」判斷。

◆

日期分隔符用點或反斜線

2026.07.30（實測 3 行）與 2026\07\09 都出現過。 目前樣式只認 / 與 -。

實際影響只有一筆真活動（2024 的【火線整備】）， 但這是靜默失效：官方哪天全面改用點分隔，整批活動會安靜地不產生， 而 lowYield 要整篇都抓不到才會響。一個字元的修改，值得排進去。

獎勵行落在區塊外
