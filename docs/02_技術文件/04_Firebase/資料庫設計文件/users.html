01 — Security
存取控制
🔐 用戶資料安全規則 users/{uid} 及其所有子 Collection 僅本人（isOwner(uid)）可讀寫，其他用戶與管理員均無法存取。 詳細 Firestore Security Rules 請見 安全規則文件。

📧 Email 驗證流程 使用 Email 註冊的帳號，系統會透過 Firebase Auth 寄送驗證信（sendEmailVerification）。 驗證信寄出後帳號自動登出，使用者點擊信中連結後方可登入（user.emailVerified === true）。 未驗證帳號嘗試登入時，系統會重新寄出驗證信並拒絕登入。Google 登入不受此限制。
✅ 2026-08-23：profile 讀取收斂 ＋ 首頁團隊名單改由 Worker 供應（PLAN-051） 在此之前，安全規則有一條沒有 auth gate 的分支「role 是 ADMIN/OWNER 就人人可讀」， 為的是讓首頁的維護團隊區塊在未登入時顯示。但 Firestore 的授權單位是文件、 沒有欄位級 read mask，讀得到文件就是整份 UserProfile——email 也在裡面。
現在 profile 的讀取是 isOwner(userId) || isAdmin()（collectionGroup 那條是 isAdmin()），匿名讀不到任何 profile。首頁名單改打 GET /api/site-team：Worker 以 service account 代讀 collectionGroup('profile') 後只回下列白名單欄位—— uid · displayName · role · photoURL · avatarType · avatarUrl · avatarPilotId · gameNickname · gameServer · guild。
刻意用白名單而不是「排除 email」的黑名單：黑名單在本表新增欄位時會自動把新欄位 外洩出去。要讓新欄位公開，得同時改 workers/src/index.ts 的 SITE_TEAM_FIELDS 與 src/types/user.ts 的 SiteTeamMember。
該端點在 Cloudflare 邊緣快取 1 小時（名單幾乎不變）——維護者改暱稱或頭像後， 首頁最多一小時才會反映。

03 — builds
users/{uid}/builds/{pilotId} — 雲端書架
✅ 2026-08-29 換過模型（PLAN-052-E）。 舊版一份文件是一整套配裝（buildName / weaponId / backpackId …， doc id 是 addDoc 的亂數），那個模型只裝得下「一把武器」，沒有槽位、形態、部件與模組的概念。 改版前直讀正式 Firestore 復驗過 builds 實測 0 筆， 所以是刪除而不是遷移——舊欄位一個都沒有保留，userApi 的 getUserBuilds / saveBuild / deleteBuild 三支也已移除。 現行的讀寫入口是 src/lib/buildsApi.ts。
🗃️ users/{uid}/builds/{pilotId} — 一位機師一份文件 USER DATA
欄位型別說明
doc idstring就是 pilotId（如 pilot_049_海莉絲）。規則以 ^pilot_[0-9]{3}_.* 把關
slotsmap鍵只准 '0'～'4'（每位機師 5 格）；值是一串 base64url 分享代碼，每格 ≤ 4096 字元。沒存的格子沒有那個 key，不是空字串
updatedAtstringISO 字串。整份文件一個，不是每格一個
為什麼落盤的是「一串代碼」而不是結構化欄位（總綱決策二）：
① 儲存＝分享，沒有第二套序列化 —— 存進雲端的那一串，就是貼給別人的那一串。
② 收斂成單一字串後，code.size() <= 4096 是規則層唯一精確且繞不過的上限： Firestore 規則沒有位元組長度運算子、不能對動態 key 迴圈、也沒有 count()， 巢狀結構在規則層根本設不了上限。
③ map key 白名單讓「每機師 5 套」變成結構性事實，而不是一個會漂移、 且 client 可以自己寫成 99 的計數欄位。
⚠ 因此這裡不存機師名快照、機甲名、或解好的草稿：卡片上要顯示的一切都由代碼當場解出來。 第二個真相源遲早會與第一個對不上，而對不上的那天不會有任何錯誤訊息。
安全規則（firestore.rules）
gate條件擋住什麼
身分isOwner(userId)別人的書架讀不到也寫不了（管理員也一樣）
形狀keys().hasOnly(['slots','updatedAt']) ＋ updatedAt is string夾帶額外欄位
格數slots.keys().hasOnly(['0'..'4'])第 6 格（配額變成結構性事實）
大小每格 size() > 0 && size() <= 4096超長代碼、空字串格位
doc idbuildId.matches('^pilot_[0-9]{3}_.*')任意命名的文件（縮小面，見下）
⚠ 擋不住的第五件：文件份數。 規則語言沒有 count()，也驗不了「{pilotId} 真的是一位存在的機師」—— 一個帳號可以開任意多份 builds 文件。PLAN-052-E A-3 已裁決接受這個殘餘風險： 每份有界（5 × 4096 ＋ overhead ≈ 20 KB），要塞出有意義的量需要極大量寫入， 而寫入本身受專案配額與計費保護。另一個選項是 Cloud Function 計數器， 但那會把「存一套配裝」從一次 client 寫入變成一條需要冷啟動、需要監控、會失敗的後端路徑。
⚠ 另注意 size() 回的是字元數不是位元組數。base64url 全為 ASCII， 所以「4096 字元 == 4096 bytes」剛好成立 —— 這一格只准放 base64url， 哪天有人往裡面塞中文，上限就悄悄變成 16 KB。
