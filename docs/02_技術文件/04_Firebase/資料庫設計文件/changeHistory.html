changeHistory — 資料變更歷史 MECHARASHI — FIRESTORE SCHEMA · PLAN-030

後台資料異動稽核 log · append-only（連管理員都改不了）· 雙軸分類 · 原生 TTL 兩年

PLAN-030 — 2026-07-19
01 — 用途
changeHistory Collection
📌 用途說明
後台對 BUFF / 技能 / 詞條的每一次新增、修改、刪除、還原都寫一筆記錄，作為維運追溯的黑盒子。
起因：現行寫入是 setDoc 不帶 { merge: true }，等於整份覆寫，舊值在寫入當下就消失； 誰在什麼時候改了什麼，系統裡沒有留下任何痕跡。
· 刪除另存完整快照（文件本體 + 每一處被清除的引用），誤刪可據此還原。
· 依「集合類型 × 操作類型」雙軸分類，後台歷史頁可各自或組合篩選。
· 保留兩年，由 Firestore 原生 TTL 政策自動清除（不需 Cloud Function）。
⚠ 與其他集合的三個關鍵差異
① 不進 CollectionKey / GameDataContext：前台永遠不讀它。版本 gate 三層快取是為「整包載入、長期不變的靜態遊戲資料」設計， 而 log 是持續成長、只查最近幾頁的資料，塞進那套快取只會撐爆 localStorage。它走獨立的伺服器端分頁查詢。
② 安全規則不是 allow write: if isAdmin()：全站唯一的例外，見下方 04。
③ 文件 ID 是自動生成（addDoc）：log 沒有自然 slug。全專案僅此處與 users/{uid}/builds 使用 addDoc， 其餘遊戲資料一律是 setDoc + 明確 slug ID。
🗃️ changeHistory — 變更記錄（ChangeHistoryEntry）
欄位型別說明
idstringFirestore 自動 ID（addDoc 產生）
targetChangeTargetKind分類軸一：'buff' | 'pilotSkill' | 'glossaryTerm' | 'backpack' | 'backpackSkill' | 'form'（可擴充）
actionChangeAction分類軸二：'create' | 'update' | 'delete' | 'restore'
targetIdstring被異動的文件 ID，如 buff_過熱
targetNamestring當下顯示名稱。刻意去正規化：查 log 免 join，且目標被刪後仍看得懂是什麼
actorUidstring操作者 uid（由 auth.currentUser 取得，不從 UI 傳入）
actorNamestring操作者 displayName 快照（改名後仍看得出是誰）
atTimestampserverTimestamp()。排序與範圍查詢鍵
expireAtTimestampat + 2 年。由原生 TTL 政策讀取後自動清除文件
changedFieldsstring[]?僅 update：淺層比對出的變動欄位名（不存新舊值）
snapshotDeleteSnapshot?僅 delete：文件本體 + 反向修補單，見下方 02
restoredFromstring?僅 restore：來源 delete log 的文件 ID，形成可追溯鏈
💡 為何 update 不存 before/after 快照
BUFF / 技能含 levels[] 等巢狀結構，每筆修改存完整前後快照會讓單筆 log 迅速膨脹到數 KB； 而修改的追溯需求通常「知道誰動了哪些欄位」就足以定位。刪除則是不可逆操作，必須留完整後路。
若日後發現不夠用，加一個選填 before 欄位即可，不影響已寫入的舊 log。
02 — 刪除快照
DeleteSnapshot 與反向修補單
📌 為何不只存被刪的文件
BUFF / 技能 / 詞條是被大量引用的底層實體，刪除時會級聯清除全站 9 個集合中對它的引用。 只存被刪文件的話，還原得回文件，卻還原不回引用關係。
因此快照是三段式：文件本體 + 每一處引用移除的反向修補單。
🗃️ DeleteSnapshot
欄位型別說明
docRecord<string, unknown>被刪文件的完整內容（不含 id，id 記在 targetId）
patchesReversePatch[]級聯清除過程中每一處移除的反向修補單
🗃️ ReversePatch
欄位型別說明
collstring引用來源集合，如 pilots
docIdstring引用來源文件 ID，如 pilot_038_艾達
pathstring欄位路徑（. 分隔，陣列以索引表示），如 talents.2.descriptionRefs.凝勢
opstringarrayRemove / mapKeyDelete / fieldClear / textFreeze
valueunknown被移除的原值；textFreeze 時存「凍結前」的完整原始字串
🔑 關鍵設計：前三種 op 天然冪等
arrayRemove / mapKeyDelete / fieldClear 的還原都是「把元素加回集合」，重複套用結果相同。 因此還原時不需要比對整份文件是否未被改動（那等於做時光機）， 只需檢查「該欄位現在還缺不缺這個值」——缺就補、已有就跳過。
textFreeze 是唯一非冪等的（覆寫字串），還原時需比對現值是否仍等於凍結後的文字，不符則跳過並列入報告。
❄️ textFreeze 是什麼
引用有兩種存法：[虛粒子形態] 這類錨點在文案、綁定在 descriptionRefs 側錄表（可外科手術式移除）， 以及 <buff_凝勢.lv3.maxStack> 這類數值 token 直接內嵌在文案字串（無法機械移除）。
後者的處理是「凍結而非移除」：刪除前用 resolveNumRefs() 把 token 換算成實際數值寫回文字 （"可疊加<buff_凝勢.lv3.maxStack>層" → "可疊加5層"），token 就地變成常數、不再依賴已刪的 BUFF。 凍結前的原始文字存進 value，還原時才能復原成 token 形式。
03 — 查詢與索引
雙軸分類查詢
📌 為何 target 與 action 必須是兩個獨立欄位
Firestore 的 where 只能對獨立欄位做等值比對。若圖方便寫成 'buff:create' 這種複合字串， 就永遠無法查詢「所有集合的刪除記錄」。兩個欄位分開存，可各自篩選、也可組合。
🔍 需要的複合索引（firestore.indexes.json）
索引對應查詢
(target ASC, at DESC)只看某個集合類型的記錄
(action ASC, at DESC)只看某種操作（如「所有刪除」）
(target ASC, action ASC, at DESC)雙軸同時篩選
⚠ 兩個實作陷阱
① 模擬器不強制複合索引：查詢在本機照跑，缺索引只有 prod 會炸。索引正確性必須在正式環境驗證。
② 缺 at 欄位的文件會被 orderBy('at') 完全排除（Firestore 行為）。 正常路徑一定有 at，但這代表萬一 serverTimestamp() 寫入失敗，該筆 log 會在歷史頁「無聲消失」而非顯示異常。
🛠️ API
src/lib/api/changeHistory.ts：
· logChange(input) — fire-and-forget，失敗只警告不拋錯（新增／修改路徑用）
· logChangeOrThrow(input) — 失敗拋錯（刪除路徑專用：刪除的 log 承載還原快照，漏記等於永久失去救回能力， 因此刪除必須「先寫 log 成功、再執行刪除」）
· getChangeHistoryPage({ target?, action?, cursor?, pageSize }) — 雙軸篩選分頁查詢
· saveWithHistory(target, item) — 集合無關的「寫入 + 稽核」helper，三個 update* 都走它
⚠ log 寫入路徑一律不得經過 stripUndefined
該函式會遞迴走物件，把 serverTimestamp() 這種哨兵值拆成普通物件而失效（at 會變成 null）。 改為在組裝時就不放進 undefined 欄位。
04 — 安全規則與保留期限
append-only 與 TTL
match /changeHistory/{docId} { allow read: if isAdmin(); allow create: if isAdmin() && request.resource.data.actorUid == request.auth.uid; allow update, delete: if false; }
🔏 create 為何要綁定 actorUid
只驗身分不驗內容的話，管理員可用 client SDK 直接寫入 actorUid 冒名的偽造記錄嫁禍他人， 且因下方 append-only，連本人也刪不掉、永久化（PLAN-030 Phase C 破壞性測試發現③）。
append-only 防的是「竄改既有記錄」，這條防的是「偽造新記錄」，同屬稽核完整性。 與程式相容：buildEntry 走管理員路徑時 actorUid 恆為 auth.currentUser.uid。
🔒 全站唯一不使用 allow write: if isAdmin() 的集合
write 涵蓋 create / update / delete。若沿用那套，管理員就能竄改或抹除自己的操作記錄，稽核價值歸零。 因此拆開寫：可新增、可讀取，但寫下去就定型。
讀取也限管理員（不像遊戲資料公開）：這是內部維運記錄，且刪除快照內含完整文件內容。
副作用：日後若要人工清理舊 log，必須從 Firebase Console 或 Admin SDK 執行（繞過 rules），前端做不到。這正是要的性質。
⏳ TTL 政策（取代 Cloud Function）
在 changeHistory 集合群組上設一條 TTL 政策指向 expireAt 欄位，保留兩年。
為何不寫 Cloud Function：原生 TTL 只計 delete 費用、不計 read； 而排程 Function 必須先 query 才知道刪誰（每筆計 read），還要加上 Function 調用與 Cloud Scheduler 成本，並且要寫程式碼維護。 原生 TTL 在此場景嚴格更優，且是純設定、零程式碼。
⚠ TTL 的四個已知行為
① TTL 不受安全規則約束——它是後端程序，與上方的 delete: if false 並不衝突。 這正是理想組合：前端永遠刪不掉，但系統會自己過期清理。
② expireAt 需設單欄位索引豁免——官方明確警告索引 timestamp 欄位會造成寫入 hotspot， 而此欄位從不參與查詢（只有 TTL 程序讀它），保留自動索引純屬有害。
③ 刪除延遲約 24 小時，過期文件在實際清除前仍會出現在查詢結果。
④ TTL 一併帶走還原能力——兩年後 log 被清除，刪除快照也隨之消失。
