01 — 用途
mechLore Collection
📌 用途說明
官方遊戲內機甲圖鑑有介紹與依解析等級解鎖的逸聞（PART 1..N）（站長 10-16 確認，Q1），兩者都住本集合：
· 扉頁＝介紹 intro（原 mechs.lore，首行型號切到 modelNo）＋ 譯本來源 frontSource ＋ 英文名 nameEn。
· 兵器型錄＝型號 modelNo、廠商 maker、系列 series、非數值諸元 specs、系譜 relations。
· 逸聞＝章節 chapters，與機師故事館同一套 LoreChapter。
· 塗裝顯示設定＝ skins（名稱、隱藏、順序），站長：塗裝名稱要能編輯。
前台於故事館 /lore/mechs/:id（扉頁＋卷宗）與 /lore/mechs/:id/:part（章節）渲染；圖鑑詳情頁不讀本集合（042-B H-4 起圖鑑只留一顆入口）。
✅ 欄位放哪：套 042-E 判準「與數值、機制有沒有關係」（決策 B-7）
armorType、quality、debutVersion、gameId 與數值有關或是識別鍵，留在 mechs，故事館唯讀引用。 官配機師不存：沿用 pairedPilotOf() 從 pilots.pairedMechId 反查。 廠商歸故事館——遊戲目前沒有任何廠商相關的加成（站長 10-16 確認，取代舊決策 B-4「廠商留 mechs」）。
依賴是單向的：故事館讀 mechs 的身分欄位，圖鑑不讀本集合。
🗃️ mechLore — 機甲故事館文件（MechLoreDoc）
🧱 型別＝ LoreDocBase ＋ 機甲擴充（決策 B-3）
下表前半是與 pilotLore 共用的底座欄位（意義相同，只列機甲側的差異）；後半是機甲專屬欄位。 「這份逸聞屬於機師還是機甲」由住在哪個集合表達，型別上沒有 kind 欄位（總綱決策三）。
欄位型別說明
共同底座（LoreDocBase）
idstring文件 ID ＝ 機甲的文件 ID（mech_001_都卜勒）。故事與機甲一對一，不另造 slug
namestring?機甲名快照（去正規化），供 saveWithHistory 的 targetName 與後台列表使用
introstring?介紹（原 mechs.lore，Q2）。純文字、換行即分段。首行型號已切到 modelNo。
有台版公告譯文的 49 台改用台版（用「機甲」），其餘 43 台照陸版原文（簡轉繁、用「機兵」），不自行改字（決策 B-9）。 mechs.lore 在 B-3 只「複製」過來，H-7 觀察一週後才刪。
frontSourcestring?介紹的譯本來源（台版公告譯文／陸版原文），前台右對齊小字
nameEnstring?英文名：卷宗標題副標、名冊搜尋。初值取 v3 mapping 的 mechEnKeys（62／92），排除聯動與雙機池鍵（GlaDre／MalAgl／Nvidia／ROG），「有全名就用全名」
skinsLoreSkinSetting[]?塗裝顯示設定：key 為塗裝圖檔鍵（Img_Skin_wap*，34 台 38 張），名稱、隱藏、順序同機師外觀。圖檔上站見 042-B F-1
chaptersLoreChapter[]逸聞章節（PART 1..N），結構與 pilotLore 完全相同（必填穩定鍵 key、bodyRefs、draft…）。型別上必填，讀取端一律 ?.chapters 防禦
機甲專屬
modelNostring?型號，如 DD-117、OS-07X：卷宗標題與舞台上的型號鋼印（取代機師的英文簽名，決策 B-5）。初值由草稿腳本從介紹首行切出（92 篇中 90 篇首行即型號）＋人工複核
makerstring?廠商：mechMakers 的文件 ID（＝官方舞台背景鍵，如 Doll）。空或對不到文件＝前台顯示「廠商未載」，不留白。
型號前綴可對到 12 家，約 78 台可自動建議、約 15 台（REV／NED／聯動等）人工判；前綴只做建議、不自動指派。
seriesstring?系列，如「破曉者」「KX 系列」
specsLoreDossierField[]?非數值諸元（量產狀態、搭載核心…），陣列順序＝顯示順序。形狀與機師人物檔案的 extra 相同（label／value），存檔前一樣擋同名標籤
relationsMechRelation[]?系譜，陣列順序＝顯示順序，結構見下方子表
gachaTitlestring?卡池名稱，如「可能性的彼端」（莫比烏斯X）：卷宗最後招募插畫卡的標題（英文固定 KEY ART）與鑑賞時的圖名；空＝顯示「卡池」。 台版公告「【特選】<卡池名> – S級…機甲「<機甲>」」那一段，照錄不改字。
初值由一次性腳本 scripts/temp_scripts/fill-mech-gacha-titles.mjs（不進版控）從公告封存（2024-03～2026-08）＋公告草稿帶入：有公告可查的 54 台，只填空欄位； 之後的新卡池由後台扉頁從版本活動（specificMechBanner）帶出建議，一鍵採用。
🧬 MechRelation — 系譜一條（relations[]）
欄位型別說明
mechIdstringmechs 文件 ID
kindMechRelationKind?一律從本文件的角度讀「mechId 是這台的 ___」： base 原型（這台衍生自它）／variant 改型／rival 競品／series 同系列。空＝僅提及（草稿抓到、還沒人判種類）

一律人工連（決策 B-10，總綱「交叉連結自動生成不做」）：介紹文裡 36 處互提只在一次性草稿腳本當候選，名稱 ≤2 字或常用詞（原點、尖兵、XR）標警告； 渲染路徑不做任何文字比對。單向存：A 寫了「B 是原型」不會自動在 B 寫「A 是改型」。
02 — 引用關係
箭頭方向
正文引用：  mechLore ─(chapters[].bodyRefs)──→ buff / term / skill / form …
旁白說話者：mechLore ─(chapters[].commentary[].speakerId)──→ pilot
系譜：      mechLore ─(relations[].mechId)──→ mech
廠商：      mechLore ─(maker)──→ mechMakers
文件歸屬：  mechLore.id ═══════════════════→ mech（同一個 ID）

            ↑ 沒有任何東西指回 mechLore
本集合只有 outbound，沒有 inbound。故事館全程不新增 RefType（REF_TYPE_OF['mechLore'] = null），理由同 pilotLore。
⚠ 還沒登記 entityRefs SPECS（042-B H-6）
章節正文開始出現 [xxx] 引用時才登記 MECH_LORE。一登記就連動級聯刪除與「影響 N 處引用」的全集合掃描： rules 晚一步部署的話，全站既有的後台刪除會 permission-denied（PLAN-042-A 踩過）。
在那之前 entityRefs.ts 的 SPEC_COLL_OF['mechLore'] 是 null（042-B 起這張表允許 null＝「有稽核記錄、但不被掃」）， 所以 saveWithHistory('mechLore', …) 照樣能寫稽核記錄。登記時要回來把 null 改成 'mechLore'。
系譜的 mechId 與廠商的 maker 指向 mechs／mechMakers，但不會有級聯刪除替本集合清掉懸空的指向——前台（042-B D-3）查不到對象時要略過那一條，廠商則退回「廠商未載」。
03 — 維護
資料維護
🌱 初始資料（042-B Phase B）
一次性草稿腳本 scripts/temp_scripts/draft-mech-lore.mjs（不進版控）從 92 篇介紹整理出 modelNo、maker 建議、relations 候選、nameEn、台版譯文對照， 產出草稿 JSON → 站長複核 → --apply 寫入並 bump。編輯台（042-B G-1）完成前，資料只由這支腳本寫入。
🛠️ 寫入路徑
updateMechLore() → saveWithHistory('mechLore', …)：整份覆寫，自動寫入 changeHistory（篩選器標籤「機甲逸聞」）並 bumpDataVersion('mechLore')。 src/lib/api/mechLore.ts 刻意沒有 deleteMechLore，理由同 pilotLore。
💾 不進 localStorage 快取層
列於 src/lib/collectionKeys.ts 的 NO_LOCAL_CACHE_KEYS，理由同 pilotLore：92 台介紹約 20 KB 起跳、之後逐台加 PART 章節， 成長曲線陡而命中率低（純欣賞、低流量）。仍走記憶體快取與版本 gate。
🔒 安全規則與讀取路徑
match /mechLore/{docId}：read / write 皆 isAdmin()。 前台不直讀，走 Cloudflare Worker 代理（/api/data/mechLore）。
⚠ 部署順序
firestore.rules → Worker（ARRAY_COLLECTIONS、統計的 ENTITY_TYPES 加 loreMechs）→ B-3 寫入＋bump → 網站。 rules 與 Worker 都不在 npm run build / git push 的流程內；漏 Worker 的症狀是正式站 /api/data/mechLore 404（本機全綠）。 集合清單的同步由 src/lib/collectionKeys.test.ts 斷言（Worker、KNOWN_KEYS、rules、GameDataContext）。
