announcementDrafts / pendingActivities MECHARASHI — FIRESTORE SCHEMA · PLAN-048 Phase 2

台版官方公告的抓取與審核暫存 · 審核最小單位是「一個活動」· 後台專用（前台完全不讀）· 原生 TTL 六個月

PLAN-048 Phase 2 — 2026-08-16
01 — 用途
兩個 staging 集合
📌 用途說明
scripts/scrape-tw-announcements.mjs 抓台版官方公告（ma.tentree-games.com）、 以 scripts/lib/parseAnnouncement.mjs 解析出活動檔期，先落在這兩個集合， 經 /admin/announcements 人工審核後才合併進 patchVersions 的 upper/lower.twActivities。
· announcementDrafts：一則公告的原文草稿（含 rawText 與解析統計）。
· pendingActivities：解析出的待審活動，一則公告 n 筆。
型別定義在 src/types/announcementStaging.ts（比照 changeHistory.ts， 刻意不進 src/types/index.ts barrel）。
⚠ 三個關鍵設計決定
① 審核最小單位是「一個活動」不是「一則公告」：一則公告十個活動，看得懂九個就先放行九個， 剩一個留在 buffer。新玩法不該卡住整批 —— 這正是待處理 buffer 要解決的事。
② 必須是獨立頂層集合，絕不能做成 PatchVersion.inbox 欄位： AdminVersionEditorPage.tsx 存檔是整份 setDoc、沒有 merge: true。 若 buffer 是 PatchVersion 的欄位，腳本追加 → 管理員存檔 → 追加內容無聲消失。 同型事故已有前例（scrape-pilots-v3.js:117）。
③ 不進 CollectionKey / GameDataContext / Worker ARRAY_COLLECTIONS： 前台永遠不讀它們。版本 gate 三層快取是為「整包載入、長期不變的靜態遊戲資料」設計， staging 是持續成長、只查最近幾頁的資料（同 changeHistory 的理由）。
🗃️ announcementDrafts — 公告原文草稿（AnnouncementDraft）
欄位型別說明
idstring文件 ID＝${source}_${officialId}，如 tw_1799。由公告 URL 推導 → 重爬必然命中同一份＝冪等免費
source'tw'資料來源。陸版公告頻道已廢棄故不解析，此 union 目前只有一個值
channelAnnouncementChannel'maAffiche' | 'maNews' | 'maGuide' | 'maOther'
officialIdstring官方公告編號（清單 JSON 的 id）
titlestring公告標題
publishedAtstring官方發佈日 YYYY/MM/DD（清單的 time 是 'YYYY-MM.DD'，已正規化）
sourceUrlstring官方公告網址，原樣抄進 TimedActivity.sourceUrl
rawTextstring正規化後的公告純文字。實測 266 篇最大 15.9 KB（p50 3.0 KB），離 1 MB 硬限很遠 → 不做 Storage 分流
rawTextTruncatedboolean?超過 MAX_RAW_TEXT_BYTES（200 KB）被截斷。是保險不是常態路徑
contentHashstringsha256(rawText)。冪等判斷的唯一依據——不比對 fetchedAt、不比對 ETag（官網 ETag 實測不穩），只認內容
statusDraftStatus'raw' | 'parsed' | 'parseFailed' | 'triaged' | 'superseded'
parserVersionnumber產生此結果的解析器版本。改規則後靠它挑出「該重跑的舊公告」
activityCountnumber本篇解析出的待審活動數（0 也合法，如純維護公告）
unmatchedstring[]沒被任何規則認領的原文片段。後台標紅 → 「這段我沒看懂」自動浮現
warningsParseWarning[]整篇層級告警，見下方 03
fetchedAt / parsedAtTimestamp抓取／最後解析時間
expireAtTimestampfetchedAt + 6 個月。由原生 TTL 政策清除
etag / lastModifiedstring?條件式請求用。不存在也不影響冪等（contentHash 才是權威）
🗃️ pendingActivities — 待審活動（PendingActivity）
欄位型別說明
idstring文件 ID＝${draftId}_${seq}，如 tw_1799_0。決定性 ID → 重新解析同一篇直接覆寫同一批，不會每跑一次多一份垃圾
draftIdstring來源 announcementDrafts 文件 ID
seqnumber該篇公告內的出現序（0-based），也是後台預設排序
statusPendingStatus'parsed' | 'needsReview' | 'approved' | 'merged' | 'rejected' | 'superseded' | 'conflict'。merged / rejected 是收據——記的是「當時人工放行了什麼」，解析器重跑（--reparse）一律不覆寫這兩種，否則會被打回待審而重複合併。重跑後若解析結果與收據不同，腳本會列出清單提示正式資料可能要人工回頭改
flagsPendingFlag[]有任何一個 flag → status 落在 needsReview。見下方 02
extractedPartial<TimedActivity>解析器原始產出，人工永不修改（保持原樣供 diff）。抽不到的欄位留 undefined，絕不填預設值
reviewedPartial<TimedActivity>?人工編修後版本。存在時以它為準寫入；兩份並存才做得出 diff
excerptstring原文片段（不是整篇）。後台左欄只載這段，免得每開一筆就傳 16 KB 全文
excerptStartnumber?片段在 rawText 內的起始位移，供「看完整原文」捲到正確位置
rawTypeLabelstring?型別未命中 registry 時，從公告抄下的原始段落標題
targetVersion / targetHalfstring? / 'upper'|'lower'?依 startDate 推測的目標版本半期。只是預填；推不出來時該筆一律 needsReview（猜錯版本比沒猜更難發現）
mergedIntoMergeReceipt?寫入收據，見下方 04
rejectReasonstring?判定不進時間線的理由（選填）
reviewerUid / reviewerName / reviewedAtstring? / string? / Timestamp?審核者。status 進入 merged / rejected 時寫入
createdAt / expireAtTimestamp與來源 draft 同步，TTL 到期一起清掉
02 — flag
解析器對單筆活動的標記
📌 flag 的作用：把「我沒把握」明確化。有任何一個 flag，該筆就進 needsReview， 後台預設只顯示這些。實測 266 篇歸檔語料 625 筆活動中，零 flag 可直接放行者佔 66%。
flag中文標籤觸發條件與實測數量（625 筆中）
openEnded無結束時刻「YYYY/MM/DD HH:mm 起」沒有結束時刻 → weeks 留空。193 筆（31%），主要是卡池
nonThursdayStart非週四開始起始日不是週四，與既有資料慣例不符。16 筆（2.6%）
nonWholeWeek非整週持續時間非整週，weeks 會是小數。14 筆（2.2%）
unknownActivityType未知型別type 不在 activityTypeRegistry 裡 —— 新玩法。8 筆（1.3%）
missingName缺名稱抽不到活動名。3 筆（0.5%）
missingDate缺日期抽不到起始日。1 筆（0.2%）
unmatchedText有未認領原文該活動所屬段落有未被規則認領的原文
duplicate疑似重複同版本半期內已有相同 anchor 的活動
💡 為什麼 openEnded 不自動補一個「慣例 2 週」
填了預設值就再也分不出「官方真的是這樣」與「我沒抽到」。
早期版本曾在後台表單預填建議值（2 週），已經拿掉 —— 預填值會在維護者沒細看時直接變成資料，而那正是這條界線要防的事。
現在的做法：週數留空也能合併，但該筆會帶著 hidden 與 note 進入 patchVersions。事實先留住（不會卡在待審清單被遺忘），但上不了首頁。 之後在版本編輯頁補上長度、取消隱藏即上線，不需要重跑爬蟲或審核流程。 細節見 patchVersions 資料模型 的 hidden / note 兩欄與「前台顯示閘門」。
03 — 監控
產出量告警（ParseWarning）
⚠ 爬蟲失效時不會報錯，只會靜默降低品質
官網句型逐年漂移已實測：本期機師征招「X」 2024／2025 出現 0 次、2026 才 1 次； 維護計畫 段落 2026 才有；2024 有整批公告沒有 活動時間 錨點只有裸日期。 只看 HTTP 200 完全看不出解析器已經瞎了。
warning觸發條件
lowYield一篇【版本前瞻】抽出的活動數 < 2 —— 週報不可能只有一個活動
pilotSectionNoName有「機師征招招募活動」段落卻抽不到機師名
mechSectionNoName有「機甲獲取海運活動」段落卻抽不到機甲名
yieldRegression本次執行的每篇產出量低於前次 20% 以上（前次統計存在 meta/announcementScrape）
contentSelectorMiss正文抓不到 <div class="content">，退回整頁去標籤 —— 官網改版的徵兆
04 — 合併
寫入 patchVersions 的兩條紅線
⚠ 紅線一：合併寫入必須 runTransaction
patchVersions 既有的存檔路徑是整份 setDoc。合併時若「讀出來 → 改陣列 → 寫回去」不在交易內， 管理員同時在版本編輯頁按存檔就會覆蓋掉剛合併的內容。
MergeReceipt.anchor 用 { name, startDate } 定位而不是陣列 index： twActivities 是陣列，管理員增刪排序後 index 就指向別的活動了 （同 changeHistory.RefAnchor 的教訓：索引式路徑不是穩定識別子）。
⚠ 紅線二：合併後必須 bumpDataVersion('patchVersions')
patchVersions 走 Cloudflare Worker 邊緣快取（workers/src/index.ts 以集合版本號當 cache key、max-age=86400）。不 bump 就是「資料寫進去了、前台看不到、硬重整也沒用」，最長 24 小時 —— 快取在邊緣不在瀏覽器。
反過來說，抓取腳本刻意不 bump：它只寫這兩個 staging 集合，沒動 patchVersions， 平白 bump 等於讓所有使用者重抓一次。
MergeReceipt
欄位型別說明
versionIdstringpatchVersions 文件 ID，如 v3.3
half'upper' | 'lower'寫進上半或下半
field'twActivities'目前一律台服欄位（台版公告只餵台服）
anchor{ name, startDate }重定位錨點，不用 index

05 — 規則
安全規則與保留期限
match /announcementDrafts/{docId} {
  allow read:  if isAdmin();
  allow write: if isAdmin();
}
match /pendingActivities/{docId} {
  allow read:  if isAdmin();
  allow write: if isAdmin();
}
📌 為什麼不是 write: if false
寫入者有二：爬蟲以 service account（Admin SDK）繞過規則；管理員在 /admin/announcements 審核時以 client SDK 更新 status / reviewed / mergedInto。 因此不能照 analytics 那樣一律禁寫 client。
⏳ TTL 政策（需在 Firebase Console 手動建立，同 changeHistory）
兩個集合各建一條，欄位皆為 expireAt，保留期限 6 個月。
理由：已合併的活動其事實已進 patchVersions，公告原文在本地歸檔另有完整一份 （_local-notes/2026-08/tw-announcements-archive/），staging 留著沒有意義。
🔧 「規則待擴充」彙總（/admin/announcements 分頁）
解析器不可能一次寫對所有句型，官方寫法逐年漂移是實測過的事實。與其每次逐篇翻公告找漏， 後台把三張表依出現次數排好，讓「碰到很多次的寫法」自己浮上來：
① 待補資料 —— 所有 hidden 的活動連同 note，標明缺哪些欄位。
② 待擴充規則 —— 未認領原文依句型彙總。實測 492 行未認領原文收斂成 57 組句型， 最高的一組出現 52 次（【⟨名稱⟩】補充說明）—— 那就是下一版解析器最該處理的。 只出現一次的預設不列（滿頁雜訊等於沒有清單）。
③ 未登錄型別 —— 對照計畫書的升級觸發點（穩定超過 20 種才把 activityTypes 開成獨立集合）。
句型彙總不是抽四字片語：試過，同一句樣板會被拆成十幾個重疊窗格 （則下一次／下一次獲／一次獲得…），整張榜單被一句話洗版。改為整行正規化 （抹掉日期、數量、括號內容與已知的卡池標題文法）後才收斂得起來。
