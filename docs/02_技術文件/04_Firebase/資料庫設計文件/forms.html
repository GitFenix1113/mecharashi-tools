PLAN-041 — 2026-08-12
01 — 用途
forms Collection
📌 用途說明
調構師（目前僅海莉絲）駕駛的機甲會在戰鬥中切換形態，每個形態有各自的固有效果與裝備限制。
形態既不是技能也不是 BUFF：它要承載裝備限制（union）、顯示順序、形態增益連結與「是否天賦專屬」， PilotSkill 與 GameBuff 兩個既有型別都裝不下，故獨立成集合。
· 前台於機師詳情頁的「形態」分頁與跨分頁常駐的特殊能力列渲染；渲染條件一律是 forms.length > 0，禁止用 pilot.class === '調構師' （官方職業 icon 跳號，且實測 2/82 機師的 class 字串與職業機制對不上）。
· 任意 description 中的 [xxx] 可指向此集合（refType:'form'）→ 懸停顯示形態卡， 「查看完整詳情」導向 /pilots/<pilotId>?tab=形態（形態沒有獨立路由）。
· 官方 API 與 WIKI 都沒有這份資料 → 全數人工於後台「機師形態」分頁維護。
· 前台讀取走 GameDataContext 一次預載 + PLAN-017 版本快取（回訪 0 讀取）。
🗃️ forms — 形態文件（MechForm）
欄位型別說明
idstring文件 ID。格式 form_<機師名>_<形態名去「形態」尾綴>，如 form_海莉絲_先鋒。與其他集合的 <prefix>_<slug(name)> 不同——形態名（先鋒／突擊…）在不同調構師之間必然重複，只用名稱會直接撞 ID
pilotIdstring所屬機師文件 ID（pilots）
namestring形態名稱。統一用「形態」不用「型」態（舊 pilotSkills 遺留文件的 id 是「型」態）
ordernumber顯示順序。形態數不固定 → UI 一律 map，不寫死欄數
iconstring?選填圖示（後台以 IconField 從 public/images 挑選）
descriptionstring形態固有效果，官方形態卡正文逐字。這是形態效果的唯一真相源（見下方「刻意不開的欄位」）
descriptionRefsDescriptionRefs?正文內 [xxx] → 實體引用側錄（PLAN-019 Layer 1）
restrictFormRestrict裝備限制，discriminated union，見下表
grantedBuffIdsstring[]?形態增益：天賦滿星另給的一次性 BUFF（正文多含「觸發效果後移除」）。與 description 逐句零重疊，前台分兩段各自標來源、不合併
entryNotestring?入／退場條件，官方正文逐字。刻意不結構化——全站沒有回合模型可以消費它
isSignatureboolean?天賦專屬形態（海莉絲僅「虛粒子形態」為 true）。決定前台是否加 ★ 與金框、與一般戰鬥形態視覺分層
manualboolean?手建文件保護旗標；官方無此資料，補丁腳本應略過
🔀 FormRestrict — 裝備限制（sum type）
kind欄位語意
'weaponType' allow: WeaponType[] 可自由換裝，但只能裝白名單內的武器類型（先鋒＝格鬥+射擊 / 突擊＝突擊 / 戰術＝戰術）。
白名單不含「特殊」：那是焊死的固定武裝，本來就換不掉，拿類型過濾它沒有意義。
'fixedArmament' weaponIds: string[] 該形態下所有槽位皆不可調整（雙手＋雙肩＋背部），不只是被 weaponIds 佔住的那幾格—— 實機實測「虛粒子形態沒辦法調整任何裝備」，遊戲內雙肩顯示為空的 [+] 但點不下去（空槽 ≠ 可填）。
對應 PLAN-047 的「全鎖型」derive；帕斯卡／破曉者-01／霸王的肩槽封鎖是正交的「佔據型」，不歸本集合。
⚠ 刻意不開的欄位（理由同步寫在 src/types/form.ts 的型別註解裡）
  • effects：形態固有的九條正文，現行 SkillEffect + 封閉 34 key 的 STAT_OPTIONS 只表達得出約 2 條 （填不進去的：移動力+1、不消耗彈藥、可行動 2 次、每 1AP+5% 上限 25%、每回合最多 2 次、免疫［反擊先手］、子彈數+1）。 缺的是四個結構性軸，屬傷害公式範疇。佐證：全庫 effects 非空 0 筆。 另注：3375→3675 的出力差來自強襲者背包而非形態，形態身上沒有任何數值可落盤。
  • lockedSkillIds（2026-08-12 移除）：「被鎖住的技能」已由 description 內的 [虛粒子刃][虛粒子炮][虛粒子矩陣] 引用完整表達（可解析、可 hover、刪技能時會被級聯掃到）。 另存 id 清單＝第二個真相源，且兩份對不上時沒有任何機制會發現；填基礎版還會誤導 （該形態下三支已被 skill_虛粒子程式 強化為 EX 版）。
  • skillsByWeaponKind：「形態 × 武器種類 → 子技能」矩陣的擁有者是技能不是形態， 歸 SkillVariant，箭頭 skill → form。
  • hasFixedArmament：由 restrict.kind derive，不存平行布林。
  • 配裝總重：官方形態卡左側的 1125 / 3125 / 1895 / 1825 是隨玩家配裝即時改變的 derived 值，落盤即失準。
  • per-form 武器背包 loadout：屬模擬器範疇（Build.weaponId 是單值 string），已由 PLAN-047 承接。
02 — 引用關係
箭頭方向
海莉絲的固定武裝：  form ─(restrict.fixedArmament.weaponIds)──→ weapon
形態增益：          form ─(grantedBuffIds)────────────────────→ buff
正文引用：          form ─(descriptionRefs)──────────────────→ buff / term / skill …
子技能矩陣（未做）： skill ─(SkillVariant.formId)──────────────→ form

                    ↑ 武器不認識形態；形態不認識子技能
反向一律禁止。武器完全不認識形態 → 固定武裝的建檔（PLAN-040）與本集合徹底解耦； 形態不認識子技能 → 新增一支子技能只要改該技能一份文件，不用改 4 個形態文件。
🔁 inbound 引用（refType:'form'）
指向形態的引用共 12 條：mod_彌造者_fixed_1（帕姆斯陣列）7 條、 skill_粒子爆發／skill_虛粒子程式／skill_嵐循環 各 1 條、 pilot_049_海莉絲 天賦 1 條。
RefType 新增值時要補的窮舉消費端共 6 處，其中 RefPicker.REF_TYPE_OPTIONS（手寫陣列）與 EntityRefView.resolve() 的 switch（有 default） tsc 抓不到——清單列於 src/types/common.ts 的 RefType 註解。
03 — 維護
資料維護
🛠️ 後台編輯
管理後台「機師形態」分頁新增 / 編輯。機師下拉預設只列調構師（另有「顯示全部機師」開關， 且已有形態的機師一律列出，避免 class 字串變動後資料被過濾器藏成孤兒）。
存檔走 updateForm() → saveWithHistory('form', …)：自動寫入 changeHistory 並 bumpDataVersion('forms')；刪除走 planCascadeDelete('form', id) 兩段式， 確認對話框先顯示影響範圍再原子提交。
🔒 安全規則
match /forms/{docId}：read / write 皆 isAdmin()。 前台不直讀，改走 Cloudflare Worker 代理（/api/data/forms，service account 代讀）。
⚠ 新增集合時的部署順序（PLAN-041 實地踩到）
workers/src/index.ts 的 ARRAY_COLLECTIONS 必須在後台第一次要讀該集合之前就 wrangler deploy——本機 dev 的 VITE_WORKER_API_BASE 指向正式 Worker， 「本機先開發、最後才部署」在這個架構下不成立，症狀是後台整頁 載入失敗：Worker /api/data/forms 失敗 404。
firestore.rules 同理（存檔／撞名檢查／級聯掃描都是瀏覽器直連 Firestore）。 兩者都不在 npm run build / git push 的流程內。
另有三處硬性守衛由 src/lib/collectionKeys.test.ts 斷言：Worker 的 ARRAY_COLLECTIONS、 scripts/bump-data-version.mjs 的 KNOWN_KEYS、firestore.rules 的 match 區塊。
