systemLog — 系統診斷日誌 MECHARASHI — FIRESTORE SCHEMA · PLAN-045

維護者非預期登出的證據 · append-only · 讀取限 OWNER（全站唯一 read 比 write 嚴格）· 原生 TTL 90 天

PLAN-045 — 2026-08-08
01 — 用途
systemLog Collection
📌 用途說明
維護者持續回報「編輯資料到一半被登出」，但站上沒有任何持久化的診斷記錄，每次回報都只能靠猜。 本集合記錄兩類事件的完整環境證據，讓 OWNER 能直接看出成因而非再次臆測。
· logout — 非預期登出。含三態哨兵判定的成因與當下的儲存／瀏覽器環境快照。
· writeDenied — 仍登入著，但存檔收到 permission-denied。 對使用者而言這和被登出無法區分（按下儲存、沒反應），只記登出會漏掉這一整類。
· 保留 90 天，由 Firestore 原生 TTL 政策自動清除。診斷資料的價值隨時間急遽衰減， 半年前的登出記錄對排查今天的問題沒有意義（故比 changeHistory 的兩年短得多）。
⚠ 為什麼登出當下寫不進這個集合
這是整套設計的形狀來源。被動登出時，onAuthStateChanged 拿到 null 的那一刻 auth.currentUser 已經是 null，而寫入規則要求 isAdmin() —— 此時寫入必定 permission-denied。
因此登出證據改為兩段式上報：登出瞬間寫進 localStorage 佇列 （mecharashi_diag_queue，上限 20 筆），下次登入成功後 flush 到 Firestore。 這也是 at 與 occurredAt 必須是兩個欄位的原因（見下方 02）。
writeDenied 事件則當下仍登入著，可直接寫入、不必走佇列。
⚠ 與 changeHistory 的異同
相同：append-only、addDoc 自動 ID、不進 CollectionKey / GameDataContext （持續成長、只查最近幾頁，塞進版本快取只會撐爆 localStorage）、伺服器端分頁查詢、原生 TTL。
不同：changeHistory 是 read: isAdmin()，本集合收緊為 read: isOwnerRole()。記錄內含 UA、儲存用量、螢幕尺寸等裝置指紋， 屬於維護者個人的環境資訊，不該讓其他 ADMIN 互看。

02 — 時間欄位
at 與 occurredAt 為何必須分開
📌 兩個時間戳的分工
logout 事件走 localStorage 佇列延遲上報，at（serverTimestamp()）記的是 「重新登入並 flush」的時刻，而不是被登出的時刻。若只有一個時間欄位，日誌上看到的會是 使用者重新登入的時間，完全誤導判讀。
⚠ 排序用 at 而非 occurredAt
occurredAt 來自使用者本機時鐘 —— 可能錯得離譜，甚至是刻意調過的， 拿它當排序鍵會讓分頁游標行為不可預測。at 是伺服器權威時間且已建索引。
代價是延遲上報的事件會排在「上報時刻」而非「發生時刻」。 後台頁在兩者差距超過 5 分鐘時會標示（延遲上報），避免看列表的人誤判。
03 — 成因判定
三態哨兵
📌 為什麼需要「兩顆哨兵」而不是一顆
直覺做法是只在 localStorage 種一顆哨兵，「哨兵不見了」就判定儲存被清。但那有個會汙染整份日誌的誤報： 從未登入過的訪客，onAuthStateChanged 同樣給 null、同樣沒有哨兵， 會被判成儲存被清 —— 而前台每次載入都會觸發一次。
關鍵在於必須先回答「這台裝置到底登入過沒有」，而這個問題不能問正在被懷疑的那個儲存機制。 故種兩顆在不同存活條件的位置：
· localStorage 哨兵（mecharashi_diag_sentinel）—— quota-managed storage，Chrome 空間壓力下第一個被 evict
· cookie 哨兵（mr_diag，僅存 uid 前 8 碼）—— 不屬於 quota-managed storage，Chrome eviction 清不到它
🔍 判定表（classifyLogout，純函式）
條件reason意義
我方呼叫過 signOut()explicit主動登出。優先於一切環境探針，且不寫入日誌
ls 哨兵在tokenRevokedquota storage 完好卻登出 → 改密碼 / 帳號停用 / 後端撤銷

兩顆哨兵皆不見neverSignedIn查無登入痕跡 → 不產生事件（多半是匿名訪客）
localStorage 本身不可用unknown隱私模式等；「沒有哨兵」與「讀不到哨兵」無法區分，不硬猜
🐛 為什麼判定不碰 IndexedDB —— 瀏覽器實測推翻的初版設計
初版讓「Firebase 的 firebaseLocalStorageDb 還在不在」參與判定，並有一個 idbEvicted 成因。實測發現那顆探針恆為 present： 該 database 會在 SDK 初始化時自動重建，所以等 onAuthStateChanged(null) 觸發、探針執行時，就算使用者前一秒手動刪光整個 database，它也早就回來了。

後果有兩層：
① idbEvicted 永遠產生不出來（條件是「IDB 不見」，而它不會不見），該情境全數落到 tokenRevoked；
② 更嚴重——原本「cookie 沒了但 IDB 還在 → 證明登入過 → storageCleared」這條，會讓 每個第一次進站的匿名訪客（哨兵、cookie 都沒有，IDB 由 SDK 剛建好） 被判成 storageCleared 並跳出登出橫幅。

修正後判定只採用不受 Firebase 干擾的兩顆哨兵。 idbEvicted 停用（型別保留，僅為讓既有記錄顯示得出標籤）。

單元測試為什麼沒抓到：它測的是「給定探針值 → 判定是否正確」， 而錯的是探針值本身測不到真實狀態。那一層只有真實瀏覽器測得出來—— 這正是進度表把「四種成因的瀏覽器手動驗證」列為獨立任務的價值所在。
🔬 authRecord：改對語意後保留為佐證
探針改為檢查 object store 裡有沒有 firebase:authUser:* 記錄， 而非 database 是否存在。不參與判定，只在人工判讀時提供線索 （例如「憑證明明還在卻登出了」是值得警覺的異常）。
實作注意：必須先用 indexedDB.databases() 確認 database 存在再 open()—— open() 對不存在的 database 會「建立」它，診斷探針絕不該產生副作用。 另設 1 秒 timeout，避免被其他分頁的交易 block 住而拖住登出流程。
⚠ 探針 unknown 不可當成 absent
indexedDB.databases() 並非所有瀏覽器都有（Firefox 長年未實作）。 測不到時必須誠實回報 unknown。
判定已抽成無副作用純函式，src/lib/diag/sentinel.test.ts 窮舉全部 162 種輸入組合 （34 探針 × 2 explicit），並額外釘住「authRecord / authLocal 的任何值都不得改變判定結果」。
🔁 同一次登出只記一筆
onAuthStateChanged(null) 不是「登出的那一瞬間」才觸發——只要處於未登入狀態， 每次重新載入頁面都會再觸發一次。實測時刪掉 IndexedDB 就抓到兩筆： 一筆是刪除當下 Firebase 立即登出，一筆是接著按 F5 重整。
去重用 sessionStorage 旗標（mecharashi_diag_reported）： 它的生命週期正好是「這個分頁」——重整會保留（擋掉重複），關閉分頁後清除（新的瀏覽視為新的觀察）。 登入成功時主動清除，確保「登入→被登出→再登入→再被登出」每次都記得到。
橫幅不受去重影響：重整後仍會顯示，因為「要不要提醒使用者」與「要不要再記一筆」是兩件事。
🍎 Safari 的特殊性 —— 這是本集合要證實的關鍵假說
storageCleared 有兩個對策完全不同的來源：
· Chrome 系：空間吃緊時 evict。可用 navigator.storage.persist() 申請豁免， 且 Chrome 對有互動的站台通常會核准 —— src/lib/firebase.ts 已在做這件事。
· Safari：一律不核准 persist()（除非站台被加入主畫面）， 且 ITP 政策是 7 天無互動就清除 script-writable storage。現有防護對 Safari 使用者完全無效， 他們被登出是必然而非偶然。
兩者在使用者眼中是同一個症狀。沒有 env.persisted + env.ua 就分不出來，只能繼續猜。
另注意：Safari ITP 會連 cookie 一起清，故 Safari 的儲存清除會落到 neverSignedIn 而非 storageCleared。這是刻意的取捨 —— 寧可漏報也不要誤報， Safari 情境可由日誌的 UA 分布另行辨識。
04 — persistence 降級假說與心跳
把「發現時刻」壓縮成「失效區間」
🔎 首批真實樣本推翻了原本的假說
2026-08-08 收到四筆 tokenRevoked，指紋高度一致：
· persisted ✓ 已獲准、儲存用量 1.2 MB / 10 GB（離配額壓力十萬八千里）
· 哨兵在、cookie 在 —— quota-managed storage 完好
· 只有 IndexedDB 的 firebase:authUser:* 不見
· sessionAgeSec 為 0～1 秒 —— 登出在頁面載入之前就已是既成事實
這同時排除了空間壓力 eviction、使用者手動清除、Safari ITP（樣本是 Chrome/Windows）。 不是整包被清，是單點遺失。
📌 persistence 是階梯，不是單一選擇
getAuth() 的預設 persistence 依序嘗試：
indexedDBLocalPersistence → browserLocalPersistence（localStorage） → browserSessionPersistence → inMemoryPersistence
若 IndexedDB 在初始化那一瞬間不可用（磁碟 I/O 抖動、被其他分頁的 versionchange 卡住、 測試寫入逾時），SDK 會降級到 localStorage。此時兩層互不讀取，使用者被登出， 而只查 IndexedDB 的探針會回報 absent —— 與「憑證真的被撤銷」完全無法區分。
⚠ 更糟的是：降級會把 IndexedDB 的憑證「刪掉」，不可逆
讀 @firebase/auth 的 PersistenceUserManager.create 可以看到兩個危險性質：
① 逐層讀取既有憑證時用 catch {} 靜默吞掉錯誤——IndexedDB 讀取拋錯 會被當成「查無使用者」，與真的沒登入無法區分；
② 選定一層之後，會對其他所有層呼叫 _remove(key) （原始碼註解寫的目的是「避免登出後重整還黏著舊帳號」）。
兩者相加：IndexedDB 只要瞬間不可用一次，使用者不只被登出，IndexedDB 裡的憑證會被順手刪掉， 下次 IndexedDB 恢復也救不回來。這條路徑留下的痕跡是 authRecord=absent + authLocal=absent + 哨兵完好。
🔍 為此新增的四顆探針
探針落點欄位回答什麼問題
probeAuthLocal()probes.authLocal 憑證是不是其實躺在 localStorage 那層？authRecord=absent + authLocal=present 就是降級指紋
probeActivePersistence()persistence / lastSeen.persistence 最直接的一顆：SDK 這次載入實際挑了哪一層。非 indexedDB 即為當場抓到降級
心跳 touchSentinel()sinceSentinelSeenSec / lastSeen 最後一次確認「還登入著」是什麼時候 → 失效區間的寬度
probeToken()authErrors / lastSeen.token* idToken 何時到期、refresh 有沒有失敗過（error code）
📌 心跳為什麼是必要的，而不是錦上添花
occurredAt 記的是發現登出的時刻，而樣本顯示那幾乎都是 「開新分頁／重整後的第 0～1 秒」。真正的失效時刻完全落在觀測範圍外， 可能是 1 分鐘前也可能是昨晚 —— 這種情況下任何成因假說都能自圓其說，等於沒有證據。
心跳（src/lib/diag/heartbeat.ts）在登入期間持續留下「這一刻還好好的」時間戳， 於是登出事件從一個孤立時間點變成有上下界的區間：
· 區間 ≤ 60 秒且分頁可見 → 「用著用著就掉了」
· 區間很寬且最後一眼是 hidden → 「關著的期間掉的」
在加上心跳之前，這兩者在日誌上長得一模一樣。
📌 負擔評估（刻意壓到可忽略）
· Firestore：零 —— 心跳只寫 localStorage，不產生任何文件；證據是搭既有的登出事件 一起送上去的（多幾個欄位，不是多幾筆文件）
· 網路：零 —— probeToken() 用非強制的 getIdToken()， 有效期內純讀記憶體快取。刻意不用 getIdToken(true)，那會每次心跳都打一次 Google 端點
· 頻率：60 秒一次，且只在分頁可見時跑（背景分頁完全不動）
· localStorage：mecharashi_diag_lastseen + mecharashi_diag_autherr 合計 < 1 KB，覆寫而非累積
· IndexedDB：可見時每 60 秒一次唯讀開關；Firebase Auth 自己的跨分頁同步是 800 ms 輪詢一次，我們比它低兩個數量級
⚠ 新探針一律不參與判定
authLocal 最想抓的組合（IDB 沒有、localStorage 有）雖然高度可疑，但 Firebase 切換 persistence 時的遷移路徑不保證清乾淨舊鍵，殘留的舊鍵會讓這條判定變成永久誤報 —— 與初版被 authIdb 恆 present 坑到是同一類錯誤。
故新證據只以判讀提示的形式呈現在後台頁（hintsOf()）， reason 仍由 classifyLogout 的兩顆哨兵決定。 提示寫錯頂多誤導人一次，判定寫錯會污染整份日誌。 sentinel.test.ts 有一條測試專門防止日後有人「順手」把它接進判定。

🛠️ API
src/lib/api/systemLog.ts：
· logSystemEvent(event) — fire-and-forget，失敗只警告不拋錯
· writeSystemLogOrThrow(event) — 失敗拋錯（flush 需要知道哪幾筆沒送成功，留在佇列下次再試）
· getSystemLogPage({ kind?, reason?, cursor?, pageSize }) — 雙軸篩選分頁查詢
· getSystemLogSummary(sampleSize) — 最近 N 筆的成因分布。刻意獨立一次查詢： 列表會被使用者的篩選條件影響，摘要必須永遠是「未篩選的最近 N 筆」才有代表性

src/lib/diag/（採集層，無 Firestore 依賴）：
· sentinel.ts — 哨兵讀寫與三態判定（純函式部分可單測）
· collect.ts — 環境與 session 證據採集
· queue.ts — localStorage 事件佇列（上限 20 筆）
· report.ts — captureLogout() / flushQueue() / onSignedIn()
· writeGuard.ts — permission-denied 攔截（唯一攔截點在 firestoreCore.writeDoc）
· draft.ts — 後台編輯草稿本機暫存
⚠ 與 changeHistory 相同的兩個陷阱
① log 寫入路徑一律不得經過 stripUndefined：它會遞迴走物件， 把 serverTimestamp() 哨兵值拆成普通物件而失效。改為組裝時就不放進 undefined 欄位。
② 缺 at 欄位的文件會被 orderBy('at') 完全排除，在日誌頁「無聲消失」而非顯示異常。
🚫 非瀏覽器環境一律停用診斷
reportWriteDenied() 開頭即檢查 typeof window === 'undefined' 並直接返回。 模擬器整合測試與 scripts/ 的 migrate 腳本都會走到 writeDoc， 其中破壞性測試更是刻意製造 permission-denied —— 讓診斷在那裡開火只會產生無人閱讀的雜訊記錄，還可能干擾計算寫入次數的測試。
06 — 安全規則與保留期限
append-only、讀寫不對稱與 TTL
match /systemLog/{docId} { allow read: if isOwnerRole(); allow create: if isAdmin() && request.resource.data.uid == request.auth.uid; allow update, delete: if false; }
🔒 全站唯一 read 比 write 嚴格的集合
每個維護者都得寫得進去（否則登出證據送不出來），但診斷記錄含 UA、儲存用量等裝置指紋， 不該讓 ADMIN 互看，故讀取限 OWNER。
正因為這個不對稱在本專案裡是獨一無二的，特別容易在日後重構規則時被「順手改成一致」而破功。 tests/emulator/suites/rules.test.ts 案例 h 已把它釘住 （ADMIN 寫得進、讀不到、刪不掉；USER 讀寫皆拒）。
create 維持 isAdmin() 而非 isAuthenticated()： 本設計只追蹤維護者，放寬到一般登入使用者只會擴大寫入面並帶來限流需求。
⚠ 登出當下寫不進來是預期行為，不是規則沒設好
此時 request.auth 已為 null，isAdmin() 恆為 false。 那條路徑刻意改走 localStorage 佇列、等下次登入再補送。 排查時若看到「登出事件延遲數小時才出現」，那是設計如此，不是故障。
⏳ TTL 政策
在 firestore.indexes.json 的 fieldOverrides 宣告 （{ "collectionGroup": "systemLog", "fieldPath": "expireAt", "ttl": true, "indexes": [] }）， 隨 firebase deploy --only firestore:indexes 一併生效，不需要到 Console 手動設定。
