PLAN-042-A — 2026-08-31 · 042-E 資料分家 2026-10-13
01 — 用途
pilotLore Collection
📌 用途說明
官方遊戲內機師有兩個不同的頁面：「機師檔案」與「逸聞（PART 1..N）」。PLAN-042-E（2026-10-13）起兩者都住本集合：
· 機師檔案＝扉頁簡介 intro（原 pilots.lore，官方 API detail.Introduction 的鏡像） ＋ 署名 frontSource ＋ 英文名 nameEn（原 pilots.nameEn） ＋ 人物檔案 dossier（原 pilots.profile）＋ 陣營徽章 factionLogos。
· 逸聞＝每段數百字、有標題（「光環遍身」「定命恩垂」）的章節 chapters， 官方 API 完全沒有，須以 OCR 輔助人工輸入。
· 外觀顯示設定＝ skins（名稱、隱藏、順序）；圖檔本身仍是 build 時決定的靜態層。
前台於故事館 /lore/pilots/:id（扉頁＋卷宗）與 /lore/pilots/:id/:part（章節）渲染；圖鑑詳情頁不讀本集合。
✅ 接縫判準是「與數值、機制有沒有關係」（PLAN-042-E 決策一，取代總綱決策二）
有關的留 pilots（圖鑑讀），其餘全部進 pilotLore（故事館讀）。邊界依站長 Q1 裁決： name／fullName／faction 以及 class、license、rarity、masterLevel、debutVersion、 gameId、artKey、portrait、pairedMechId、數值類留在 pilots——它們是兩館共用的身分欄位，陣營日後還會有機制作用；預設外觀＝pilots.artKey，圖鑑頭像也在用，所以不歸故事館管。
依賴是單向的（決策二）：圖鑑只讀 pilots；故事館讀 pilotLore ＋ pilots 的身分欄位。 故事館壞掉、資料還沒填，都不影響圖鑑——機師詳情頁只留一顆不帶任何故事內容的「故事館 ▸」連結，不載入本集合。
（歷史）042-A 時的判準是「誰是權威來源」：爬蟲寫的留 pilots、人寫的進 pilotLore，所以 lore／profile 當時不搬—— 圖鑑 hover 浮窗（EntityRefView）與引用稽核（entityRefs 的「機師簡介」站點）都還在讀它。 這兩個前提先後失效：浮窗 2026-10-09 改列天賦、官網爬蟲 2026-10-11 退場，所有資料都成了人寫的，這條判準已分不出任何東西。
🗃️ pilotLore — 故事館文件（LoreDoc）
欄位型別說明

namestring?機師名快照（去正規化）。供 saveWithHistory 的 targetName 與後台列表使用，目標被刪後仍看得懂 log 在講誰
introstring?🆕 PLAN-042-E 扉頁簡介（原 pilots.lore，搬遷 B-2 搬來）。純文字、換行即分段，前台走 readableParagraphs() 排版。

dossierLoreDossierInfo?🆕 PLAN-042-E 人物檔案（原 pilots.profile），結構見下方子表。沒有就不出現卷宗的「個人資料」卡。

skinsLoreSkinSetting[]?🆕 PLAN-042-E 外觀顯示設定（決策六的動態層）：名稱、隱藏、順序，陣列順序＝顯示順序，後台存檔即生效、不必部署。結構見下方子表。
執行期由 pilotSkins(pilot, loreDoc)（src/utils/gameArt.ts）與 build 清單合併：依陣列排序、套名稱、濾掉 hidden；沒列在陣列裡的外觀依原索引接在後面、顯示「外觀 N」（N＝build 清單原索引，穩定不變）；DB 有、圖卻不存在的 key 直接忽略；同一個 key 列兩次只認第一筆。後台外觀分頁用 pilotSkinCatalog(pilot) 列出 build 清單（含隱藏的）。 預設外觀＝pilots.artKey，不在本欄管。
factionLogosstring[]?陣營徽章（PLAN-059 D，2026-10-13）：官方檔名、含變體，最多 2 個，例 ["Icon_logo_0025_00"]。圖在 public/images/game/icons/camp/。_00＝白色單色（前台以 CSS mask 上色：紙色扉頁是墨色、暗底縮圖是白色），_01＝彩色（原樣）。只有故事館讀（扉頁徽記、館首頁卡片角標）；後台在故事館編輯台的「扉頁」分頁挑選。
⚠ 刻意不做「陣營 → 徽章」字典：pilots.faction 是自由文字（31 種寫法、含複合值），改為逐位挑選＋「同陣營文字的其他機師已選」一鍵套用。沒有官方資料能對到徽章編號，開發端不預填。2026-10-14 PLAN-042-F 修訂：徽章本身的名稱、圖上字樣與「對應的陣營文字」改存 factionEmblems，選圖器據此顯示名稱、把建議排前面——仍是逐位挑選、不自動寫入本欄。讀寫一律經 src/utils/factionLogos.ts 的 normalizeFactionLogos()（只留合法檔名、去重、最多 2 個）；清空時欄位直接移除（writeDoc 是整份覆寫）。
chaptersLoreChapter[]逸聞章節（PART 1..N）。不含扉頁——扉頁是上面的 intro／frontSource。草稿章見 LoreChapter.draft。
型別上必填，但執行期不保證存在（Firestore 沒有 schema 強制），讀取端一律 ?.chapters 防禦。

欄位型別說明

🎭 LoreCustomSpeaker — 自訂說話者（commentary[].speaker）
欄位型別說明
namestring顯示名稱，照遊戲畫面逐字填（例：匿名使用者）。存檔時 trim；名稱與頭像都空 → 存檔時拿掉整個 speaker（normalizeCommentary()）
artstring?頭像：NPC 圖庫（public/images/game/npc/）的官方立繪鍵，例 Pilot_99999（匿名使用者的聲波圖）。 DB 只存鍵、不存路徑（同 PLAN-055 圖示慣例），讀取端走 npcGameArt(art, 'half')。空＝不顯示頭像；鍵在圖庫找不到也只是不顯示
不是引用：名稱是純文字快照、頭像是圖檔鍵，沒有任何東西指向另一份文件——總綱決策三「不開新 RefType」照舊成立。 同一位 NPC 在多篇故事裡重複出現時，後台的名稱建議（customSpeakerPresets()，掃全館已用過的自訂說話者）維持寫法一致、同名自動帶入頭像； 不另開「NPC 說話者」集合——今天只有零星幾句，集合會是 0/5 定律說的空殼。頭像選圖器只列 NPC 圖庫：說話的是可抽機師就該選機師本人。
⚠ 刻意不開的欄位（理由同步寫在 src/types/lore.ts 的型別註解裡）
  • subject / kind 之類的 discriminated union：「這份逸聞屬於機師還是機甲」 已由它住在哪個集合完整表達。再存一次就是第二個真相源，而 repo 內沒有 exhaustive 檢查的既有慣例 （要自己補 assertNever）——union 的成本會在零消費端的情況下先付掉。
  • key?: string（選填鍵 ＋ 索引 fallback）：加了 fallback 的選填鍵實務上沒人填， 上線跑的就是那個以索引為底的 fallback；而索引一旦被插章打亂，所有已分享的連結會集體指向錯誤章節且不報錯 （總綱決策五、PLAN-041 的「0/5 定律」）。
  • LoreCommentary.textRefs：旁白是短句評註，全站今天沒有一段旁白需要 [xxx]。 要開的時候補一個選填欄位是零成本的。
  • 文件層的 status／進度欄位（PLAN-042-E 決策五）：「有沒有簡介、檔案幾欄、章節數、草稿數、外觀命名數、有沒有徽章」 全部從資料推導（src/utils/loreProgress.ts），後台進度總覽就是這樣算的。理由同 key 那一條的「0/5 定律」——選填的狀態欄位最後沒人會填，填了也會跟資料本身漂移。
  • 扉頁正文：住 pilots.lore——（歷史）042-A 的決定，PLAN-042-E 已搬進本集合的 intro，見上方決策一。

箭頭方向
正文引用：  pilotLore ─(chapters[].bodyRefs)──→ buff / term / skill / form …
旁白說話者：pilotLore ─(chapters[].commentary[].speakerId)──→ pilot
            （自訂說話者 commentary[].speaker 不指向任何文件：名稱是文字、art 是 NPC 圖庫的圖檔鍵）
文件歸屬：  pilotLore.id ═══════════════════→ pilot（同一個 ID）

            ↑ 沒有任何東西指回 pilotLore
本集合只有 outbound，沒有 inbound。
PLAN-042-E：entityRefs 的 PILOT_LORE 多了一個文字單元——origin「扉頁簡介」、texts: { intro }（承接原本 PILOTS 的「機師簡介」站點 texts: { lore }，該站點已移除）。 簡介今天 0 篇含 [xxx]／<id.attr>、也沒有側錄表；這個站點是防日後誤加——漏掃的話刪 BUFF 後簡介裡會留下解析不出來的 token。
🚫 故事館全程不新增 RefType
src/types/common.ts 的 RefType 註解逐字列出新增值要補的五處窮舉消費端， 其中 RefPicker.REF_TYPE_OPTIONS 是手寫陣列、漏了不報錯。 逸聞是被讀的終點、不是被指的目標——沒有任何一段正文會寫 [某某的逸聞]。
對應到 entityRefs.ts：REF_TYPE_OF['pilotLore'] = null（明示的編輯決策，不是漏填）， speakerId 也只允許指向 pilots。
03 — 維護
資料維護
🛠️ 後台編輯：故事館編輯台 /admin/lore（PLAN-042-E 改版）
一位機師的故事資料全部在這裡編：扉頁（英文名、簡介、署名、陣營徽章）／人物檔案／逸聞章節／外觀，右欄即時預覽。 機師管理（PilotAdmin）的「個人資料」分頁已移除，面板標題下留一條連到 /admin/lore?pilot=<id> 的捷徑。
獨立子頁（不是後台的第 15 顆 Tab）：一份文件 N 章長文的互動形狀與既有「列表 → AdminModal → 存檔」的 CRUD 殼不同構；且未來若開給協作者， 必須是一條能獨立授權的路由（目前仍是 ADMIN 即可，EDITOR 角色先不做——決策八）。
存檔走 updatePilotLore() → saveWithHistory('pilotLore', …)：整份覆寫，自動寫入 changeHistory 並 bumpDataVersion('pilotLore')。草稿自動暫存的 kind 自 042-E 起改為 'pilotLore.v2'—— 改版前的草稿沒有 intro／dossier／nameEn／skins，還原後一存檔就會把搬遷進來的資料整份洗掉。
⚠ 為什麼寫入一定要掛 saveWithHistory
本集合是全站人工逐字輸入的長文集中處：寫壞一章、或一次整份覆寫漏帶欄位，就是永久失去 （官網爬蟲 2026-10-11 退場後，沒有任何來源能重抓回來）。changeHistory 的底層 helper 是集合無關設計，接上去的成本只有一行。
對應地，src/lib/api/pilotLore.ts 刻意沒有 deletePilotLore： 本集合不是任何引用的目標、沒有級聯要跑，但「刪掉一整份人工長文」也不該是一顆按鈕—— 要清空就把內容逐項清掉後存檔，那條路徑會留下 update 記錄，前一版內容也還在 changeHistory 裡。
👀 誰讀本集合
· 故事館前台：PilotLorePage／LoreHomePage 依 id 合併 pilots ＋ pilotLore。整頁只等 pilots； pilotLore 的 loading／error 交給卷宗（LoreDossier 的 status）——讀不到時明講「故事資料載入失敗」，不退化成看起來像空白資料的扉頁。館首頁讀不到時只少章節數與徽章角標。
· Cloudflare Worker 分享卡：/lore/pilots/* 多讀一份同 ID 的 pilotLore 文件，og:description ＝ intro（讀不到退回「某某｜機師故事館」）；title 與 og:image 仍取 pilots。
· 故事館編輯台：列表進度總覽、編輯面板與預覽。
· 圖鑑（/pilots/:id）不讀——單向依賴（決策二）。
💾 不進 localStorage 快取層
列於 src/lib/collectionKeys.ts 的 NO_LOCAL_CACHE_KEYS。仍走記憶體快取與版本 gate， 差別只是「關掉分頁後重讀一次」。
理由：全集合快取展開後已佔 4.2–4.5 MB（UTF-16 計，pilots 一個就 2.09 MB），逼近 Chrome 約 5 MB 上限； 而配額超限不會只讓最後那個集合寫失敗——setItem 一旦開始拋 QuotaExceededError，之後每個集合每次都重讀，全站快取效益一起賠掉。 逸聞是成長曲線最陡（89 人 × 4 PART × 500 字 ≈ 534 KB raw）而命中率最低（純欣賞、低流量）的那一個。
PLAN-042-E 搬遷後整包由約 6.8 KB 長到約 70 KB（不含之後增加的章節），仍留在 NO_LOCAL_CACHE_KEYS； Worker 的邊緣快取 key 帶版本號，故事館多讀這一份的 Firestore 成本可以忽略。
