PLAN-042-A — 2026-08-31
01 — 用途
pilotLore Collection
📌 用途說明
官方遊戲內機師有兩個不同的頁面：「機師檔案」與「逸聞（PART 1..N）」。
· 機師檔案＝ pilots.lore ＋ pilots.profile，是官方 API detail.Introduction 的鏡像，89/89 已有值 → 留在 pilots。
· 逸聞＝每段數百字、有標題（「光環遍身」「定命恩垂」）的章節， 官方 API 完全沒有 → 本集合，須以 OCR 輔助人工輸入。
前台於故事館 /lore/pilots/:id/:part 渲染；圖鑑詳情頁不讀本集合。
✅ 接縫判準是「誰是權威來源」，不是「故事 vs 數值」（總綱決策二）
爬蟲寫的留 pilots；人寫的進 pilotLore。這條判準能回答 lore 這種「看起來像故事、其實是官方原文鏡像」的邊界案例——它不搬，因為圖鑑的 hover 浮窗 （EntityRefView）與引用稽核（entityRefs 的「機師簡介」站點）都還在用它， 搬走等於浮窗變空白，或製造兩個真相源。
🗃️ pilotLore — 逸聞文件（LoreDoc）
欄位型別說明
idstring文件 ID ＝ 機師的文件 ID（pilot_049_海莉絲），比照 pilotResearch 慣例。故事與機師一對一，不另造 slug
namestring?機師名快照（去正規化）。供 saveWithHistory 的 targetName 與後台列表使用，目標被刪後仍看得懂 log 在講誰
frontSourcestring?扉頁署名：從 pilots.lore 尾端抽出的出處（如 ——《週刊米赫瑪·文娛版》）。
⚠ 正文本身不複製到這裡。這一欄只存「原文的哪一段是署名」這個編輯決策。初值由一次性草稿腳本 scripts/temp_scripts/extract-lore-source.mjs 產出（實測命中 32 / 誤判 0 / 疑似漏抓 2）＋ 人工複核；不在執行期即時 parse。
chaptersLoreChapter[]逸聞章節（PART 1..N）。不含扉頁——扉頁由渲染端從 pilots.lore derive
📖 LoreChapter — 一章
欄位型別說明
keystring必填穩定鍵，進網址（/lore/pilots/:id/:part）。由後台編輯器在新增章節當下自動產生
labelstring?章節標籤（PART 1）。未設定則由渲染端依索引生成
titlestring章節標題（光環遍身）
bodystring正文。支援 PLAN-019 的 [xxx] 標記，由 <RefText> 解析
bodyRefsDescriptionRefs?正文內 [xxx] → 實體引用側錄。欄位名是 bodyRefs 不是 descriptionRefs（正文欄位叫 body）——entityRefs 的站點必須指定 refsField: 'bodyRefs'，否則級聯清除會去清一個不存在的欄位且靜默不報錯
sourcestring?本章的出處署名。前台右對齊小字 ＋ 分隔細線
commentaryLoreCommentary[]?NPC 旁白列。{ speakerId, text }，speakerId 指向 pilots 文件 ID
⚠ 刻意不開的欄位（理由同步寫在 src/types/lore.ts 的型別註解裡）
  • subject / kind 之類的 discriminated union：「這份逸聞屬於機師還是機甲」 已由它住在哪個集合完整表達。再存一次就是第二個真相源，而 repo 內沒有 exhaustive 檢查的既有慣例 （要自己補 assertNever）——union 的成本會在零消費端的情況下先付掉。
  • key?: string（選填鍵 ＋ 索引 fallback）：加了 fallback 的選填鍵實務上沒人填， 上線跑的就是那個以索引為底的 fallback；而索引一旦被插章打亂，所有已分享的連結會集體指向錯誤章節且不報錯 （總綱決策五、PLAN-041 的「0/5 定律」）。
  • LoreCommentary.textRefs：旁白是短句評註，全站今天沒有一段旁白需要 [xxx]。 要開的時候補一個選填欄位是零成本的。
  • 扉頁正文：住 pilots.lore，見上方決策二。
02 — 引用關係
箭頭方向
正文引用：  pilotLore ─(chapters[].bodyRefs)──→ buff / term / skill / form …
旁白說話者：pilotLore ─(chapters[].commentary[].speakerId)──→ pilot
文件歸屬：  pilotLore.id ═══════════════════→ pilot（同一個 ID）

            ↑ 沒有任何東西指回 pilotLore
本集合只有 outbound，沒有 inbound。
🚫 故事館全程不新增 RefType
src/types/common.ts 的 RefType 註解逐字列出新增值要補的五處窮舉消費端， 其中 RefPicker.REF_TYPE_OPTIONS 是手寫陣列、漏了不報錯。 逸聞是被讀的終點、不是被指的目標——沒有任何一段正文會寫 [某某的逸聞]。
對應到 entityRefs.ts：REF_TYPE_OF['pilotLore'] = null（明示的編輯決策，不是漏填）， speakerId 也只允許指向 pilots。
03 — 維護
資料維護
🛠️ 後台編輯
/admin/lore 獨立子頁（不是後台的第 15 顆 Tab）：互動形狀是「章節側欄 ＋ 長文 textarea ＋ 即時預覽」，與既有「列表 → AdminModal → 存檔」的 CRUD 殼不同構；且未來若開給協作者， 必須是一條能獨立授權的路由。
存檔走 updatePilotLore() → saveWithHistory('pilotLore', …)：自動寫入 changeHistory 並 bumpDataVersion('pilotLore')。
⚠ 為什麼寫入一定要掛 saveWithHistory
本集合是全站唯一「人工逐字輸入、重跑爬蟲也生不回來」的資料。其餘集合寫壞了重抓官網即可， 這裡寫壞一章就是永久失去。changeHistory 的底層 helper 是集合無關設計，接上去的成本只有一行。
對應地，src/lib/api/pilotLore.ts 刻意沒有 deletePilotLore： 本集合不是任何引用的目標、沒有級聯要跑，但「刪掉一整份人工長文」也不該是一顆按鈕—— 要清空就把 chapters 存成 []，那條路徑會留下 update 記錄。
💾 不進 localStorage 快取層
列於 src/lib/collectionKeys.ts 的 NO_LOCAL_CACHE_KEYS。仍走記憶體快取與版本 gate， 差別只是「關掉分頁後重讀一次」。
理由：全集合快取展開後已佔 4.2–4.5 MB（UTF-16 計，pilots 一個就 2.09 MB），逼近 Chrome 約 5 MB 上限； 而配額超限不會只讓最後那個集合寫失敗——setItem 一旦開始拋 QuotaExceededError，之後每個集合每次都重讀，全站快取效益一起賠掉。 逸聞是成長曲線最陡（89 人 × 4 PART × 500 字 ≈ 534 KB raw）而命中率最低（純欣賞、低流量）的那一個。
🔒 安全規則
match /pilotLore/{docId}：read / write 皆 isAdmin()。 前台不直讀，改走 Cloudflare Worker 代理（/api/data/pilotLore，service account 代讀）。
⚠ 新增集合的七處同步（PLAN-043 曾為此炸在正式站）
collectionKeys.ts／workers/src/index.ts 的 ARRAY_COLLECTIONS（漏＝正式站 404、本機全綠）／ scripts/bump-data-version.mjs 的 KNOWN_KEYS（漏＝整條指令 exit(1)）／ entityRefs 的 SPECS／測試 helper／firestore.rules／ GameDataContext 的 state ＋ switch ＋ 型別。
其中五處已由 src/lib/collectionKeys.test.ts 斷言（PLAN-042-A 補上了 GameDataContext 的 switch 與 state 兩項——那原本是唯一沒有任何自動檢查的一處， 漏掉一支 case 的症狀是「該集合永遠是空陣列」，沒有錯誤、沒有紅字）。
wrangler deploy 與 firebase deploy --only firestore:rules 都不在 npm run build / git push 的流程內，且本機 dev 的 VITE_WORKER_API_BASE 指向正式 Worker ——「本機先開發、最後才部署」在這個架構下不成立。
