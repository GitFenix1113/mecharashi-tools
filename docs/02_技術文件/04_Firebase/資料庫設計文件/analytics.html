analyticsDaily / analyticsEntity — 使用統計 MECHARASHI — FIRESTORE SCHEMA · PLAN-046

匿名彙總計數 · 預聚合（看 30 天＝30 reads）· 全站唯一 write: if false 的集合 · 不含任何可識別個人的資料

PLAN-046 — 2026-08-08
01 — 用途
為什麼需要這兩個集合
📌 用途說明
原本唯一的觀測手段是 Firebase 主控台的讀寫次數，它能回答「花了多少額度」，卻答不出 「哪些頁面真的有人用」——而後者才是決定改版順序與資料補齊順序的依據。
· analyticsDaily/{YYYY-MM-DD} — 一天一份，全站彙總與低基數維度。
· analyticsEntity/{YYYY-MM} — 一月一份，個別機師／機甲／武器的熱度（高基數）。
⚠ 為什麼不能靠 Cloudflare 請求日誌反推
本站的兩項架構優化剛好讓被動日誌結構性地測不準：
① SPA 路由不產生伺服器請求——從 /pilots 點進 /pilots/艾達，瀏覽器一個請求都沒發；
② 三層快取讓資料請求與瀏覽次數脫鉤——回訪使用者整場 session 可能發出 0 次 /api/data，Worker 邊緣快取再吃一層。
快取做得越好，被動日誌越測不準。因此必須主動埋點，沒有捷徑。
02 — Schema
欄位結構

analyticsDaily/{YYYY-MM-DD}

{ date: '2026-08-08', // 文件 ID 同值；日界線為 UTC+8 // ── 總量 ── pv: 1240, // 原始瀏覽次數（含來回點擊） upv: 820, // 去重後：同 session 同頁只計一次 ← 主指標 sessions: 210, // 造訪次數（10 分鐘閒置切分） visitors: 168, // 當日不重複裝置數 // ── 維度（皆為低基數 map，以「造訪」為計數單位）── byRoute: { pilots: { pv: 190, upv: 96 }, pilots_detail: { … } }, byLang: { zh_tw: 90, zh_cn: 55, en: 48, ja: 9, other: 8 }, byCountry: { TW: 120, CN: 48, HK: 22, XX: 20 }, byAuth: { guest: 145, user: 65 }, byDevice: { mobile: 130, desktop: 75, tablet: 5 }, byRef: { direct: 150, google_com: 30, … }, // ── 維運 ── writes: 210, // 當日寫入文件數＝熔斷器的燃料表 truncatedAt: null, // 有值代表當日資料不完整（見 04） truncatedReason: 'writeBudget', updatedAt: Timestamp }

analyticsEntity/{YYYY-MM}

{ month: '2026-08', pilots: { '艾達': 320, '露娜': 210, … }, // key 是 Firestore 文件 ID mechs: { … }, weapons: { … } }
⚠ entity 的欄位路徑必須反引號包裹
本專案的文件 ID 含中文（src/utils/idSlug.ts 的 slugify 刻意保留 CJK）， 而 Firestore 未引用的欄位路徑片段只允許 [a-zA-Z_][a-zA-Z0-9_]*。 因此 Worker 組出的是 pilots.`艾達`。
既然要包裹，就必須確保 id 逃不出引號——故採白名單字元類別 （只放行 CJK／英數／_／-），反引號、反斜線、點全落在範圍外，逃逸在字面上不可能發生。
為什麼路由用「樣板」而非實際網址
/pilots/艾達 與 /pilots/露娜 都記成 pilots_detail。 若用實際網址當 key，byRoute 這個 map 會長出上百個鍵並撐爆日文件（單文件上限 1 MiB）。 個別實體的熱度改存 analyticsEntity 的月文件（1,500 個 id 約 60 KB，餘裕充足）。
03 — 安全規則
全站唯一 write: if false 的集合
match /analyticsDaily/{docId} { allow read: if isAdmin(); allow write: if false; } match /analyticsEntity/{docId} { allow read: if isAdmin(); allow write: if false; }
⚠ 為什麼對所有 client 禁寫（連管理員都不行）
訪客也要統計 ⇒ 不能要求登入 ⇒ 若改成 client 直寫就得開 create: if true， 那等於讓任何人用迴圈寫爆全專案共用的每日寫入額度，並任意灌水數字。
唯一的寫入者是 Cloudflare Worker，它以 service account 繞過安全規則（同 PLAN-029 的代讀架構）， 另有格式防護、數量上限、寫入預算熔斷器三層把關。
讀取為何是 isAdmin() 而非 isOwnerRole()
內容是站務彙總數字，不含任何可識別個人的行為資料（PLAN-046 Q4 裁決不記錄個別使用者）， 敏感度低於 systemLog 那種帶裝置指紋的記錄，沒必要收到只有 OWNER 看得到。
保留期限：刻意不設 TTL
日文件約 3 KB、月文件約 60 KB，一年合計不到 2 MB —— 與 changeHistory／ systemLog（存整份文件快照，故需過期政策）不同，本集合小到可永久保留。
04 — 讀取時必讀
truncatedAt：資料完整性標記
⚠ 消費這份資料的任何介面都必須檢查 truncatedAt
有值代表當日統計在該時刻因寫入預算熔斷而中止，之後的資料全部沒有記到。
最危險的不是熔斷，是熔斷了但報表看不出來——若某天下午三點熔斷、儀表板卻照樣畫出一條 完整曲線，就會拿一個「看起來正常但少了半天」的數字去做決策，那比沒有統計更糟。
後台約定：該日資料點改紅色虛線並標註中止時間； 趨勢圖與 TOP N 排行自動排除被截斷的日子，避免污染比較基準。
其他已知誤差（後台應一併標示）
· UV 是裝置估算值：清快取／無痕／換裝置都會多算一人。
· byCountry 是網路位置，不是受眾語言：EN 服玩家散布各國、CN 玩家常走 VPN 顯示為 US／JP／HK。要看受眾組成請用 byLang，兩者並存互補。
· 關頁太快時 beacon 可能未送出（少數）；爬蟲只擋得掉機房 IP。
· UPV 的去重窗口是 10 分鐘，與多數統計工具的 30 分鐘不同，不可直接與別站數字比較。

讀取端的兩個約定
· 缺漏的日子由 API 端補零，保證回傳長度等於天數。若讓每個消費端自己處理 「陣列長度不等於天數」，很容易寫成把 7 天畫成 5 天——看起來正常，實際上把沒有流量的日子悄悄壓縮掉了。
· 用 getDocs 不用 onSnapshot：統計不需要即時，卻會為此持續佔用連線與讀取配額。 查詢用 where('date','>=') + orderBy('date')，同欄位故不需要複合索引。
⚠ Worker 端刻意不放頁面白名單
若 /api/collect 持有一份「合法頁面 key 清單」，就是原封不動重演 PLAN-043 的雙名單不同步事故 （漏一個 key → 正式站壞、本機全綠），而且更難發現——它不報 404，只是數字少了。
改用格式正則 + 數量上限：名單式防護問「這個 key 合法嗎」（需要知識 → 需要同步 → 會腐化）； 格式式防護問「這個 key 會不會造成傷害」（不需要知識 → 永遠不用改）。
代價僅是報表可能多一列雜訊，由顯示層過濾即可——把不同步的後果從「資料遺失」降級成「顯示雜訊」。
