01 — Security Rules
Firestore 安全規則
現行授權模型四句話：遊戲資料一律 read/write: if isAdmin()（前台改由 Cloudflare Worker 以 service account 代讀）；故事館四個集合另開給 canEditLore() （ADMIN／OWNER 之外再加故事館協作編輯 LORE_EDITOR，可讀、建、改但不能刪，且碰不到遊戲資料）； 用戶資料本人可讀寫，但不能自行提權，角色只有 OWNER 能授予； 稽核類集合 append-only，寫下去連管理員也改不掉。
角色與輔助函數
輔助函數放行的 role用在哪
isOwner(userId)（不看角色，request.auth.uid == userId）用戶自己的資料
canEditLore()LORE_EDITOR / ADMIN / OWNER故事館四個集合的讀／建／改、meta/gameData 的故事館版本號 bump、changeHistory（限 lore 兩類）與 systemLog 的 create
isAdmin()ADMIN / OWNER遊戲資料與 meta、公告 staging、使用統計的讀取、故事館的 delete、changeHistory 的讀取、使用者 profile 的讀取
isOwnerRole()OWNER改任何人的 profile（授予角色）、systemLog 的讀取

稽核紀錄
changeHistory		 isAdmin() 僅 create，且須 actorUid == request.auth.uid && (isAdmin() || (canEditLore() && target in ['pilotLore', 'mechLore']))；
update, delete: if false		 全站唯一不用 write: if isAdmin() 的寫法。write 涵蓋 update/delete，沿用那套的話管理員能竄改或抹除自己的操作記錄，稽核價值歸零。額外綁 actorUid 是第二層：append-only 防「竄改既有記錄」，綁 uid 防「偽造新記錄嫁禍他人」（後者因 append-only 還永久刪不掉）。過期交給 Firestore 原生 TTL，TTL 是後端程序、不受規則約束。
PLAN-042-H：協作編輯也要能寫自己的存檔記錄，但 target 限 pilotLore／mechLore（saveWithRevision 只有這兩館會走到；徽章與廠商是 writeDoc＋bump、不留稽核）。讀取仍只給管理者。 這兩館的存檔是「文件＋帶前一版快照的 log」同一筆交易：log 被這條擋下時整筆失敗、文件不變（emu:test-rules「存檔交易」五項）。

update 本人不得改 role，isOwnerRole() 可改任何人		 提權防護：建立時強制 role='USER'，更新時用 diff().affectedKeys().hasAny(['role']) 擋自改角色，只有 OWNER 能授予角色（含 PLAN-042-H 的 LORE_EDITOR；這條規則本身未因此改動）。
2026-08-23 起沒有任何匿名讀取分支，見下方。
✅ 2026-08-23：管理員 profile 的匿名讀取已收回（PLAN-051） 在此之前，match /{path=**}/profile/{docId} 與 match /users/{userId}/profile/{docId} 都帶著 || resource.data.role in ['ADMIN', 'OWNER']，而這個條件沒有任何 auth gate。 用意是讓首頁的維護團隊區塊在未登入時也能顯示（getSiteTeamProfiles() 走 collectionGroup('profile')）。
代價是 Firestore 的授權單位是文件而不是欄位——沒有 field-level read mask， 讀得到文件就是整份 UserProfile，其中 email 是必填， 等於每一位匿名訪客的瀏覽器裡都有全部管理員的 email。
解法是換資料來源而非改規則：兩條規則的匿名分支已移除（收成 isOwner(userId) || isAdmin() 與 isAdmin()）， 首頁團隊名單改由 Worker 的 GET /api/site-team 以 service account 代讀、 只回白名單欄位（見 users.html）。profile 仍然只有一份資料來源， Worker 只是在出口做欄位過濾。 → PLAN-051
✅ 2026-10-17：新增故事館協作編輯角色 LORE_EDITOR（PLAN-042-H） 在 USER 與 ADMIN 之間多一個角色：只拿得到故事館四個集合（pilotLore／mechLore／ factionEmblems／mechMakers），外加兩件存檔的附帶寫入——稽核 （changeHistory，限 lore 兩類 target）與版本號 bump（meta/gameData，限那四個鍵）。 遊戲資料一律仍是 isAdmin()；systemLog 的 create 一併改為 canEditLore()。
規則側的角色清單 ['LORE_EDITOR', 'ADMIN', 'OWNER'] 對應前端 src/utils/userRole.ts 的 canEditLore()，兩邊要一起改（規則語言讀不到 TS 常數）。
驗證：npm run emu:test-rules 的 loreEditorSuite（26 項）每一條「應放行」都配一條相鄰的「應被擋」—— 只驗被擋那側的話 canEditLore() 寫成永遠為假也會全綠，只驗放行那側的話把集合開成 isAuthenticated() 也會全綠。
關鍵片段
firestore.rules（輔助函數與提權防護，節錄）// role 存在子文件 users/{uid}/profile/main，不是 users/{uid}/profile function isAdmin() { return isAuthenticated() && get(/databases/$(database)/documents/users/$(request.auth.uid)/profile/main) .data.role in ['ADMIN', 'OWNER']; } function isOwnerRole() { return isAuthenticated() && get(/databases/$(database)/documents/users/$(request.auth.uid)/profile/main) .data.role == 'OWNER'; } // PLAN-042-H：故事館協作編輯。⚠ 角色清單對應 src/utils/userRole.ts 的 canEditLore() function canEditLore() { return isAuthenticated() && get(/databases/$(database)/documents/users/$(request.auth.uid)/profile/main) .data.role in ['LORE_EDITOR', 'ADMIN', 'OWNER']; } // bumpDataVersion 的寫入形狀是 merge { versions: { <key>: 時間戳 }, updatedAt }，兩層都用 hasOnly() 鎖死 function isLoreVersionBump() { return request.resource.data.diff(resource.data).affectedKeys().hasOnly(['versions', 'updatedAt']) && request.resource.data.versions.diff(resource.data.versions).affectedKeys() .hasOnly(['pilotLore', 'mechLore', 'factionEmblems', 'mechMakers']); } match /pilotLore/{docId} { // mechLore / factionEmblems / mechMakers 同形 allow read, create, update: if canEditLore(); allow delete: if isAdmin(); } match /meta/{docId} { allow read: if isAdmin(); allow write: if isAdmin(); allow update: if docId == 'gameData' && canEditLore() && isLoreVersionBump(); } match /users/{userId}/profile/{docId} { // 建立時只允許 role='USER'，禁止自行設為 ADMIN/OWNER allow create: if isOwner(userId) && request.resource.data.role == 'USER'; // 本人可更新自己 profile，但不能碰 role；OWNER 可改任何人（含授予角色） allow update: if (isOwner(userId) && !request.resource.data.diff(resource.data).affectedKeys().hasAny(['role'])) || isOwnerRole(); }
⚠️ 管理員設定與讀取成本 初始管理員需透過 Firebase Console 或 Admin SDK 手動把 users/{uid}/profile/main 的 role 設為 'OWNER'；之後 OWNER 可在後台「用戶管理」分頁的下拉選單授予他人 LORE_EDITOR（故事館協作編輯）或 ADMIN（UI 不提供指派 OWNER）。
isAdmin()／canEditLore()／isOwnerRole() 每次驗證都會 get() 一次 profile 文件，計入 Firestore 讀取次數。 這是把角色存在 Firestore 而非 custom claims 的代價——換來的是不必重新簽發 token 就能即時改角色。
02 — Storage Rules
Firebase Storage 安全規則（未啟用）
storage.rules 存在於 repo，但從未部署、目前也部署不了——本專案的 Firebase Storage 從來沒有啟用過。使用者上傳的圖片實際走 Cloudinary。
⚠️ 這份規則現在一條都沒有效力 執行 firebase deploy --only storage 會得到 Firebase Storage has not been set up on project 'mecharashi-tools'（2026-08-23 實測）。
保留檔案的用意是：哪天真的在 Console 啟用 Storage，這份規則會立刻生效， 所以裡面不能留有「反正沒部署」心態寫下的寬鬆規則。
storage.rules（現況）rules_version = '2'; service firebase.storage { match /b/{bucket}/o { // ── 用戶頭像（公開讀，本人限寫）─────────────── match /avatars/{uid}/{allPaths=**} { allow read: if true; allow write: if request.auth != null && request.auth.uid == uid && request.resource.size < 2 * 1024 * 1024 && request.resource.contentType.matches('image/.*'); } // ── 版本前瞻圖（公開讀，寫入已關閉）───────────── match /banners/{allPaths=**} { allow read: if true; allow write: if false; } } }
🔄 2026-08-23：banners 的寫入權限收掉 原本是 allow write: if request.auth != null ＋ 10MB／圖片格式限制， 註解寫「管理員身分由應用層驗證」。但應用層擋不住直接呼叫 Storage SDK 的人， 規則層才是唯一防線——照那樣寫，任何人辦一個 Google 帳號登入本站，就能往 banners/ 無限寫 10MB 檔案（{allPaths=**} 檔名任取、沒有數量上限）。
因為 Storage 未啟用，這個缺口目前不會被利用；收掉是為了避免它在啟用當天變成活的。 改成 if false 不影響任何功能：版本橫幅走的是本地 /images/banners/*.webp（見 src/data/patchVersions/）。
使用者上傳的圖片實際走哪裡：Cloudinary
  • 實作：src/lib/imageUpload.ts — 前端壓縮為 WebP（quality 0.85）後， 以 unsigned upload preset 直接 POST 到 api.cloudinary.com。
  • 頭像流程：uploadAvatar()（src/lib/profileApi.ts） 取得 secure_url 後寫回 users/{uid}/profile/main 的 avatarUrl。 Firestore 只存網址，不存圖。
  • ⚠ 2MB 與 WebP 限制在前端：MAX_BYTES 與 compressToWebP() 都是瀏覽器端的檢查，對直接呼叫 Cloudinary API 的人無效—— 這與上面 banners 註解犯的是同一種錯。cloud name 與 upload_preset 都在前端 bundle 裡（VITE_ 開頭必然公開），任何人都能拿去上傳。
  • 因此真正的把關在 Cloudinary preset 設定，不在這個 repo： 允許的格式、單檔大小上限、資料夾鎖定（folder 參數目前由前端傳，未鎖）、 以及 moderation／rate limit。修改站台程式碼無法補這一塊。

04 — Migration Plan
資料遷移計畫：JSON → Firestore
Phase 4（Firebase 資料庫建置）的具體執行步驟。
1
建立 Firebase 專案 + 啟用 Firestore
Firebase Console 建立專案，選擇 Cloud Firestore（Production mode），設定台灣/亞洲地區（asia-east1）。安裝 Firebase SDK：npm install firebase。
2
建立 src/types/enums.ts
將所有 Enum 定義寫入 enums.ts，同步更新 src/types/index.ts 的 interface 定義，所有字串字面量欄位替換為對應 Enum 型別。
3
建立 src/lib/firebase.ts — Firebase 初始化
初始化 Firebase App、Auth、Firestore 實例。環境變數存放 Firebase 設定（VITE_FIREBASE_API_KEY 等）於 .env.local。
4
撰寫遷移腳本：scripts/migrate-to-firestore.ts
讀取現有 JSON 檔案 → 欄位值轉換為 Enum 字串值 → 使用 Firebase Admin SDK 批量寫入（每批 500 筆，Firestore 批次限制）。腳本支援 dry-run 模式，先驗證資料格式再實際寫入。
5
部署 Firestore Security Rules + 複合索引
執行 firebase deploy --only firestore:rules,firestore:indexes。驗證：用一般帳號測試只能讀不能寫；用 Admin 帳號測試可寫入。
6
建立 Firestore 資料讀取 Hooks
src/hooks/ 下建立 usePilots、useMechs、useModules 等 React Query / SWR hooks，取代現有的 fetch('/data/pilots.json')。實作分頁、篩選、快取策略。
7
逐頁替換資料來源
依序更新：機師圖鑑 → 機甲圖鑑 → 模組圖鑑 → 武器圖鑑 → 背包圖鑑 → 配裝模擬器。每頁替換後執行 build + 功能測試，確認無回歸問題。
8
移除靜態 JSON 檔案（或保留為備份）
確認所有頁面均從 Firestore 讀取後，可將 public/data/*.json 移至 scripts/backup/ 做為歷史備份，不再部署至 GitHub Pages。
9
初始化 buffs + skills Collections
建立空的 buffs Collection（文件結構佔位），從現有 pilot 技能資料抽取共用技能寫入 skills Collection。BUFF 具體定義待遊戲資料整理後補充。
⚠️ 注意事項（2026-08-23 校正，原內容已全數過時） • 方案已是 Blaze（用量計費），不是 Spark。免費額度（50,000 讀取／20,000 寫入 每日）仍然照給， 差別在超出後不會停擺而是計費——因此「任何人可寫」的缺口在這裡是帳單問題，不會被額度自動擋下。
• 快取不是 React Query／SWR，是自建的三層版本 gate：記憶體 → localStorage （mecharashi_gd_*）→ Firestore，由 GameDataContext 依 meta/gameData 的集合版本號決定是否重抓（PLAN-016／017）。
• 前端已不再直連 Firestore 讀公開資料。PLAN-029 之後遊戲資料集合一律 read: if isAdmin()，前台改走同源的 Cloudflare Worker （/api/data/:collection，Worker 以 service account 繞過規則代讀）。 上面那句「確認安全規則允許公開讀取」是舊架構的說法，切勿照做。
