01 — 為什麼需要這份文件
一把金鑰擋住全站，而且症狀不像設定問題
⚠ 本文件刻意不公開
02_技術文件/04_Firebase 不在 scripts/copy-docs.mjs 的 INCLUDE 白名單內，故本頁不會被複製進 dist/、也不會出現在 /documents。內容含專案 ID 與金鑰設定，不要把此目錄加進白名單。
📌 這把金鑰是什麼
GCP 憑證名稱 Firebase Browser Key (mecharashi)（值 AIza…Qj8V0）， 也就是 .env.local / CI 的 VITE_FIREBASE_API_KEY。
它會隨 JS bundle 出貨給所有訪客，本來就是公開值——真正的防護是它身上那兩份限制清單， 不是保密。前台每一次 Firestore 讀寫、每一次登入、每一次登入狀態續期都要經過它。
🩸 為什麼特別容易出事：症狀不像設定問題
白名單缺項的表現是「某個功能在某個時機壞掉」，而不是「整站掛掉」。 2026-08-09 那次是「登入永遠成功，但一小時後掉登入」——完全看不出跟 API 金鑰有關， 整整兩個多月被誤判成瀏覽器儲存問題（見下方 04）。
凡是看到 *-are-blocked 結尾的錯誤碼，第一個就查這裡。
02 — 兩份清單，別搞混
應用程式限制 vs API 限制
📌 金鑰編輯頁上下兩塊，管的是完全不同的事
· 應用程式限制（上）＝誰可以用這把金鑰 → HTTP 參照網址（referrer）白名單
· API 限制（下）＝這把金鑰可以打哪些 API → 服務白名單
兩者各自獨立把關，缺哪一份就報哪一種錯，症狀不同、要各加各的。 第三份常被一起搞混的是 Firebase Console 的「Auth 授權網域」，那又是另一個地方。
🔍 錯誤碼對照表（判讀的關鍵）
錯誤 reasonFirebase SDK 端的錯誤碼長相缺哪一份去哪裡加
API_KEY_SERVICE_BLOCKED auth/requests-to-this-api-…-are-blocked API 限制（服務白名單） GCP 憑證 → 該金鑰 → API 限制
API_KEY_HTTP_REFERRER_BLOCKED auth/requests-from-referer-…-are-blocked 應用程式限制（referrer 白名單） GCP 憑證 → 該金鑰 → 應用程式限制
— auth/unauthorized-domain Firebase Auth 授權網域 Firebase Console → Authentication → Settings
⚠ 兩種 403 長得很像，差在 this-api 與 referer 一字
用 curl 驗證時尤其要注意：沒帶 Referer 標頭的請求會先被 referrer 那層擋掉， 永遠測不到 API 限制那層，很容易誤判成「referrer 白名單壞了」。驗證方式見下方 05。
🌐 換網域時的三件必辦事項
2026-07-25 切換到 mecharashi.wiki 時，這三項各漏一項就壞一次，最後是逐一補齊的：
① GCP 憑證 → 該金鑰 → 應用程式限制 加 https://mecharashi.wiki/* 與 https://www.mecharashi.wiki/* （GCP 萬用字元不涵蓋子網域，子網域要另加 https://*.mecharashi.wiki/*）
② Firebase Console → Authentication → 授權網域
③ 若當時仍有 reCAPTCHA／App Check，還要加它的網域白名單 （本專案已於 PLAN-029 Phase 3-3 退場，故現在只剩 ①②）

04 — 2026-08-09 事故
「用著用著就登出」追了兩個月，真因是這裡缺一個勾
⛓️ 完整因果鏈
Browser API key 的「API 限制」白名單缺 Token Service API ↓ 登入走 identitytoolkit（在白名單內）→ 永遠成功 ↓ idToken 壽命 1 小時，SDK 在到期前 ~5 分鐘自動續期 → 呼叫 securetoken.googleapis.com 的 SecureToken.GrantToken ↓ 403 API_KEY_SERVICE_BLOCKED ↓ SDK 判定憑證無效 → 主動 signOut，並從 IndexedDB 移除憑證記錄 ↓ 使用者下次 F5／開新分頁 → 才「發現」已經被登出
🕵️ 為什麼誤判了兩個月
症狀全部指向「瀏覽器把資料清掉了」，而且每一項都很有說服力：
· 被登出的那一刻 IndexedDB 的 firebase:authUser:* 確實不見了
· sessionAgeSec 恆為 0～1 秒 → 看起來像「載入時儲存已經是空的」
· 間隔不規則（24 分鐘～1.1 小時）→ 看起來不像固定週期的 token 到期
實際上：憑證是 SDK 自己刪的；0 秒是因為續期在背景失敗、F5 時才被發現； 間隔不規則是因為續期時機取決於「當下 token 已經多老」，而重新整理會沿用既有 token 而非換新的。
教訓：從儲存層反推永遠猜不到答案。真正破案的是把 getIdToken() 的 error code 直接記下來（PLAN-045 的 probeToken() → systemLog.authErrors）。
💀 更值得記取的：這件事我們預言過
2026-07-26 換網域補 referrer 白名單時，就已經寫下 「這把金鑰的 API 限制清單若缺 Token Service API，症狀會是能登入但一小時後掉登入」。 但那句話只存在於一則除錯筆記的附註裡，沒有人回頭去補，於是它一路發作到 8/9。
這份文件的存在本身就是那個教訓的產物——會反覆踩的坑要進版控，不能只活在筆記裡。
✅ 修復（2026-08-09）
GCP Console → API 和服務 → 憑證 → Firebase Browser Key (mecharashi) → API 限制 → 勾選 Token Service API → 儲存。
不需改任何程式碼、不需重新部署，設定在 Google 端，數分鐘內生效。 唯一的後續動作是各維護者重新登入一次（舊憑證已被 SDK 刪除，救不回來）。
05 — 驗證手法
不需登入、不需部署，30 秒內確認
📌 原理
直接對目標 API 送一個故意無效的請求，看它是被「金鑰限制」擋掉（403）， 還是順利抵達 API 後才因為參數無效被拒（400）。
400 才是我們要的結果——它證明金鑰打得到這個 API。
KEY=$(grep '^VITE_FIREBASE_API_KEY=' .env.local | cut -d= -f2 | tr -d '\r"') curl -s -w "\nHTTP %{http_code}\n" -X POST \ "https://securetoken.googleapis.com/v1/token?key=$KEY" \ -H "Content-Type: application/x-www-form-urlencoded" \ -H "Referer: https://mecharashi.wiki/" # ← 必帶，否則測不到 API 限制那層 \ -d "grant_type=refresh_token&refresh_token=deliberately-invalid"
結果reason意義
HTTP 400INVALID_REFRESH_TOKEN ✅ 正常——API 通了，只是拒絕我們故意送的假 token
HTTP 403API_KEY_SERVICE_BLOCKED ❌ API 限制缺這個服務 → 去補白名單
HTTP 403API_KEY_HTTP_REFERRER_BLOCKED ⚠ 你忘了帶 Referer，或該網域不在 referrer 白名單
⚠ 為什麼不用「登入後等一小時」來驗證
那要等一小時，而且失敗時分不出是設定沒生效還是還沒到續期時機。上面這發 curl 是 確定性的：改設定前打一次、改完打一次，兩次結果不同就是生效了。
同樣手法可套用到任何一個 API——把 URL 換成該服務的端點即可。
06 — 維護規則
什麼時候要回來動這裡
1
新增任何 Firebase 產品時
Realtime Database、Cloud Functions（client 呼叫）、Remote Config、Cloud Messaging… 每一個都有自己的 *.googleapis.com，一律要回來把對應 API 加進白名單。 開發時通常不會發現——localhost 也在 referrer 白名單內，但 API 限制是全域的， 所以本機一樣會壞；真正危險的是「本機沒用到那個產品、上線才用到」的情況。
2
換網域 / 加子網域時
動的是應用程式限制那一份，不是 API 限制。三件必辦見上方 02 節末。
3
看到 *-are-blocked 錯誤時
先用 02 節的對照表判斷是哪一份清單，再用 05 節的 curl 確認。 不要先去查程式碼——這類錯誤跟前端實作無關。
4
看到「能用但過一陣子就壞」的怪症狀時
這是白名單缺項最典型、也最難聯想的表現形式：初次操作的 API 有授權、 背景續期／輪詢的那支沒有。把它列進懷疑清單的前三名。
⚠ 永遠不要為了排錯而切成「不限制金鑰」
那會讓這把公開金鑰能打專案內任何 API，等於把 GCP 專案敞開。 要排錯就用 05 節的 curl 精準定位，只補真正缺的那一個。
