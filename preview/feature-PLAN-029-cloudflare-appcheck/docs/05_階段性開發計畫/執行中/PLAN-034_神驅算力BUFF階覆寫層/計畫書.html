Problem
問題背景
問題一：同一頁上，天賦說「凝勢III」而技能說「凝勢I」
PLAN-021 為艾達建立了 PilotTalent.ndVariants，讓天賦正文隨神經驅動算力就地改寫。 但艾達的技能（skill_輝斷終焉「並獲得2層[凝勢I]」、skill_破勢）同樣引用凝勢， 而凝勢的階也是隨 γ2 算力提升的（γ2 ≥ 10 → 凝勢II、≥ 13 → 凝勢III）。 PilotSkill / PilotSkillDoc 沒有任何 nd 相關欄位， 於是使用者在同一頁點動算力時，天賦跟著變、技能不動——這就是斷裂引用。
問題二：「凝勢是第幾階」這個事實在系統裡存了三份且互不連通
① 技能正文字串裡寫死的中文「凝勢Ⅰ」； ② descriptionRefs['凝勢Ⅰ'].level； ③ 天賦 ndVariants[].minSum 抄了一份 ND 門檻、再整段換文。
這正是 src/utils/numRefs.ts 檔頭所警告的「同一個數字存兩份必然漂移」， 只是這次漂移的不是數值而是階級。若照 PLAN-021 的模式把 ndVariants 複製到技能層， 這條規則會變成第四份、第五份——而且技能的 base 在 pilotSkills 集合、 副本會落在 pilots 集合，分屬 SkillAdmin 與 PilotAdmin 兩個後台分頁， 兩邊無任何連動提示，漂移必然發生且無人會發現。
問題三（既有 bug，與本計畫獨立）：畫面上那個 chip 的浮窗現在就是空的
實測 skill_破勢 與 skill_輝斷終焉 的 refId 寫成裸字 凝勢、漏了 buff_ 前綴，buffs 集合查無此 id， EntityRefView 查不到直接 return null。 同類斷鏈共 10 筆（多為 PLAN-024 等級化合併後未回頭修的舊分級 ID， 如 BUFF_命中率降低II、BUFF_護甲提升I、BUFF_隱形I）， 另有 12 筆引用指向有 levels[] 的階梯 buff 卻沒填 level。
盤點數據（實測 emulator-seed，2026-07-19）
  • 10 筆斷鏈 refId（buffs 集合查無）、12 筆指向階梯 buff 卻缺 level
  • 98 筆技能引用指向 39 族階梯 buff——覆寫層的實際作用面遠大於「艾達的凝勢」
  • pilotSkills 705 份正文中 <refId.lvN.attr> 數值 token 出現 0 次 （全部數值 token 只存在於天賦正文）→ 數值症狀在技能側沒有掛載點
  • 有 ndVariants 的是兩位機師：艾達（凝勢 lv1→2/3）與梅利莎（常效維護 lv1→2/3/4/5）
核心建模假設已驗證成立
「升階門檻 = 掛載該能力的 NeuralDriveLevel.minSum」—— 艾達 γ2 Lv4/Lv5/Lv6 的 minSum = 10/13/16，與其 ndVariants 的 10/13/16 完全吻合； 梅利莎 γ2 Lv1/Lv4/Lv5/Lv6 = 1/10/13/16，與其四個變體逐一對齊。 門檻本來就已經在資料裡了，不需要新的門檻欄位——這是本方案「零重複」賣點的事實基礎。
Design
設計決策
決策一：階不是引用點上的常數，而是配裝狀態的函數
不幫技能抄一份 ndVariants，改在解析引用時插一層情境覆寫： 機師頁依當前 ND 算力算出一張 Map<buffId, {level, name}>， chip 顯示名、浮窗內容、（Slice 2 起）數值 token 都問這張表。 全頁只有一張表 → 「天賦說 III、技能說 I」在結構上不可能發生。
決策二：升階規則存在「神經驅動能力」上，門檻沿用掛載級
在 NeuralDriveAbility 新增 buffUpgrades?: string[]（元素格式同 buffIds 的 id@N）。 語意是「升階」而非「賦予」——本能力生效時，該 buff 家族在本機師頁的生效階至少為 N。 刻意不存 zone / minSum：門檻就是它被掛在哪一個 NeuralDriveLevel（見上方已驗證的建模假設）， 使同一條規則在系統中只存一份、漂移面積為 1 而非 N。
更正：門檻「由爬蟲維護會自癒」不成立
scripts/scrape-pilots-v3.js 的 ndAreIds guard：只要該機師每個 ND level 都有 abilityId（PLAN-023 flip 後全站如此），neuralDrive 整段跳過補丁， minSum 永遠不會被 API 值刷新。本方案的優勢須誠實表述為 「同一條門檻只存一份，漂移面積 1 而非 N」，而非「會自動更新」。 緩解手段見 Phase H 的 check-nd-minsum-drift.mjs。
決策三：換字條件是「確實抬升」，不是「有值」
lifted = ov != null && ov.level > (ref.level ?? 0)。
這是本設計最容易寫錯、也最致命的一行。若寫成「覆寫表有值就換字」， 由於 eff = max(ref.level, override) 在無覆寫時也等於 ref.level， 只要 BuffLevel.name 一填，全站 20 個 RefText 站點近 100 個 chip 的字面 都會被靜默替換成 BuffLevel.name——而實測這些字面全形（凝勢Ⅰ）半形（短路I）混用， 還有 縱敵ⅠⅠ、失穩ⅠⅠⅠ（重複 U+2160）這種損毀 name 會被升格成顯示值。 抬升時必須加視覺標記（雙底線 + title「已由 γ2 算力自 Lv1 提升至 Lv3」）—— 技能區是使用者對照官方 wiki 最頻繁的地方。
決策四：降級以 buff 家族為單位「原子化」
覆寫表建表時即驗證，五道閘門任一不過則該家族整族不進表（字面／浮窗／數值一起維持原狀）： ① buffs 已載入 ② 該級存在 ③ BuffLevel.name 有值 ④ 掛載級 minSum > 0 ⑤ 屬自身增益。 絕不允許「不換字但數值照抬」——那會產生「獲得2層[凝勢Ⅰ]，可疊加7層」這種字面與數字自相矛盾的句子， 比修改前更難察覺。使用者看到的是「點了沒反應」（可回報、dev 有 warn），而不是錯誤資訊。
決策五：四條寫死的資料規則
  • 等級變更一律走 buffUpgrades；ndVariants 只准表達非等級性變更 （如艾達 γ2 ≥ 16 的 [星爆] 與 3AP→5AP）
  • 只能選既有等級，不能計算等級——不得為了讓 buffUpgrades 能用而在共享 buffs 集合裡憑空造級
  • 通用能力不得填 buffUpgrades（nd_AP優化3 這類跨機師共享能力）
  • debuff 家族一律禁用，由 assertSelfBuff 在建表時攔截，不是只寫進文件
決策六：顯示名的權威落在 BuffLevel.name
實測 222 筆 buffs、39 族階梯 buff，目前「第 N 級叫什麼」在系統中完全沒有落點， 所以光把 ref 指到 lv3 也渲染不出「凝勢III」。
遊戲裡沒有階名的家族（BUFF_幹勁、BUFF_情報、buff_隱形） 填 name = buff.name 原字——這是「明示此級顯示為原名」的編輯決策， 字面不變但浮窗與數值正確抬升，且是 opt-in 而非靜默漏填。
刻意不做羅馬數字自動推導：現況資料已知損壞（失穩ⅠⅠⅠ／護甲降低ⅠⅠ）， 且 虛粒子矩陣EX 的 X 是羅馬字母、skill_緊急避險 的 [隱形] 字面根本沒有羅馬數字 卻指向 BUFF_隱形I——推導在實測髒資料上必然失敗。
決策七：模擬層不吃 buffUpgrades，且由 runSpec 強制
保護手段是 Site.excludeFromPool 宣告式排除，不用既有的 skipSiteId。 實測 buildBuffPool 只跑 SPECS 的 pilots / pilotSkills / modules / weapons / backpacks， 從不 traverse SPECS.neuralDriveAbilities，而 skipSiteId 是 runSpec 的單一 optional 參數、只有 pilots 傳入。靠呼叫端記得傳＝零保護， 而且測試會因「測到一條本來就沒被走過的路徑」而恆綠、零資訊量。

Scope
實作範圍與不在範圍內
分兩批交付。 Slice 1（Phase 0 / A / B / C / D / E）解掉使用者實際看到的技能斷裂； Slice 2（Phase F / G）只服務天賦側，是「塌縮 ndVariants 後仍維持正確」的配套。 理由：實測 705 支 pilotSkills 中 <refId.lvN.attr> token 出現 0 次， 數值症狀在技能這個實際斷裂點上沒有掛載點。
此外 Phase A（資料債修復）可獨立出貨——即使全案被否決也有殘值，它修的是現在畫面上就是錯的東西。
在範圍內：
  • 三個選填欄位：NeuralDriveAbility.buffUpgrades、BuffLevel.name、EntityRef.fixedLevel
  • src/utils/ndOverrides.ts 純函式層（建表即驗證、effectiveLevel、pickLevel、defaultNdLevels）
  • NdOverrideContext 與 RefChip 的抬升渲染 + 視覺標記 + 浮窗覆寫快照
  • 資料債修復：10 筆斷鏈 refId、12 筆缺 level、羅馬數字字形統一、3 筆損毀 buff.name
  • Site.excludeFromPool 與 red-case-first 的模擬層保護測試
  • 後台：NeuralDriveAdmin 的 buffUpgrades 下拉編輯器、BuffAdmin 階名欄位與 level 粒度級聯
  • Slice 2：numRefs 情境化、ndVariants 塌縮（艾達 + 梅利莎）
不在範圍內：
  • 模擬器同步——詳情頁點算力不影響模擬器，維持 buffPool 的滿級假設
  • EntityRef 的 scope（self/enemy）維度——根治敵我混用需要這個，是另一個量級的工程； 本計畫用「限縮 + 逐筆 fixedLevel 逃生門」緩解
  • 增量語意的升級（「最大疊加層數增加3層」）與絕對值缺級（「情報上限提升至35層」但資料裡沒有 35 層那一級）
  • 武器頁 / 模組頁等非機師情境的同段文字——它們沒有機師情境，維持原字面（列為已知限制）
  • 浮窗內再往下 drill 兩層以上——明訂不沿用覆寫快照
  • refType='term' 的引用——覆寫以 buffId 為 key，純概念指涉的 term chip 不加階名
Pitfalls
已驗證的地雷
地雷一：浮窗拿不到 provider——架構上不可能，不是實作疏忽
ReferenceProvider 在 src/App.tsx 位於 <Routes> 之上， EntityRefView 是 {children} 的兄弟—— PilotDetailPage 內部包的任何 provider 永遠不可能成為它的祖先。 因此浮窗唯一可行路徑是：RefChip 在送出 hoverRef / pinRef 前 把 level 烘進 EntityRef，並把覆寫快照一併存進 ReferenceContext。 換機師時必須清快照，否則釘選浮窗會殘留上一位機師的算力狀態。
地雷二：敵我混用（無解問題，只能緩解）
覆寫粒度是「buff 家族 × 整頁」，分不清敵我與來源。實測 98 筆階梯 buff 引用中， buff_失穩／護甲降低／命中率降低／迴避率降低 都是對敵 debuff 且被十數支技能共用。緩解＝硬性限縮（assertSelfBuff 建表時攔截） ＋ 逐筆 fixedLevel ＋ 掃描規則納入 npm test。 仍無法根治「同一族同時有敵我兩種用法」；Phase 0 若掃出這種家族且它正好是候選，該家族一律排除。
地雷三：本地模擬器對本案永久是盲的
scripts/export-emulator-slice.mjs 的 DICT_COLLECTIONS 缺 neuralDriveAbilities （實測 emulator-seed/ 只有四個檔）。不補進去的話，任何人在模擬器裡驗證機師頁， ND 能力都會查無 → 覆寫恆為空 → 「測起來完全正常（就是今天的行為）」，測不出任何回歸。 Phase 0 必須把它永久加進並提交，不是一次性調查動作。
地雷四：bump 腳本會直接拒絕本案的收尾指令
scripts/bump-data-version.mjs 的 KNOWN_KEYS 缺 neuralDriveAbilities（它是合法的 CollectionKey）。 收尾指令會在 initFirebase 之前就 exit(1)、一個集合都沒 bump。 操作者若沒細看輸出，資料已寫進 Firestore 但全站快取不失效 → 使用者點算力毫無反應， 而編輯者自己因 patchCollectionItem 就地同步、看起來一切正常。
地雷五：塌縮 ndVariants 會讓天賦面板整組消失
TalentNdPanel 第一行是 if (variants.length === 0) return null。 梅利莎 4 個變體與 base 的差異 100% 只有階級與 .lvN，依規則會被全數刪除 → 面板 return null → 「算力階／生效中」徽章與差異高亮全部消失，而正文卻仍在隨算力變動。 塌縮的前置條件是先把面板改成「依 ndOverrides 或 ndVariants 任一有值即渲染」。
地雷六：等級來源從兩個變三個，破壞既有不變式
正文的 .lvN token、EntityRef.level、ND 覆寫——三個來源。 這破壞了 numRefs.ts 檔頭明文宣告的「token 自描述、不靠出現位置」不變式 （資料庫寫 lv1.maxStack、buff lv1.maxStack=5，畫面卻顯示 7）。 改寫該檔頭註解是 Phase B 的交付項，不可默默帶過； NumRefValue 的 title 也須明寫抬升來源。
地雷七：爬蟲會洗掉掛載路徑
buffUpgrades 存在 neuralDriveAbilities 集合，天然避開 pilots 文件的 --force 洗值風險。但 abilityId 是存在 pilots.neuralDrive[].levels[].abilityId 上的——爬蟲補丁若重寫 neuralDrive 陣列會洗掉它， resolveNeuralDriveLevel 退回嵌入欄位（實測 buffIds 已全空）→ 覆寫恆為空。 這是 PLAN-023 既有暴露面，但本案讓它從「顯示能力描述缺失」升級為「全頁 buff 等級靜默失效」。
地雷八：效能——context value 必須 memo 化
RefChip 是全站扇出最高的葉節點。NdOverrideContext 的 value 若每次 render 新建物件，provider 底下所有 chip 都會失去 memo（即使覆寫表為空的機師頁也一樣）。 無 provider 的頁面走模組級 EMPTY 常數則無此問題。
