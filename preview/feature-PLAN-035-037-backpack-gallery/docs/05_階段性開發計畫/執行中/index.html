PLAN-037 · 背包圖鑑優化

背包圖鑑最終優化四連：① 預設階層只選特種(SS)、查詢量小故移除分頁；② 把「變體」子篩選升級為「能力」並沿 craft 前置鏈跨階篩選——新增 backpackAbility 循鏈取底層 S 變體背包的 line+variant，讓「強化→首攻」能命中原本名字無變體的 SS（主宰者背包 → 飛行強化背包·首攻 → 強化背包·首攻），line 篩改嚴格（一併定案 PLAN-035 遺留問題）；③ 移除被取代的前置背包 facet；④「特種背包製作」toggle 改為「包含武器」預設開（來源池加複合武器、與背包同條件篩選；冷快取 +169 read、回訪 0）。整合 PLAN-035 階層與 PLAN-036 前置關係，live 驗證通過。

PLAN-036 · 特種背包前置關係

SS 特種背包在遊戲【特種背包製作】台是「圖紙＋前置主背包＋複合背包(S+)＋任意 3 個 S」的固定配方合成的。其中「前置主背包」無法從名字 derive（征服者背包 ← 某前置背包，名字無關聯），故新增 Backpack.craft.prereqBackpackId 只存這一個事實、後台手輸，其餘（種類/圖紙）全 derive。背包圖鑑新增「依前置背包種類篩選」，未輸入關聯的 SS 先不顯示。圖紙統一顯示「{名}設計圖」，材料來源（武裝討伐）與形態二（特種背包武器，屬 PLAN-031）另做。是 PLAN-035 決策六的第一步。

PLAN-035 · 背包分類階層

依遊戲背包合成階層把 180 件背包分成素材(A/B) / 基礎(S) / 複合(S+) / 特種(SS)四層——預設隱藏沒人用的 A/B 素材、補上「強化 vs 干擾」第二軸與變體篩選。實測 rarity 與階層一對一，且 type 欄位只編碼「基礎功能軸」、「強化/干擾」只存在名字字串（出力強化背包 vs 出力干擾背包 同 type=PowerAdd），故第二軸須靠 name 解析。階層與軸皆從既有資料 derive，零資料改動；先驗證够用再決定是否結構化。延伸的「背包合成關係鏈」是 PLAN-031 武器 upgrade 的背包版，列為可選後續。前置 PLAN-031（同動 BackpacksPage）已 commit。

PLAN-034 · 神驅算力 BUFF 階覆寫層

PLAN-021 讓艾達的天賦正文隨神經驅動算力改寫，但她的技能也引用凝勢，而凝勢的階同樣隨 γ2 提升（≥10 → II、≥13 → III）。PilotSkill 沒有對應機制，於是點動算力時天賦跟著變、技能不動——斷裂引用。根因是「凝勢是第幾階」在系統裡存了三份互不連通（正文字面／descriptionRefs.level／ndVariants.minSum），照 PLAN-021 模式複製到技能層只會變成第四第五份，且 base 在 pilotSkills、副本在 pilots，跨集合跨後台分頁必然漂移。本計畫改以階不是常數而是配裝狀態的函數建模：升階規則存在 NeuralDriveAbility.buffUpgrades（id@N），門檻沿用它掛載的那一級——實測艾達 γ2 Lv4/5/6 minSum=10/13/16 與其變體 100% 吻合，門檻本來就在資料裡，不需新欄位。機師頁算出單一 Map<buffId, {level,name}> 經 context 餵給 RefChip，全頁一張表 → 天賦說 III 而技能說 I 結構上不可能。設計上兩個關鍵防線：換字條件必須是「確實抬升」而非「有值」（否則 BuffLevel.name 一填就靜默改寫全站近 100 個 chip 的字面），降級必須以家族為單位原子化（否則會產生「獲得2層[凝勢Ⅰ]，可疊加7層」這種字面與數字自相矛盾）。另修 10 筆現在就查不到浮窗的斷鏈 refId（含凝勢本身漏了 buff_ 前綴）與 12 筆缺 level——此批可獨立出貨。已知無解限制：覆寫粒度是「家族×整頁」，分不清敵我，故硬性限縮只准用於自身增益家族。

PLAN-033 · 後台編輯視窗加寬

後台編輯彈窗固定 672px（AdminModal 的 max-w-2xl），12 個分頁中有 10 個共用這層殼；維護者只在 PC 上作業，等於為不存在的手機情境留白大半螢幕。高度早已是 max-h-[90vh]，問題純在寬度。但掃描後發現單純加寬是負優化——.input-field 為 width:100%，且 59 處格線有 58 處是固定欄數，多出的寬度會全變成胖輸入框，排數一排都沒少。故加寬（A）與格線改造（B）綁定交付。B 原訂用階梯式容器查詢，開工後改為 CSS auto-fill：階梯解不掉「欄位數本來就少」的區塊（射程頁只有 2 個欄位，再多斷點也排不滿），而 auto-fill 排不滿就留白、不把空間分給現有欄位；且它量的是元素自身寬度，窄版彈窗與巢狀卡片自動得到正確欄數，校準從「35 處各配階梯」簡化為調一個數字。過程中另拆掉一顆雷：容器查詢的 contain:layout 會使彈窗成為 position:fixed 子孫的 containing block，將打壞六個編輯器共用的 IconPicker 全螢幕浮層。寬度經互動示範實測由 80% 上修為 90vw。四個大編輯器的 Tab 版面重構（C）已納入範圍但延後。

PLAN-032 · 武器技能引用化

82 把武器內散落著 170 份技能拷貝，實際上只有 124 個相異技能（重複率 27.1%），而且已經開始漂移——「起爆」在凱旋·改與獵器上是同一個官方技能，文字卻一份補了 PLAN-019 方括號、一份沒有。本計畫沿用 PLAN-004 已驗證的漸進路徑（雙格式 union + 相容層 + 兩階段 flip），把武器技能收進既有技能庫共用。實測發現該集合早已不是「機師的技能」而是全站技能字典（84% 的 skill 引用目標無任何機師持有，維護者甚至已自行放入兩個武器技能），故不另開集合、改用 domain 欄位分類、後台同頁篩選。使用者可見行為完全不變，換來的是「改一處全站生效」。

PLAN-029 · Cloudflare 化與 App Check 退場

用 Cloudflare 一層邊緣基建接手「反白嫖 + 反爬 + 加速」，讓 App Check／reCAPTCHA 退場。前端不再直連 Firestore，公開遊戲資料改走 Cloudflare Worker 代理、Firestore 規則收成 read:if false（比 App Check 硬）；用戶資料維持直連 Auth。反爬用 CF 現成能力（封阿里雲／騰訊雲機房 ASN + 限流），順帶盡量改善中國讀取（不碰 ICP）。分階段灰度、每步可回退。
