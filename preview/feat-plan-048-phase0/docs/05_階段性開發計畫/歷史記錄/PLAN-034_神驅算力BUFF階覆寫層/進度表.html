0-1 附帶確認的限制條件：文案風格因角色設計者而異（2026-07-26）

官方不同角色的文案由不同人撰寫，規則並不統一：有些機師的技能敘述會隨算力改寫，有些不會。 因此計畫書決策一「全頁一張表 → 天賦說 III、技能說 I 在結構上不可能發生」 應理解為本站呈現的內部一致性保證，而非「官方一定也這樣顯示」。 這使 EntityRef.fixedLevel 從「逐筆逃生門」升級為必要機制： 凡官方在該處不改寫的引用點，必須逐筆釘死，否則本站會顯示出遊戲裡看不到的階名。

連帶的 SOP 要求：每族啟用 buffUpgrades 前，必須實機確認 「該族在該機師的技能敘述是否跟著變」，逐筆決定 level 或 fixedLevel。 此項須併入 Phase E 的後台警示與 Phase H 的 data-patch SOP。

G 的執行方式：把「塌縮是等價的」變成腳本自己證明的事

不可逆刪除最怕的是「我記得是等價的」。腳本因此在寫入前做等價性驗證： 對每一個即將被刪的變體，用覆寫層的規則在該變體自己的門檻算力下重算一次， 比對「算出來的階」與「變體正文宣告的階」。7 個變體逐一通過才放行，任一不符即中止。 另有五道前置閘門（通用能力／既有等級／自身增益／minSum>0／全站引用點的 level 與 fixedLevel 不得皆空）。
刻意不寫成「掃出所有只差階級的變體就自動塌縮」——通用化只會讓下一個沒讀過 Phase 0 盤點的人 對 87 位機師跑一次。每一筆都是看過原文後列上去的常數。

執行順序（重要）：先 commit → build → push 部署程式碼，才寫資料。 反過來的話，線上跑的舊程式碼不認得 buffUpgrades（不會抬升）但 ndVariants 已被刪， 使用者會看到梅利莎天賦只剩死的「常效維護Ⅰ」、艾達少掉兩階，直到下次部署為止。 寫入前跑 backup-firestore.mjs（18 collections / 2545 docs）， 腳本本身另存逐文件還原檔並支援 --rollback。

寫入時踩到的坑：自製的 bump 是「假成功」

腳本第一版自己寫了 bump，把版本當成頂層的遞增整數（{pilots: 1}）。 實際 schema 是 versions.<集合> 的 ISO 時間戳 （見 src/lib/api/versions.ts 的 getDataVersions：global=version、 byKey=versions）。後果是快取完全沒有失效，而輸出照印「✅ 已 bump」—— 這正是本計畫一路在防的那種假成功，只是這次發生在自己的工具上。 另外還在 meta/gameData 留下三個垃圾頂層欄位（已清除）。
