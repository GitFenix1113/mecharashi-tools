槽位與裝備限制模型 · Slot Model · 固定武裝佔位 · 裝備限制 · 模擬器 gate

機甲側今天沒有任何欄位說得出「我有幾個肩槽、幾個背槽」。本計畫補上共用的槽位詞彙，讓 PLAN-040 建出來的固定武裝真的「佔住位置」，並替模擬器裝上第一道裝備合法性檢查。

PLAN-040 固定武裝（武器文件）
本計畫的由來：從 PLAN-040 拆出來
PLAN-040 原本一手包辦「建武器文件」與「刪三個死槽位」。實際盤點後發現後者不是一次刪除，而是一整套槽位模型—— 要同時回答「機甲有幾個槽」「哪個槽被固定武裝佔住」「模擬器怎麼擋非法配裝」三題， 而且 PLAN-041 的形態層之後也要用同一套詞彙。
因此 PLAN-040 縮回成純武器層（並把三個死槽位凍結、不刪不改），槽位模型獨立成本計畫。 （編號跳過 042 是因為 042 已被「機甲故事館」佔用。）

前置關係：本計畫要「把武器綁到槽位上」，那些武器必須先存在。 PLAN-040 交付的 6 筆固定武裝文件（衝擊炮 / 嵐質儲能艙 / 多功能彈倉 / 耀星 / 隕星 / 千星）是本計畫 Phase B 的輸入。
Problem
問題背景
問題一：機甲側沒有任何欄位說得出「我有幾個肩槽／背槽」
武器側說得出自己的限制——weapon.ts:118 的 mechRestriction（none / light / medium / heavy）與 :119 的 equipSlot（singleHand / dualHand / shoulder / back）都是實裝欄位。 但這只表達了「武器願意上哪種機甲」，反方向完全空白。
REV-01 的［嵐質儲能艙］×2 要吃掉兩個肩槽——這件事無法從武器側推導： 武器只知道自己是 shoulder，不知道它把誰的肩膀佔了、佔了幾個、還剩幾個。 Mech 型別（src/types/mech.ts:28）裡也沒有任何容量欄位。
問題二：三個死槽位被 PLAN-040 凍結，需要一個替代品
mech.ts:56 leftShoulderSlot / :57 rightShoulderSlot / :62 backSlot， 三態設計其實很講究（undefined＝無此槽、null＝空槽、string＝固定武器 ID）， 後台有專屬編輯器（MechAdmin.tsx:559-561 三個 SlotEditor，元件本體在 :638），資料模型文件也有記載—— 實測 0/63 台機甲有填（2026-08-09 複查：連宣告過該欄位的都是 0 台），前台零消費端。
PLAN-040 已決定凍結而非刪除（在型別註解與 SlotEditor 加註「PLAN-047 將取代，勿填」）， 把「用什麼取代它」整題留給本計畫。凍結狀態不能無限期存在——它仍在後台誘導維護者填錯地方。
問題三：模擬器完全沒有槽位概念
SimState（SimulatorPage.tsx:48-59）與 Build（src/types/user.ts:40-58） 都只有 weaponId / backpackId 兩個獨立單值，沒有槽位陣列、沒有左右手。
而 getFilteredWeapons（SimulatorPage.tsx:187-191）全文只有一條規則： w.weight <= mech.output - mech.weight。 也就是說今天的模擬器不檢查 mechRestriction、不檢查 equipSlot—— 只要重量夠，輕型機甲照樣選得到 22 把肩部武器與 21 把背部武器（那 43 把 100% 是 medium 限定）。
問題四：兩個既有 bug，都在同一段程式碼裡
Bug位置症狀
執照 enum 用錯型別，靜默全放行 SimulatorPage.tsx:181 if (license === '中甲') ——license 是 MechLicense（enums.ts:14-19，中型值是 '中型'）， '中甲' 是 ArmorType.MEDIUM（enums.ts:35）。 兩個 enum 的字面量不同 → 條件永遠為假 → 中型執照機師的機甲篩選整條失效，重型機甲照樣選得到。 TypeScript 抓不到，因為兩者都推導成 string。
back 槽不互斥 SimulatorPage.tsx:193-205 getFilteredBackpacks 只檢查重量與 assemblableArmorType， 不檢查背部槽是否已被背部武器佔用。 而 backpacks 181 筆的 slot 181/181 全部是 'back' （backpack.ts:27 註解逐字：「與武器共用 enum 供裝備計算器統一判斷部位」）。 → 21 把背部武器中的任一把，可與 181 個背包中的任一個同時裝上。
這兩個 bug 都不是「加功能」，是既有邏輯的錯誤。它們與槽位模型同屬一段程式碼，一起修比分兩次改便宜。
Design
設計決策
決策一：ArmamentMount 共用型別——全站已有三套部位詞彙，不要開第四套
最直覺的做法是給機甲開一個 'leftShoulder' | 'rightShoulder' | 'back' 的新聯合型別。 這是錯的，理由是全站已經有三套部位詞彙，而它們是互通的：
既有詞彙位置值用途
WeaponEquipSlot enums.ts:127-133 singleHand / dualHand / shoulder / back 武器裝配位置（對應官方 API RestrictionsPositionOfWeapon）
MechPartPosition（Module.boundPart） enums.ts:40-46 / module.ts:71 torso / leftArm / rightArm / legs 模組綁定的機體部件，與武器槽是不同維度
Backpack.slot backpack.ts:27 181/181 = 'back' 註解逐字：「與武器共用 enum 供裝備計算器統一判斷部位」
第三套已經明文承諾與武器共用 enum。若機甲側再開第四套：
(a) 新型別與 WeaponEquipSlot 不可互推——校驗腳本無法比對「這個 mount 的 slot 跟這把武器的 equipSlot 是不是同一個位置」；
(b) 耀星／隕星是 singleHand、千星是 back，它們落地時新型別必須從 3 值擴成 5 值，而那時 Firestore 裡已經寫進舊值，要跑 migrate；
(c) 前台要為兩套詞彙各寫一份 label map。
→ 採用共用型別，放共用位置（src/types/common.ts，或新開 src/types/slots.ts）， Mech 層與 PLAN-041 的 Form 層共用同一個 ArmamentMount：
// src/types/common.ts（或新開 src/types/slots.ts） import type { WeaponEquipSlot } from './enums' /** * 一件「固定佔位」的武裝：把某個槽位鎖死，不可更換、不可裝元件、不可改裝。 * ⚠ slot 刻意直接用 WeaponEquipSlot，不另造機甲側的部位詞彙—— * 全站已有三套（WeaponEquipSlot / MechPartPosition / Backpack.slot）， * 第四套會與 weapon.equipSlot 不可互推，校驗腳本就寫不出來。 */ export interface ArmamentMount { weaponId: string slot: WeaponEquipSlot /** 僅 singleHand / shoulder 需要；dualHand 與 back 沒有左右之分 */ side?: 'left' | 'right' } /** 一台機甲（或 PLAN-041 的一個形態）可用的槽位數量 */ export interface SlotCapacity { /** dualHand 武器佔用 2 個 singleHand，不是獨立槽，故不列 */ singleHand: number shoulder: number back: number /** * 備用手持槽。⚠ 這一維由「背包」決定，不由機甲或形態決定： * backpack.type === 'BackupEquipment' → 2，否則 0。 * 見決策十一（強襲者背包＝另揹一套可拿在手上的武器）。 */ backupHand: number }
校驗腳本加一條硬規則：mount.slot === weapons[mount.weaponId].equipSlot，允許 0 例外。 這條規則只有在兩邊共用同一個 enum 時才寫得出來，是採用共用型別最直接的回報。
決策二：固定武裝掛 MechPart.fixedArmament?: ArmamentMount[]——肩槽附屬於手臂
（原 Open Question Q-A「掛 chassis 還是 MechPart」，2026-08-09 使用者答覆後升格為決策；原三個候選方案中 (1) 勝出，(2)(3) 作廢。）
使用者原話逐字：「會，跟手臂綁在一起，左手綁左肩、右手綁右肩。」

四條佐證鏈，彼此獨立：
佐證逐字內容推得什麼
① 專案自己的 enum 早就這樣定義 enums.ts:130：SHOULDER: 'shoulder', // 肩膀：左臂或右臂其中一個肩膀 「肩膀」在本專案的定義裡本來就掛在手臂底下，不是獨立部位。這條在寫 Q-A 之前就已經存在於 codebase。
② 帕斯卡的模組綁在單一手臂 mod_帕斯卡_fixed_2 boundPart: ["rightArm"]／mod_帕斯卡_fixed_3 boundPart: ["leftArm"]， 兩者描述皆為「固定裝備[衝擊炮]…；同時攜帶兩門[衝擊炮]時，可使用[浪潮來襲]」 兩個獨立模組、兩隻手臂。「同時攜帶兩門」這個條件句只有在「可能只有一門」時才需要存在——而只有換掉單邊手臂才做得到「只有一門」。
③ 霸王的 lore 直接寫「同側手臂」 「MCT-AP07霸王于肩部外側掛載的增設彈倉，通過硬式彈鏈導軌向同側手臂所持雙聯裝速射機炮供彈」 肩上的彈倉在設定上是同側手臂的附屬件，供彈對象就是那隻手拿的槍。左右各一、互不相干。
④ 破曉者-01 的 lore 把肩部接口與手臂綁在一起 「REV-01捨棄了肩部戰術武器的部署接口與空間，替換為嵐物質粒子儲存裝置，能在手臂部位被破壞時使用儲存的嵐物質粒子即刻修復手臂」 同一句話裡，被犧牲的是肩部接口、受益的是手臂——兩者是同一個部件的兩面。
映射規則（可程式化，不需要任何額外資料）： parts.leftArm.fixedArmament → 左肩槽；parts.rightArm.fixedArmament → 右肩槽。
// src/types/mech.ts —— 加在既有的 MechPart（mech.ts:3）上 export interface MechPart { position: 'torso' | 'leftArm' | 'rightArm' | 'legs' // mech.ts:4，既有 // …既有欄位（durable / armor / firepower / weight / interface …）… /** * 該部件自帶、不可更換的固定武裝。 * 映射：leftArm → 左肩槽、rightArm → 右肩槽 * （enums.ts:130 逐字「肩膀：左臂或右臂其中一個肩膀」）。 * 換掉這個部件，掛在它上面的固定武裝一起消失，該肩槽隨之解除封鎖。 */ fixedArmament?: ArmamentMount[] }
四個推論，全部讓模型變簡單：
  • 三台走同一條路徑：帕斯卡（衝擊炮）／破曉者-01（嵐質儲能艙）／霸王（多功能彈倉）的固定武裝全部與手臂關聯—— 破曉者-01 與霸王雖然沒有「武裝來源模組」，但佐證 ③④ 顯示它們的肩部裝備在設定上同樣附屬於手臂。 → 不需要 source: 'part' | 'chassis' 判別欄位（原方案 (2)）， 也不需要兩條資料路徑（原方案 (3)）。原本擔心的「一套結構容納兩種來源」根本不存在。
  • 不開 Mech.fixedArmament（chassis 層）——順帶消除一個命名衝突： PLAN-041 的 FormRestrict.fixedArmament 是形態層的限制，若機甲層再開一個同名頂層欄位，兩者會同名異義。 現在機甲層的路徑是 mech.parts.rightArm.fixedArmament，與 form.restrict.fixedArmament 一眼可辨。
  • 換部件的語意天然正確：換掉帕斯卡的右臂 → 右肩的衝擊炮消失、右肩槽解除封鎖。 這不需要任何額外規則來描述——欄位掛在部件上，部件走了它就走了。這正是 Q-B 的實機答案（見 Open Questions 已答紀錄）。
  • 底盤視角是純 derive：圖鑑要問「這台機甲總共有哪些固定武裝」時，flatten 四個部件的 fixedArmament 即可， 不落盤第二份，也就沒有兩份資料對不上的可能。
仍然要保留的邊界聲明：站上呈現的是原廠配置，部件混裝不在表達範圍。
Q-A 的答案讓「換手臂會改變固定武裝」成為遊戲事實，這反而讓這條聲明更必要—— MechPart.interface（mech.ts:19）全庫 252 個部件只有一種接口值（Ⅱ型接口 248 ＋ 髒資料 ⅠⅠ型接口 4），全機種部件互通， 使用者完全可能把帕斯卡的手臂裝到別台上。但本站的機甲詳情頁顯示的永遠是該機甲出廠時的固定武裝。 不明講這句，使用者會合理期待「換部件後站上跟著變」，而那需要一整套部件配裝器——不在任何已立計畫的範圍內。
決策三：兩種槽位封鎖來源正交——occupiedSlots() 與 lockedSlots() 是兩個獨立 derive
槽位「不能用」有兩個成因，它們的層級、範圍、理由全都不同，不可以塞進同一個「不可用槽」清單：
封鎖型態來源層級效果範圍實例
佔據型 機甲部件層（決策二） 某槽被固定武裝實際佔住 → 該槽不可用，其他槽照常 破曉者-01 兩個肩槽被［嵐質儲能艙］佔滿，但雙手與背部照常配裝
全鎖型 機師形態層（PLAN-041） 該形態下所有槽位皆不可調整，與有沒有被佔住無關 海莉絲［虛粒子形態］
全鎖型的依據（原 Q-C，2026-08-09 已答）：使用者原話逐字「虛粒子形態沒辦法調整任何裝備」—— 這比 PLAN-041 引用的官方原文「無法變更武裝和技能」更強。
截圖是最直接的反證材料：虛粒子形態的雙肩顯示為空的 [+]，但點不下去。 該形態的三把固定武裝（耀星／隕星／千星）佔的是右手／左手／背部，雙肩根本沒被佔住—— 若模型裡只有佔據型，雙肩會被算成「空著、可裝」，與實際完全相反。

落地：兩個獨立 derive，禁止合併成一個函式
// src/utils/mechSlots.ts /** ① 佔據型：被固定武裝實際佔住的槽。來源＝mech.parts.*.fixedArmament（決策二） */ export function occupiedSlots(mech: Mech): ArmamentMount[] /** ② 全鎖型：該情境下所有槽位皆不可調整。來源＝機師形態， * 參數形狀待 PLAN-041 的 forms 集合落地後補，本計畫只保證它是獨立函式。 */ export function lockedSlots(/* PLAN-041 形態層 */): WeaponEquipSlot[]
合併的具體代價：
(a) UI 講不出話——「這格被［嵐質儲能艙］佔住」與「這個形態不能換裝備」是兩句不同的話，合併後只剩「不可用」；
(b) gate 行為不同——佔據型只擋該槽，全鎖型擋全部；用同一份清單表達，全鎖型就得把每個槽都塞一筆假的佔據紀錄，而那些紀錄沒有對應的 weaponId；
(c) 層級不同——佔據型是機甲資料（本計畫落盤），全鎖型是形態資料（PLAN-041 落盤），合併會讓兩個計畫共寫同一個欄位。
決策四：不新增 Mech.shoulderSlots?: number——「保留未來可能性」要兌現成單一 derive 入口，不是欄位
使用者已答覆的規則是「肩槽：中甲 2 個、輕型／重型 0 個，但保留未來特殊機甲的覆寫空間」。 直覺做法是開一個 shoulderSlots?: number 讓後台可覆寫。本計畫刻意不做，三個理由：
  • 今天需要覆寫的機甲是 0 台。mechs 63 筆（輕型 19 / 中甲 25 / 重型 19），derive 規則覆蓋 63/63，沒有任何例外。
  • 0/5 定律的前車之鑑就在同一個型別裡：leftShoulderSlot 三欄設計良好（三態語意清楚）、後台有編輯器、docs 有記載， 實測 0/63 填寫。「開了選填欄位，未來就會有人填」在本專案已被證偽一次——集合會被填滿，選填欄位不會。
  • 屆時真出現例外，正確形狀也不是 scalar。若某台機甲肩槽異常，它的背槽或手持槽多半也異常； 正確的擴充是 slotOverride?: Partial<SlotCapacity>（且與 PLAN-041 的形態層共用），不是一個孤立的 shoulderSlots 數字。 先開 scalar 反而卡住未來的正確解。
兌現方式：單一 derive 入口。全站只有一個地方知道「一台機甲有幾個槽」，真出現例外時改一個檔案：
// src/utils/mechSlots.ts —— 全站唯一的槽位真相入口 import { ArmorType } from '../types/enums' export function mechSlotCapacity(mech: Mech): SlotCapacity { // ⚠ 一定要用 enum 常數，不可寫中文字面量 '中甲'——見決策五 const isMedium = mech.armorType === ArmorType.MEDIUM return { singleHand: 2, // 左右手，全機種相同 shoulder: isMedium ? 2 : 0, // 肩槽：中甲 2、輕/重 0 back: 1, // 背部＝背包槽，全機種都有（見下方論證） backupHand: 0, // ⚠ 機甲不決定這一維，由背包給（決策十一） } }
back: 1 對全機種成立，這點必須寫清楚：實測 backpacks 181 筆的 assemblableArmorType 分布為 無限制 106 / 限輕 35 / 限中 21 / 限重 19—— 那 35 個「限輕」背包如果輕型機甲沒有背部槽，就永遠無處可裝。 所以「背槽是中甲專屬」是錯的；真正限中甲的是背部武器（戰術武器），而那件事已由 mechRestriction 表達（見決策七）。
決策五：derive 條件一律寫 ArmorType.MEDIUM，禁止中文字面量 '中甲'
這條不是風格潔癖，是問題四 bug 一的直接教訓：SimulatorPage.tsx:181 正是因為把 '中甲'（ArmorType.MEDIUM）拿去比 pilot.license（MechLicense.MEDIUM = '中型'） 而靜默全放行，錯了不知道多久都沒人發現。
兩個 enum 的中文值只差一個字（中甲 / 中型），肉眼審查抓不到， 而 mech.ts 與 pilot.ts 的欄位都宣告成 string，tsc 也抓不到。 唯一的防線是「所有比較都經過 enum 常數」——打錯常數名 tsc 會報錯，打錯中文字面量不會。
同一原則套用到 MechLicense：修 bug 一時要把 '中甲'／'重型'／'輕型' 三個字面量全換成 MechLicense.*，並順手把 Mech.armorType / Pilot.license 的宣告從 string 收緊成 enum 型別。
決策六：用陣列存固定武裝，不用選填 scalar——stripUndefined 有硬傷
這是「舊的三個槽位欄位確實該退場」的獨立理由，與 0/63 使用率無關：
firestoreCore.ts:43-53 的 stripUndefined 會在寫入前遞迴濾掉所有 undefined（保留 null）， 各集合的 update* 全部共用它。
而 SlotEditor（MechAdmin.tsx:638）在「取消勾選此機甲有肩槽」時，寫回的值就是 undefined。 → 該欄位在 payload 裡整個消失 → Firestore 的 updateDoc 只是「沒有提到它」，不是「刪除它」→ 舊值原封不動留著。
結論：一旦某台機甲寫進了槽位欄位，後台再也無法把它取消。三態設計（undefined／null／string）在這條管線下只剩兩態可用。
陣列形狀天然避開這個陷阱：「不存在」＝空陣列或欄位不存在，兩者語意相同， 要清空就寫 []，是一個真實的值，過得了 stripUndefined。 （附帶好處：帕斯卡「同一把衝擊炮 × 左右兩肩」用 ArmamentMount[] 兩筆自然表達，scalar 三欄則要為左右各開一欄。）
決策七：「戰術武器限中甲」不需要新規則——已由 mechRestriction 100% 表達
使用者提供的遊戲事實是「所有［戰術武器］目前限中甲，暫無例外（武器卡紅字『[僅限中型機甲裝配]』）」。 直覺會想在槽位模型裡加一條「戰術類武器只能上中甲」。實測證明這條規則是冗餘的：

雙射實測（weapons 172 筆，2026-08-09）：type === '戰術' 43 筆， mechRestriction === 'medium' 43 筆，雙向零反例—— 沒有一把戰術武器不是 medium，也沒有一把 medium 武器不是戰術。

決策八：三個死槽位是「替換」不是「刪除後不補」

決策九：機甲詳情頁「固定武裝」區塊的 UI 規格（寫死，不留給實作者臨場決定）
這個區塊原本是 PLAN-040 的 D-3，因為需要槽位資料才渲染得正確而移交本計畫。三條寫死的規格：
  • 同一把佔兩肩 → 合併顯示「×2」，不分槽列兩張卡。 （理由已隨 Q-A 答覆更新） mod_帕斯卡_fixed_2/_3 描述逐字的「同時攜帶兩門[衝擊炮]時」現在確定不是文案慣用語—— 決策二成立後，左右臂可分別更換，「只有一門」是真的做得到。
    但站上呈現的是原廠配置（決策二的邊界聲明），而原廠就是兩門， 所以合併顯示 ×2 仍然成立——差別只在理由從「資訊量最保守」變成「與原廠配置這條邊界一致」。 分兩張卡反而會誘導使用者以為站上支援單邊配置。
  • React key 用 `${slot}:${side}`，不可用 w.id。 既有慣例是 WeaponsPage.tsx:500 的 key={w.id}，照抄到這裡會直接撞 key—— 左右肩是同一個 weaponId，React 會警告並可能複用錯誤的 DOM 節點。
  • 沒有固定武裝 ⇒ 整區不渲染，絕不渲染「無固定武裝」字樣。 （理由已隨 Q2 答覆更新） 固定武裝清單現在是「已窮舉 6 種」——使用者逐字答覆「目前有固定武裝的我都列上來了，君權、青鳥、奈芙蒂斯、復仇女神都沒有固定武裝」。 即便如此這條規則維持不變：未來改版仍可能出現新的固定武裝機甲， 「整區不渲染」讓「未知」與「沒有」共用同一種呈現，不會把一句肯定的否定陳述寫死在頁面上。
決策十：模擬器 gate 分三條規則，各自可獨立上線

決策十一：SlotCapacity 加 backupHand 維度，且這一維由背包決定
本計畫的模型主要是減法（固定武裝佔據槽位 → 可用槽變少），但遊戲裡存在相反方向的機制， 而且它不歸機甲、也不歸形態管：

實測資料：backpacks/60101706［強襲者背包］，type: 'BackupEquipment'（全庫 181 筆中僅此 1 筆）、 slot: 'back'、weight: 150、assemblableArmorType: ["Light","Medium","Heavy"]（無機甲限制）。 觸發條件見其技能 bpskill_強襲者驅動·增傷 正文逐字：「可以使用[武器切換]指令，每回合最多使用 1 次；行動結束時，若雙手完好，可以額外使用[武器切換]指令，每 2 回合最多使用 1 次」。

使用者對這個背包的完整描述（原 PLAN-040 規格 Q7，2026-08-09 已答）逐字：
「強襲者背包是相當於另外揹著『另一套可以拿在手上的武器』，可以讓你在戰鬥中更換， 他不能換單一把，替換就是直接兩手都換，所以那個備用武器是隨你裝備的，只要負重夠就可以， 你裝備雙手武器就會直接占用兩格。所以目前強襲者背包的分類在背包內也是特殊的。」

從這段話讀出來的五條規格：
規格內容對模型的意義
容量 備用槽＝2 格，與主手同構（「另一套可以拿在手上的武器」） 是 SlotCapacity 的第四個維度，不是把 singleHand 從 2 改成 4——兩套手不能混用
雙手武器 「裝備雙手武器就會直接占用兩格」 與主手同一條規則（dualHand 佔 2 個 singleHand），備用槽不需要另立規則
交換是原子操作 「不能換單一把，替換就是直接兩手都換」 切換的單位是整套，不是單槽。任何 UI／模擬器實作都不得提供「只換左手」
內容玩家自選 「那個備用武器是隨你裝備的，只要負重夠就可以」 備用武器不是背包的固有資料——這一點直接推翻了先前「Backpack 缺『背包內武器』欄位」的判斷，見 Inherited
受負重限制 同上，「只要負重夠」 備用武器照樣計入既有的 w.weight <= mech.output - mech.weight 帳，不是免費欄位
因此 backupHand 的值來自背包，不是機甲、也不是形態：
// backupHand 的唯一來源：當前裝備的背包 // backpack.type === 'BackupEquipment' → 2；否則 0 // ⚠ 不要放進 mechSlotCapacity()——那個函式的輸入只有 mech，看不到背包
這件事必須現在就寫進型別，理由是形狀問題而非工期問題：backupHand 的值與其他三維來自不同的輸入 （singleHand／shoulder／back 只看 mech，backupHand 只看背包）。 若先做成三維常數、之後才補，需要的會是「基礎容量 ＋ 裝備帶來的增量」兩層結構，等於把 SlotCapacity 重寫一次。
本輪仍不實作備用手的實際配裝——Build.weaponId（user.ts:44）是單值 string， 放不下「主手一套 ＋ 備用一套」，那是 Build 層的缺口（見 Inherited），不是槽位模型的缺口。
決策十二：明確不做的四件事，各附理由
  • 不改 Build 成多槽陣列：weaponId／backpackId 兩個單值不動。 改成陣列是全站 breaking change（SimState、存讀檔、ProfilePage、傷害計算全要改）， 而本計畫要交付的是「檢查」不是「多槽配裝」。多槽配裝待模擬器改版時整批處理。
    ⚠ 這個缺口已因決策十一而變大——強襲者背包會開出第二套完整手部配裝，單值 weaponId 連「主手一套 ＋ 備用一套」都表達不了。缺口本身記入 Inherited。
  • 不做 PLAN-041 的形態獨立配裝：海莉絲四形態各一套裝備需要 Build 多槽化，同上。 本計畫只保證 ArmamentMount／SlotCapacity 兩個型別與 lockedSlots() 這個獨立 derive，Form 層能直接複用。
  • 不新增 RangeType 的「扇形」：PLAN-040 決策十已否決，理由不變（三個 formatter 會靜默吃掉， 且扇形需要的朝向／張角參數一個都沒有）。千星的扇形特性寫在 description。 使用者對此的答覆逐字：「這是我們之前沒有定義的一種攻擊方式，後面再補，這跟傷害模擬有關，暫時跟目前技能無關。」→ 歸屬已明確移交傷害模擬範疇，見 Inherited。
  • 不做部件混裝：見決策二的邊界聲明——站上呈現的是原廠配置。 Q-A 答覆後這條更需要明講，因為「換手臂會改變固定武裝」已是遊戲事實。

43 把戰術武器的天生主動技能全站未記錄 2026-08-09 新增 使用者答覆逐字：「每一個戰術武器都有自身天生配備的主動技能，戰術武器本身不存在『普通攻擊』。 目前我們沒有把戰術武器的主動技能寫上，但未來可能會補。」
對象是 type === '戰術' 的 43 筆（肩部 22 ＋ 背部 21，與 mechRestriction === 'medium' 雙向零反例，見決策七）。		 不是資料錯，是整層資訊從未建過——與槽位模型同屬「機甲能裝什麼、裝了會怎樣」這條線。 WeaponSkillRef（weapon.ts:34-56，PLAN-032 已歸檔）已是正式格式，形狀不缺，缺的是 43 筆內容。 規模夠大，落地時應獨立成計畫而非塞進本計畫的 Phase。
扇形射程與 orthogonal 歸屬 → 移交傷害模擬範疇 2026-08-09 改寫 RangeType.ORTHOGONAL（enums.ts:137）宣告了但 0/172 使用； 該行註解逐字寫「十字直線（電磁炮）」，而實測 12 把電磁炮全部是 manhattan。
千星的「扇形 4 格」則連參數都沒有（朝向／張角／是否隨面向旋轉，現有型別只有 minRange／maxRange 兩個 scalar）。		 使用者對扇形的答覆逐字：「這是我們之前沒有定義的一種攻擊方式，後面再補，這跟傷害模擬有關，暫時跟目前技能無關。」 → 兩者一併移交傷害模擬範疇，非 PLAN-040、非本計畫主線。
orthogonal 那 12 筆仍是既有 172 筆的正確性問題（要嘛改成 orthogonal、要嘛刪掉這個殭屍值）， 優先於在同一個維度上疊加第四個值。
武器「觀測值 vs 基準值」標註機制 型別上沒有任何欄位可以承載「這個數字是滿級觀測值」。 旁證：諸神黃昏 DB attack=876（基準總攻擊，876/6=146），遊戲卡面顯示 173（每發、含改裝與等級加成） → 現有欄位已在混用兩種語意。 PLAN-040 會把耀星／隕星／千星的滿級觀測值以與其他 172 筆相同的格式填進去，這是已知缺陷。 修法（加標註欄位或分成兩欄）牽涉全站渲染，屬模型層問題。
